# ロジック設計ガイドライン

## 1 はじめに

### 1.1 目的

本書の目的は、業務ルール、状態及び整合性を扱うロジックを、誤りにくく、速く、かつ変更しやすい形で設計するための判断基準を共有することである。

### 1.2 適用範囲

本書は、一つの機能の中のユースケースの処理の流れ、業務ルール、状態遷移、トランザクション、同時実行及び外部への作用の設計について規定する。

本書は、[ソフトウェア設計ガイドライン](software-design-guidelines.md)及び[アプリケーション設計ガイドライン](application-design-guidelines.md)を前提とする。責務の分離、型、エラーハンドリングの一般的な規則は、ソフトウェア設計ガイドラインによる。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| ユースケース | 利用者又は外部のシステムが、一つの目的を達成するために行う一連の操作。 |
| 業務ルール | 業務上の判断、計算及び制約の規則。 |
| 不変条件 | 対象のデータが常に満たさなければならない条件。 |
| 決定表 | 条件の組合せごとに、取る動作を一覧にした表。 |
| 集約 | 一つのトランザクションで整合性を保つ、データのまとまり。 |
| 楽観的ロック | 更新の時点で、読み込んだ後に他の更新がなかったことを版の番号で確かめる同時実行の制御。 |
| 悲観的ロック | 読み込む時点で対象を占有し、他の更新を待たせる同時実行の制御。 |
| べき等 | 同じ要求を複数回行っても、1回行った場合と結果が同じである性質。 |
| トランザクショナルアウトボックス | データの更新と送信するイベントとを同じトランザクションで保存し、イベントを後から送る方式。 |
| サーガ | 複数のサービスにまたがる処理を、各サービスのトランザクションと、失敗時の取消しの処理の連なりで行う方式。 |

## 2 設計の前提と結果

### 2.1 設計の前に確定する事項

ロジックを設計する前に、[表2](#table-2)の事項を確定する。確定できない事項は、未確定であることを明記する。これらの事項が欠けると、前提を推測して設計することになり、推測が外れれば最適な設計にならない。

<a id="table-2"></a>表2−設計の前に確定する事項

| 事項 | 内容 | 例 |
| --- | --- | --- |
| 目的 | 利用者が達成したいこと | 注文を確定し、在庫を引き当てる。 |
| 入力と出力 | ユースケースが受け取る値と返す値 | 商品ID、数量、配送先を受け取り、注文番号を返す。 |
| 業務ルール | 判断、計算及び制約 | 在庫がない商品は注文できない。送料は合計金額で決まる。 |
| 状態 | 対象がとる状態と、状態が変わる契機 | 注文は、受付、確定、出荷、取消しの状態をとる。 |
| 失敗時の扱い | 途中で失敗した場合に、どの状態に戻すか | 決済が失敗した場合は、在庫の引当てを解除する。 |
| 同時実行 | 同じ対象を同時に操作する可能性 | 最後の1個を複数の利用者が同時に注文する。 |
| 外部への作用 | メール、決済、他のサービスへの通知 | 確定時に確認のメールを送る。 |
| 量と頻度 | データの件数、要求の頻度、ピーク | 1日1万件、セールの開始時に毎秒100件。 |
| 性能の目標 | 応答時間の目標 | 注文の確定は95パーセンタイルで500ミリ秒以内。 |
| 未確定の事項 | 決まっていない事項 | 一部の商品だけ在庫がない場合の扱いは未定。 |

### 2.2 設計の結果に記載する事項

ロジックの設計の結果には、次の事項を記載する。

- 選んだ設計と、その理由

- 比較した他の案と、選ばなかった理由

- 性能と整合性への影響

- 変更が及ぶ範囲

- テストで確認する観点

- 依頼者が確定する必要のある未確定の事項

構成に関わる決定は、[ADRテンプレート](../../templates/documentation/architecture-decision-record.md)で記録する。

## 3 業務ルール

### 3.1 条件の組合せは決定表で整理する

条件が三つ以上組み合わさる業務ルールは、実装の前に決定表で整理し、全ての組合せに対する動作を決める。組合せを整理せずに条件分岐を書くと、考慮漏れの組合せが残る。決定表は、そのままテストケースにもなる（[テストガイドライン](testing-guidelines.md)の4.4参照）。

### 3.2 業務ルールは中核のロジックに置く

業務ルールは、画面、HTTPハンドラー、データベースの手続きに置かず、外部技術から独立した中核のロジックに置く（[ソフトウェア設計ガイドライン](software-design-guidelines.md)の2.2参照）。同じルールを画面とサーバーの両方で使う場合も、正となる判定はサーバーで行う。

### 3.3 金額は整数又は10進数で扱う

金額は、浮動小数点数で扱わず、最小の単位の整数又は10進数の型で扱う。浮動小数点数は、0.1のような値を正確に表せず、合計に誤差が出る。端数の処理は、丸めの方法と、丸める時点（明細ごとか合計か）を仕様で決める。

### 3.4 日時は時点と暦の日付を区別する

日時は、次によって扱う。

- 発生した時点は、UTCの時刻で保存する。

- 誕生日、締め日など、暦の上の日付は、時刻をもたない日付の型で扱う。

- “毎日9時”のように地域の時刻で決まる規則は、時刻とタイムゾーンを組み合わせて保存する。

- 現在時刻は、時刻を返す依存として受け取り、テストで固定できるようにする。

## 4 状態遷移

状態をもつ対象は、状態の一覧と、許可する遷移を表で定義してから実装する。状態は、複数の真偽値の組合せではなく、一つの列挙型で表す（[ソフトウェア設計ガイドライン](software-design-guidelines.md)の4.6及び6.3参照）。許可していない遷移の要求は、業務ルールの違反として拒否する。

状態遷移の表の例は、[表3](#table-3)による。

<a id="table-3"></a>表3−状態遷移の表の例

| 現在の状態 | 契機 | 次の状態 | 条件 |
| --- | --- | --- | --- |
| 受付 | 決済の成功 | 確定 | — |
| 受付 | 決済の失敗 | 取消し | — |
| 確定 | 出荷 | 出荷済み | — |
| 確定 | 利用者による取消し | 取消し | 出荷の準備を始めていない。 |

## 5 ユースケースの処理の流れ

### 5.1 処理の順序

一つのユースケースの処理は、次の順に行う。

1. 入力の形式を検証する。

2. 操作の権限を、対象のデータごとに確認する。

3. 必要なデータを読み込む。

4. 業務ルールを判定し、状態を変更する。

5. 変更を保存する。

6. 外部への作用を行う。外部への作用は、保存が確定した後に行う。

### 5.2 検証の層を分ける

入力の検証は、層ごとに役割を分ける。

- 境界では、形式、型、長さ及び必須の項目を検証する。

- 中核のロジックでは、業務ルールと不変条件を検証する。

- データベースでは、一意制約、外部キー制約及びチェック制約で、最後の防御を行う。

データベースの制約は、同時実行による競合でアプリケーションの検証をすり抜けた場合にも、不正なデータの保存を防ぐ。

### 5.3 データの読込みをまとめる

ループの中でデータベース又は外部のサービスを呼び出さない。必要なデータは、処理の前にまとめて読み込む（[アプリケーション設計ガイドライン](application-design-guidelines.md)の3.1参照）。

## 6 整合性とトランザクション

### 6.1 トランザクションを短くする

トランザクションの範囲は、一つのユースケースで一つの集約を更新する範囲とする。トランザクションの中で、外部のサービスの呼出し、ファイルの読み書き、利用者の操作の待機を行わない。トランザクションが長いと、ロックの保持時間が延び、他の要求が待たされる。

### 6.2 同時実行を制御する

同時実行の制御は、[表4](#table-4)によって選ぶ。

<a id="table-4"></a>表4−同時実行の制御の選択

| 状況 | 方式 | 理由 |
| --- | --- | --- |
| 利用者が画面で編集して保存する。競合はまれである。 | 楽観的ロック | 読込みの間はロックせず、競合した場合だけ利用者に再操作を求める。 |
| 在庫の引当てのように、数値を増減する。 | 条件付きの単一の更新文（例: `UPDATE ... SET stock = stock - 1 WHERE stock >= 1`） | 読込みと更新の間に他の更新が入る余地がなく、ロックの時間が最も短い。 |
| 競合が多く、読込みから更新までに複数の判定が必要である。 | 悲観的ロック（`SELECT ... FOR UPDATE`など） | 判定の間に他の更新が入らない。ロックの順序を決め、デッドロックを防ぐ。 |
| 同じデータの重複した作成を防ぐ。 | 一意制約 | 同時の要求でも、データベースが重複を拒否する。 |

### 6.3 再試行される操作をべき等にする

決済、注文の確定など、通信の失敗によってクライアントが再試行する可能性のある操作は、べき等キーを受け取り、同じキーの要求には最初の結果を返す（[通信方式ガイドライン](../architecture/communication-protocol-guidelines.md)の5.1参照）。べき等キーと結果は、操作の結果と同じトランザクションで保存する。

### 6.4 データの更新とイベントの送信を両立させる

データベースの更新と、メッセージキューへのイベントの送信とを、両方とも確実に行う必要がある場合は、トランザクショナルアウトボックスを使う。データベースの更新の後に直接イベントを送ると、送信の前に処理が停止した場合にイベントが失われる。イベントを受け取る側は、同じイベントを複数回受け取ることを前提に、べき等にする。

### 6.5 複数のサービスにまたがる処理

複数のサービスのデータを更新する処理は、分散トランザクションを使わず、サーガで行う。各段階に、失敗した場合の取消しの処理を定義する。取消しの処理もべき等にする。

### 6.6 結果整合性を画面に反映する

非同期に更新する読取り用のデータを使う場合は、利用者が自分の更新の直後に古い値を見ないようにする。更新の応答で新しい値を返して画面へ反映するか、更新した利用者の読取りだけは書込み用のデータから行う。

## 7 エラー

業務ルールの違反と、システムの障害とを区別する（[ソフトウェア設計ガイドライン](software-design-guidelines.md)の8章参照）。業務ルールの違反は、利用者が取れる操作が分かる理由とともに返す。システムの障害は、詳細を記録し、利用者には再試行又は問合せの方法を示す。

## 8 長時間の処理

### 8.1 要求の中で完了しない処理

応答の目標時間の中で完了しない処理は、ジョブとして非同期に実行し、ジョブの状態を返す（[アーキテクチャ設計ガイドライン](../architecture/architecture-guidelines.md)の4.2参照）。

### 8.2 バッチ処理

大量のデータを処理するバッチ処理は、次による。

- 一定の件数ごとに区切って処理し、区切りごとにトランザクションを確定する。

- 処理済みの位置を記録し、途中で停止しても続きから再開できるようにする。

- 同じデータを再び処理しても結果が変わらないようにする。

- 1件ずつではなく、まとめて読み書きする。

## 9 チェックリスト

- [表2](#table-2)の事項が確定している。確定できない事項は、未確定であることが明記されている。

- 三つ以上の条件の組合せが、決定表で整理されている。

- 業務ルールが、中核のロジックにある。

- 金額を浮動小数点数で扱っていない。丸めの方法と時点が決まっている。

- 時点と暦の日付を区別している。

- 状態遷移が表で定義され、許可していない遷移を拒否している。

- 外部への作用を、保存が確定した後に行っている。

- データベースの制約で、不正なデータの保存を防いでいる。

- トランザクションの中で、外部の呼出しをしていない。

- 同時実行の制御を、[表4](#table-4)から選んでいる。

- 再試行される操作が、べき等である。

- データの更新とイベントの送信を両立させる必要がある箇所で、トランザクショナルアウトボックスを使っている。

- バッチ処理が、途中から再開できる。
