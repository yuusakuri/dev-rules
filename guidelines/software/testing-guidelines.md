## 1. 概要

本書は、何をテスト対象にし、どのテストケースを選び、何を検証するかを定義する。本書は、[ソフトウェア設計ガイドライン](software-design-guidelines.md)を前提とする。

---

## 2. テスト対象の決定

### 利用者に価値のある振る舞いだけを検証する

テストの観点は、利用者が観測でき、壊れると利用者が目的を果たせなくなる振る舞いに限定する。利用者には、画面を操作する人に加えて、公開されたAPIを呼び出すプログラム、出力されたファイルを読み込む別のシステム、ログやメトリクスで監視する運用者のように、対象の外側から依存するものを含める。

観点を加える前に、そのテストが失敗したときに、どの利用者の何が損なわれるかを説明できるかを確かめる。説明できない観点のテストは、失敗しても利用者に影響する欠陥を示さず、振る舞いを変えない変更のたびに修正を求めるため、テストへ加えない。

| 観点 | 判断 |
| --- | --- |
| 在庫が不足しているときに注文が拒否される | 対象にする。購入者が受け取れない商品の代金を請求される。 |
| 公開APIが不正な引数に対して定められたエラーを返す | 対象にする。呼び出し側のプログラムがエラーを処理できなくなる。 |
| 監視に使う障害のログが定められた項目を出力する | 対象にする。運用者が障害を検知できなくなる。 |
| 計算結果が内部のキャッシュへ格納される | 対象にしない。応答時間に要求があるときは、その応答時間を検証する。 |
| 処理の途中で内部の補助関数が呼ばれる | 対象にしない。補助関数を使った結果として利用者が観測する値を検証する。 |
| 外部ライブラリがオブジェクトをJSONへ変換する | 対象にしない。変換の正しさはライブラリ自身のテストで担保される。自分たちが定めた項目名や形式は、公開APIの応答として検証する。 |

選んだ観点は、正常時、異常時、境界条件のそれぞれについて、仕様が定める振る舞いを期待する結果としてテストする。実装から読み取った動作をそのままテストへ書き写すと、仕様との食い違いをテストが追認してしまう。

### 品質特性への要求も検証対象にする

性能、信頼性、セキュリティ、互換性など、品質特性に要求がある場合は、機能の結果に加えて、その要求を満たしていることを検証する。機能が正しくても、応答時間や権限の扱いが要求に届かなければ、製品は使える状態にならない。

### リスクに応じて重点を決める

すべての組み合わせを同じ深さで検証せず、故障の起こりやすさと、故障したときの影響が大きい箇所を厚く検証する。限られた時間の中で、重大な欠陥から先に見つけられる。

### 自分たちが書いていない振る舞いはテストしない

フレームワークやライブラリが提供する動作、生成されたGetterやSetter、判断を持たないデータ構造の値の入れ替えは、テスト対象にしない。これらのテストは自分たちのコードの欠陥を見つけず、実装をなぞった写しとして保守の手間だけを増やす。フレームワークやライブラリの動作は提供元のテストで担保するものであり、欠陥を見つけた場合も利用する側のテストは加えず、提供元へ修正を求める。

自分たちが書いた処理と組み合わせて初めて成立する振る舞いは、その組み合わせを対象として検証する。

## 3. テストの種別

テストは次の種別に分け、同じ振る舞いは確認できる最も下位の種別で検証する。上位の種別ほど実行に時間がかかって結果が返るまで待たされ、変更で壊れやすく、失敗しても原因の箇所を絞り込みにくい。

| 種別 | 担当する範囲 |
| --- | --- |
| 単体テスト | 外部I/Oを持たない計算、変換、業務上の制約、状態遷移。複数の処理を組み合わせる対象では、組み合わせた結果として現れる値と状態。 |
| 結合テスト | データベース、HTTP、OSの機能、ミドルウェアなど、外部と接続する処理と内部処理のつながり。 |
| E2Eテスト | 利用者の主要な操作と、停止するとサービスの提供に重大な影響を与える処理経路。 |

## 4. テストケースの設計

### 同じ振る舞いになる入力をまとめる

入力の範囲を、同じ振る舞いが期待されるグループへ分け、各グループの代表値をテストする。有効な入力だけでなく、無効な入力のグループも対象にする。

### 境界の値を選ぶ

数値、日時、件数、長さなどに境界がある場合は、境界の値とその前後を選ぶ。欠陥は境界に集まりやすく、範囲の内側の値だけでは見落とす。有効範囲が1から100までであれば、0、1、100、101を検討する。

### 誤りやすい入力を加える

仕様から導いたケースに加えて、空の値、null、重複した値、桁あふれする値、過去に欠陥が見つかった入力のように、誤りやすいと分かっている入力をケースへ加えることが望ましい。これらの入力は仕様に明記されないことが多く、仕様から導いたケースだけでは漏れやすい。

### 条件の組み合わせを整理して選ぶ

複数の条件によって結果が変わる場合は、条件と期待結果の対応を整理し、意味の異なる組み合わせを選ぶ。組み合わせを数えずに選ぶと、結果が変わる条件の抜けに気づけない。

MC/DC（Modified Condition/Decision Coverage）を満たすように組み合わせを選ぶことが望ましい。MC/DCでは、ほかの条件を変えずにその条件だけを変えると結果が変わるケースの組を、条件ごとに含める。n個の条件をおよそn+1件のケースで検証でき、どの条件の判定を誤っても結果の違いとして現れる。

会員が5,000円以上を購入するか、クーポンを持っている場合に送料を無料にする仕様では、次の4件を選ぶ。

| 会員 | 5,000円以上 | クーポン | 送料無料 | 結果を変える条件 |
| --- | --- | --- | --- | --- |
| はい | はい | いいえ | はい | 基準とするケース |
| いいえ | はい | いいえ | いいえ | 会員（1行目と比べる） |
| はい | いいえ | いいえ | いいえ | 5,000円以上（1行目と比べる） |
| はい | いいえ | はい | はい | クーポン（3行目と比べる） |

### 状態遷移は禁止された遷移も検証する

状態によって許可される操作や結果が変わる場合は、状態、操作、遷移先を基準にケースを選ぶ。許可された遷移が成立することに加えて、禁止された遷移が拒否されることも検証する。

### 依存先の故障を注入して異常時の振る舞いを確かめる

依存先のタイムアウト、接続の切断、不正な応答、資源の枯渇のような故障をStubなどで注入し、対象がエラーの通知、再試行、処理の中止、安全な状態への移行のような定められた振る舞いをとることを検証することが望ましい。正常に応答する依存先だけで検証すると、故障時に誤ったデータを書き込む、応答を返さないといった欠陥を見落とす。

### 処理の間で受け渡す値を検証する

組み合わせた処理の間や外部との間で値を受け渡す箇所では、範囲の端の値、単位、精度、欠落した値が受け手で意図どおりに扱われることを、組み合わせた結果として検証することが望ましい。それぞれの処理を単独で検証しても、送り手と受け手で値の解釈が食い違う欠陥は見つからない。

### 機能の間の依存から影響を洗い出す

ある機能が別の機能の状態や出力を使う場合は、その依存を整理し、一方の機能の異常や設定の変更が他方へ与える影響をケースへ加えることが望ましい。機能ごとに検証するだけでは、機能の間の相互作用で起きる欠陥を見落とす。

### 実際の利用の流れからケースを導く

個々の機能の仕様に加えて、利用者が実際に行う操作の流れと、長時間の稼働、再起動、データの蓄積のような運用の条件からもケースを導くことが望ましい。機能の仕様から導いたケースだけでは、運用を続けたときに初めて現れる欠陥を見落とす。

### カバレッジはテストの不足を見つけるために使う

分岐や条件のカバレッジは、要求された振る舞いから作ったテストで届いていない箇所を探すために使う。カバレッジ率は実行された箇所を示すだけで、期待する振る舞いを確認したことは示さないため、テストが十分であることの根拠にしない。

単体テストでは分岐に加えて、複合条件を含む判定でMC/DCを、結合テストでは関数とその呼び出しが実行されたかを測ることが望ましい。分岐だけを測ると、判定の中の一部の条件や、組み合わせた処理の間の呼び出しが検証されていないことに気づけない。

命令や分岐がテストで実行されない箇所を見つけた場合は、ケースを加えるだけでなく、仕様にない不要なコードではないかも確かめることが望ましい。仕様に対応しないコードは、テストされないまま意図しない振る舞いを生む。

## 5. 検証の方針

### 実装の手順ではなく期待する振る舞いを検証する

実装の手順を書き写したテストは、本番コードを変更するだけで失敗する一方で、変更前後のどちらについても正しさを確認できない。欠陥を見つけないまま保守の手間だけを増やすため、検証するのは対象に期待する振る舞いだけにする。

### 観測できる結果があるときは状態を検証する

戻り値、対象や協力先の状態、永続化された内容など、処理の後に観測できるものが検証する結果である。呼び出しの検証は対象が正しく動いたことまでは示さないのに対し、状態の検証は結果そのものを確認するため、同じ振る舞いを保ったまま内部構造を変更してもテストを維持できる。

### 状態で確認できない場合にインタラクションを検証する

検証するのは、呼び出し先、引数、回数、順序など、正しさに関わるやり取りである。該当するのは次の場合である。

| 場合 | 例 |
| --- | --- |
| 実物やFakeを使えず、結果を状態として観測できない | メール送信、イベント発行、決済要求など、外部への作用が期待する振る舞いである処理 |
| 呼び出しの回数や順序の違いが望まない振る舞いを生む | 重複した送信、余分なディスク読み取り、順序の誤りによるデッドロック |
| 出力の内容だけでなく、その求め方が仕様に含まれる | 特定のアルゴリズムを使うことが仕様で決まっている処理 |
| 描画の詳細を分離したUIで、表示側への指示が対象の責務である | 画面を描画する部品へ表示内容を渡すPresenter、ViewModel、Controller |

応答時間のように達成すべき値だけが要求されている場合は、内部の呼び出しではなく、その値を満たしていることを検証する。

### 外部への作用は作用の内容まで検証する

呼び出しの有無だけでなく、宛先、内容、回数など、要件が定める作用の中身まで確認する。確認したいのは特定の関数が呼ばれたことではなく、要件どおりの作用が発生したことである。

### 同じ仕様を満たす別の実装と結果を比べる

設計モデル、置き換え前の実装、参照実装のように、同じ仕様を満たす別の実装がある場合は、同じ入力に対する両者の出力を比べることが望ましい。期待する結果を1件ずつ書き出せないほど多くの入力でも、出力の食い違いとして欠陥を見つけられる。

## 6. 内部実装の呼び出し

### 観測できる結果があるときは内部実装の呼び出しを検証しない

内部で利用する関数や協力先の構成は、利用者から観測できない。呼び出しを検証すると、振る舞いを変えないリファクタリングでもテストが失敗する。

### private関数は公開された振る舞いを通して検証する

公開された振る舞いから十分に検証できない場合は、テストの方法ではなく責務の分割を見直す。

## 7. Test Doubleの選び方

Test Doubleには、テストで果たす役割ごとに次の種類がある。

| 種類 | 役割 |
| --- | --- |
| Dummy | 引数を埋めるためだけに渡し、処理では使用しない。 |
| Fake | 実物と同じ働きをする軽量な実装を持つが、本番では使えない近道を含む。 |
| Stub | テストで決めた値を返し、対象を目的の状態にする。 |
| Spy | Stubとして応答しながら、呼び出された内容を記録する。 |
| Mock | 期待する呼び出しをあらかじめ設定し、そのとおりに呼ばれたかを判定する。 |

### 実物を優先し、代わりはテストの目的で選ぶ

依存先には実物の実装を優先する。実物に近いほどテストは本番の動作を再現するため、対象が正しく動いていることを確かめられる。

実物を使えない場合は、依存先の振る舞いが結果に影響するならFakeを使い、特定の値、異常、応答の遅延など、実物やFakeでは作りにくい状況を再現するならStubを使う。

SpyとMockも依存先を置き換えるが、選ぶ理由は振る舞いの再現ではなく、やり取りの記録と判定にある。使うのは、インタラクションを検証する場合に限る。

### 独立して変更される依存先はContract Testで裏付ける

自分たちの変更とは別に更新される依存先をTest Doubleへ置き換える場合は、Contract Testを設け、Test Doubleの応答が実物の契約と一致していることを定期的に確認する。依存先の変更にTest Doubleが追随できないと、テストは通るのに本番では動かない状態になる。
