# Webアーキテクチャガイドライン

## 1 はじめに

### 1.1 目的

この文書の目的は、Webサイト及びWebアプリケーションの用途から、性能を最大にする構成を選ぶための判断基準を共有することである。想定する読者は、Webサイト及びWebアプリケーションを設計する開発者及びAIエージェントである。

### 1.2 適用範囲

この文書は、Webサイト及びWebアプリケーションのレンダリング方式、データの取得、キャッシュ、性能、検索エンジンへの対応、セッション及び配信について規定する。

この文書は、[アーキテクチャ設計ガイドライン](architecture-guidelines.md)を前提とする。画面の視覚表現は[Web UIガイドライン](../ui/web-ui-guidelines.md)、実装は[JavaScript実装ガイドライン](../implementation/javascript-guidelines.md)、通信方式は[通信方式ガイドライン](communication-protocol-guidelines.md)による。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)によるほか、[アーキテクチャ設計ガイドライン](architecture-guidelines.md)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| SSG（Static Site Generation、静的生成） | ビルド時にHTMLを生成し、静的ファイルとして配信する方式。 |
| ISR（Incremental Static Regeneration、増分静的再生成） | 静的に生成したHTMLを、期限又はデータの更新を契機にページ単位で再生成する方式。 |
| SSR（Server-Side Rendering、サーバーサイドレンダリング） | 要求ごとにサーバーでHTMLを生成する方式。 |
| ストリーミングSSR | サーバーで生成したHTMLを、準備ができた部分から順に送るSSR。 |
| CSR（Client-Side Rendering、クライアントサイドレンダリング） | ブラウザーでJavaScriptを実行してHTMLを生成する方式。 |
| SPA（Single Page Application） | 最初に読み込んだページの中で、画面の切替えをJavaScriptで行うアプリケーション。 |
| ハイドレーション | サーバーで生成したHTMLに、ブラウザーでイベント処理及び状態を結び付ける処理。 |
| アイランドアーキテクチャ | 静的なHTMLの中で、操作が必要な部分だけをハイドレーションする構成。 |
| BFF（Backend for Frontend） | 一つの種類の画面のために、データの集約、認証情報の保持などを行うサーバー。 |
| PWA（Progressive Web App） | Service Workerなどを使い、インストール及びオフラインでの動作を可能にしたWebアプリケーション。 |
| LCP（Largest Contentful Paint） | 表示領域の中で最も大きいコンテンツが表示されるまでの時間。読込みの速さの指標。 |
| INP（Interaction to Next Paint） | 利用者の操作から次の描画までの時間。応答性の指標。 |
| CLS（Cumulative Layout Shift） | 予期しないレイアウトのずれの量。視覚的な安定性の指標。 |

## 2 構成の選び方

### 2.1 選択の手順

構成は、次の手順で選ぶ。

1. [表2](#table-2)から、用途が最も近い行を選ぶ。

2. ページが[表3](#table-3)の要件をもつ場合は、そのページの方式を置き換える。

3. レンダリング方式は、サイト全体ではなく、ページ又は経路ごとに選ぶ。同じサイトの中でも、公開ページと管理画面とでは、最適な方式が異なる。

4. [5章](#5-キャッシュ)及び[6章](#6-性能)によって、キャッシュ及び性能の目標を決める。

5. 決定をADRに記録する。

### 2.2 用途別の推奨構成

用途別の推奨構成は、[表2](#table-2)による。各行は、その用途で利用者が体感する遅延を最も小さくする構成を示す。

<a id="table-2"></a>表2−用途別の推奨構成

| 用途 | 例 | レンダリング | データの取得及び更新 | キャッシュ及び配信 | 重視する指標 |
| --- | --- | --- | --- | --- | --- |
| 企業サイト、製品紹介、キャンペーン | コーポレートサイト<br>ランディングページ | SSG。操作が必要な部分だけをアイランドにする。 | ヘッドレスCMS（Content Management System）での公開を契機に、再ビルド又はページの再生成を行う。 | 全てのページをCDNから配信する。 | LCP<br>CLS<br>検索順位 |
| メディア、ブログ、ドキュメント | ニュース<br>技術文書<br>ヘルプセンター | SSG。ページ数が多い場合はISR。 | 記事の更新を契機に、該当するページだけを再生成する。サイト内検索は、静的な索引又は検索サービスで行う。 | CDNから配信する。広告などの外部スクリプトは、遅延して読み込む。 | LCP<br>CLS<br>検索順位 |
| ECサイト | 商品一覧<br>商品詳細<br>カート<br>決済 | 商品一覧及び商品詳細はISR。在庫、価格、カートなど、利用者又は時点で変わる部分はクライアントで取得する。カート及び決済はSSR。 | 在庫及び価格は、短い期限で取得する。決済は、決済代行の画面又は部品を使う。 | 商品ページはCDNから配信する。カート及び決済はキャッシュしない。 | LCP<br>INP<br>検索順位<br>購入完了率 |
| 会員向けサービス、SNS | マイページ<br>タイムライン | 最初の表示はストリーミングSSR。以降の画面切替えはクライアントで行う。 | 一覧は、カーソルによるページ送りで少しずつ取得する。投稿は、楽観的に画面へ反映する。 | 静的ファイルだけをCDNに置く。HTML及びAPIの応答は、利用者ごとに扱う。 | LCP<br>INP |
| 業務アプリケーション、管理画面、SaaSのダッシュボード | 受発注管理<br>分析画面 | SPA。検索エンジンへの対応は不要である。 | サーバー状態のキャッシュを使い、古い値を表示しながら裏で再取得する。大量の行は、仮想スクロールで表示する。 | アプリケーションの殻をCDNから配信する。APIの応答は、共有のキャッシュに置かない。 | INP<br>操作の完了までの時間 |
| リアルタイムの共同作業 | チャット<br>共同編集<br>ホワイトボード | SPA | WebSocketで双方向に通信する。共同編集の競合は、CRDT（Conflict-free Replicated Data Type）又はOT（Operational Transformation）で解決する。 | 静的ファイルだけをCDNに置く。 | 操作の反映の遅延<br>INP |
| 地図、位置情報 | 店舗検索<br>配車<br>資産管理 | 地図以外の部分はSSR又はSSG。地図はクライアントでWebGLによって描画する。 | 表示範囲及びズームレベルに応じて、タイルを取得する。 | タイルをCDNから配信する。 | 描画のフレームレート<br>タイルの読込み時間 |
| オフラインでも使う業務 | 現場の点検<br>倉庫の棚卸 | PWA化したSPA | 端末内のデータベースに保存し、接続の回復時に同期する。 | Service Workerで、静的ファイル及びデータをキャッシュする。 | オフラインでの操作の継続<br>同期の完了時間 |
| AI機能を含むアプリケーション | チャット<br>文書の生成<br>画像の解析<br>音声の対話 | SPA又はストリーミングSSR | 生成結果をServer-Sent Eventsで逐次表示する。ファイルはオブジェクトストレージへ直接送る。APIキーはBFFに置く。 | 静的ファイルだけをCDNに置く。 | 最初の結果が表示されるまでの時間 |

地図の詳細は[地図アプリケーション設計ガイドライン](map-application-guidelines.md)、AI機能の詳細は[AI機能設計ガイドライン](../ai/ai-feature-design-guidelines.md)による。

### 2.3 要件による方式の置換え

ページが次の要件をもつ場合は、[表2](#table-2)の行に加えて、[表3](#table-3)の方式を使う。

<a id="table-3"></a>表3−要件による方式の置換え

| 要件 | 使う方式 | 使わない方式 |
| --- | --- | --- |
| 検索結果に表示させる。 | SSG、ISR又はSSR | CSRだけでの描画 |
| 全員に同じ内容を表示し、更新は1日に数回以下である。 | SSG | 要求ごとのSSR |
| 全員に同じ内容を表示し、更新は数分〜数時間ごとである。 | ISR又は短い期限のCDNキャッシュ | 要求ごとのSSR |
| 利用者ごとに内容が異なり、最初の表示を速くする。 | ストリーミングSSR。共通の部分を先に送る。 | CSRだけでの描画 |
| 操作が多く、画面の切替えが頻繁である。 | クライアントでの画面切替え | 操作ごとのページ全体の再読込み |
| 操作がほとんどなく、読むことが主である。 | アイランドアーキテクチャ又はJavaScriptを送らない静的なHTML | ページ全体のハイドレーション |
| オフラインで動作させる。 | PWA | サーバーに依存する描画 |

## 3 レンダリング方式

レンダリング方式の比較は、[表4](#table-4)による。

<a id="table-4"></a>表4−レンダリング方式の比較

| 方式 | HTMLを生成する時点 | 最初の表示の速さ | 適する内容 | 欠点 |
| --- | --- | --- | --- | --- |
| SSG | ビルド時 | 最も速い。CDNからすぐに返る。 | 全員に同じで、更新が少ない内容 | ページ数が多いと、ビルドが長い。更新の反映にビルドが必要である。 |
| ISR | 初回の要求時又は更新時 | SSGと同等である。再生成の間は、古い内容を返す。 | 全員に同じで、ページ数が多いか、更新が多い内容 | 再生成の期限の間は、古い内容が表示される。 |
| ストリーミングSSR | 要求ごと | 速い。共通の部分を先に表示できる。 | 利用者ごとに異なる内容 | サーバーの計算資源が必要である。データの取得が遅いと、表示も遅れる。 |
| SSR（ストリーミングなし） | 要求ごと | 全てのデータがそろうまで表示されない。 | ストリーミングを使えない環境での、利用者ごとに異なる内容 | 最も遅いデータの取得に、表示が左右される。 |
| CSR | ブラウザーでの実行時 | 最も遅い。JavaScriptの読込み及び実行の後に表示される。 | ログイン後の操作の多い画面 | 検索エンジンへの対応が弱い。端末の性能に左右される。 |

SSR及びSSGでも、ページ全体をハイドレーションすると、送るJavaScriptが増えてINPが悪化する。操作が必要な部分だけをハイドレーションし、それ以外の部分にはJavaScriptを送らない。

## 4 データの取得及び状態

### 4.1 往復の回数を減らす

一つの画面に必要なデータは、1回の往復で取得できるようにする。画面ごとにデータを集約する必要がある場合は、BFF又はサーバーでのデータの取得を使う。部品ごとに順番にデータを取得すると、往復の時間が直列に積み重なる。独立したデータの取得は、並列に行う。

### 4.2 サーバーの状態をクライアントで複製しない

サーバーから取得したデータは、サーバー状態のキャッシュの仕組みで扱い、クライアントの共通の状態管理へ複製しない。複製すると、同じデータの更新の反映漏れが起きる。クライアントの状態は、入力中の値、開閉の状態など、画面だけがもつ値に限る。

### 4.3 画面の条件をURLに持たせる

検索条件、絞込み、並べ替え、ページ番号及び選択中のタブは、URLのパス又はクエリパラメーターに持たせる。URLに持たせれば、再読込み、共有及びブラウザーの戻る操作で同じ画面を再現でき、ページ単位のキャッシュも効く。

### 4.4 楽観的な更新は失敗がまれな操作に限る

いいね、並べ替えのように、失敗がまれで、取り消しても利用者が困らない操作は、サーバーの応答を待たずに画面へ反映する。決済、予約のように、失敗した場合の影響が大きい操作は、サーバーの応答を待ってから反映する。

## 5 キャッシュ

### 5.1 HTTPキャッシュを設定する

応答の種類ごとのCache-Controlは、[表5](#table-5)による。

<a id="table-5"></a>表5−応答の種類ごとのCache-Control

| 応答 | Cache-Control | 理由 |
| --- | --- | --- |
| ファイル名に内容のハッシュを含むJavaScript、CSS、画像及びフォント | `public, max-age=31536000, immutable` | 内容が変われば、ファイル名も変わるため、無期限にキャッシュできる。 |
| 全員に同じHTML | `public, max-age=0, s-maxage=<秒>, stale-while-revalidate=<秒>` | ブラウザーは毎回確認し、CDNは期限の間保持する。期限切れの後も、再取得の間は古い内容を返す。 |
| 利用者ごとに異なるHTML及びAPIの応答 | `private, no-cache`又は`no-store` | 共有のキャッシュに保存させない。 |
| 個人情報又は認証情報を含む応答 | `no-store` | どこにも保存させない。 |

### 5.2 CDNのキャッシュを無効化できるようにする

CDNのキャッシュは、内容の更新を契機に、該当するURL又はタグの単位で無効化できるようにする。無効化できない場合は、更新の反映までの時間がキャッシュの期限で決まり、期限を短くするしかなくなる。

## 6 性能

### 6.1 目標

Core Web Vitalsの目標は、実利用者の75パーセンタイルで、LCP 2.5秒以下、INP 200ミリ秒以下及びCLS 0.1以下とする。目標は、開発者の端末での計測ではなく、実利用者の計測で判定する。

### 6.2 LCPを短くする

LCPの対象となる画像及び文字は、次によって最も早く表示させる。

- LCPの画像は、HTMLの中に直接記載し、`fetchpriority="high"`を付ける。遅延読込みにしない。

- 表示領域の外にある画像は、`loading="lazy"`で遅延して読み込む。

- 画像は、表示の大きさに合わせた複数の解像度を`srcset`で示し、AVIF又はWebPで配信する。

- フォントは、使う文字だけに絞ったサブセットを使い、`font-display`を指定する。日本語のフォントは大きいため、システムフォントで足りる場合は、Webフォントを使わない。

- 最初の表示に必要なCSSだけを先に読み込み、表示を妨げるスクリプトを置かない。

### 6.3 INPを短くする

操作への応答を速くするため、次による。

- JavaScriptは、経路ごとに分割し、その画面で必要な分だけを読み込む。

- 50ミリ秒を超える処理は、分割するか、Web Workerへ移す。

- 外部のスクリプトは、表示及び操作の後に読み込む。

- 大量の行又は要素は、仮想スクロールで、表示領域の分だけを描画する。

### 6.4 CLSを抑える

画像、動画、広告及び埋込みには、幅と高さ又は縦横比をあらかじめ指定し、読込みの後にレイアウトがずれないようにする。

### 6.5 性能の予算を決める

経路ごとに、JavaScriptの転送量、LCP及びINPの上限を性能の予算として決め、予算を超えた変更をCIで検出する。予算がなければ、機能の追加ごとに性能が少しずつ劣化しても、気付けない。

## 7 検索エンジン及び共有への対応

検索結果に表示させるページは、次による。

- 検索エンジンが読む内容を、JavaScriptを実行しなくても読めるHTMLとして返す。

- ページごとに、固有の`title`、`meta name="description"`及び正規URL（`link rel="canonical"`）を設定する。

- `sitemap.xml`及び`robots.txt`を配置する。

- 構造化データをJSON-LDで記載する。

- SNSで共有されるページには、Open Graphのメタデータを設定する。

- 多言語のページには、`hreflang`で言語ごとのURLを示す。

- URLを変更する場合は、旧URLから新URLへ、恒久的なリダイレクト（301又は308）を設定する。

## 8 セッション及びセキュリティ

認証の方式は、[アプリケーション設計ガイドライン](../software/application-design-guidelines.md)の4章による。Webでは、次の事項を加える。

- セッションは、`HttpOnly`、`Secure`及び`SameSite=Lax`以上を付けたCookieで保持する。アクセストークンを`localStorage`に保存しない。

- 外部の認証基盤とOAuthで連携する場合は、トークンをBFFで保持し、ブラウザーにはセッションのCookieだけを渡す。

- 状態を変更する要求には、CSRF（Cross-Site Request Forgery）の対策を行う。

- Content-Security-Policy、Strict-Transport-Security、X-Content-Type-Options及び`frame-ancestors`を設定する。

## 9 配信及び運用

配信及び運用は、次による。配置先の選択は、[アーキテクチャ設計ガイドライン](architecture-guidelines.md)の4.5による。

- SSGのページは、静的ホスティング及びCDNから配信する。

- エッジの実行環境でSSRを行うのは、データベースへの問合せがない場合、又はエッジの近くにデータの複製がある場合に限る。

- プルリクエストごとに確認用の環境を作り、性能の予算を検査する。

- 実利用者の計測で、Core Web Vitals及びエラーを継続して監視する。

## 10 チェックリスト

- 用途を[表2](#table-2)から選び、[表3](#table-3)の要件で置き換えた結果を、ADRに記録している。

- レンダリング方式を、経路ごとに選んでいる。

- 検索結果に表示させるページを、CSRだけで描画していない。

- 操作が必要な部分だけをハイドレーションしている。

- 一つの画面のデータを、1回の往復で取得できる。

- 画面の条件が、URLに含まれている。

- 応答の種類ごとに、[表5](#table-5)のCache-Controlを設定している。

- 利用者ごとに異なる応答を、共有のキャッシュに保存していない。

- LCPの画像を、遅延読込みにしていない。

- 経路ごとに性能の予算があり、CIで検査している。

- Core Web Vitalsを、実利用者の計測で監視している。
