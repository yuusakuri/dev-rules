# 通信方式ガイドライン

## 1 はじめに

### 1.1 目的

本書は、通信の性能の最大化を目的とする。

### 1.2 適用範囲

本書は、ブラウザー、モバイルアプリケーション、サーバー及び機器の間の通信方式、データ形式及び接続の設定について規定する。

本書は、[アーキテクチャ設計ガイドライン](architecture-guidelines.md)を前提とする。

### 1.3 用語及び定義

本書で用いる主な用語及び定義は、[表1](#table-1)によるほか、[アーキテクチャ設計ガイドライン](architecture-guidelines.md)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| HTTP/2 | 一つのTCP接続の上で、複数の要求及び応答を並行して扱うHTTPの版。 |
| HTTP/3 | QUICの上で動作するHTTPの版。パケットの損失が、他の要求の遅延に波及しない。 |
| QUIC | UDPの上で、暗号化、多重化及び再送を行うトランスポートプロトコル。 |
| REST | HTTPのメソッド及びURLでリソースを操作するAPIの設計様式。 |
| GraphQL | クライアントが必要な項目を問合せで指定する、APIの問合せ言語。 |
| gRPC | Protocol Buffers及びHTTP/2を使うRPCの仕組み。 |
| Protocol Buffers | スキーマに基づいて、データを小さなバイナリにする形式。 |
| SSE（Server-Sent Events） | サーバーからブラウザーへ、HTTPの応答としてイベントを逐次送る仕組み。 |
| WebSocket | 一つのTCP接続の上で、双方向にメッセージを送る通信規約。 |
| WebTransport | HTTP/3の上で、双方向のストリーム、及び順序を保証しないデータグラムを扱う通信規約。 |
| WebRTC | ブラウザー間で、音声、映像及びデータを直接送る仕組み。 |
| SFU（Selective Forwarding Unit） | WebRTCで、各参加者から受けた映像及び音声を、他の参加者へ転送するサーバー。 |
| HLS（HTTP Live Streaming）、DASH（Dynamic Adaptive Streaming over HTTP） | 動画を短い区間のファイルに分け、回線の速度に合わせた画質でHTTPによって配信する方式。 |
| MQTT | 発行及び購読の形式で、小さなメッセージを送る軽量の通信規約。 |
| Webhook | イベントの発生時に、提供者が、登録されたURLへHTTPの要求を送る仕組み。 |
| べき等 | 同じ要求を複数回行っても、1回行った場合と結果が同じである性質。 |
| デッドレターキュー | 処理に繰り返し失敗したメッセージを移すキュー。 |

## 2 選択の手順

通信方式は、次の手順で選ぶ。

1. 通信の相手を、ブラウザー、モバイルアプリケーション、自社のサーバー、外部のサービス及び機器から特定する。

2. 通信の型を、要求と応答、サーバーからの送信、双方向の通信、一方向のイベント及び大きなデータの転送から特定する。

3. [表2](#table-2)から、相手及び型が一致する行を選ぶ。

4. [4章](#4-接続の設定)の設定を適用する。

既定の選択肢は、HTTP/2又はHTTP/3の上のHTTPとする。HTTPを使えば、CDN、プロキシ、キャッシュ及び監視の仕組みをそのまま使える。HTTP以外の方式は、[表2](#table-2)でその方式が性能上有利な用途にだけ使う。

## 3 用途別の推奨方式

### 3.1 推奨方式の一覧

用途別の推奨方式は、[表2](#table-2)による。

<a id="table-2"></a>表2−用途別の推奨方式

| 用途 | 推奨方式 | 性能上の理由 | 条件付きの代替 |
| --- | --- | --- | --- |
| ブラウザー又はモバイルアプリケーションから、自社のAPIへの要求及び応答 | REST及びJSON（HTTP/2又はHTTP/3） | CDN及びHTTPキャッシュで、応答を再利用できる。 | 画面ごとに必要な項目が大きく異なり、往復が増える場合はGraphQL。クライアント及びサーバーを同じチームがTypeScriptで実装する場合は、型を共有するRPC。 |
| 外部の開発者に公開するAPI | REST及びJSON。OpenAPIで定義する。 | 利用者が標準の道具で扱え、キャッシュも効く。 | 大量のデータを扱う利用者には、gRPC又は一括取得のAPIを追加する。 |
| 自社のサーバー間の要求及び応答 | gRPC | バイナリ形式で小さく、HTTP/2で接続を再利用し、スキーマから型を生成できる。 | ブラウザーから直接呼ぶ場合は、gRPC-Web又はREST。 |
| サーバーからブラウザーへの一方向の通知及び逐次送信 | SSE | HTTPの上で動作し、切断時の再接続及び再開が標準で定められている。 | 双方向の通信が必要な場合は、WebSocket。 |
| ブラウザーとサーバーとの双方向の低遅延の通信 | WebSocket | 接続を維持し、要求ごとのヘッダーなしでメッセージを送れる。 | 順序の保証が不要なデータが多い場合、又は一つの接続で多数のストリームを独立に扱う場合は、WebTransport。 |
| 音声、映像及びブラウザー間の直接のデータ通信 | WebRTC | 端末の間で直接、損失に強い方式で送れる。 | 1対多の配信は、SFUを経由する。 |
| 録画した動画及び大規模な生放送の配信 | HLS又はDASH。CDNから配信する。 | 短い区間のファイルとしてCDNでキャッシュでき、回線に合わせて画質を切り替えられる。 | 2秒未満の遅延が必要な場合は、WebRTC。 |
| 不安定な回線又は省電力の機器からの送信 | MQTT | ヘッダーが小さく、接続を維持して小さなメッセージを送れる。配信の保証の水準を選べる。 | 機器が少なく、送信の間隔が長い場合は、HTTP。 |
| 自社のサーバー間の非同期の処理の依頼 | メッセージキュー | 送信側は処理の完了を待たずに応答でき、受信側は自分の速度で処理できる。 | 同じイベントを複数の処理で読む場合、又は過去のイベントを再処理する場合は、イベントストリーム。 |
| 外部のサービスから自社へのイベントの通知 | Webhook | ポーリングの往復がなく、発生の直後に届く。 | 提供者がイベントストリームを提供する場合は、イベントストリーム。 |
| 大きなファイルのアップロード | 署名付きURLによるオブジェクトストレージへの直接の送信。大きなファイルは、分割して再開可能にする。 | アプリケーションのサーバーを経由せず、その帯域及び処理を消費しない。 | − |
| 大きなファイルのダウンロード | CDN又はオブジェクトストレージからの配信。範囲要求に対応する。 | 利用者に近い拠点から送り、途中から再開できる。 | − |

### 3.2 ポーリングを避ける

更新を知るための定期的な問合せ（ポーリング）は、更新がない間も往復及び処理を消費し、更新の反映が問合せの間隔だけ遅れる。サーバーからの送信は、SSE、WebSocket又はWebhookで行う。ポーリングを使うのは、相手がこれらに対応していない場合に限り、その場合は間隔を指数関数的に延ばす。

### 3.3 GraphQLを使う場合の条件

GraphQLを使う場合は、問合せを事前に登録し、IDで呼び出す方式（persisted queries）にする。事前に登録すれば、問合せの文字列を送らずに済み、GETで送ってCDNのキャッシュも使える。問合せの深さ及び計算量には上限を設け、一つの問合せでサーバーを占有させない。関連するデータは、まとめて取得する仕組みで取得し、N+1クエリを避ける。

## 4 接続の設定

### 4.1 HTTP/2及びHTTP/3を有効にする

外部に公開するHTTPの通信では、HTTP/2及びHTTP/3を有効にする。HTTP/3は、パケットの損失が多いモバイルの回線で、遅延を小さくする。TLSは、1.3を使う。

TLS 1.3及びQUICの0-RTTの再開は、べき等な要求にだけ使う。0-RTTのデータは、第三者が再送できる。

### 4.2 接続を再利用する

サーバーから他のサーバー又はデータベースへの接続は、接続プールで再利用する。要求ごとに接続すると、TCP及びTLSの確立に往復が加わる。ブラウザーから別のドメインへ接続する場合は、`<link rel="preconnect">`で事前に接続する。

### 4.3 圧縮する

テキストの応答は、Brotli又はgzipで圧縮する。JPEG、PNG、動画など、既に圧縮されている形式は、再び圧縮しない。

### 4.4 データ形式を選ぶ

データ形式は、次による。

- ブラウザーとの通信は、JSONを既定とする。

- サーバー間の通信は、Protocol Buffersを使う。

- 大量の数値の配列、座標、ベクトルなどは、JSONで送らず、バイナリ形式で送る。

- 応答には、呼出し元が使う項目だけを含める。

- 一覧は、カーソルによるページ送りで返し、件数の上限を設ける。オフセットによるページ送りは、件数が増えると遅くなる。

### 4.5 往復をまとめる

画面の表示又は一つの処理のために、同じ相手へ複数の要求を直列に送らない。複数の資源を一度に取得するAPI、又は画面単位で集約するBFF（Backend for Frontend）を用意する。

## 5 信頼性

### 5.1 べき等でない要求の再試行

タイムアウト、再試行の条件及び待機の間隔は、[アーキテクチャ設計ガイドライン](architecture-guidelines.md)の5.1による。POSTなど、べき等でない要求を再試行する場合は、クライアントが生成したべき等キーを`Idempotency-Key`ヘッダーで送り、サーバーは同じキーの要求に同じ結果を返す。

### 5.2 接続を維持する通信の再接続

SSE、WebSocket、WebTransport及びMQTTでは、次による。

- 切断を検知するため、一定の間隔で生存確認のメッセージを送る。

- 切断した場合は、間隔を延ばしながら再接続する。

- 再接続の後に、受け取っていないイベントから再開できるようにする。SSEでは、イベントにIDを付け、`Last-Event-ID`から再開する。

- 受信側が処理しきれない場合に、送信を抑える仕組み（背圧）を設ける。

### 5.3 非同期のメッセージ

メッセージキュー及びイベントストリームは、少なくとも1回の配信を前提とし、受信側の処理をべき等にする。処理に繰り返し失敗したメッセージは、デッドレターキューへ移し、他のメッセージの処理を止めない。

### 5.4 Webhookの受信

Webhookを受信する場合は、署名を検証した後すぐに2xxを返し、処理は非同期に行う。同じイベントが複数回届くことを前提に、イベントのIDで重複を除く。

## 6 セキュリティ

通信のセキュリティは、次による。

- 全ての通信を、TLSで暗号化する。サーバー間の通信は、相互TLSで相手を認証する。

- WebSocket及びWebTransportは、接続の確立時に、`Origin`及び認証を検証する。

- Webhookの送信及び受信には、本文及び時刻に対する署名を付け、古い時刻の要求を拒否する。

- メッセージの大きさ、接続数及び要求の頻度に上限を設ける。

## 7 チェックリスト

- 通信の相手及び型から、[表2](#table-2)で方式を選んでいる。

- HTTP以外の方式を使う箇所に、性能上の理由がある。

- ポーリングを使っていない。使う場合は、相手が他の方式に対応していない。

- 外部に公開するHTTPの通信で、HTTP/2及びHTTP/3が有効である。

- サーバーからの接続を、接続プールで再利用している。

- 一つの処理で、同じ相手へ直列の要求を送っていない。

- べき等でない要求の再試行に、べき等キーを使っている。

- 接続を維持する通信に、生存確認、再接続及び再開の仕組みがある。

- 非同期のメッセージの受信側が、べき等である。
