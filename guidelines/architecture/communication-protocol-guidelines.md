# 通信方式ガイドライン

## 1 はじめに

### 1.1 目的

本書の目的は、通信の用途から、遅延とスループットが最も良い通信方式を選ぶための判断基準を共有することである。

### 1.2 適用範囲

本書は、ブラウザ、モバイルアプリケーション、サーバー及び機器の間の通信方式、データ形式及び接続の設定について規定する。

本書は、[アーキテクチャ設計ガイドライン](architecture-guidelines.md)を前提とする。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| HTTP/2 | 一つのTCP接続の上で、複数の要求と応答を並行して扱うHTTPの版。 |
| HTTP/3 | QUICの上で動作するHTTPの版。パケットの損失が他の要求の遅延に波及しない。 |
| QUIC | UDPの上で、暗号化、多重化及び再送を行うトランスポートプロトコル。 |
| REST | HTTPのメソッドとURLでリソースを操作するAPIの設計様式。 |
| GraphQL | クライアントが必要な項目を問合せで指定するAPIの問合せ言語。 |
| gRPC | Protocol BuffersとHTTP/2を使うRPCの仕組み。 |
| Protocol Buffers | スキーマに基づいてデータを小さなバイナリにする形式。 |
| SSE（Server-Sent Events） | サーバーからブラウザへ、HTTPの応答としてイベントを逐次送る仕組み。 |
| WebSocket | 一つのTCP接続の上で、双方向にメッセージを送る通信規約。 |
| WebTransport | HTTP/3の上で、双方向のストリームと、順序を保証しないデータグラムを扱う通信規約。 |
| WebRTC | ブラウザ間で、音声、映像及びデータを直接送る仕組み。 |
| MQTT | 発行と購読の形式で、小さなメッセージを送る軽量の通信規約。 |
| Webhook | イベントの発生時に、提供者が登録されたURLへHTTPの要求を送る仕組み。 |
| べき等 | 同じ要求を複数回行っても、1回行った場合と結果が同じである性質。 |

## 2 選択の手順

通信方式は、次の手順で選ぶ。

1. 通信の相手を、ブラウザ、モバイルアプリケーション、自社のサーバー、外部のサービス又は機器から特定する。

2. 通信の型を、要求と応答、サーバーからの送信、双方向、一方向のイベント又は大きなデータの転送から特定する。

3. [表2](#table-2)から、相手と型が一致する行を選ぶ。

4. [4章](#4-接続の設定)の設定を適用する。

既定の選択肢は、HTTP/2又はHTTP/3の上のHTTPである。HTTP以外の方式は、[表2](#table-2)でその方式が性能上有利な用途にだけ使う。HTTPは、CDN、プロキシ、キャッシュ、監視などの周辺の仕組みがそのまま使える。

## 3 用途別の推奨方式

### 3.1 推奨方式の一覧

用途別の推奨方式は、[表2](#table-2)による。

<a id="table-2"></a>表2−用途別の推奨方式

| 用途 | 推奨方式 | 性能上の理由 | 条件付きの代替 |
| --- | --- | --- | --- |
| ブラウザ又はモバイルアプリケーションから自社のAPIへの要求と応答 | HTTP/2又はHTTP/3の上のREST、JSON | CDN及びHTTPキャッシュで応答を再利用できる。 | 画面ごとに必要な項目が大きく異なり、往復が増える場合はGraphQL。クライアントとサーバーを同じチームがTypeScriptで実装する場合は型を共有するRPC。 |
| 外部の開発者に公開するAPI | REST、JSON、OpenAPIで定義 | 利用者が標準の道具で扱え、キャッシュも効く。 | 大量のデータを扱う利用者向けにはgRPC又は一括取得のAPIを追加する。 |
| 自社のサーバー間の要求と応答 | gRPC | バイナリ形式で小さく、HTTP/2で接続を再利用し、スキーマから型を生成できる。 | ブラウザから直接呼ぶ場合はgRPC-Web又はREST。 |
| サーバーからブラウザへの一方向の通知及び逐次送信 | SSE | HTTPの上で動き、切断時の再接続と再開が標準で定められている。 | 双方向が必要になればWebSocket。 |
| ブラウザとサーバーの双方向の低遅延の通信 | WebSocket | 接続を維持し、要求ごとのヘッダーなしでメッセージを送れる。 | 順序の保証が不要なデータが多い場合、又は一つの接続で多数のストリームを独立に扱う場合はWebTransport。 |
| 音声、映像及びブラウザ間の直接のデータ通信 | WebRTC | 端末間で直接、損失に強い方式で送れる。 | 1対多の配信は、メディアサーバー（SFU）を経由する。 |
| 録画した動画及び大規模な生放送の配信 | HLS又はDASHをCDNから配信 | 小さな区間のファイルとしてCDNでキャッシュでき、回線に合わせて画質を切り替えられる。 | 2秒未満の遅延が必要な場合はWebRTC。 |
| 不安定な回線又は省電力の機器からの送信 | MQTT | ヘッダーが小さく、接続を維持して小さなメッセージを送れる。配信の保証の水準を選べる。 | 機器が少なく、送信の間隔が長い場合はHTTP。 |
| 自社のサーバー間の非同期の処理の依頼 | メッセージキュー | 送信側は処理の完了を待たずに応答でき、受信側は自分の速度で処理できる。 | 同じイベントを複数の処理で読む、又は過去のイベントを再処理する場合はイベントストリーム。 |
| 外部のサービスから自社へのイベントの通知 | Webhook | ポーリングの往復がなく、発生の直後に届く。 | 提供者がイベントストリームを提供する場合はそれを使う。 |
| 大きなファイルのアップロード | オブジェクトストレージへ署名付きURLで直接送る。大きなファイルは分割して再開可能にする。 | アプリケーションのサーバーを経由せず、帯域と処理を消費しない。 | — |
| 大きなファイルのダウンロード | CDN又はオブジェクトストレージから配信する。範囲要求に対応する。 | 利用者に近い拠点から送り、途中から再開できる。 | — |

### 3.2 ポーリングを避ける

更新を知るための定期的な問合せ（ポーリング）は、更新がない間も往復と処理を消費し、更新の反映が問合せの間隔だけ遅れる。サーバーからの送信は、SSE、WebSocket又はWebhookで行う。ポーリングを使うのは、相手がこれらに対応していない場合に限り、その場合は間隔を指数関数的に延ばす。

### 3.3 GraphQLを使う場合の条件

GraphQLを使う場合は、問合せを事前に登録し、IDで呼び出す方式（persisted queries）にする。事前に登録すれば、問合せの文字列を送らずに済み、GETで送ってCDNのキャッシュも使える。問合せの深さと計算量には上限を設け、一つの問合せでサーバーを占有させない。関連するデータは、まとめて取得する仕組みで取得し、N+1クエリを避ける。

## 4 接続の設定

### 4.1 HTTP/2及びHTTP/3を有効にする

外部に公開するHTTPの通信では、HTTP/2とHTTP/3を有効にする。HTTP/3は、パケットの損失が多いモバイルの回線で、遅延を小さくする。TLSは1.3を使う。

TLS 1.3及びQUICの0-RTTの再開は、べき等な要求にだけ使う。0-RTTのデータは、第三者が再送できる。

### 4.2 接続を再利用する

サーバーから他のサーバーやデータベースへの接続は、接続プールで再利用する。要求ごとに接続すると、TCPとTLSの確立に往復が加わる。ブラウザから別のドメインへ接続する場合は、`<link rel="preconnect">`で事前に接続する。

### 4.3 圧縮する

テキストの応答は、Brotli又はgzipで圧縮する。JPEG、PNG、動画など既に圧縮されている形式は、再び圧縮しない。

### 4.4 データ形式を選ぶ

データ形式は、次による。

- ブラウザとの通信は、JSONを既定とする。

- サーバー間の通信は、Protocol Buffersを使う。

- 大量の数値の配列、座標、ベクトルなどは、JSONで送らず、バイナリ形式で送る。

- 応答には、呼出し元が使う項目だけを含める。

- 一覧は、カーソルによるページ送りで返し、件数の上限を設ける。オフセットによるページ送りは、件数が増えると遅くなる。

### 4.5 往復をまとめる

画面の表示又は一つの処理のために、同じ相手へ複数の要求を直列に送らない。複数の資源を一度に取得するAPI、又は画面単位で集約するBFFを用意する。

## 5 信頼性

### 5.1 タイムアウトと再試行

全ての要求に、タイムアウトを設定する。再試行は、べき等な要求にだけ行う。POSTなどべき等でない要求を再試行する場合は、クライアントが生成したべき等キーを`Idempotency-Key`ヘッダーで送り、サーバーは同じキーの要求に同じ結果を返す。再試行の間隔は、指数関数的に延ばし、ゆらぎを加える。

### 5.2 接続を維持する通信の再接続

SSE、WebSocket、WebTransport及びMQTTでは、次による。

- 切断を検知するため、一定の間隔で生存確認のメッセージを送る。

- 切断した場合は、間隔を延ばしながら再接続する。

- 再接続の後に、受け取っていないイベントから再開できるようにする。SSEでは、イベントにIDを付け、`Last-Event-ID`から再開する。

- 受信側が処理しきれない場合に送信を抑える仕組み（背圧）を設ける。

### 5.3 非同期のメッセージ

メッセージキュー及びイベントストリームは、少なくとも1回の配信を前提とし、受信側の処理をべき等にする。処理に繰り返し失敗したメッセージは、デッドレターキューへ移し、他のメッセージの処理を止めない。

### 5.4 Webhookの受信

Webhookを受信する場合は、署名を検証した後すぐに2xxを返し、処理は非同期に行う。同じイベントが複数回届くことを前提に、イベントのIDで重複を除く。

## 6 セキュリティ

- 全ての通信を、TLSで暗号化する。サーバー間の通信は、相互TLSで相手を認証する。

- WebSocket及びWebTransportは、接続の確立時に、`Origin`と認証を検証する。

- Webhookの送信と受信には、本文と時刻に対する署名を付け、古い時刻の要求を拒否する。

- メッセージの大きさ、接続数及び要求の頻度に上限を設ける。

## 7 チェックリスト

- 通信の相手と型から、[表2](#table-2)で方式を選んでいる。

- HTTP以外の方式を使う箇所に、性能上の理由がある。

- ポーリングを使っていない。使う場合は、相手が他の方式に対応していない。

- 外部に公開するHTTPの通信で、HTTP/2及びHTTP/3が有効である。

- サーバーからの接続を、接続プールで再利用している。

- 一つの処理で、同じ相手へ直列の要求を送っていない。

- 全ての要求にタイムアウトがあり、再試行するのはべき等な要求だけである。

- 接続を維持する通信に、生存確認、再接続及び再開の仕組みがある。

- 非同期のメッセージの受信側がべき等である。
