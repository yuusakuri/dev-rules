# アーキテクチャ設計ガイドライン

## 1 はじめに

### 1.1 目的

本書の目的は、システムの構成を、要件及び品質特性から根拠をもって選ぶための判断基準を共有することである。

### 1.2 適用範囲

本書は、実行単位の分け方、データストア、通信方式、配置先など、システム全体の構成の設計について規定する。

実行単位の内部のフォルダ及びモジュールの構成は、[アプリケーション設計ガイドライン](../software/application-design-guidelines.md)による。用途別の構成は、[表1](#table-1)の文書による。

<a id="table-1"></a>表1−用途別の構成を定める文書

| 用途 | 文書 |
| --- | --- |
| Webサイト及びWebアプリケーション | [Webアーキテクチャガイドライン](web-architecture-guidelines.md) |
| 通信方式の選択 | [通信方式ガイドライン](communication-protocol-guidelines.md) |
| 地図を表示するアプリケーション | [地図アプリケーション設計ガイドライン](map-application-guidelines.md) |
| テキスト、画像、動画、音声などを扱うAI機能 | [AI機能設計ガイドライン](../ai/ai-feature-design-guidelines.md) |

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表2](#table-2)による。

<a id="table-2"></a>表2−用語及び定義

| 用語 | 定義 |
| --- | --- |
| 品質特性 | 性能効率性、信頼性、保守性、セキュリティなど、機能以外にシステムが満たすべき性質。ISO/IEC 25010の分類による。 |
| 実行単位 | 独立して起動、配置及びスケールできるプログラムの単位。 |

| スループット | 単位時間に処理できる要求又はデータの量。 |

## 2 基本方針

### 2.1 性能を最優先の品質特性とする

利用側プロジェクトが別の優先順位を定めていない場合は、性能効率性を最優先の品質特性とし、選択肢の中から、要件を満たし、かつ利用者が体感する遅延が最も小さいものを選ぶ。利用者が待つ時間は、全ての機能の価値を下げる。

性能と他の品質特性とが競合する場合は、次の順に判断する。

a) セキュリティ及びデータの正しさを損なう選択はしない。

b) a)を満たす選択肢の中から、利用者が体感する遅延が最も小さいものを選ぶ。

c) 遅延が同等の場合は、費用及び運用の負担が小さいものを選ぶ。

### 2.2 性能の目標を数値で決める

性能の目標は、“速い”のような形容ではなく、指標、測定点、パーセンタイル及び値で決める。測定できない目標は、選択肢の比較にも、劣化の検出にも使えない。

性能の目標の例は、[表3](#table-3)による。

<a id="table-3"></a>表3−性能の目標の例

| 対象 | 指標 | 目標の例 |
| --- | --- | --- |
| Webページ | LCP、INP、CLS（実利用者の75パーセンタイル） | LCP 2.5秒以下、INP 200ミリ秒以下、CLS 0.1以下 |
| 利用者が操作するAPI | サーバーの応答時間の95パーセンタイル | 200ミリ秒以下 |
| 非同期の処理 | 受付から完了までの時間の95パーセンタイル | 30秒以下 |
| バッチ処理 | 処理時間 | 定められた時間枠の50 %以下 |

Webページの指標は、[Webアーキテクチャガイドライン](web-architecture-guidelines.md)による。

### 2.3 遅延の内訳から構成を決める

構成を決める前に、主要な操作について、ネットワークの往復、サーバーの処理、データストアの読み書き、外部サービスの呼出しに分けて遅延の内訳を見積もる。遅延の大部分は、往復回数及びデータの移動量で決まる。

遅延を減らす手段は、効果の大きい順に、次による。

a) 処理そのものをなくす。結果を事前に作る、キャッシュする、又は不要な処理を削る。

b) 往復をなくす。利用者に近い場所で応答する、複数の要求をまとめる、又は直列の呼出しを並列にする。

c) 移動するデータを減らす。必要な項目だけを返す、圧縮する、又は形式を小さくする。

d) 処理を速くする。索引を追加する、アルゴリズムを変える、又は計算資源を増やす。

### 2.4 測定してから最適化する

性能の改善は、本番又は本番相当の環境で測定し、遅延の最も大きい箇所から行う。測定せずに行う最適化は、効果のない箇所へ複雑さを加える。

測定には、実利用者の計測、分散トレース及び負荷試験を使い分ける。負荷試験は、本番で想定する最大の同時利用数とデータ量で行う。

### 2.5 後から変えにくい決定を先に検討する

データモデル、識別子の形式、テナントの分離方式、認証の方式、データを置く地域は、運用を開始した後に変えると移行の費用が大きい。これらは、他の決定より先に、複数の選択肢を比較して決める。

## 3 設計の進め方

### 3.1 要件及び制約を確認する

構成を検討する前に、次の事項を確認する。確定していない事項は、依頼者に確認する。

- 主要な操作と、その頻度及びピーク時の量

- データの件数、大きさ及び増加の速さ

- 性能、可用性及びセキュリティの目標

- 利用者の所在地及び利用する端末とネットワーク

- 開発、運用する体制の人数

- 予算、既存のシステム、法令及び契約による制約

### 3.2 決定をADRに記録する

構成に関する決定は、[ADRテンプレート](../../templates/documentation/architecture-decision-record.md)を使い、1件の決定を1件のADRに記録する。ADRには、比較した選択肢、各選択肢の性能の見積り又は測定結果、選んだ理由、及び受け入れた欠点を記載する。理由を残しておけば、前提が変わったときに、どの決定を見直すべきかが分かる。

### 3.3 構成をC4モデルで図示する

システムの構成は、C4モデルのシステムコンテキスト図、コンテナ図及びコンポーネント図で示す。図の作成方法は、[Mermaid図の画像変換ガイドライン](../documentation/mermaid-image-guidelines.md)又は[PlantUML図の画像変換ガイドライン](../documentation/plantuml-image-guidelines.md)による。

## 4 構成の選択

### 4.1 実行単位の分け方

実行単位は、一つのモジュラーモノリスから始める。実行単位を分けると、プロセス内の関数呼出しがネットワーク越しの通信に変わり、遅延、障害の箇所及び運用の負担が増える。

実行単位を分けるのは、[表4](#table-4)の条件に当てはまる部分だけとする。

<a id="table-4"></a>表4−実行単位を分ける条件

| 条件 | 分ける部分の例 |
| --- | --- |
| 必要な計算資源の種類又は量が他と大きく異なる。 | GPUを使う推論、画像の変換、大量のバッチ処理 |
| 処理時間が長く、利用者の要求への応答を待たせる。 | 動画の変換、AIの処理、帳票の生成 |
| 障害の影響を他の機能へ広げてはならない。 | 決済、認証 |
| 別のチームが独立して頻繁に配置する必要がある。 | 組織の境界に沿った機能 |
| 異なる言語又は実行環境が必要である。 | Pythonで実装する機械学習の処理 |

### 4.2 同期処理と非同期処理

利用者が結果を待つ処理は、要求の中で完了させる。要求の中で完了しない処理は、キューを介した非同期の処理にし、受付をすぐに返す。

同期処理と非同期処理の選択は、[表5](#table-5)による。

<a id="table-5"></a>表5−同期処理と非同期処理の選択

| 処理の性質 | 選択 |
| --- | --- |
| 利用者が結果を待ち、遅延の目標内に完了する。 | 同期処理 |
| 遅延の目標を超える、又は処理時間が入力によって大きく変わる。 | 非同期処理。受付を返し、完了を通知する。 |
| 外部サービスの呼出しで、相手の速度制限又は障害の影響を受ける。 | 非同期処理。キューで流量を調整し、再試行する。 |
| 一時的に大量の要求が集中する。 | 非同期処理。キューで負荷を平準化する。 |
| 後続の処理が、結果を待たなくてよい。 | 非同期処理。イベントとして発行する。 |

非同期処理の通知の方式は、[通信方式ガイドライン](communication-protocol-guidelines.md)による。

### 4.3 データストアの選択

データストアは、リレーショナルデータベースを既定とし、その他の種類は、リレーショナルデータベースで性能の目標を満たせない用途にだけ追加する。データストアの種類が増えるほど、データの同期と運用の負担が増える。

データストアの選択は、[表6](#table-6)による。

<a id="table-6"></a>表6−データストアの選択

| 用途 | データストア | 選ぶ理由 |
| --- | --- | --- |
| 業務データ、トランザクションが必要なデータ | リレーショナルデータベース（PostgreSQLなど） | 整合性、結合、索引による検索を一つで扱える。 |
| 頻繁に読む値、セッション、速度制限の計数 | インメモリのキーバリューストア（Redis、Valkeyなど） | メモリ上で1ミリ秒未満で読み書きできる。 |
| 全文検索、あいまい検索、検索結果の集計 | 検索エンジン（OpenSearch、Elasticsearchなど） | 転置索引で大量の文書から高速に検索できる。 |
| 画像、動画、文書などのファイル | オブジェクトストレージ（Amazon S3、Cloud Storageなど） | 大きなファイルを安価に保存し、CDNから配信できる。 |
| 位置、範囲などの地理データ | 空間索引をもつデータベース（PostGISなど） | 空間索引で範囲内の地物を高速に検索できる。 |
| 時系列の計測値 | 時系列データベース | 時刻の範囲での集計及び古いデータの削除が速い。 |
| 埋め込みベクトルの近傍検索 | ベクトル索引（pgvector、専用のベクトルデータベースなど） | 近似最近傍探索で類似の項目を高速に検索できる。 |
| 大量のイベントの記録と再処理 | イベントストリーム（Apache Kafkaなど） | 高いスループットで書き込み、過去のイベントを読み直せる。 |

データ件数が少ない間は、ベクトル索引及び空間索引も、PostgreSQLの拡張機能で扱える。専用のデータストアへの移行は、測定した性能が目標を満たさない場合に行う。

### 4.4 キャッシュ

読取りが書込みより十分に多く、多少古い値を返してよいデータは、キャッシュする。キャッシュは、利用者に近い層から順に、ブラウザ、CDN、アプリケーションのメモリ、共有のキャッシュストアの順で検討する。利用者に近いほど、往復の時間が短い。

キャッシュには、有効期限と無効化の方法を必ず決める。利用者ごとに異なるデータは、共有のキャッシュへ置かない。

### 4.5 配置先の選択

配置先は、管理されたサービスを既定とする。サーバーの保守、スケールの調整及びセキュリティの更新を提供者に任せれば、性能の改善に工数を使える。

配置先の選択は、[表7](#table-7)による。

<a id="table-7"></a>表7−配置先の選択

| 配置先 | 適する処理 | 性能上の注意 |
| --- | --- | --- |
| CDN及び静的ホスティング | 事前に生成したHTML、画像、JavaScriptなどの静的ファイル | 利用者に最も近い場所から配信でき、最も速い。 |
| エッジの実行環境 | 認証の確認、振分け、軽い加工など、データベースを使わない処理 | データベースが遠い場合は、往復が増えて遅くなる。 |
| サーバーレスの関数 | 要求の量が大きく変動する処理 | 起動直後の要求が遅くなる。遅延の目標が厳しい処理では、常時起動の設定を使う。 |
| 管理されたコンテナの実行環境 | 常時要求を受けるAPI、長時間の処理 | 起動の遅延がなく、接続を再利用できる。 |
| 仮想マシン | GPU、特殊な構成が必要な処理 | 運用の負担が最も大きい。 |

計算資源とデータベースは、同じ地域に置く。異なる地域に置くと、全ての問合せに地域間の往復が加わる。

## 5 信頼性と運用

### 5.1 失敗を前提に設計する

ネットワーク越しの全ての呼出しには、タイムアウトを設定する。再試行は、べき等な操作だけに行い、指数関数的に間隔を延ばし、ゆらぎを加える。失敗が続く依存先には、サーキットブレーカーで呼出しを止め、待ち時間が連鎖して全体が遅くなることを防ぐ。

### 5.2 SLOを定めて監視する

主要な操作ごとに、遅延と成功率のSLOを定め、達成状況を監視する。SLOを下回った場合は、新しい機能より、性能と信頼性の改善を優先する。

### 5.3 可観測性を確保する

ログ、メトリクス及びトレースを、OpenTelemetryなどの標準の形式で出力し、要求ごとの識別子で相互に関連付ける。トレースがあれば、遅延の内訳を測定でき、[2.4](#24-測定してから最適化する)の改善の対象を特定できる。ログの規則は、[ソフトウェア設計ガイドライン](../software/software-design-guidelines.md)の10章による。

## 6 セキュリティ

アプリケーションのセキュリティは、[アプリケーション設計ガイドライン](../software/application-design-guidelines.md)の4章による。構成の設計では、次の事項を追加で確認する。

- データの流れを図にし、信頼の境界ごとに脅威を洗い出す。

- 実行単位、データストア及び外部サービスへの権限は、必要な操作だけに限定する。

- データストアは、インターネットから直接接続できない位置に置く。

- 通信は、内部の通信も含めて暗号化する。

## 7 チェックリスト

- 性能の目標が、指標、パーセンタイル及び値で定められている。

- 主要な操作について、遅延の内訳を見積もっている。

- 選択肢を比較し、要件を満たす中で遅延が最も小さいものを選んでいる。

- 実行単位を分けた部分が、[表4](#table-4)の条件に当てはまる。

- 遅延の目標を超える処理が、非同期の処理になっている。

- データストアの種類ごとに、リレーショナルデータベースで目標を満たせない理由がある。

- キャッシュごとに、有効期限と無効化の方法が決まっている。

- 計算資源とデータベースが同じ地域にある。

- 全てのネットワーク越しの呼出しに、タイムアウトがある。

- 構成の決定が、ADRに記録されている。
