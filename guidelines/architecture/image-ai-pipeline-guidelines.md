# 画像AI処理設計ガイドライン

## 1 はじめに

### 1.1 目的

本書の目的は、画像の受付からAIによる処理及び結果の提示までを、速く、安全に、かつ失敗しても回復できるように設計するための判断基準を共有することである。

### 1.2 適用範囲

本書は、ブラウザ又はモバイルアプリケーションからの画像のアップロード、画像の保存と検証、分類、文字認識、物体検出、画像を入力とするLLMなどのAIによる処理、及び結果の通知について規定する。

本書は、[アーキテクチャ設計ガイドライン](architecture-guidelines.md)及び[通信方式ガイドライン](communication-protocol-guidelines.md)を前提とする。LLMを使う処理の評価と運用は、[LLMアプリケーション設計ガイドライン](../ai/llm-application-guidelines.md)による。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| オブジェクトストレージ | ファイルをキーで保存し、HTTPで読み書きする保存先。 |
| 署名付きURL | 期限と操作を限定して、認証なしでオブジェクトストレージへの読み書きを許可するURL。 |
| ジョブ | 1枚の画像に対する一連の処理の単位。状態をもつ。 |
| ワーカー | キューからジョブを受け取って処理する実行単位。 |
| デッドレターキュー | 処理に繰り返し失敗したメッセージを移すキュー。 |
| べき等キー | 同じ処理の重複を判別するための一意の値。 |
| EXIF | 画像ファイルに埋め込まれた、撮影日時、撮影位置、向きなどの付加情報。 |
| 解凍爆弾 | ファイルの大きさは小さいが、展開すると膨大な画素数になる画像。 |
| 信頼度 | AIが出力した結果について、モデルが示す確からしさの値。 |

## 2 全体の構成

### 2.1 処理の流れ

画像の処理は、[表2](#table-2)の流れで行う。画像の本体はアプリケーションのサーバーを経由させず、キューにも載せない。キューには、画像の保存先のキーだけを載せる。

<a id="table-2"></a>表2−処理の流れ

| 順序 | 段階 | 実行する場所 | 行うこと |
| --- | --- | --- | --- |
| 1 | 事前の検証と縮小 | クライアント | 形式と大きさを検証し、AIの処理に必要な解像度まで縮小する。縮小した画像をプレビューとしてすぐに表示する。 |
| 2 | アップロードの受付 | API | ジョブを作成し、形式、大きさ及び期限を限定した署名付きURLを返す。 |
| 3 | アップロード | クライアントからオブジェクトストレージへ直接 | 署名付きURLで送る。大きなファイルは分割して再開可能にする。 |
| 4 | 処理の依頼 | オブジェクトストレージのイベント又はAPI | ジョブのIDと画像のキーをキューへ送る。 |
| 5 | 検証と正規化 | ワーカー | 実際の形式と画素数を検証し、向きを補正し、EXIFを除き、AIの入力に合わせて変換する。 |
| 6 | AIによる処理 | ワーカー | モデルを呼び出し、結果を検証して保存する。 |
| 7 | 結果の通知 | API | ジョブの状態の変化をクライアントへ通知する。 |
| 8 | 結果の表示と訂正 | クライアント | 結果と信頼度を表示し、利用者が訂正できるようにする。 |

### 2.2 同期処理と非同期処理の選択

AIによる処理は、非同期の処理を既定とする。AIの処理時間は入力とモデルの混雑によって変わり、外部のAIサービスは速度制限と一時的な障害を伴う。同期処理にすると、遅い要求がサーバーの接続を占有し、他の利用者の応答も遅くなる。

同期処理にするのは、次の全てを満たす場合に限る。

- 処理時間の99パーセンタイルが、利用者が待てる時間に収まる。

- 要求の量が、AIサービスの速度制限より十分に小さい。

- 失敗した場合に、利用者がその場でやり直せばよい。

## 3 アップロード

### 3.1 オブジェクトストレージへ直接送る

画像は、署名付きURLを使い、クライアントからオブジェクトストレージへ直接送る。アプリケーションのサーバーを経由すると、画像の大きさの分だけ帯域、メモリ及び処理時間を消費し、他の要求の遅延が増える。

署名付きURLは、次によって限定する。

- 期限を数分にする。

- 書き込める保存先のキーを、サーバーが生成した一つのキーに限る。

- Content-Typeと大きさの上限を、署名の条件に含める。

### 3.2 クライアントで縮小する

クライアントでは、AIの処理に必要な解像度まで画像を縮小してから送る。携帯電話で撮影した画像は数MBあり、多くのAIのモデルは、入力をそれより小さな解像度に縮小して処理する。縮小すれば、アップロードの時間、保存の費用及びAIの処理の費用が減る。

AIの処理に必要な解像度は、使うモデルの資料で確認する。原寸の画像を保存する必要がある場合は、縮小した画像と原寸の画像を分けて送り、AIの処理は縮小した画像で先に始める。

### 3.3 不安定な回線に備える

モバイルアプリケーションからのアップロードは、通信が途切れても途中から再開できる方式（分割アップロード、tusなど）を使う。HEIC形式で撮影された画像は、端末でJPEGに変換するか、サーバーで変換する。

### 3.4 保存先を分ける

オブジェクトストレージは、利用者からの読み取りを禁止し、検証前の画像と検証済みの画像とで保存先を分ける。保存先のキーは、サーバーが生成したランダムな値とし、利用者が指定したファイル名を使わない。画像を利用者に表示する場合は、検証済みの画像を、期限付きの署名付きURL又は認証付きのCDNから配信する。

## 4 検証と正規化

画像は、ワーカーで次によって検証し、正規化する。クライアントでの検証は利用者への案内のためであり、改ざんできるため、安全の根拠にしない。

- ファイルの先頭のバイト列で実際の形式を判定し、許可した形式だけを受け付ける。拡張子とContent-Typeは信用しない。

- 展開する前に、画像の幅と高さを読み、画素数の上限を超える画像を拒否する。解凍爆弾は、展開の時点でメモリを使い果たす。

- 画像を再エンコードし、画像以外のデータを除く。

- EXIFの向きの情報に従って画素を回転させた後、EXIFを除く。撮影位置は個人の所在を示す。

- 画像を処理するライブラリは、最新の版に保ち、権限を限定した環境で実行する。

- 不特定の利用者が投稿し、他の利用者に公開する画像は、公開の前に不適切な内容の検出を行う。

## 5 AIによる処理

### 5.1 ジョブを状態で管理する

ジョブは、`pending`、`uploaded`、`processing`、`succeeded`、`failed`の状態をもち、許可した遷移だけを行う。状態の遷移の規則は、[ロジック設計ガイドライン](../software/logic-design-guidelines.md)による。

### 5.2 処理をべき等にする

キューは、同じメッセージを複数回配信することがある。ワーカーは、ジョブのIDとモデルの版をべき等キーにし、既に結果があるジョブを再び処理しない。

### 5.3 失敗の種類ごとに扱いを変える

失敗は、次によって扱う。

- 速度制限、タイムアウト、サーバーの一時的な障害は、間隔を指数関数的に延ばして再試行する。

- 形式の誤り、内容の拒否など、再試行しても成功しない失敗は、再試行せずに`failed`にし、理由を記録する。

- 再試行の上限に達したメッセージは、デッドレターキューへ移し、監視の対象にする。

- キューのメッセージを他のワーカーに見えなくする時間は、処理時間の上限より長くする。短いと、処理中のジョブを別のワーカーが重ねて処理する。

### 5.4 流量を制御する

外部のAIサービスを呼ぶワーカーの同時実行数は、サービスの速度制限から決め、超えないようにする。急がない大量の処理は、提供元のバッチAPIを使い、費用を下げる。

### 5.5 出力を検証する

AIの出力は、スキーマで形式を検証し、値の範囲と業務上の制約を確認してから保存する。検証に失敗した出力は、再試行するか、人の確認に回す。AIの出力をそのまま画面のHTML又はデータベースの問合せに埋め込まない。

### 5.6 人の確認を組み込む

信頼度が閾値を下回る結果、及び利用者の権利又は金銭に影響する判断は、人が確認してから確定する。利用者が訂正した結果は保存し、評価用のデータとして使う。

### 5.7 再現できるように記録する

結果ごとに、モデルの名前と版、プロンプトの版、前処理の設定及び処理の日時を記録する。記録がなければ、結果が変わった原因をモデルの変更と入力の変更とで区別できない。

### 5.8 データの扱いを確認する

外部のAIサービスへ画像を送る前に、提供元のデータの保存期間、学習への利用の有無及び処理する地域を確認し、利用者への説明と同意の範囲に収める。顔などの個人を識別できる画像は、個人情報として扱う。

## 6 結果の通知と表示

- アップロードの直後に、クライアントの画像からプレビューを表示し、処理の状態を示す。

- 処理の状態の変化は、SSE又はWebSocketで通知する。これらを使えない場合は、間隔を延ばしながら問い合わせる。

- 利用者が画面を離れても処理を続け、完了をプッシュ通知又は一覧の表示で知らせる。

- 失敗した場合は、理由と、利用者が取れる操作（撮り直し、再試行など）を示す。

- 結果には、信頼度の低い箇所が分かる表示と、訂正の操作を設ける。

## 7 運用

次のメトリクスを監視する。

- キューの長さと、最も古いメッセージの経過時間

- 受付から完了までの時間の95パーセンタイル

- 失敗の理由ごとの件数

- 画像1枚あたりのAIの処理の費用

キューの長さに応じて、ワーカーの数を自動で増減する。検証前の画像と、保存期間を過ぎた画像は、オブジェクトストレージのライフサイクルの規則で自動で削除する。

## 8 チェックリスト

- 画像の本体が、アプリケーションのサーバーを経由していない。

- キューに、画像の本体ではなく保存先のキーを載せている。

- 署名付きURLの期限、キー、形式及び大きさを限定している。

- クライアントで、AIの処理に必要な解像度まで縮小している。

- ワーカーで、実際の形式と画素数を検証し、EXIFを除いている。

- AIによる処理を、非同期の処理にしている。同期処理の場合は、[2.2](#22-同期処理と非同期処理の選択)の条件を満たす。

- ワーカーの処理がべき等である。

- 再試行する失敗と、再試行しない失敗を区別している。

- AIの出力を、スキーマで検証している。

- 結果ごとに、モデル、プロンプト及び前処理の版を記録している。

- キューの長さと処理時間を監視している。
