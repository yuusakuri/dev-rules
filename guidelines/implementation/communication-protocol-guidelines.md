## 1. 概要

本書は、[ソフトウェア設計ガイドライン](../software/software-design-guidelines.md)を前提に、新しい通信プロトコルの設計・実装と検証を扱います。

既存の通信規格やシリアル通信実装は、各層の役割や処理方法を考えるための設計例として参照します。

## 2. 通信層の分担

まず、下位層が提供する入出力の単位と保証を確認し、フレーム境界、順序、誤り検出、再送及びアドレスをどの層で扱うか決めます。

上位のメッセージを複数のフレームに分割する場合は、識別子、順序、再構成の上限及び欠落時の処理も定めます。

実装では、フレームの読み書きと、通信開始・終了などの状態管理を分けます。

PPPでは、フレーム化を担う仕様と、リンクや上位プロトコルの設定を担う仕様が分かれています。

## 3. フレーム境界と符号化

下位層がメッセージ境界を保つ場合は、その受信単位と設計するフレームを対応付けます。

バイトストリームを扱う場合は、長さや区切り文字からフレームの境界を求め、データが壊れたときに次の境界を探す方法も決めます。

### 長さに基づく区切り

長さフィールドを持つ方式では、ヘッダーから後続データの長さを読み取り、フレームの終端を求めます。

長さ自体が壊れた場合に備え、同期用の値や検査値と組み合わせて次のフレームを見つける手順を定めます。

### 予約値とデータの区別

区切り文字を使う方式では、同じ値がデータに含まれるときのエスケープ表現と、不正な列や空フレームの扱いを定めます。

SLIPはENDでフレームを終え、データ中のENDとESCを別のバイト列に置き換えます。

処理単位は通信路によって異なり、PPPのHDLC-like framingでは、非同期回線で予約バイトをエスケープし、ビット同期回線では連続する5個の`1`の後へ`0`を挿入します。

### COBSによる符号化

COBS（Consistent Overhead Byte Stuffing）は、ゼロの位置をコードバイトで表して`0x00`を含まないバイト列にし、末尾の`0x00`でフレームを区切れるようにします。

符号化後のサイズは、入力長を`n`バイトとすると`n + floor(n / 254) + 1`バイト以下なので、終端用の1バイトを加えてバッファを確保します（`floor`は小数点以下の切り捨てです）。

空データと末尾のコードの表現を決め、復号時はコードが示す長さを入力の残り長さと照合します。

送信しながら符号化する場合は、コード確定までの最大254バイトの先読みを考慮し、必要なバッファと送信開始までの待ち時間を見積もります。

## 4. フレーム内容と検査

### フィールドの定義

各フィールドの順序、幅、値の範囲及びバイトオーダーを定め、採用するフィールドについて次の内容を仕様へ記載します。

| フィールド | 定義する内容 |
| --- | --- |
| バージョン | 形式の互換性と、未知の値を受け取ったときの処理。 |
| 種別 | ペイロードの解釈、予約値及び未知の値を受け取ったときの処理。 |
| 長さ | 数える範囲、単位、最小値・最大値及びヘッダーや検査値を含むかどうか。 |
| 識別・順序 | アドレス、チャネル、シーケンス番号などの役割と、重複・欠落・順序逆転の扱い。 |
| ペイロード | データの形式、最大長及び空データの扱い。 |

格納できるデータ量は、通信路の上限と、各層のヘッダー・検査値・符号化による増加量から求めます。

識別子へ送信優先度も割り当てる場合は、CANのように値が競合時の待ち時間へ影響するため、その関係を仕様に含めます。

送信するバイト列は、定めたフィールドの幅とバイトオーダーに従って組み立てます。

### データの検査と保護

検査値の計算対象と符号化との順序を定め、送受信で同じ範囲を検査します。

受信側は、形式と検査値を確認してからペイロードを上位層へ渡します。

PPPの非同期フレームは、FCSを計算してからエスケープし、受信側でエスケープを復元してから検査する例です。

COBSを使う場合も、伝送誤りを検出する検査値を別途設けます。

CRCを使う場合は、生成多項式、初期値、入力・出力のビット順反転の有無、最終XOR、検査値の幅と格納順序を定めます。

改ざんやなりすましへの対策が必要な場合はMACや署名を、機密性の保護が必要な場合は暗号化を設計します。

## 5. 受信処理とバッファ管理

### 一括入力と解析状態

解析器は、バイト列をまとめて受け取り、途中の状態を次の呼び出しへ保持するAPIにします。

入力が1バイトずつでも、複数のフレームが一度に届いても、同じ解析結果を返せるようにします。

解析状態は、入力に応じた遷移、保持するデータ及び完了・失敗の判定を状態機械で表します。

内部で1バイトずつ解析する場合も、読み取り、ロック取得、タスク起動及びメモリ確保は入力やバッファの単位でまとめます。

ZephyrのModbus RTU実装はUART FIFOから空き容量に応じてまとめて読み取り、Linuxの非同期PPP実装は通常のデータが続く範囲をまとめてフレームバッファへコピーします。

### バッファの上限と所有権

受信した長さは、整数演算が範囲内に収まることと最大フレーム長を検証してから、バッファの確保や参照に使います。

受信バッファ、未処理入力及びキュー件数には上限を設け、超過時の破棄や再同期の処理を定めます。

ペイロードを参照で返すAPIでは、参照が有効な期間とバッファの再利用時点を明確にします。

その期間を超えてデータを保持する必要がある場合は、所有権を移すか、必要な範囲を所有バッファへコピーします。

## 6. 通信状態と障害からの復帰

### 受信エラーとタイムアウト

検査値の不一致、形式不正、長さ超過及び入力の途中終了などを区別し、発生数と解析状態を記録します。

フレーム受信、応答、送信及び再接続には待ち時間の上限を設け、期限切れになった処理を終了できるようにします。

不正なフレームや期限切れのフレームは破棄し、次の境界を検出できる状態へ戻します。

### 再送と接続状態

再送する場合は、要求と応答を対応付ける識別子、再送回数・間隔、期限後の応答の扱い及び失敗とする条件を定めます。

要求の重複に備え、同じ要求を繰り返しても一度の処理と同じ効果になるようにするか、識別子で重複を判定して処理を一度に限定します。

接続を確立する方式では、接続前、設定中、通信中及び終了時に受け付けるメッセージと、イベントや期限による状態遷移を定義します。

PPPはリンクの確立・設定・終了を状態遷移で表し、PPPoEは相手の発見とセッション中の通信を分けています。

再接続時は、解析途中のデータ、シーケンス番号、応答待ち、再送キュー及び認証状態を引き継ぐか破棄するかを決めます。

## 7. 検証

### 送受信と異常系

[テストガイドライン](../software/testing-guidelines.md)に従い、仕様から期待するバイト列と解析結果を用意して、送信・受信を個別に検証します。

往復変換と独立した送受信実装の接続も確認し、次の入力や状態で仕様どおりに動くことを確かめます。

| 検証対象 | 確認する入力や状態 |
| --- | --- |
| 入力の分割 | 完全なフレーム、任意位置での分割、1バイトずつの入力及び複数フレームの一括入力。 |
| フレーム境界 | 空フレーム、連続する区切り、終端不足及び通信ノイズ後の入力。 |
| フィールド | 最小長・最大長とその前後、未知のバージョン・種別、予約値、バイトオーダー及び長さ不一致。 |
| COBS | 空データ、254バイト境界の前後、ゼロの連続、ゼロを含まない最大長、不正なコード、終端不足及び連続するフレーム。 |
| エスケープ | 予約バイトの有無、予約バイトだけの入力、連続・不正なエスケープ列及び最大増加量。 |
| 誤り検出 | ヘッダー・ペイロード・検査値のビット反転、検査範囲の境界及び誤った初期値・バイトオーダー。 |
| 復帰 | 長さ超過、キュー満杯、タイムアウト、切断・再接続、重複要求、応答の欠落・遅延及び順序逆転。 |

### 転送量と処理時間

性能の測定では、通信速度、CPU、入力サイズ・内容及び同時実行数を記録し、比較する項目以外の条件をそろえます。

転送量は、最悪時の符号化による増加と区切りを含めて求めます。

予約バイトを2バイトに置き換える方式では、対象データがすべて予約バイトになる場合の2倍の長さに、区切りなどの固定部分を加えます。

付加ビットを含むデータ量を通信速度で割り、フレーム間隔を加えた最大転送時間が、許容する待ち時間に収まることを確認します。

処理負荷は、送受信の呼び出し回数、CPU時間、最大バッファ長、メモリ確保回数及びコピー量で評価し、破損した入力から再同期するまでの時間も測ります。

入力をまとめるサイズも変え、呼び出し負荷と、データがそろうまでの待ち時間の関係を確認します。
