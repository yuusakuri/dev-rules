# 検索システム構築ガイドライン

## 1 はじめに

### 1.1 目的

本書の目的は、LLMが外部の文書を根拠に回答するRAG（Retrieval-Augmented Generation）を、検索の精度、回答の根拠、権限、費用を一貫した基準で設計し、改善できるようにすることである。

### 1.2 適用範囲

本書は、社内文書、製品の文書、コード、問い合わせの履歴などを根拠にLLMが回答するシステムと、AIエージェントが文書又はコードを検索する仕組みの、取り込み、索引、検索、権限、生成、評価、運用を規定する。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| RAG | 質問に関連する文書の断片を検索し、LLMへの入力に加えて回答を生成する方式。 |
| チャンク | 索引と検索の単位として文書を分割した断片。 |
| 埋め込み | 文章の意味を表す数値のベクトル。意味の近さで検索するために使用する。 |
| ベクトル検索 | 埋め込みの類似度で検索する方式。言い換え又は表現の揺れに強い。 |
| 全文検索 | BM25などの、語の一致で検索する方式。固有名詞、型番、エラーコードに強い。 |
| ハイブリッド検索 | ベクトル検索と全文検索の結果を統合する方式。 |
| リランキング | 検索した候補を、質問との関連度を精密に評価するモデルで並べ替える処理。 |
| Contextual Retrieval | チャンクに、文書全体から見た位置付けの説明を加えてから索引する方式。 |
| エージェント型の検索 | エージェントが検索のツールを使用し、検索語の作成、検索、読み込みを繰り返して必要な情報を集める方式。 |
| GraphRAG | 文書から抽出したエンティティと関係のグラフを使用して検索又は要約を行う方式。 |
| コネクター | 業務システムから文書と権限の情報を取り込む部品。 |
| 正本 | 複数の版又は写しがある文書のうち、正しいものとして扱う文書。 |
| アクセス制御リスト（ACL） | 文書ごとに、読める利用者とグループ、読めない利用者とグループを定めた一覧。 |

## 2 方式の選び方

### 2.1 検索が必要かを先に判断する

文書の総量がモデルのコンテキストに収まる場合は、検索を作らず、文書の全体をプロンプトに入れる。文書の総量がおよそ20万トークン以下であれば、全体をプロンプトに入れ、プロンプトキャッシュで費用と遅延を抑える方が、検索の誤りがなく単純である。

状況ごとの方式は、[表2](#table-2)による。

<a id="table-2"></a>表2−状況ごとの方式

| 状況 | 方式 | 例 |
| --- | --- | --- |
| 文書がコンテキストに収まり、更新が少ない。 | 全体をプロンプトに入れ、プロンプトキャッシュを使用する。 | 100ページの製品マニュアルについて答える。 |
| 文書がコンテキストに収まらない、又は頻繁に更新される。 | RAGを構築する。 | 社内規程と手順書の1万件について答える。 |
| 対象がコードのリポジトリで、エージェントがコードを探す。 | エージェント型の検索（ファイル名、文字列、シンボルの検索）から始める。 | `refreshToken` の呼び出し元を探す。 |
| 文書の集合全体の傾向又は主題を問う質問が多い。 | グラフを使用する検索を加える。 | “過去3年の障害報告で繰り返す原因は何か” |
| 利用者によって読める文書が異なる。 | 検索の条件に権限を含める。全体の投入は、読める文書が同じ利用者の間に限る。 | 部署ごとに共有範囲が異なる社内文書について答える。 |
| 図、表、画面の画像に情報がある文書が多い。 | 文書の解析を強化するか、ページの画像で検索する方式を加える。 | 決算資料のグラフ、機器の配線図、スライドから答える。 |

| --- | --- | --- |

## 3 文書の取り込み

### 3.1 質問に必要な情報源から順に集める

全ての業務システムを最初から取り込まない。実際の質問を集め、答えるのに必要な情報源から順にコネクターでつなぐ。

情報源は、[表6](#table-6)による。

<a id="table-6"></a>表6−情報源

| 情報源 | 例 | 取り込む内容 | 扱い方 |
| --- | --- | --- | --- |
| ファイル共有 | SharePoint、Google Drive、Box | 文書、版、共有の設定 | 正本のフォルダに限って取り込む。 |
| Wiki | Confluence、Notion | ページ、ページの階層、更新日時 | 階層を見出しとしてチャンクに加える。 |
| チャット | Slack、Microsoft Teams | スレッド | スレッドを一つの単位にする。結論が出たチャンネル又は期間に限る。 |
| チケット | Jira、ServiceNow、Zendesk | 問題、対応、解決の状態 | 解決済みのものを、問題と解決の組にする。 |
| 業務データ | Salesforce、会計システム | 取引先、案件、金額 | “今月の受注額は？”のような集計は、検索せず、SQL又はAPIをツールとして渡す。 |

### 3.2 正本を決める

同じ内容の文書が複数あると、古い内容又は下書きが根拠になる。取り込みの段階で、正本を判定する規則を決める。

正本の判定の規則は、[表7](#table-7)による。

<a id="table-7"></a>表7−正本の判定の規則

| 状況 | 規則 | 例 |
| --- | --- | --- |
| 同じ内容の写しが複数ある。 | 内容のハッシュで重複を除き、正本だけを索引する。 | 各部署のフォルダにある就業規則の写しを除く。 |
| 旧版と現行版がある。 | 現行版だけを通常の検索の対象にする。旧版は、過去の時点を問う質問に限って検索する。 | “2024年度の規程では？”の質問に限って旧版を検索する。 |
| 下書きと承認済みがある。 | 承認済みだけを索引する。 | `draft_` の付くファイルを取り込まない。 |
| 文書の間で内容が矛盾する。 | 情報源の優先順を決め、回答では優先する根拠を示す。 | 規程、手順書、チャットの順に優先し、“規程では5営業日。Slackの案内では3営業日とあるが、規程を優先する”と答える。 |

### 3.3 文書の構造を保って解析する

PDF、Office文書、HTMLは、見出し、段落、表、リスト、コードの構造を保ったMarkdownなどの形式へ変換してから分割する。表の行と列が崩れた文章や、段組みの順序が入れ替わった文章は、検索でも生成でも正しく扱えない。

スキャンした文書や、図表に情報がある文書は、OCRとレイアウト解析を行うツールを使用する。図の内容を文章で説明できない場合は、ページの画像による検索を検討する。

### 3.4 構造に沿って分割する

チャンクは、見出し、段落、リスト、表、関数などの構造の境界で分割する。文字数だけで分割すると、文又は表の途中で切れる。

分割の目安は、[表8](#table-8)による。

<a id="table-8"></a>表8−分割の目安

| 項目 | 目安 |
| --- | --- |
| 大きさ | 数百トークン。質問一つに答えられる意味のまとまりにする。 |
| 重なり | 構造の境界で分割する場合は、重なりを小さくするか、なくす。文字数で分割する場合は、前後の文が欠けない程度の重なりを設ける。 |
| 表 | 表を一つのチャンクにし、見出しの行をチャンクごとに繰り返す。 |
| コード | 関数、クラスの単位で分割し、ファイルのパスとシンボル名をチャンクに含める。 |
| 見出し | チャンクの先頭に、文書名と見出しの階層を加える。 |

分割の方式は、評価セットで複数の大きさを比べて決める。

### 3.5 チャンクに文脈を付与する

チャンクは、文書から切り離すと、何についての記述かが分からなくなることがある。各チャンクの先頭に、文書の全体を参照してLLMが作成した50〜100トークン程度の説明（どの文書のどの部分か、何について述べているか）を加え、その文章で埋め込みと全文検索の索引の両方を作る。

文脈の付与の例は、[表9](#table-9)による。

<a id="table-9"></a>表9−文脈の付与の例

| 状態 | チャンクの例 |
| --- | --- |
| 付与の前 | 売上は前四半期から3%増加した。 |
| 付与の後 | この断片は、ACME社の2023年第2四半期の決算報告の一部である。前四半期の売上は3億1 400万ドルだった。売上は前四半期から3%増加した。 |

説明の作成では、同じ文書の全体を何度もLLMへ渡すため、プロンプトキャッシュを使用して費用を抑える。

### 3.6 メタデータを付ける

チャンクには、検索の絞り込み、根拠の提示、更新に使用するメタデータを付ける。

メタデータは、[表10](#table-10)による。

<a id="table-10"></a>表10−メタデータ

| メタデータ | 用途 | 例 |
| --- | --- | --- |
| 文書のIDとチャンクのID | 根拠の提示、更新、削除 | `doc-1042#17` |
| 文書名、見出し、URL又はパス | 根拠の提示 | `料金表 > Enterpriseプラン`、`https://docs.example.com/pricing` |
| 文書の種類、製品、版、言語 | 検索の絞り込み | `manual`、`enterprise`、`3.2`、`ja` |
| 更新日時と内容のハッシュ | 変更の検出、新しい版の優先 | `2026-10-01`、`sha256:9f2c…` |
| 文書の状態と適用の開始日 | 正本の判定 | `approved`、`2026-04-01` |
| 読める利用者とグループ、読めない利用者とグループ | 権限の絞り込み | `allowed_groups=["hr"]`、`denied_users=["a@example.com"]` |
| 担当者と次の見直しの日 | 文書の更新の依頼 | `hr-docs@example.com`、`2027-04-01` |
| 埋め込みのモデルと分割の方式の版 | 索引の作り直しの判断 | `voyage-3`、`chunker-v2` |

### 3.7 文書ごとに担当者と見直しの日を決める

文書の内容が古いと、検索が正しくても誤った回答になる。文書ごとに担当者と次の見直しの日を決め、期限を過ぎた文書を担当者へ通知する。担当者の異動又は退職で不在になった文書は、部署の管理者へ引き継ぐ。例えば、“出張旅費規程の見直しの日を30日過ぎている”と総務部の担当者へ通知する。

### 3.8 差分で更新する

文書の更新は、内容のハッシュで変更を検出し、変更された文書のチャンクだけを作り直す。削除された文書のチャンクは、索引から削除する。古い版のチャンクが残ると、新旧で矛盾した回答になる。

更新の周期は、情報源ごとに決める。元のシステムから削除を検知できない場合に備えて、索引と元のシステムの文書の一覧を定期的に突き合わせる。例えば、Onyxの既定では、新しい文書と更新を30分ごとに取り込み、元のシステムにない文書の削除を7日ごとに行う。

## 4 索引と検索

### 4.1 ハイブリッド検索を標準とする

検索は、ベクトル検索と全文検索を併用し、両方の候補をReciprocal Rank Fusion（RRF）などで統合する。ベクトル検索は言い換えに、全文検索は固有名詞、型番、エラーコード、識別子に強く、互いの検索漏れを補う。

質問ごとに効く検索は、[表11](#table-11)による。

<a id="table-11"></a>表11−質問ごとに効く検索

| 質問 | 効く検索 | 理由 |
| --- | --- | --- |
| “契約をやめたい場合の手続きは？” | ベクトル検索 | 文書の“解約”“退会”と語が一致しなくても、意味で見つかる。 |
| “`ERR_CONN_RESET` の対処は？” | 全文検索 | 識別子が完全に一致する文書を見つける。 |
| “型番 XR-2040 の保証期間は？” | 両方 | 型番の一致と、保証の意味の両方が要る。 |

日本語の文書の全文検索では、形態素解析又はn-gramで語を分割する設定を使用する。既定の設定では日本語の語を適切に区切れず、検索の精度が下がる。Elasticsearchではkuromoji、PostgreSQLではPGroonga又はpg_bigmが使用できる。

### 4.2 候補を多めに取り、リランキングで絞る

検索では、ハイブリッド検索で50〜150件程度の候補を取り、クロスエンコーダーなどのリランキングのモデルで並べ替えてから、上位をLLMへ渡す。リランキングのモデルは、候補ごとに質問と合わせて関連度を評価するため、埋め込みの類似度より精密に順位を付けられる。Anthropicの評価では、150件からリランキングで20件に絞って渡す構成を使用した。

渡すチャンクの数は、評価で決める。少なすぎると根拠が欠け、多すぎると関係のない文章が回答を乱す。Anthropicの評価では、20件を渡す方が5件又は10件より良い結果だった。

### 4.3 埋め込みのモデルは自分のデータで選ぶ

埋め込みのモデルは、公開されたベンチマーク（MTEB、日本語はJMTEB）で候補を絞り、自分の評価セットの検索の結果で選ぶ。ベンチマークの順位は、対象の分野、言語、文書の形式によって入れ替わる。

埋め込みのモデルの確認事項は、[表12](#table-12)による。

<a id="table-12"></a>表12−埋め込みのモデルの確認事項

| 観点 | 確認する事項 |
| --- | --- |
| 言語 | 対象の言語の評価で、上位の性能があるか。 |
| 分野 | 専門用語の多い文書で、評価セットの検索漏れが少ないか。 |
| 入力の長さ | チャンクの大きさを切り詰めずに扱えるか。 |
| 次元数 | 索引の大きさと検索の速さが要件に収まるか。次元を削減できるモデルもある。 |
| 提供の形 | APIで使用するか、自分で実行するか。 |

埋め込みのモデルを変更する場合は、全てのチャンクの埋め込みを作り直す。異なるモデルの埋め込みは比べられない。

### 4.4 絞り込みをメタデータで行う

製品、版、言語、文書の種類のように、質問から条件が決まる場合は、検索の前にメタデータで候補を絞り込む。意味の近さだけで検索すると、別の製品又は古い版の文書が上位に入る。例えば、“Enterpriseプランの3.2の上限は？”では、`product=enterprise`、`version=3.2` で絞ってから検索する。

### 4.5 質問の書き換えは評価で効果を確認してから使用する

質問の書き換えの手法は、[表13](#table-13)による。

<a id="table-13"></a>表13−質問の書き換えの手法

| 手法 | 内容 | 使用する場面 | 例 |
| --- | --- | --- | --- |
| 書き換え | 会話の文脈を補い、独立した検索語にする。 | 会話の途中の質問 | “それの料金は？”→“Enterpriseプランの料金” |
| 社内用語の展開 | 用語集で、略語又は社内の呼び名を文書の表記へ展開する。 | 部署又は製品に固有の用語が多い組織 | “SFA”→“営業支援システム”、“Aプロジェクト”→“基幹システムの刷新” |
| 分解 | 複数の問いを含む質問を、個別の検索に分ける。 | 比較又は複数の条件を含む質問 | “AとBのSLAの違いは？”→“AのSLA”“BのSLA” |
| 複数の言い換え | 言い換えた複数の検索語で検索し、結果を統合する。 | 表現の揺れが大きい分野 | “解約”“退会”“契約の終了” |
| 仮の回答による検索 | LLMが作った仮の回答で検索する。 | 効果が小さいことがあるため、評価で確認した場合に限る。 | 質問から回答の文章を作り、その文章で検索する。 |

書き換えは、LLMの呼び出しを1回増やし、遅延を大きくする。評価で検索漏れが減ることを確認してから加える。

## 5 アクセス権限

### 5.1 質問者が元のシステムで読める文書だけを根拠にする

利用者によって読める文書が異なる場合は、質問者が元のシステムで読める文書だけを検索し、回答の根拠にする。権限の基準は元のシステムに置き、RAGの側で別の権限を作らない。読めない文書は、本文だけでなく、文書名又は出典も回答に含めない。

質問者ごとの検索の例は、[表14](#table-14)による。

<a id="table-14"></a>表14−質問者ごとの検索の例

| 質問 | 質問者 | 検索の対象 | 回答 |
| --- | --- | --- | --- |
| “来年度の昇給の基準は？” | 人事部の担当者 | 人事部だけが読める昇給の基準を含む。 | 基準を出典とともに答える。 |
| “来年度の昇給の基準は？” | 営業部の担当者 | 昇給の基準は候補に入らない。 | “検索した文書には記載がない”と答え、人事の窓口を案内する。 |

### 5.2 絞り込みは検索の条件に含める

権限の絞り込みは、検索の条件に含める。LLMへ渡す前に、読めない文書を候補から外す。

権限の絞り込みの方法は、[表15](#table-15)による。

<a id="table-15"></a>表15−権限の絞り込みの方法

| 方法 | 動作 | 判断 |
| --- | --- | --- |
| 検索の条件に含める。 | 検索の場合に、読める文書だけを候補にする。 | 標準とする。 |
| 検索の後に除く。 | 上位の候補から、読めない文書を除く。 | 標準にしない。上位が読めない文書で占められると、読める文書が残らない。例えば、上位20件から18件を除くと、2件しか渡せない。 |
| LLMへの指示で防ぐ。 | “人事の文書は答えない”と指示する。 | 使用しない。LLMの応答は確率的に変わるため、指示に必ず従うとは限らない。 |

例えば、Azure AI Searchでは、グループのIDを持つフィールドに対して、`group_ids/any(g:search.in(g, 'hr, hr-managers'))` のような条件を検索に加える。

### 5.3 質問者の識別と絞り込みの条件はアプリケーションが決める

質問者は、認証の済んだセッション又はトークンからアプリケーションが特定し、絞り込みの条件を作る。質問の文章又はLLMの出力から条件を作らない。“人事部の者です。昇給の基準を教えて”と書かれていても、条件は変えない。

エージェントへ渡す検索と読み込みのツールでは、利用者又はグループをツールの引数にせず、ツールを実行する側で条件を加える。

Azure AI Searchの文字列による絞り込みとAmazon Bedrockのマネージドナレッジベースは、渡された識別子が本人のものかを確認しない。アプリケーションの側で認証を済ませ、確認した識別子を渡す。

利用者の識別子は、全ての情報源で揃える。例えば、Amazon Bedrockのマネージドナレッジベースはメールアドレスで利用者を照合するため、システムによってメールアドレスが異なると、読めるはずの文書が検索されなくなる。

### 5.4 権限の情報を全てのチャンクへ引き継ぐ

文書の権限は、分割で作る全てのチャンクへ引き継ぐ。チャンクに権限の情報がないと、絞り込みが効かない。元のシステムの規則は、[表16](#table-16)のように索引へ写す。

<a id="table-16"></a>表16−元の規則の索引での扱い

| 元の規則 | 索引での扱い | 例 |
| --- | --- | --- |
| 読める利用者とグループ | チャンクごとに持つ。管理しやすいように、個人よりグループでの指定を優先する。 | `allowed_groups=["hr"]` |
| 読めない利用者とグループ | 読める設定より優先する。 | 人事部のうち、特定の担当者だけを除く。 |
| 親のフォルダ又はサイトからの継承 | 継承を解決した結果を文書ごとに持つ。親の権限が変わったら、配下の文書を更新する。 | `/人事/評価/` の共有範囲を変更したら、配下の全ての文書を更新する。 |
| グループの入れ子 | 所属の判定で、親のグループまでたどる。 | `hr-managers` が `hr` に含まれる。 |

### 5.5 権限の変更を索引へ反映する

索引に複製した権限は、最後に同期した時点の情報である。変更の種類ごとに、反映の方法を決める。

権限の変更の反映の方法は、[表17](#table-17)による。

<a id="table-17"></a>表17−権限の変更の反映の方法

| 起きた事 | 反映の方法 |
| --- | --- |
| 文書の共有範囲の変更 | チャンクの権限の情報だけを更新する。埋め込みは作り直さない。 |
| 異動によるグループの変更 | 所属の情報を同期するか、質問の場合にID基盤から取得する。 |
| 退職 | 認証で質問を止める。メールアドレスを別の人へ割り当てる場合は、前の利用者の権限を引き継がないようにする。 |
| 文書の削除 | チャンクを索引から削除する。 |

同期の遅れをどこまで許容するかは、文書の種類ごとに決める。[表18](#table-18)は決め方の例である。

<a id="table-18"></a>表18−文書ごとの同期の遅れの例

| 文書 | 許容する遅れ | 方式 |
| --- | --- | --- |
| 全社の規程 | 1日 | 定期的な同期 |
| 部署の手順書 | 1時間 | 定期的な同期 |
| 人事の評価、経営会議の資料 | 許容しない | 定期的な同期に加え、回答の前に元のシステムへ確認する。 |

### 5.6 権限の方式を選ぶ

権限の方式は、[表19](#table-19)による。

<a id="table-19"></a>表19−権限の方式

| 方式 | 動作 | 長所 | 短所 | 実現手段 |
| --- | --- | --- | --- | --- |
| 権限を索引へ複製する。 | コネクターが権限を索引へ同期し、質問の場合に絞り込む。 | 検索が速い。 | 同期までの変更が反映されない。元の規則を正しく写す必要がある。 | Azure AI Searchの文字列による絞り込み、Amazon Bedrockのメタデータの絞り込み、Onyx |
| データベースの行の権限を使用する。 | PostgreSQLのRow Level Securityで、類似度の検索の結果を自動で絞る。 | 検索と権限の判定が一つの問い合わせで済む。 | PostgreSQLに限る。外部のシステムの権限は同期が要る。 | pgvectorとRow Level Security |
| 元のシステムへの確認を加える。 | 索引で候補を絞った後、回答の前に、元のシステムのAPIで今の権限を確認する。 | 同期の間の変更も反映される。 | APIの呼び出しの分だけ遅延が増える。 | Amazon Bedrockのマネージドナレッジベース、Amazon Quick |

元のシステムへの確認だけで全ての文書を判定すると、呼び出しの数が多すぎる。索引での絞り込みと組み合わせ、候補の文書に限って確認する。

### 5.7 判定に失敗した文書は返さない

権限の判定又は元のシステムへの確認に失敗した場合は、その文書を返さない。このとき、文書が存在しない場合と区別し、“権限の確認に失敗したため、一部の文書を検索できなかった”と答える。

## 6 回答の生成

### 6.1 根拠を識別できる形で渡す

LLMへ渡すチャンクには、文書のID、文書名、見出し、URL又はパスを付ける。回答には、根拠としたチャンクの出典を“Enterpriseプランの保証期間は3年である［料金表 > Enterpriseプラン］”のように付けさせる。Claudeは、検索結果を検索結果のブロックとして渡すと、出典の付いた引用を返す。OpenAIのファイル検索は、回答にファイルの引用の注釈を付ける。

### 6.2 根拠がない場合の答え方を決める

渡した文書に答えがない場合は、推測で答えずに、“検索した文書には2027年の料金の記載がない”のように、見つからなかったことを答えさせる。根拠のない質問を評価セットに含め、答えなかった割合を測る。問い合わせの窓口がある分野では、“在宅勤務の手当は規程に記載がないため、人事の窓口へ確認する”のように、次の行き先も示す。

### 6.3 渡す文脈を整える

文脈の整え方は、[表20](#table-20)による。

<a id="table-20"></a>表20−文脈の整え方

| 処理 | 内容 |
| --- | --- |
| 重複の除去 | 同じ内容のチャンクを一つにする。 |
| 隣接するチャンクの結合 | 同じ文書の連続するチャンクは、つなげて渡す。 |
| 並べ方 | 関連度の順、又は文書内の順に並べる。 |
| 変わらない部分のキャッシュ | システムの指示又は共通の文書はプロンプトの先頭に置き、プロンプトキャッシュを使用する。 |

## 7 エージェント型の検索

### 7.1 検索をエージェントのツールとして渡す

複数の段階を要する質問では、検索をツールとしてエージェントに渡し、エージェントに検索語の作成、検索、読み込みを繰り返させる。ツールは、MCPサーバー又は関数呼び出しとして提供する。例えば、“先月の障害の原因になった設定を、今のマニュアルはどう案内しているか”では、障害報告を検索して設定の名前を得てから、その名前でマニュアルを検索する。

検索のツールは、[表21](#table-21)による。

<a id="table-21"></a>表21−検索のツール

| ツール | 返す内容 |
| --- | --- |
| 検索 | チャンクのID、出典、短い抜粋、スコア。件数の上限を設ける。 |
| 読み込み | 指定したIDの文書の全体、又は前後の範囲。 |
| 一覧 | 文書の種類、製品、版などの絞り込みに使用できる値。 |

ツールの出力は短くし、続きを読むための手段（IDの指定、ページの指定）を用意する。

### 7.2 コードはファイルとシンボルの検索から始める

エージェントがコードを探す場合は、埋め込みの索引を作る前に、ファイル名の検索、文字列の検索、言語サーバーによるシンボルの検索を使用する。コードは識別子が一致するかで探せることが多く、索引の更新も要らない。埋め込みによる検索は、リポジトリが大きく文字列の検索だけでは候補が多すぎる場合や、自然言語の説明から探す場合に補助として加える。

### 7.3 検索の回数と費用に上限を設ける

エージェント型の検索は、検索と読み込みの回数に比例して費用と遅延が増える。一つの質問で行う検索の回数の上限（例：5回）を決め、上限に達した場合は、集めた範囲で回答させる。

## 8 グラフを使用する検索

### 8.1 全体の主題を問う質問に使用する

“文書全体で繰り返し出てくる課題は何か”のように、文書の集合全体を要約する質問は、上位のチャンクを集めるだけでは答えられない。このような質問が多い場合は、文書からエンティティと関係を抽出したグラフと、そのコミュニティごとの要約を使用する検索を加える。

グラフを使う検索の方式は、[表22](#table-22)による。

<a id="table-22"></a>表22−グラフを使う検索の方式

| 方式 | 特徴 |
| --- | --- |
| GraphRAG | エンティティと関係のグラフと、コミュニティごとの要約を事前に作る。全体の主題を問う質問に強いが、索引の作成にLLMの呼び出しが多く要る。 |
| LazyGraphRAG | 要約の作成を質問の時まで遅らせ、索引の作成の費用を通常のRAGと同程度に抑える。 |
| LightRAG | グラフと通常の検索を組み合わせ、索引の作成と更新の費用を抑える。 |

### 8.2 通常のRAGと比べてから採用する

グラフを使用する検索は、特定の事実を問う局所的な質問では、通常のRAGより精度が下がることがある。評価セットで通常のRAGと比べ、全体の主題を問う質問だけをグラフを使用する検索へ振り分ける。

### 8.3 要約に読める範囲の異なる文書を混ぜない

コミュニティ要約は、複数の文書から作る。読める範囲の異なる文書を混ぜると、質問者が読めない文書の内容が要約を通じて回答に現れる。グラフと要約を、全社向けと人事部向けのように読める範囲ごとに分ける。質問の場合に要約を作る方式では、権限で絞り込んだ文書だけから要約を作る。

### 9.1 評価セットを最初に作る

評価セットは、実際の質問から作り、[表23](#table-23)の項目を含める。数十件から始め、誤りが見つかるたびに追加する。

<a id="table-23"></a>表23−評価セットの項目

| 項目 | 内容 |
| --- | --- |
| 質問 | 実際の利用者の質問、又は想定する質問。 |
| 正解のチャンク | 回答に必要なチャンクのID。 |
| 参照の回答 | 正しい回答の要点。 |
| 種類 | 事実、手順、比較、複数の段階、文書にない質問の区別。 |

評価セットの例は、[表24](#table-24)による。

<a id="table-24"></a>表24−評価セットの例

| 質問 | 正解のチャンク | 参照の回答 | 種類 |
| --- | --- | --- | --- |
| XR-2040の保証期間は？ | `doc-1042#17` | 3年。 | 事実 |
| 請求先の住所を変える手順は？ | `doc-0311#4` | 管理画面の“請求情報”から変更し、翌月の請求から反映される。 | 手順 |

| 2027年の料金は？ | なし | 文書に記載がないと答える。 | 文書にない質問 |

### 9.2 検索と生成を分けて評価する

検索の誤りと生成の誤りは、対策が異なる。検索と生成を、別の指標で評価する。

評価の指標は、[表25](#table-25)による。

<a id="table-25"></a>表25−評価の指標

| 対象 | 指標 | 意味 |
| --- | --- | --- |
| 検索 | Recall@k | 正解のチャンクが上位k件に含まれる割合。 |
| 検索 | MRR、nDCG | 正解のチャンクが上位に並ぶ度合い。 |
| 検索 | コンテキスト適合率（Context precision） | 渡したチャンクのうち、関連するものの割合と順位。 |
| 検索 | コンテキスト再現率（Context recall） | 回答に必要な情報のうち、渡したチャンクに含まれる割合。 |
| 検索 | 正本以外の混入 | 渡したチャンクのうち、旧版又は下書きが占める割合。 |
| 検索 | 権限の外の混入 | 渡したチャンクに、質問者が読めない文書が含まれた件数。 |
| 生成 | 忠実性（Faithfulness） | 回答の主張が、渡したチャンクで裏付けられる割合。 |
| 生成 | 回答の関連性（Answer relevancy） | 回答が質問に答えている度合い。 |
| 生成 | 回答の正しさ | 参照の回答と一致する度合い。 |
| 生成 | 答えない割合 | 文書にない質問に、答えなかった割合。 |

### 9.3 権限を評価に含める

読める文書が異なる質問者を評価セットに含め、同じ質問を質問者ごとに評価する。権限の外の混入は、0件でなければ公開しない。読める文書の検索漏れも合わせて測る。識別子の不一致又は同期の失敗があると、読めるはずの文書が検索されなくなる。

権限の評価の例は、[表26](#table-26)による。

<a id="table-26"></a>表26−権限の評価の例

| 質問 | 質問者 | 期待する結果 |
| --- | --- | --- |
| 来年度の昇給の基準は？ | 人事部の担当者 | `doc-2210#5` を根拠に答える。 |
| 来年度の昇給の基準は？ | 営業部の担当者 | `doc-2210` のチャンクが候補に入らず、記載がないと答える。 |
| 来年度の昇給の基準は？ | 人事部から営業部へ異動した担当者 | 異動の同期の後は、`doc-2210` のチャンクが候補に入らない。 |
| 営業部の値引きの基準は？ | 営業部の担当者 | `doc-3307#2` を根拠に答える。 |

### 9.4 LLMによる採点は条件を固定して比べる

忠実性又は関連性をLLMで採点する場合は、採点のモデル、指示、埋め込みのモデルを固定して比べる。採点の条件が変わると、点数を比べられない。採点の結果の一部を人が確認し、人の判断と食い違う場合は採点の指示を直す。

### 9.5 変更のたびに評価を実行する

分割の方式、埋め込みのモデル、検索の設定、リランキング、プロンプトを変更するたびに、評価セットで評価し、結果を記録する。[表27](#table-27)は記録の形を示す例であり、数値は説明のための仮の値である。

<a id="table-27"></a>表27−評価の記録の例

| 変更 | Recall@20 | 忠実性 | 判断 |
| --- | --- | --- | --- |
| 基準（512トークンの固定の分割） | 82% | 0.88 | なし |
| 見出しに沿った分割 | 88% | 0.90 | 採用する。 |
| リランキングの追加 | 88% | 0.94 | 採用する。 |
| 質問の書き換えの追加 | 88% | 0.94 | 遅延が増えるだけのため採用しない。 |

## 10 運用

### 10.1 検索と回答の記録を残す

本番の質問ごとに、質問者、権限の絞り込みの条件、質問、書き換えた検索語、検索したチャンクのIDとスコア、渡したチャンク、回答、利用者の評価を記録する。誤った回答は、記録から検索と生成のどちらの誤りかを切り分け、評価セットへ追加する。正解のチャンクが渡した中になければ検索の誤り、渡した中にあるのに回答が誤っていれば生成の誤りである。

### 10.2 誤回答の報告を文書と検索の改善につなげる

回答の画面に、誤りを報告する手段を設ける。報告を定期的に原因ごとに分類し、担当者へ渡す。直した質問は評価セットへ追加する。

## 12 チェックリスト

- 文書の総量がコンテキストに収まる場合に、全体をプロンプトに入れる方式と比べた。
- 評価セットがあり、検索と生成を別の指標で評価している。
- 実際の質問に答えるのに必要な情報源から順に取り込んでいる。
- 写し、旧版、下書き、矛盾する文書の扱いを決め、正本を判定している。
- 文書ごとに担当者と見直しの日があり、期限を過ぎると担当者へ通知される。
- 文書を、見出し、表、リストの構造を保って解析し、構造の境界で分割している。
- チャンクに、出典、絞り込み、更新に使用するメタデータがある。
- 文書の変更と削除が、索引に反映される。
- 質問者が元のシステムで読める文書だけを、検索の条件で絞り込んでいる。
- 質問者の識別と絞り込みの条件をアプリケーションが決めており、質問の文章又はLLMの出力から作っていない。
- 全てのチャンクに権限の情報があり、読めない設定、継承、グループの入れ子を再現している。
- 権限の変更の反映までの遅れを文書の種類ごとに決め、遅れを許容しない文書は元のシステムへ確認している。
- 権限の判定に失敗した文書を返さない。
- 読める文書が異なる質問者を評価し、権限の外の混入が0件である。
- ベクトル検索と全文検索のハイブリッド検索を使用し、日本語の全文検索で語を分割する設定がある。
- 候補を多めに取り、リランキングで絞っている。
- 埋め込みのモデルを、自分の評価セットの結果で選んだ。
- 回答に出典が付き、文書にない質問には答えないことを確認した。
- 質問の書き換え、エージェント型の検索、グラフを使用する検索は、評価で効果を確認してから加えた。
- 質問ごとに、質問者、絞り込みの条件、検索したチャンク、渡したチャンク、回答を記録している。
- 誤回答の報告を原因ごとに分類し、文書又は検索の担当者へ渡している。
