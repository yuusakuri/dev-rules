# 検索システム構築ガイドライン

## 1 はじめに

### 1.1 目的

この文書の目的は、検索システムの設計者及び運用者が、文書を根拠に回答するシステムを、検索精度、アクセス権限及び費用を評価しながら設計可能にすることである。

### 1.2 適用範囲

この文書は、外部の文書を根拠にLLMが回答するシステム、及びAIエージェントが文書又はコードを検索する仕組みの設計及び運用について規定する。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| LLM（large language model、大規模言語モデル） | 大量の文章を学習し、文章の生成又は分析を行うモデル。 |
| MCP（Model Context Protocol） | AIアプリケーションと外部のツール又はデータを接続するための通信規約。 |
| RRF（reciprocal rank fusion） | 複数の検索結果を、それぞれの順位の逆数に基づいて統合する方法。 |
| エンティティ | 文書中で識別する人物、組織、製品又はその他の対象。 |
| Late Interaction | 質問及び文書を複数のベクトルとして表し、検索時にベクトル間の類似度を集約する照合方式。 |
| RAG（Retrieval-Augmented Generation） | 質問に関連する文書の断片を検索し、LLMへの入力に加えて回答を生成する方式。 |
| チャンク | 索引及び検索の単位として文書を分割した断片。 |
| 埋め込み | 文章の意味を表す数値のベクトル。意味の近さで検索するために使用する。 |
| ベクトル検索 | 埋め込みの類似度で検索する方式。言い換え又は表現の揺れに強い。 |
| 全文検索 | BM25などの、語の一致で検索する方式。固有名詞、型番及びエラーコードに強い。 |
| ハイブリッド検索 | ベクトル検索及び全文検索の結果を統合する方式。 |
| リランキング | 検索した候補を、質問との関連度を精密に評価するモデルで並べ替える処理。 |
| Contextual Retrieval | チャンクに、文書全体から見た位置付けの説明を加えてから索引する方式。 |
| エージェント型の検索 | エージェントが検索のツールを使用し、検索語の作成、検索及び読み込みを繰り返して必要な情報を集める方式。 |
| GraphRAG | 文書から抽出したエンティティ及び関係のグラフを使用して検索又は要約を行う方式。 |
| コネクター | 業務システムから文書及び権限の情報を取り込む部品。 |
| 正本 | 複数の版又は写しがある文書のうち、正しいものとして扱う文書。 |
| ACL（access control list、アクセス制御リスト） | 文書ごとに、読める利用者及びグループ、並びに読めない利用者及びグループを定めた一覧。 |

## 2 方式の選び方

### 2.1 検索が必要かを先に判断する

文書の総量がモデルのコンテキストに収まる場合は、検索を構築せず、文書の全体をプロンプトに入れる。文書の総量がおよそ20万トークン以下であれば、全体をプロンプトに入れ、プロンプトキャッシュで費用及び遅延を抑える方が、検索の誤りがなく単純である。

状況ごとの方式は、[表2](#table-2)による。

<a id="table-2"></a>表2−状況ごとの方式

| 状況 | 方式 | 例 |
| --- | --- | --- |
| 文書がコンテキストに収まり、更新が少ない。 | 全体をプロンプトに入れ、プロンプトキャッシュを使用する。 | 100ページの製品マニュアルについて答える。 |
| 文書がコンテキストに収まらない、又は頻繁に更新される。 | RAGを構築する。 | 社内規程及び手順書の1万件について答える。 |
| 対象がコードのリポジトリで、エージェントがコードを検索する。 | エージェント型の検索（ファイル名、文字列及びシンボルの検索）から開始する。 | `refreshToken` の呼出し元を検索する。 |
| 文書の集合全体の傾向又は主題を問う質問が多い。 | グラフを使用する検索を加える。 | “過去3年の障害報告で繰り返す原因は何か” |
| 利用者によって読める文書が異なる。 | 検索の条件に権限を含める。全体の投入は、読める文書が同じ利用者の間に限る。 | 部署ごとに共有範囲が異なる社内文書について答える。 |
| 図、表又は画面の画像に情報がある文書が多い。 | 文書の解析を強化するか、ページの画像で検索する方式を加える。 | 決算資料のグラフ、機器の配線図及びスライドから答える。 |

| ページの画像による検索 | ページの画像を埋め込み、Late Interactionで照合する。 | 図表、帳票又はスライドの多い文書 | 計算及び保存の量が大きい。 | 大量の文書では索引の大きさが問題になる。 |

## 3 文書の取り込み

### 3.1 質問に必要な情報源から順に集める

実際の質問を集め、その回答に必要な情報源から順にコネクターで接続する。取り込みの範囲を質問に対応させ、検索に必要な文書を優先する。

情報源は、[表6](#table-6)による。

<a id="table-6"></a>表6−情報源

| 情報源 | 例 | 取り込む内容 | 扱い方 |
| --- | --- | --- | --- |
| ファイル共有 | SharePoint<br>Google Drive<br>Box | 文書<br>版<br>共有の設定 | 正本のフォルダに限って取り込む。 |
| Wiki | Confluence<br>Notion | ページ<br>ページの階層<br>更新日時 | 階層を見出しとしてチャンクに加える。 |
| チャット | Slack<br>Microsoft Teams | スレッド | スレッドを一つの単位にする。結論が出たチャンネル又は期間に限る。 |
| チケット | Jira<br>ServiceNow<br>Zendesk | 問題<br>対応<br>解決の状態 | 解決済みのものを、問題と解決との組にする。 |
| 業務データ | Salesforce<br>会計システム | 取引先<br>案件<br>金額 | “今月の受注額は？”のような集計は、検索せず、SQL又はAPIをツールとして渡す。 |

### 3.2 正本を定める

正本の判定方法は、取り込みの段階で定義する。同じ内容の写し、旧版又は下書きを区別し、質問に対応する版を回答の根拠にする。

正本の判定の規則は、[表7](#table-7)による。

<a id="table-7"></a>表7−正本の判定の規則

| 状況 | 規則 | 例 |
| --- | --- | --- |
| 同じ内容の写しが複数ある。 | 内容のハッシュで重複を除き、正本だけを索引する。 | 各部署のフォルダにある就業規則の写しを除く。 |
| 旧版及び現行版がある。 | 現行版だけを通常の検索の対象にする。旧版は、過去の時点を問う質問に限って検索する。 | “2024年度の規程では？”の質問に限って旧版を検索する。 |
| 下書き及び承認済みがある。 | 承認済みだけを索引する。 | `draft_` の付くファイルを取り込まない。 |
| 文書の間で内容が矛盾する。 | 情報源の優先順を定め、回答では優先する根拠を示す。 | 規程、手順書及びチャットの順に優先し、“規程では5営業日。Slackの案内では3営業日とあるが、規程を優先する”と答える。 |

### 3.3 文書の構造を保って解析する

PDF、Office文書及びHTMLは、見出し、段落、表、リスト及びコードの構造を保った、Markdownなどの形式へ変換してから分割する。表の行及び列が崩れた文章、又は段組みの順序が入れ替わった文章は、検索でも生成でも正しく扱えない。

スキャンした文書、及び図表に情報がある文書は、OCR及びレイアウト解析を行うツールを使用する。図の内容を文章で説明できない場合は、ページの画像による検索を検討する。

### 3.4 構造に沿って分割する

チャンクは、見出し、段落、リスト、表、関数などの構造の境界で分割する。文字数だけで分割すると、文又は表の途中で切れる。

分割の目安は、[表8](#table-8)による。

<a id="table-8"></a>表8−分割の目安

| 項目 | 目安 |
| --- | --- |
| 大きさ | 数百トークン。質問一つに答えられる意味のまとまりにする。 |
| 重なり | 構造の境界で分割する場合は、重なりを小さくするか、なくす。文字数で分割する場合は、前後の文が欠けない程度の重なりを設ける。 |
| 表 | 表を一つのチャンクにし、見出しの行をチャンクごとに繰り返す。 |
| コード | 関数又はクラスの単位で分割し、ファイルのパス及びシンボル名をチャンクに含める。 |
| 見出し | チャンクの先頭に、文書名及び見出しの階層を加える。 |

分割の方式は、評価セットで複数の大きさを比較して決定する。

### 3.5 チャンクに文脈を付与する

チャンクの先頭に、文書全体における位置付けを示す50〜100トークン程度の説明を加え、その説明を含めて埋め込み及び全文検索の索引を作成する。断片だけでは対象を特定しにくい記述に、文書名又は記述対象の文脈を補うためである。説明は、文書全体を参照してLLMに生成させる。

文脈の付与の例は、[表9](#table-9)による。

<a id="table-9"></a>表9−文脈の付与の例

| 状態 | チャンクの例 |
| --- | --- |
| 付与の前 | 売上は前四半期から3%増加した。 |
| 付与の後 | この断片は、ACME社の2023年第2四半期の決算報告の一部である。前四半期の売上は3億1 400万ドルだった。売上は前四半期から3%増加した。 |

説明の作成では、同じ文書の全体を何度もLLMへ渡すため、プロンプトキャッシュを使用して費用を抑える。

### 3.6 メタデータを付ける

チャンクには、検索の絞り込み、根拠の提示及び更新に使用するメタデータを付ける。

メタデータは、[表10](#table-10)による。

<a id="table-10"></a>表10−メタデータ

| メタデータ | 用途 | 例 |
| --- | --- | --- |
| 文書のID及びチャンクのID | 根拠の提示<br>更新<br>削除 | `doc-1042#17` |
| 文書名、見出し、URL又はパス | 根拠の提示 | `料金表 > Enterpriseプラン`、`https://docs.example.com/pricing` |

### 3.7 文書ごとに担当者及び見直しの日を定める

文書の内容が古いと、検索が正しくても誤った回答になる。文書ごとに担当者及び次の見直しの日を定め、期限を過ぎた文書を担当者へ通知する。担当者の異動又は退職で不在になった文書は、部署の管理者へ引き継ぐ。例えば、“出張旅費規程の見直しの日を30日過ぎている”と総務部の担当者へ通知する。

### 3.8 差分で更新する

文書の更新は、内容のハッシュで変更を検出し、変更された文書のチャンクだけを作成し直す。削除された文書のチャンクは、索引から削除する。古い版のチャンクが残ると、新旧で矛盾した回答になる。

更新の周期は、情報源ごとに定める。元のシステムから削除を検知できない場合に備えて、索引と元のシステムの文書の一覧とを定期的に照合する。例えば、Onyxの既定では、新しい文書及び更新を30分ごとに取り込み、元のシステムにない文書の削除を7日ごとに行う。

## 4 索引及び検索

### 4.1 ハイブリッド検索を標準とする

検索は、ベクトル検索及び全文検索を併用し、両方の候補をRRFなどで統合する。ベクトル検索は言い換えに、全文検索は固有名詞、型番、エラーコード及び識別子に強く、互いの検索漏れを補う。

質問ごとに効く検索は、[表11](#table-11)による。

<a id="table-11"></a>表11−質問ごとに効く検索

| 質問 | 効く検索 | 理由 |
| --- | --- | --- |
| “契約をやめたい場合の手続きは？” | ベクトル検索 | 文書の“解約”“退会”と語が一致しなくても、意味で検出できる。 |
| “`ERR_CONN_RESET` の対処は？” | 全文検索 | 識別子が完全に一致する文書を検出する。 |
| “型番 XR-2040 の保証期間は？” | 両方 | 型番の一致及び保証の意味の両方が必要である。 |

日本語の文書の全文検索では、形態素解析又はn-gramで語を分割する設定を使用する。既定の設定では日本語の語を適切に区切れず、検索の精度が下がる。Elasticsearchではkuromoji、PostgreSQLではPGroonga又はpg_bigmが使用できる。

### 4.2 候補を多めに取り、リランキングで絞る

検索では、ハイブリッド検索で50〜150件程度の候補を取り、クロスエンコーダーなどのリランキングのモデルで並べ替えてから、上位をLLMへ渡す。リランキングのモデルは、候補ごとに質問と合わせて関連度を評価するため、埋め込みの類似度より精密に順位を付けられる。Anthropicの評価では、150件からリランキングで20件に絞って渡す構成を使用した。

渡すチャンクの数は、評価で決定する。少なすぎると根拠が欠け、多すぎると関係のない文章が回答を乱す。Anthropicの評価では、20件を渡す方が5件又は10件より良い結果だった。

### 4.3 埋め込みのモデルは自分のデータで選ぶ

埋め込みのモデルは、公開されたベンチマーク（MTEB、日本語はJMTEB）で候補を絞り、自分の評価セットの検索の結果で選ぶ。ベンチマークの順位は、対象の分野、言語及び文書の形式によって入れ替わる。

埋め込みのモデルの確認事項は、[表12](#table-12)による。

<a id="table-12"></a>表12−埋め込みのモデルの確認事項

| 観点 | 確認する事項 |
| --- | --- |
| 言語 | 対象の言語の評価で、上位の性能があるか。 |
| 分野 | 専門用語の多い文書で、評価セットの検索漏れが少ないか。 |
| 入力の長さ | チャンクの大きさを切り詰めずに扱えるか。 |
| 次元数 | 索引の大きさ及び検索の速さが要件に収まるか。次元を削減できるモデルもある。 |
| 提供の形 | APIで使用するか、自分で実行するか。 |

埋め込みのモデルを変更する場合は、全てのチャンクの埋め込みを作成し直す。異なるモデルの埋め込みは比較できない。

### 4.4 絞り込みをメタデータで行う

製品、版、言語、文書の種類のように、質問から条件が定まる場合は、検索の前にメタデータで候補を絞り込む。意味の近さだけで検索すると、別の製品又は古い版の文書が上位に入る。例えば、“Enterpriseプランの3.2の上限は？”では、`product=enterprise`、`version=3.2` で絞ってから検索する。

### 4.5 質問の書き換えは評価で効果を確認してから使用する

質問の書き換えは、評価で検索漏れの減少を確認してから採用する。LLMの呼出しが増えるため、精度の改善と遅延の増加とを比較する。手法は、[表13](#table-13)による。

<a id="table-13"></a>表13−質問の書き換えの手法

| 手法 | 内容 | 使用する場面 | 例 |
| --- | --- | --- | --- |
| 書き換え | 会話の文脈を補い、独立した検索語にする。 | 会話の途中の質問 | “それの料金は？”→“Enterpriseプランの料金” |
| 社内用語の展開 | 用語集で、略語又は社内の呼び名を文書の表記へ展開する。 | 部署又は製品に固有の用語が多い組織 | “SFA”→“営業支援システム”<br>“Aプロジェクト”→“基幹システムの刷新” |
| 分解 | 複数の問いを含む質問を、個別の検索に分ける。 | 比較又は複数の条件を含む質問 | “AとBのSLAの違いは？”→“AのSLA”“BのSLA” |
| 複数の言い換え | 言い換えた複数の検索語で検索し、結果を統合する。 | 表現の揺れが大きい分野 | “解約”“退会”“契約の終了” |
| 仮の回答による検索 | LLMが作成した仮の回答で検索する。 | 効果が小さいことがあるため、評価で確認した場合に限る。 | 質問から回答の文章を作成し、その文章で検索する。 |

## 5 アクセス権限

### 5.1 質問者が元のシステムで読める文書だけを根拠にする

利用者によって読める文書が異なる場合は、質問者が元のシステムで読める文書だけを検索し、回答の根拠にする。権限の基準は元のシステムに置き、RAGの側で別の権限を作成しない。読めない文書は、本文だけでなく、文書名又は出典も回答に含めない。

質問者ごとの検索の例は、[表14](#table-14)による。

<a id="table-14"></a>表14−質問者ごとの検索の例

| 質問 | 質問者 | 検索の対象 | 回答 |
| --- | --- | --- | --- |
| “来年度の昇給の基準は？” | 人事部の担当者 | 人事部だけが読める昇給の基準を含む。 | 基準を出典とともに答える。 |
| “来年度の昇給の基準は？” | 営業部の担当者 | 昇給の基準は候補に入らない。 | “検索した文書には記載がない”と答え、人事の窓口を案内する。 |

### 5.2 絞り込みは検索の条件に含める

権限の絞り込みは、検索の条件に含める。LLMへ渡す前に、読めない文書を候補から外す。

権限の絞り込みの方法は、[表15](#table-15)による。

<a id="table-15"></a>表15−権限の絞り込みの方法

| 方法 | 動作 | 判断 |
| --- | --- | --- |
| 検索の条件に含める。 | 検索時に、読める文書だけを候補にする。 | 標準とする。 |
| 検索の後に除く。 | 上位の候補から、読めない文書を除く。 | 標準にしない。上位が読めない文書で占められると、読める文書が残らない。例えば、上位20件から18件を除くと、2件しか渡せない。 |
| LLMへの指示で防ぐ。 | “人事の文書は答えない”と指示する。 | 使用しない。LLMの応答は確率的に変化するため、指示に必ず従うとは限らない。 |

例えば、Azure AI Searchでは、グループのIDを持つフィールドに対して、`group_ids/any(g:search.in(g, 'hr, hr-managers'))` のような条件を検索に加える。

### 5.3 質問者の識別及び絞り込みの条件はアプリケーションが決定する

質問者は、認証の済んだセッション又はトークンからアプリケーションが特定し、絞り込みの条件を作成する。質問の文章又はLLMの出力から条件を作成しない。“人事部の者です。昇給の基準を教えて”と書かれていても、条件は変更しない。

エージェントへ渡す検索及び読み込みのツールでは、利用者又はグループをツールの引数にせず、ツールを実行する側で条件を加える。

Azure AI Searchの文字列による絞り込み及びAmazon Bedrockのマネージドナレッジベースは、渡された識別子が本人のものかを確認しない。アプリケーションの側で認証を済ませ、確認した識別子を渡す。

利用者の識別子は、全ての情報源でそろえる。例えば、Amazon Bedrockのマネージドナレッジベースはメールアドレスで利用者を照合するため、システムによってメールアドレスが異なると、読めるはずの文書が検索されなくなる。

### 5.4 権限の情報を全てのチャンクへ引き継ぐ

文書の権限は、分割で作成する全てのチャンクへ引き継ぐ。チャンクに権限の情報がないと、絞り込みが機能しない。元のシステムの規則は、[表16](#table-16)のように索引へ写す。

<a id="table-16"></a>表16−元の規則の索引での扱い

| 元の規則 | 索引での扱い | 例 |
| --- | --- | --- |
| 読める利用者及びグループ | チャンクごとに持つ。管理しやすいように、個人よりグループでの指定を優先する。 | `allowed_groups=["hr"]` |
| 読めない利用者及びグループ | 読める設定より優先する。 | 人事部のうち、特定の担当者だけを除く。 |
| 親のフォルダ又はサイトからの継承 | 継承を解決した結果を文書ごとに持つ。親の権限が変更された場合は、配下の文書を更新する。 | `/人事/評価/` の共有範囲を変更したら、配下の全ての文書を更新する。 |
| グループの入れ子 | 所属の判定で、親のグループまでたどる。 | `hr-managers` が `hr` に含まれる。 |

### 5.5 権限の変更を索引へ反映する

索引に複製した権限は、最後に同期した時点の情報である。変更の種類ごとに、反映の方法を定める。

権限の変更の反映の方法は、[表17](#table-17)による。

<a id="table-17"></a>表17−権限の変更の反映の方法

| 発生した事象 | 反映の方法 |
| --- | --- |
| 文書の共有範囲の変更 | チャンクの権限の情報だけを更新する。埋め込みは作成し直さない。 |
| 異動によるグループの変更 | 所属の情報を同期するか、質問時にID基盤から取得する。 |
| 退職 | 認証で質問を拒否する。メールアドレスを別の人へ割り当てる場合は、前の利用者の権限を引き継がないようにする。 |
| 文書の削除 | チャンクを索引から削除する。 |

同期の遅れをどこまで許容するかは、文書の種類ごとに定める。[表18](#table-18)は、決定方法の例である。

<a id="table-18"></a>表18−文書ごとの同期の遅れの例

| --- | --- | --- |
| 全社の規程 | 1日 | 定期的な同期 |
| 部署の手順書 | 1時間 | 定期的な同期 |
| 人事の評価<br>経営会議の資料 | 許容しない | 定期的な同期に加え、回答の前に元のシステムへ確認する。 |

### 5.6 権限の方式を選ぶ

権限の方式は、[表19](#table-19)による。

<a id="table-19"></a>表19−権限の方式

| 方式 | 動作 | 長所 | 短所 | 実現手段 |
| --- | --- | --- | --- | --- |
| 権限を索引へ複製する。 | コネクターが権限を索引へ同期し、質問時に絞り込む。 | 検索が速い。 | 同期までの変更が反映されない。元の規則を正しく写す必要がある。 | Azure AI Searchの文字列による絞り込み<br>Amazon Bedrockのメタデータの絞り込み<br>Onyx |

### 5.7 判定に失敗した文書は返さない

権限の判定又は元のシステムへの確認に失敗した場合は、その文書を返さない。このとき、文書が存在しない場合と区別し、“権限の確認に失敗したため、一部の文書を検索できなかった”と答える。

## 6 回答の生成

### 6.1 根拠を識別できる形で渡す

LLMへ渡すチャンクには、文書のID、文書名、見出し、URL又はパスを付ける。回答には、根拠としたチャンクの出典を“Enterpriseプランの保証期間は3年である［料金表 > Enterpriseプラン］”のように付けさせる。Claudeは、検索結果を検索結果のブロックとして渡すと、出典の付いた引用を返す。OpenAIのファイル検索は、回答にファイルの引用の注釈を付ける。

### 6.2 根拠がない場合の答え方を定める

渡した文書に答えがない場合は、推測で答えずに、“検索した文書には2027年の料金の記載がない”のように、記載がなかったことを答えさせる。根拠のない質問を評価セットに含め、答えなかった割合を測る。問い合わせの窓口がある分野では、“在宅勤務の手当は規程に記載がないため、人事の窓口へ確認する”のように、次の行き先も示す。

### 6.3 渡す文脈を整える

文脈の整え方は、[表20](#table-20)による。

<a id="table-20"></a>表20−文脈の整え方

| 処理 | 内容 |
| --- | --- |

## 7 エージェント型の検索

### 7.1 検索をエージェントのツールとして渡す

複数の段階を要する質問では、検索をツールとしてエージェントに渡し、エージェントに検索語の作成、検索及び読み込みを繰り返させる。ツールは、MCPサーバー又は関数呼び出しとして提供する。例えば、“先月の障害の原因になった設定を、今のマニュアルはどう案内しているか”では、障害報告を検索して設定の名前を得てから、その名前でマニュアルを検索する。

検索のツールは、[表21](#table-21)による。

<a id="table-21"></a>表21−検索のツール

| ツール | 返す内容 |
| --- | --- |
| 検索 | チャンクのID、出典、短い抜粋、スコア。件数の上限を設ける。 |
| 読み込み | 指定したIDの文書の全体、又は前後の範囲。 |
| 一覧 | 文書の種類、製品、版などの絞り込みに使用できる値。 |

ツールの出力は短くし、続きを読むための手段（IDの指定、ページの指定）を用意する。

### 7.2 コードはファイル及びシンボルの検索から開始する

エージェントがコードを検索する場合は、埋め込みの索引を作成する前に、ファイル名の検索、文字列の検索及び言語サーバーによるシンボルの検索を使用する。コードは識別子の一致で検索できることが多く、索引の更新も不要である。埋め込みによる検索は、リポジトリが大きく文字列の検索だけでは候補が多すぎる場合、又は自然言語の説明から検索する場合に、補助として加える。

### 7.3 検索の回数及び費用に上限を設ける

エージェント型の検索は、検索及び読み込みの回数に比例して費用及び遅延が増える。一つの質問で行う検索の回数の上限（例：5回）を定め、上限に達した場合は、集めた範囲で回答させる。

## 8 グラフを使用する検索

### 8.1 全体の主題を問う質問に使用する

“文書全体で繰り返し出てくる課題は何か”のように、文書の集合全体を要約する質問は、上位のチャンクを集めるだけでは答えられない。このような質問が多い場合は、文書からエンティティ及び関係を抽出したグラフ並びにコミュニティごとの要約を使用する検索を加える。

グラフを使用する検索の方式は、[表22](#table-22)による。

<a id="table-22"></a>表22−グラフを使用する検索の方式

| 方式 | 特徴 |
| --- | --- |
| GraphRAG | エンティティ及び関係のグラフ並びにコミュニティごとの要約を事前に作成する。全体の主題を問う質問に強いが、索引の作成にLLMの呼出しが多く必要である。 |
| LazyGraphRAG | 要約の作成を質問の時まで遅らせ、索引の作成の費用を通常のRAGと同程度に抑える。 |
| LightRAG | グラフ及び通常の検索を組み合わせ、索引の作成及び更新の費用を抑える。 |

### 8.2 通常のRAGと比較してから採用する

グラフを使用する検索は、特定の事実を問う局所的な質問では、通常のRAGより精度が下がることがある。評価セットで通常のRAGと比較し、全体の主題を問う質問だけをグラフを使用する検索へ振り分ける。

### 8.3 要約に読める範囲の異なる文書を混ぜない

コミュニティ要約は、複数の文書から作成する。読める範囲の異なる文書を混ぜると、質問者が読めない文書の内容が要約を通じて回答に現れる。グラフ及び要約を、全社向けと人事部向けとのように読める範囲ごとに分ける。質問時に要約を作成する方式では、権限で絞り込んだ文書だけから要約を作成する。

### 9.1 評価セットを最初に作成する

評価セットは、実際の質問から作成し、[表23](#table-23)の項目を含める。数十件から開始し、誤りを検出するたびに追加する。

<a id="table-23"></a>表23−評価セットの項目

| 項目 | 内容 |
| --- | --- |
| 質問 | 実際の利用者の質問、又は想定する質問。 |
| 正解のチャンク | 回答に必要なチャンクのID。 |
| 参照の回答 | 正しい回答の要点。 |
| 種類 | 事実、手順、比較、複数の段階、文書にない質問の区別。 |

評価セットの例は、[表24](#table-24)による。

<a id="table-24"></a>表24−評価セットの例

| 質問 | 正解のチャンク | 参照の回答 | 種類 |
| --- | --- | --- | --- |
| XR-2040の保証期間は？ | `doc-1042#17` | 3年。 | 事実 |
| 請求先の住所を変更する手順は？ | `doc-0311#4` | 管理画面の“請求情報”から変更し、翌月の請求から反映される。 | 手順 |

### 9.2 検索及び生成を分けて評価する

検索の誤りと生成の誤りとは、対策が異なる。検索及び生成を、別の指標で評価する。

評価の指標は、[表25](#table-25)による。

<a id="table-25"></a>表25−評価の指標

| 対象 | 指標 | 意味 |
| --- | --- | --- |
| 検索 | Recall@k | 正解のチャンクが上位k件に含まれる割合。 |
| 検索 | MRR<br>nDCG | 正解のチャンクが上位に並ぶ度合い。 |
| 検索 | コンテキスト適合率（Context precision） | 渡したチャンクのうち、関連するものの割合及び順位。 |
| 検索 | コンテキスト再現率（Context recall） | 回答に必要な情報のうち、渡したチャンクに含まれる割合。 |
| 検索 | 正本以外の混入 | 渡したチャンクのうち、旧版又は下書きが占める割合。 |
| 検索 | 権限の外の混入 | 渡したチャンクに、質問者が読めない文書が含まれた件数。 |
| 生成 | 忠実性（Faithfulness） | 回答の主張が、渡したチャンクで裏付けられる割合。 |
| 生成 | 回答の関連性（Answer relevancy） | 回答が質問に答えている度合い。 |
| 生成 | 回答の正しさ | 参照の回答と一致する度合い。 |
| 生成 | 答えない割合 | 文書にない質問に、答えなかった割合。 |

### 9.3 権限を評価に含める

読める文書が異なる質問者を評価セットに含め、同じ質問を質問者ごとに評価する。権限の外の混入は、0件でなければ公開しない。読める文書の検索漏れも合わせて測る。識別子の不一致又は同期の失敗があると、読めるはずの文書が検索されなくなる。

権限の評価の例は、[表26](#table-26)による。

<a id="table-26"></a>表26−権限の評価の例

| 質問 | 質問者 | 期待する結果 |
| --- | --- | --- |
| 来年度の昇給の基準は？ | 人事部の担当者 | `doc-2210#5` を根拠に答える。 |
| 来年度の昇給の基準は？ | 営業部の担当者 | `doc-2210` のチャンクが候補に入らず、記載がないと答える。 |

| 営業部の値引きの基準は？ | 営業部の担当者 | `doc-3307#2` を根拠に答える。 |

### 9.4 LLMによる採点は条件を固定して比較する

忠実性又は関連性をLLMで採点する場合は、採点のモデル、指示及び埋め込みのモデルを固定して比較する。採点の条件が変化すると、点数を比較できない。採点の結果の一部を人が確認し、人の判断と異なる場合は採点の指示を修正する。

### 9.5 変更のたびに評価を実行する

<a id="table-27"></a>表27−評価の記録の例

## 10 運用

### 10.1 検索及び回答の記録を残す

本番の質問ごとに、質問者、権限の絞り込みの条件、質問、書き換えた検索語、検索したチャンクのID及びスコア、渡したチャンク、回答並びに利用者の評価を記録する。誤った回答は、記録から検索と生成のどちらの誤りかを切り分け、評価セットへ追加する。正解のチャンクが渡した中になければ検索の誤り、渡した中にあるのに回答が誤っていれば生成の誤りである。

### 10.2 誤回答の報告を文書及び検索の改善につなげる

回答の画面に、誤りを報告する手段を設ける。報告を定期的に原因ごとに分類し、担当者へ渡す。修正した質問は、評価セットへ追加する。

誤回答の原因の分類は、[表28](#table-28)による。

<a id="table-28"></a>表28−誤回答の原因の分類

| 原因 | 判別方法 | 修正する内容 | 担当 |
| --- | --- | --- | --- |
| 文書に記載がない。 | 正解となる文書がどこにもない。 | 文書を作成する。 | 業務を所管する部署 |
| 文書が古い。 | 根拠の文書の内容が、現在の運用と異なる。 | 文書を修正する。 | 文書の担当者 |
| 正本ではない文書を使用した。 | 旧版又は写しが根拠になっている。 | 正本の規則又は文書の状態を修正する。 | RAGの担当者<br>文書の担当者 |
| 文書を検索できない。 | 文書はあるが、渡したチャンクに入っていない。 | 分割、検索の設定又は用語集を修正する。 | RAGの担当者 |

### 10.4 索引の版を管理する

分割の方式又は埋め込みのモデルを変更する場合は、新しい版の索引を別に作成し、評価で比較してから切り替える。切り替えの後も、問題が出た場合に戻せるように、前の版の索引を一定期間残す。

## 12 チェックリスト

- 文書の総量がコンテキストに収まる場合に、全体をプロンプトに入れる方式と比較した。
- 評価セットがあり、検索及び生成を別の指標で評価している。
- 実際の質問に答えるのに必要な情報源から順に取り込んでいる。
- 写し、旧版、下書き及び矛盾する文書の扱いを定め、正本を判定している。
- 文書ごとに担当者及び見直しの日があり、期限を過ぎると担当者へ通知される。
- 文書を、見出し、表及びリストの構造を保って解析し、構造の境界で分割している。
- チャンクに、出典、絞り込み及び更新に使用するメタデータがある。
- 文書の変更及び削除が、索引に反映される。
- 質問者が元のシステムで読める文書だけを、検索の条件で絞り込んでいる。
- 質問者の識別及び絞り込みの条件をアプリケーションが決定しており、質問の文章又はLLMの出力から作成していない。
- 全てのチャンクに権限の情報があり、読めない設定、継承及びグループの入れ子を再現している。
- 権限の変更の反映までの遅れを文書の種類ごとに定め、遅れを許容しない文書は元のシステムへ確認している。
- 権限の判定に失敗した文書を返さない。
- 読める文書が異なる質問者を評価し、権限の外の混入が0件である。
- ベクトル検索及び全文検索のハイブリッド検索を使用し、日本語の全文検索で語を分割する設定がある。
- 候補を多めに取り、リランキングで絞っている。
- 埋め込みのモデルを、自分の評価セットの結果で選んだ。
- 回答に出典が付き、文書にない質問には答えないことを確認した。
- 質問の書き換え、エージェント型の検索及びグラフを使用する検索は、評価で効果を確認してから加えた。
- 質問ごとに、質問者、絞り込みの条件、検索したチャンク、渡したチャンク及び回答を記録している。
- 誤回答の報告を原因ごとに分類し、文書又は検索の担当者へ渡している。
