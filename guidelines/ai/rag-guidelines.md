## 1 はじめに

### 1.1 目的

本書の目的は、LLMが外部の文書を根拠に回答するRAG（Retrieval-Augmented Generation）を、検索の精度、回答の根拠、費用を一貫した基準で設計し、改善できるようにすることである。

### 1.2 適用範囲

本書は、社内文書、製品の文書、コード、問い合わせの履歴などを根拠にLLMが回答するシステムと、AIエージェントが文書やコードを検索する仕組みの、取り込み、索引、検索、生成、評価、運用を規定する。

### 1.3 用語及び定義

| 用語 | 定義 |
| --- | --- |
| RAG | 質問に関連する文書の断片を検索し、LLMへの入力に加えて回答を生成する方式。 |
| チャンク | 索引と検索の単位として文書を分割した断片。 |
| 埋め込み | 文章の意味を表す数値のベクトル。意味の近さで検索するために使う。 |
| 密な検索 | 埋め込みの類似度で検索する方式。言い換えや表現の揺れに強い。 |
| 語彙の検索 | BM25などの、語の一致で検索する方式。固有名詞、型番、エラーコードに強い。 |
| ハイブリッド検索 | 密な検索と語彙の検索の結果を統合する方式。 |
| 再順位付け | 検索した候補を、質問との関連度を精密に評価するモデルで並べ替える処理。 |
| 文脈付きの検索 | チャンクに、文書全体から見た位置付けの説明を加えてから索引する方式。 |
| エージェント型の検索 | エージェントが検索の道具を使い、検索語の作成、検索、読み込みを繰り返して必要な情報を集める方式。 |
| GraphRAG | 文書から抽出した実体と関係のグラフを使って検索や要約を行う方式。 |

## 2. 方式の選び方

### 検索が必要かを先に判断する

文書の総量がモデルのコンテキストに収まる場合は、検索を作らず、文書の全体をプロンプトに入れる。文書の総量がおよそ20万トークン以下であれば、全体をプロンプトに入れ、プロンプトキャッシュで費用と遅延を抑える方が、検索の誤りがなく単純である。

| 状況 | 方式 | 例 |
| --- | --- | --- |
| 文書がコンテキストに収まり、更新が少ない。 | 全体をプロンプトに入れ、プロンプトキャッシュを使う。 | 100ページの製品マニュアルについて答える。 |
| 文書がコンテキストに収まらない、または頻繁に更新される。 | RAGを構築する。 | 社内規程と手順書の1万件について答える。 |
| 対象がコードのリポジトリで、エージェントがコードを探す。 | エージェント型の検索（ファイル名、文字列、シンボルの検索）から始める。 | `refreshToken` の呼び出し元を探す。 |
| 文書の集合全体の傾向や主題を問う質問が多い。 | グラフを使う検索を加える。 | 「過去3年の障害報告で繰り返す原因は何か」 |
| 図、表、画面の画像に情報がある文書が多い。 | 文書の解析を強化するか、ページの画像で検索する方式を加える。 | 決算資料のグラフ、機器の配線図、スライドから答える。 |

### 方式の特徴を比べて選ぶ

| 方式 | 仕組み | 向く質問 | 費用 | 注意点 |
| --- | --- | --- | --- | --- |
| 全体の投入 | 文書の全体をプロンプトに入れる。 | 全ての質問 | 文書の量に比例する。キャッシュで下げられる。 | コンテキストに収まる量に限られる。 |
| 密な検索だけのRAG | 埋め込みの類似度で上位のチャンクを渡す。 | 言い換えを含む質問 | 低い | 固有名詞、型番、コードの一致に弱い。 |
| ハイブリッド検索と再順位付け | 密な検索と語彙の検索の候補を統合し、再順位付けする。 | 多くの質問 | 中程度 | 標準の構成とする。 |
| エージェント型の検索 | エージェントが検索と読み込みを繰り返す。 | 複数の段階を要する質問、コード | 推論の回数に比例して高い。 | 遅延が大きい。索引がなくても動く。 |
| グラフを使う検索 | 実体と関係のグラフ、集団の要約を使う。 | 文書全体の主題、関係をたどる質問 | 索引の作成が高い方式がある。 | 局所的な質問では通常のRAGに劣ることがある。 |
| ページの画像による検索 | ページの画像を埋め込み、遅延相互作用で照合する。 | 図表、帳票、スライドの多い文書 | 計算と保存の量が大きい。 | 大量の文書では索引の大きさが問題になる。 |

### 改善は評価で確かめながら順に積み上げる

RAGは、次の順で改善する。前の段階で評価の結果が改善しなくなってから、次の段階へ進む。

| 順 | 改善 | 主な効果 |
| --- | --- | --- |
| 1 | 評価セットを作る。 | 以後の変更の効果を測れるようにする。 |
| 2 | 文書の解析と分割を直す。 | 表、見出し、リストの崩れによる検索漏れを防ぐ。 |
| 3 | ハイブリッド検索にする。 | 固有名詞、型番、コードの検索漏れを防ぐ。 |
| 4 | 再順位付けを加える。 | 上位に渡すチャンクの関連度を上げる。 |
| 5 | チャンクに文脈を付与する。 | 文書から切り離したチャンクの意味の欠落を補う。 |
| 6 | 質問の書き換えや分解を加える。 | 曖昧な質問や複合した質問に対応する。 |
| 7 | エージェント型の検索、グラフを使う検索を加える。 | 複数の段階を要する質問、全体の主題を問う質問に対応する。 |

効果の大きさの例として、Anthropicの評価では、上位20件に正解が含まれない割合が次のように下がった。数値は対象のデータによって変わるため、自分の評価セットで確かめる。

| 構成 | 上位20件の検索の失敗率 |
| --- | --- |
| 基準 | 5.7% |
| 文脈付きの埋め込み | 3.7% |
| 文脈付きの埋め込みとBM25 | 2.9% |
| さらに再順位付け | 1.9% |

## 3. 文書の取り込み

### 文書の構造を保って解析する

PDF、Office文書、HTMLは、見出し、段落、表、リスト、コードの構造を保ったMarkdownなどの形式へ変換してから分割する。表の行と列が崩れた文章や、段組みの順序が入れ替わった文章は、検索でも生成でも正しく扱えない。

スキャンした文書や、図表に情報がある文書は、OCRとレイアウト解析を行う道具を使う。図の内容を文章で説明できない場合は、ページの画像による検索を検討する。

### 構造に沿って分割する

チャンクは、見出し、段落、リスト、表、関数などの構造の境界で分割する。文字数だけで分割すると、文や表の途中で切れる。

| 項目 | 目安 |
| --- | --- |
| 大きさ | 数百トークン。質問1つに答えられる意味のまとまりにする。 |
| 重なり | 構造の境界で分割する場合は、重なりを小さくするか、なくす。文字数で分割する場合は、前後の文が欠けない程度の重なりを設ける。 |
| 表 | 表を1つのチャンクにし、見出しの行をチャンクごとに繰り返す。 |
| コード | 関数、クラスの単位で分割し、ファイルのパスとシンボル名をチャンクに含める。 |
| 見出し | チャンクの先頭に、文書名と見出しの階層を加える。 |

分割の方式は、評価セットで複数の大きさを比べて決める。

### チャンクに文脈を付与する

チャンクは、文書から切り離すと、何についての記述かが分からなくなることがある。各チャンクの先頭に、文書の全体を参照してLLMが作成した50〜100トークン程度の説明（どの文書のどの部分か、何について述べているか）を加え、その文章で埋め込みと語彙の索引の両方を作る。

| 状態 | チャンクの例 |
| --- | --- |
| 付与の前 | 売上は前四半期から3%増加した。 |
| 付与の後 | この断片は、ACME社の2023年第2四半期の決算報告の一部である。前四半期の売上は3億1,400万ドルだった。売上は前四半期から3%増加した。 |

説明の作成では、同じ文書の全体を何度もLLMへ渡すため、プロンプトキャッシュを使って費用を抑える。

### メタデータを付ける

チャンクには、検索の絞り込み、根拠の提示、更新に使うメタデータを付ける。

| メタデータ | 用途 | 例 |
| --- | --- | --- |
| 文書のIDとチャンクのID | 根拠の提示、更新、削除 | `doc-1042#17` |
| 文書名、見出し、URLまたはパス | 根拠の提示 | `料金表 > Enterpriseプラン`、`https://docs.example.com/pricing` |
| 文書の種類、製品、版、言語 | 検索の絞り込み | `manual`、`enterprise`、`3.2`、`ja` |
| 更新日時と内容のハッシュ | 変更の検出、新しい版の優先 | `2026-10-01`、`sha256:9f2c…` |
| 埋め込みのモデルと分割の方式の版 | 索引の作り直しの判断 | `voyage-3`、`chunker-v2` |

### 差分で更新する

文書の更新は、内容のハッシュで変更を検出し、変更された文書のチャンクだけを作り直す。削除された文書のチャンクは、索引から削除する。古い版のチャンクが残ると、新旧で矛盾した回答になる。

## 4. 索引と検索

### ハイブリッド検索を標準とする

検索は、密な検索と語彙の検索を併用し、両方の候補をReciprocal Rank Fusion（RRF）などで統合する。密な検索は言い換えに、語彙の検索は固有名詞、型番、エラーコード、識別子に強く、互いの検索漏れを補う。

| 質問 | 効く検索 | 理由 |
| --- | --- | --- |
| 「契約をやめたい時の手続きは？」 | 密な検索 | 文書の「解約」「退会」と語が一致しなくても、意味で見つかる。 |
| 「`ERR_CONN_RESET` の対処は？」 | 語彙の検索 | 識別子が完全に一致する文書を見つける。 |
| 「型番 XR-2040 の保証期間は？」 | 両方 | 型番の一致と、保証の意味の両方が要る。 |

日本語の文書の語彙の検索では、形態素解析またはn-gramで語を分割する設定を使う。既定の設定では日本語の語を適切に区切れず、検索の精度が下がる。Elasticsearchではkuromoji、PostgreSQLではPGroongaやpg_bigmが使える。

### 候補を多めに取り、再順位付けで絞る

検索では、ハイブリッド検索で50〜150件程度の候補を取り、クロスエンコーダーなどの再順位付けのモデルで並べ替えてから、上位をLLMへ渡す。再順位付けのモデルは、候補ごとに質問と合わせて関連度を評価するため、埋め込みの類似度より精密に順位を付けられる。Anthropicの評価では、150件から再順位付けで20件に絞って渡す構成を使った。

渡すチャンクの数は、評価で決める。少なすぎると根拠が欠け、多すぎると関係のない文章が回答を乱す。Anthropicの評価では、20件を渡す方が5件や10件より良い結果だった。

### 埋め込みのモデルは自分のデータで選ぶ

埋め込みのモデルは、公開されたベンチマーク（MTEB、日本語はJMTEB）で候補を絞り、自分の評価セットの検索の結果で選ぶ。ベンチマークの順位は、対象の分野、言語、文書の形式によって入れ替わる。

| 観点 | 確かめる事項 |
| --- | --- |
| 言語 | 対象の言語の評価で、上位の性能があるか。 |
| 分野 | 専門用語の多い文書で、評価セットの検索漏れが少ないか。 |
| 入力の長さ | チャンクの大きさを切り詰めずに扱えるか。 |
| 次元数 | 索引の大きさと検索の速さが要件に収まるか。次元を削減できるモデルもある。 |
| 提供の形 | APIで使うか、自分で動かすか。 |

埋め込みのモデルを変更する場合は、全てのチャンクの埋め込みを作り直す。異なるモデルの埋め込みは比べられない。

### 絞り込みをメタデータで行う

製品、版、言語、文書の種類のように、質問から条件が決まる場合は、検索の前にメタデータで候補を絞り込む。意味の近さだけで検索すると、別の製品や古い版の文書が上位に入る。たとえば、「Enterpriseプランの3.2の上限は？」では、`product=enterprise`、`version=3.2` で絞ってから検索する。

### 質問の書き換えは評価で効果を確かめてから使う

| 手法 | 内容 | 使う場面 | 例 |
| --- | --- | --- | --- |
| 書き換え | 会話の文脈を補い、独立した検索語にする。 | 会話の途中の質問 | 「それの料金は？」→「Enterpriseプランの料金」 |
| 分解 | 複数の問いを含む質問を、個別の検索に分ける。 | 比較や複数の条件を含む質問 | 「AとBのSLAの違いは？」→「AのSLA」「BのSLA」 |
| 複数の言い換え | 言い換えた複数の検索語で検索し、結果を統合する。 | 表現の揺れが大きい分野 | 「解約」「退会」「契約の終了」 |
| 仮の回答による検索 | LLMが作った仮の回答で検索する。 | 効果が小さいことがあるため、評価で確かめた場合に限る。 | 質問から回答の文章を作り、その文章で検索する。 |

書き換えは、LLMの呼び出しを1回増やし、遅延を大きくする。評価で検索漏れが減ることを確かめてから加える。

## 5. 回答の生成

### 根拠を識別できる形で渡す

LLMへ渡すチャンクには、文書のID、文書名、見出し、URLまたはパスを付ける。回答には、根拠としたチャンクの出典を「Enterpriseプランの保証期間は3年である［料金表 > Enterpriseプラン］」のように付けさせる。Claudeは、検索結果を検索結果のブロックとして渡すと、出典の付いた引用を返す。OpenAIのファイル検索は、回答にファイルの引用の注釈を付ける。

### 根拠がない場合の答え方を決める

渡した文書に答えがない場合は、推測で答えずに、「検索した文書には2027年の料金の記載がない」のように、見つからなかったことを答えさせる。根拠のない質問を評価セットに含め、答えなかった割合を測る。

### 渡す文脈を整える

| 処理 | 内容 |
| --- | --- |
| 重複の除去 | 同じ内容のチャンクを1つにする。 |
| 隣接するチャンクの結合 | 同じ文書の連続するチャンクは、つなげて渡す。 |
| 並べ方 | 関連度の順、または文書内の順に並べる。 |
| 変わらない部分のキャッシュ | システムの指示や共通の文書はプロンプトの先頭に置き、プロンプトキャッシュを使う。 |

## 6. エージェント型の検索

### 検索をエージェントの道具として渡す

複数の段階を要する質問では、検索を道具としてエージェントに渡し、エージェントに検索語の作成、検索、読み込みを繰り返させる。道具は、MCPサーバーや関数呼び出しとして提供する。たとえば、「先月の障害の原因になった設定を、今のマニュアルはどう案内しているか」では、障害報告を検索して設定の名前を得てから、その名前でマニュアルを検索する。

| 道具 | 返す内容 |
| --- | --- |
| 検索 | チャンクのID、出典、短い抜粋、スコア。件数の上限を設ける。 |
| 読み込み | 指定したIDの文書の全体、または前後の範囲。 |
| 一覧 | 文書の種類、製品、版などの絞り込みに使える値。 |

道具の出力は短くし、続きを読むための手段（IDの指定、ページの指定）を用意する。

### コードはファイルとシンボルの検索から始める

エージェントがコードを探す場合は、埋め込みの索引を作る前に、ファイル名の検索、文字列の検索、言語サーバーによるシンボルの検索を使う。コードは識別子が一致するかで探せることが多く、索引の更新も要らない。埋め込みによる検索は、リポジトリが大きく文字列の検索だけでは候補が多すぎる場合や、自然言語の説明から探す場合に補助として加える。

### 検索の回数と費用に上限を設ける

エージェント型の検索は、検索と読み込みの回数に比例して費用と遅延が増える。1つの質問で行う検索の回数の上限（例：5回）を決め、上限に達した場合は、集めた範囲で回答させる。

## 7. グラフを使う検索

### 全体の主題を問う質問に使う

「文書全体で繰り返し出てくる課題は何か」のように、文書の集合全体を要約する質問は、上位のチャンクを集めるだけでは答えられない。このような質問が多い場合は、文書から実体と関係を抽出したグラフと、その集団ごとの要約を使う検索を加える。

| 方式 | 特徴 |
| --- | --- |
| GraphRAG | 実体と関係のグラフと、集団ごとの要約を事前に作る。全体の主題を問う質問に強いが、索引の作成にLLMの呼び出しが多く要る。 |
| LazyGraphRAG | 要約の作成を質問の時まで遅らせ、索引の作成の費用を通常のRAGと同程度に抑える。 |
| LightRAG | グラフと通常の検索を組み合わせ、索引の作成と更新の費用を抑える。 |

### 通常のRAGと比べてから採用する

グラフを使う検索は、特定の事実を問う局所的な質問では、通常のRAGより精度が下がることがある。評価セットで通常のRAGと比べ、全体の主題を問う質問だけをグラフを使う検索へ振り分ける。

## 8. 評価

### 評価セットを最初に作る

評価セットは、実際の質問から作り、次の項目を含める。数十件から始め、誤りが見つかるたびに追加する。

| 項目 | 内容 |
| --- | --- |
| 質問 | 実際の利用者の質問、または想定する質問。 |
| 正解のチャンク | 回答に必要なチャンクのID。 |
| 参照の回答 | 正しい回答の要点。 |
| 種類 | 事実、手順、比較、複数の段階、文書にない質問の区別。 |

| 質問 | 正解のチャンク | 参照の回答 | 種類 |
| --- | --- | --- | --- |
| XR-2040の保証期間は？ | `doc-1042#17` | 3年。 | 事実 |
| 請求先の住所を変える手順は？ | `doc-0311#4` | 管理画面の「請求情報」から変更し、翌月の請求から反映される。 | 手順 |
| StandardとEnterpriseのSLAの違いは？ | `doc-1042#3`、`doc-1042#9` | 稼働率が99.5%と99.9%で異なる。 | 比較 |
| 2027年の料金は？ | なし | 文書に記載がないと答える。 | 文書にない質問 |

### 検索と生成を分けて評価する

検索の誤りと生成の誤りは、対策が異なる。検索と生成を、別の指標で評価する。

| 対象 | 指標 | 意味 |
| --- | --- | --- |
| 検索 | Recall@k | 正解のチャンクが上位k件に含まれる割合。 |
| 検索 | MRR、nDCG | 正解のチャンクが上位に並ぶ度合い。 |
| 検索 | 文脈の適合率（Context precision） | 渡したチャンクのうち、関連するものの割合と順位。 |
| 検索 | 文脈の再現率（Context recall） | 回答に必要な情報のうち、渡したチャンクに含まれる割合。 |
| 生成 | 忠実性（Faithfulness） | 回答の主張が、渡したチャンクで裏付けられる割合。 |
| 生成 | 回答の関連性（Answer relevancy） | 回答が質問に答えている度合い。 |
| 生成 | 回答の正しさ | 参照の回答と一致する度合い。 |
| 生成 | 答えない割合 | 文書にない質問に、答えなかった割合。 |

### LLMによる採点は条件を固定して比べる

忠実性や関連性をLLMで採点する場合は、採点のモデル、指示、埋め込みのモデルを固定して比べる。採点の条件が変わると、点数を比べられない。採点の結果の一部を人が確かめ、人の判断と食い違う場合は採点の指示を直す。

### 変更のたびに評価を実行する

分割の方式、埋め込みのモデル、検索の設定、再順位付け、プロンプトを変更するたびに、評価セットで評価し、結果を記録する。次の表は記録の形を示す例であり、数値は説明のための仮の値である。

| 変更 | Recall@20 | 忠実性 | 判断 |
| --- | --- | --- | --- |
| 基準（512トークンの固定の分割） | 82% | 0.88 | なし |
| 見出しに沿った分割 | 88% | 0.90 | 採用する。 |
| 再順位付けの追加 | 88% | 0.94 | 採用する。 |
| 質問の書き換えの追加 | 88% | 0.94 | 遅延が増えるだけのため採用しない。 |

## 9. 運用

### 検索と回答の記録を残す

本番の質問ごとに、質問、書き換えた検索語、検索したチャンクのIDとスコア、渡したチャンク、回答、利用者の評価を記録する。誤った回答は、記録から検索と生成のどちらの誤りかを切り分け、評価セットへ追加する。正解のチャンクが渡した中になければ検索の誤り、渡した中にあるのに回答が誤っていれば生成の誤りである。

### 索引の版を管理する

分割の方式や埋め込みのモデルを変更する場合は、新しい版の索引を別に作り、評価で比べてから切り替える。切り替えの後も、問題が出た場合に戻せるように、前の版の索引を一定期間残す。

### 費用と遅延を管理する

| 対策 | 内容 |
| --- | --- |
| プロンプトキャッシュ | 共通の指示や文書をキャッシュする。 |
| 候補の数の調整 | 検索と再順位付けの候補の数を、評価の結果を保てる範囲で減らす。 |
| 小さなモデルの利用 | 文脈の付与、質問の書き換え、採点に、小さく速いモデルを使う。 |
| 結果のキャッシュ | 同じ質問の検索結果や回答を再利用する。 |

## 11. チェックリスト

- 文書の総量がコンテキストに収まる場合に、全体をプロンプトに入れる方式と比べた。
- 評価セットがあり、検索と生成を別の指標で評価している。
- 文書を、見出し、表、リストの構造を保って解析し、構造の境界で分割している。
- チャンクに、出典、絞り込み、更新に使うメタデータがある。
- 文書の変更と削除が、索引に反映される。
- 密な検索と語彙の検索のハイブリッド検索を使い、日本語の語彙の検索で語を分割する設定がある。
- 候補を多めに取り、再順位付けで絞っている。
- 埋め込みのモデルを、自分の評価セットの結果で選んだ。
- 回答に出典が付き、文書にない質問には答えないことを確かめた。
- 質問の書き換え、エージェント型の検索、グラフを使う検索は、評価で効果を確かめてから加えた。
- 質問ごとに、検索したチャンク、渡したチャンク、回答を記録している。
