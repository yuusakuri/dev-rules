# ループエンジニアリングガイドライン

## 1 はじめに

### 1.1 目的

この文書の目的は、AIエージェントの運用を設計する人が、作業の反復、結果の検証及び停止を一貫した方法で制御可能にすることである。

### 1.2 適用範囲

この文書は、Claude Code、CodexなどのAIエージェントを反復実行する仕組みの設計について規定する。

## 2 ループの構成要素

### 2.1 ループを作成する前に構成要素を全て定める

ループの中でエージェントに与える指示、ツール及び検査は、[ハーネスエンジニアリングガイドライン](harness-engineering-guidelines.md)による。

ループは、[表3](#table-3)の構成要素を全て定めてから実行する。定めていない構成要素があるループは、停止しない、誤った結果で停止する、又は同じ失敗を繰り返す。

<a id="table-3"></a>表3−ループの構成要素

| 構成要素 | 定める事項 | 例：毎朝のバグ報告の仕分け |
| --- | --- | --- |
| トリガー | 何が1回の実行を開始するか。 | 平日の毎朝9時。 |
| 作業の単位 | 1回の反復で扱う範囲。 | バグ報告1件。 |
| 状態 | 反復の間で何をどこへ引き継ぐか。 | 処理済みの報告のIDを `triage-state.json` に記録する。 |
| 検証 | 完了をどの証拠で、誰が判定するか。 | 全ての報告に定義済みの8種のラベルのいずれかと担当者があることを、スクリプトで確認する。 |
| 停止条件 | 完了の条件、回数、時間及び費用の上限並びに異常の検出 | 未処理が0件で終了する。50件又は20ドルで打ち切る。同じ報告で3回失敗した場合は、人へ回す。 |
| 人の確認点 | どの操作の前に人が判断するか。 | 報告者への返信は、担当者が内容を確認して送る。 |
| 記録 | 反復ごとに何を残すか。 | 実行のID、処理件数、人へ回した件数及びトークンの量を `runs.jsonl` に追記する。 |

構成要素は、ループの設定とともにリポジトリの文書へ書き、ループの変更と同時に更新する。

### 2.2 1回の反復では一つの作業単位を扱う

1回の反復では、一つの機能、一つの修正又は一つの項目だけを扱わせる。複数の作業を同時に進めると、コンテキストを使用し切る、未完成の変更が残る、又はどの変更が失敗の原因かを特定できなくなる。

Anthropicは、200件を超える機能からなるアプリケーションの開発で、1回のセッションを一つの機能に限定したことが、作業の抱え込みを防ぐ要因になったと報告している。

### 2.3 確定した手順はスクリプトに任せる

手順が確定しており判断を必要としない処理は、エージェントに推論させず、スクリプトで実行する。スクリプトは毎回同じ結果を返し、推論より安い。例えば、CSVの取得及び集計、リンク切れの確認並びに前回の結果との差分の抽出はスクリプトに任せ、差分の原因の説明だけをエージェントに任せる。

## 3 ループの型の選び方

### 3.1 トリガー及び停止条件で型を選ぶ

ループは、起動する時点及び終了を判定する方法を選んで構成する。[表4](#table-4)は、代表的な構成を比較したものである。定期実行するゴールベースのループのように、起動方式と終了方式とを組み合わせてもよい。

<a id="table-4"></a>表4−ループの型

| 型 | トリガー | 停止条件 | エージェントに任せる処理又は判断 | 適する作業 | 例 |
| --- | --- | --- | --- | --- | --- |
| ターンベース | 人の指示 | エージェントが完了したか、追加の情報が必要と判断する。 | 手順の実行及び検証 | 短い作業<br>探索<br>判断を伴う作業 | “いいねボタンを追加し、テストを通して報告する”。人が結果を見て次を指示する。 |
| ゴールベース | 人が完了の条件を与える。 | 完了の条件を満たすか、上限に達する。 | 完了の判定及び再試行 | 完了を機械的に確認できる作業 | “トップページのLighthouseの性能スコアを90以上にする。5回試して届かなければ止める” |
| 時間ベース | 一定の間隔 | 人が取り消すか、対象の作業が終了する。 | 時刻に応じた起動 | 定期的な確認<br>外部の変化への対応 | “5分ごとにプルリクエストを確認し、レビューの指摘と失敗したCIに対応する”“毎週月曜の8時に先週の売上を集計して共有する” |
| イベント駆動 | 問い合わせの到着、ファイルの追加、外部のサービスからの通知などのイベント | 個々の作業は完了の条件で終了する。ループ自体は人が停止するまで継続する。 | イベントに応じた起動 | 定型化した反復する作業 | “フィードバックのチャンネルに届いたバグ報告を毎時確認し、分類、修正案の作成、報告者への回答案の作成を行う” |
| 期限付きの最適化 | 人が目標及び終了時刻を与える。 | 終了時刻に達する。 | 改善案の選択及び反復 | 評価で数値を測れる目標を<br>期限まで改善し続ける作業 | “明朝9時まで、負荷試験のスコアを上げ続ける” |

### 3.2 ツールの機能を型に対応させる

型に対応するツールの機能は、[表5](#table-5)による。

<a id="table-5"></a>表5−型に対応するツールの機能

| 型 | Claude Code | Codex | ツールの機能を使用しない場合 |
| --- | --- | --- | --- |
| ターンベース | 通常の対話及び検証の手順を書いたスキル | 通常の対話及び検証の手順を書いたスキル | なし |
| ゴールベース | `/goal`<br>Stopフック | `/goal`<br>Stopフック | 外側のスクリプトが非対話モードのエージェントを繰り返し起動し、検証のコマンドの終了コードで停止する。 |
| 時間ベース | セッション内の `/loop`<br>Desktop スケジュールタスク<br>クラウドスケジュールタスク（`/schedule`）<br>GitHub Actionsの `schedule` | アプリのスケジュールタスク、Codex GitHub Action及び `schedule` | cronなどから非対話モードのエージェントを起動する。 |
| イベント駆動 | クラウドスケジュールタスクのGitHub及びAPIのトリガー、Claude Code GitHub Actions、チャネル | イベントで起動するスケジュールタスク（Gmail、Slack、GitHub）、Codex GitHub Action | Webhookを受けて、非対話モードのエージェント又はSDKを起動する。 |
| 期限付きの最適化 | 起動スクリプト<br>Stopフック<br>評価のCLI | 起動スクリプト<br>Stopフック<br>評価のCLI | [エージェントハーネス](../../templates/agent-harness/README.md)のテンプレートを使用する。 |

ループの制御を自分のプログラムに組み込む場合は、Claude CodeはAgent SDK（Python、TypeScript）、CodexはCodex SDK（TypeScript、Python）を使用する。

## 4 検証

### 4.1 完了は機械的な証拠で判定する

完了は、エージェントの報告ではなく、コマンドの終了コード、数値又は件数で判定する。完了の条件は、[表6](#table-6)のように確認できる形にして与える。

<a id="table-6"></a>表6−完了の条件の例

| 曖昧な依頼 | 確認できる完了の条件 | 確認する方法 |
| --- | --- | --- |
| ログインの不具合を修正する | セッションの期限切れの後にログインが失敗する事象を再現するテストを追加し、そのテスト及び既存のテストが全て通る。 | `pnpm test` の終了コードが0である。 |
| トップページを速くする | Lighthouseの性能スコアが、3回の計測の中央値で90以上になる。 | `lighthouse` の出力のスコアを確認する。 |
| ロガーを新しいAPIへ移す | `files.txt` の全てのファイルを移し、古いAPIの呼出しが0件で、テストが通る。 | `grep` の件数及びテストの終了コードを確認する。 |
| 変更履歴を整える | 今週マージされた全てのプルリクエストに対応する項目が `CHANGELOG.md` にある。 | GitHubのプルリクエストの一覧と照合する。 |
| バグ報告を片付ける | `needs-triage` のラベルが付いたIssueが0件になる。 | `gh issue list` の件数を確認する。 |
| 月次売上レポートを作成する | 全部門の行があり、部門の合計が会計システムの月次の総額と1円単位で一致する。 | 照合のスクリプトの結果を確認する。 |
| 顧客データを移行する | 移行元と移行先との件数が一致し、メールアドレスの重複及び必須の項目の欠損が0件である。 | SQLの集計を確認する。 |
| 競合を調査する | 指定した5社の全てに、価格、主要な機能、対象の顧客の3項目があり、全ての値に出典のURLがある。 | 空欄及びURLの応答をスクリプトで確認する。 |
| FAQを更新する | 直近30日の問い合わせの上位20件の全てに回答があり、リンク切れが0件である。 | 問い合わせの集計とFAQの見出しとを照合する。 |

複数の条件がある場合は、全ての条件を満たした場合だけ完了とする。

### 4.2 検証の強さを理解して選ぶ

検証の方法によって、エージェントが誤った完了を報告した場合に停止できるかが異なる。無人で実行するループには、外側から強制する方法を使用する。

検証の方法は、[表7](#table-7)による。

<a id="table-7"></a>表7−検証の方法

| 方法 | 判定する者 | 強制の強さ | 例 |
| --- | --- | --- | --- |
| 指示の中で自己検証を求める | 生成エージェント自身 | 弱い。誤った完了をそのまま報告することがある。 | “認証のテストを実行し、通るまで続ける” |
| 検証の手順をスキルにする | 手順に従う生成エージェント | 弱い。手順を省くことがある。 | 画面を操作して前後を撮影し、コンソールの新しいエラーが0件であることを確認するスキル。 |
| ツールの組み込みの判定（`/goal`） | 判定用のモデル | 中程度。判定用のモデルは会話の内容だけを読み、コマンドを実行しない。 | `/goal test/auth の全てのテストが通り、リントのエラーが0件である` |
| 別のコンテキストのレビュアー | サブエージェント | 中程度。レビュアーも推論で判定する。 | 差分を `SPEC.md` と照合し、未実装の要件だけを報告するサブエージェント。 |
| Stopフックで検証のコマンドを実行する | フックのスクリプト | 強い。検証が通るまで停止を阻止する。 | `pnpm tsc --noEmit` が失敗する間は、終了コード2で停止を阻止する。 |
| 外側のスクリプト又はSDKで検証のコマンドを実行する | ループの外のプログラム | 強い。検証の結果で次の反復を決定する。 | `files.txt` のファイルを1件ずつ `claude -p --max-turns 20` に渡す。各実行の後にスクリプトが `grep` で古いAPIの呼出しを数えてテストを実行し、エージェントの応答ではなく、その結果で次へ進む。 |

どの方法でも、“テストは全て通った”という報告だけを信じず、実行したコマンド及び出力を証拠として残させる。

### 4.3 生成及び検証を分ける

レビュアーは、生成エージェントとは別のコンテキストで実行し、成果物、完了の条件及び検査の出力を渡す。自己評価による誤りの見逃しを減らすためである。完了の条件を満たす証拠がある場合だけ合格と判定する。

Anthropicの例では、単独のエージェントは20分及び9ドルでゲームの作成ツールを作成したが、中心の機能が動作しなかった。計画エージェント、生成エージェント及びブラウザーで操作して採点する評価エージェントに分けた構成は、6時間及び200ドルを使用して、動作するアプリケーションを作成した。

### 4.4 主観的な目標は確認できる部分だけを自動化する

読みやすさ又はデザインのように機械で確認できない目標は、ループで完了を判定しない。確認できる部分だけをループに任せ、残りは、人又は評価の基準で較正したレビュアーが判定する。

主観的な目標の分担は、[表8](#table-8)による。

<a id="table-8"></a>表8−主観的な目標の分担

| 目標 | ループに任せる部分 | 人又はレビュアーが判定する部分 |
| --- | --- | --- |
| 提案書を読みやすくする | 必須の見出しの有無<br>1文の長さの上限<br>用語の統一<br>リンク切れ | 論旨が顧客の課題に答えているか。 |
| 画面のデザインを整える | コントラスト比<br>コンソールのエラー<br>画面の幅ごとの表示の崩れ | 全体の印象及び独自性。 |

### 4.5 揺れのある数値は複数回の計測で比較する

性能又はスコアのように、同じ状態でも計測ごとに値が揺れる指標は、1回の計測で比較しない。基準を複数回測定して中央値及び揺れの幅を求め、揺れの幅を超えた差だけを改善とみなす。

例えば、基準の3回の計測が98、100及び102の場合は、中央値は100、揺れの幅は4%である。変更後の103は+3%で揺れの幅に収まるため再度計測し、110は+10%のため改善として残す。

## 5 停止条件及び予算

### 5.1 全ての自律ループに上限を設ける

全ての自律ループに、完了の条件及び[表9](#table-9)の上限を少なくとも一つ設ける。完了の条件を満たせない場合も、反復を打ち切ることが可能になる。

<a id="table-9"></a>表9−反復の上限

| 上限 | Claude Code | Codex |
| --- | --- | --- |
| 回数 | 非対話モードの `--max-turns 20`<br>Agent SDKの `maxTurns`<br>`/goal` の条件の“20ターンで止める” | `/goal` の条件の“20ターンで止める” |
| 費用 | 非対話モードの `--max-budget-usd 5.00`、Agent SDKの `maxBudgetUsd` | `/goal` のトークンの予算 |
| 時間 | 起動スクリプトの終了時刻<br>ジョブのタイムアウトの30分 | 起動スクリプトの終了時刻<br>ジョブのタイムアウトの30分 |
| 期間 | セッション内の `/loop` は7日で失効する。 | スケジュールタスクを人が停止する。 |

上限に達して停止した場合は、達成できなかった事項及び現在の状態を人へ通知する。

上限の値は、小さな対象で実行した実績から決定する。参考として、Anthropicの報告では、ゲームの作成ツールに6時間及び200ドル、音楽の制作ツールに3時間50分及び124.70ドルを要した。

### 5.2 進まない状態を検出して停止する

同じ失敗を繰り返す状態、残る問題が変化しない状態、及びツールを使用せずに応答だけを繰り返す状態では、上限を待機せずに停止する。例えば、同じエラーの文面が3回続いた場合、又は未処理の件数が3回の反復で減らない場合に停止して、人へ回す。

StopフックでClaude Codeの停止を阻止する場合は、入力の `stop_hook_active` を確認し、同じ理由で阻止を繰り返さないようにする。Claude Codeは、ツールの実行を挟まずにStopフックが8回続けて停止を阻止すると、フックを無視して停止する。

### 5.3 人がいつでも停止できるようにする

ループには、人が即座に停止する手段を用意する。`runs/current/STOP` のような停止の印のファイル、スケジュールの取消し、`/goal clear` のように、エージェントの判断を経ずに機能する手段を使用する。

### 5.4 トークンの使用量を管理する

トークンの使用量の対策は、[表10](#table-10)による。

<a id="table-10"></a>表10−トークンの使用量の対策

| 対策 | 内容 | 例 |
| --- | --- | --- |
| 作業に合うモデルを選ぶ | 定型の作業は小さく速いモデル、判断を伴う作業は高性能なモデルに任せる。 | 報告の分類はClaude Haiku、修正の方針の判断はClaude Opusに任せる。 |
| 実行の間隔を対象の変化に合わせる | 対象がほとんど変化しない場合は、間隔を長くするか、イベントで起動する。 | 週に数件しか届かない問い合わせは、5分ごとに確認せず、受信のイベントで起動する。 |
| 処理する項目がない場合は直ちに終了する | 処理する項目がない場合は、推論を開始せずに終了する。 | 未処理の件数をスクリプトで数え、0件ならエージェントを起動しない。 |
| 大きな実行は小さく試す | 多数のエージェントを起動する実行は、一部の対象で試してから広げる。 | 1 000ファイルの移行は、3ファイルで試して指示を修正してから全件を実行する。 |
| 使用量を確認する | Claude Codeの `/usage` 及び `/goal` の状態表示で、実行ごとの使用量を確認する。 | 週に1回、ループごとのトークンの量及び処理件数を比較する。 |

## 6 状態及び再開

### 6.1 状態は会話の外に置く

計画、進捗、未完了の項目及び判断の理由は、リポジトリのファイル、変更履歴又は課題トラッカーに置く。会話の中だけにある情報は、圧縮又はセッションの切り替えで失われる。例えば、Ralphループは、毎回同じ `PROMPT.md` を渡し、残りの項目を `fix_plan.md` で引き継ぐ。

### 6.2 反復ごとのコンテキストの扱いを定める

反復ごとに新しいコンテキストで開始するか、同じセッションを継続するかを決定する。

コンテキストの扱いの方式は、[表11](#table-11)による。

<a id="table-11"></a>表11−コンテキストの扱いの方式

| 方式 | 利点 | 注意点 |
| --- | --- | --- |
| 毎回新しいコンテキストで開始する（例：1ファイルずつの移行、1件ずつの問い合わせの処理） | 古い情報又は誤った推論を引き継がない。 | 必要な状態を全てファイルから読み直させる。 |
| 同じセッションを継続する（例：一つの不具合の調査、レビューの指摘への対応） | 直前の作業の詳細を使用できる。 | 長くなると圧縮で情報が失われ、品質が下がる。作業の区切りで新しいセッションへ切り替える。 |

### 6.3 状態のファイルを整理する

状態のファイルは、完了した項目を履歴へ移動するか削除して整理する。進行中の作業と履歴とを区別し、同じ作業の再実行を防ぐ。

### 6.4 処理が停止しても再開できるようにする

ループの処理は、途中で終了しても同じ状態から再開できるようにする。起動スクリプトは、エージェントが予期せず終了した場合に、セッションIDを使用して同じセッションを再開する。外部への操作は、同じ操作を2回実行しても結果が変化しないようにする。

## 7 並列及び競合

### 7.1 並列のエージェントは作業ディレクトリを分ける

複数のエージェントを並列に実行する場合は、作業ディレクトリをエージェントごとに分ける。Claude Code及びCodexは、Gitのworktreeで作業ディレクトリを分けられる。Anthropicの例では、バグ報告1件に対して三つの修正案を別々のworktreeで作成し、判定するエージェントが批判的に比較して選ぶ。

### 7.2 同じ対象を複数のループが操作しない

ループは操作の前に、対象を他のループが処理中でないことを確認し、`in-progress` のラベルのような処理中の印を残す。ループを実行する基盤に同時実行を制限する機能があれば、それを使用する。

### 7.3 ループが自分の出力で再び起動しないようにする

イベント駆動のループは、ループ自身の書き込み又は投稿で再び起動しないようにする。起動したユーザーがボットの場合は既定で処理せず、処理するボットを明示する。

## 8 自律の段階及び人の確認点

### 8.1 報告だけの段階から開始する

新しいループは、次の段階を順に進める。前の段階で、検出の精度及び誤りの頻度を一定の期間計測してから、次の段階へ移る。

自律の段階は、[表12](#table-12)による。

<a id="table-12"></a>表12−自律の段階

| 段階 | ループが行うこと | 人が行うこと | 例：バグ報告の仕分け | 次へ進む目安 |
| --- | --- | --- | --- | --- |
| 報告 | 調査し、結果を報告する。成果物は変更しない。 | 報告を読み、対応を決定する。 | 分類及び担当者の案を一覧にしてSlackへ投稿する。 | 2週間、人が案を修正した割合が10%以下である。 |
| 提案 | 変更を作成し、検証して提案する。 | 確認し、採用を判断する。 | ラベルを付け、回答の下書きを作成する。 | 2週間、人が下書きを大きく修正した割合が5%以下である。 |
| 無人の実行 | 変更から反映まで行う。 | 定期的に結果を確認する。 | ラベルの付与及び定型の回答の送信まで行う。 | 週に1回、抜き取りで確認する。 |

無人の実行で取り消しが続く場合は、そのループを提案の段階へ戻す。目安の数値は、作業の重要度に合わせて決定する。

### 8.2 人が理解できる量に出力を保つ

ループの出力量は、人がレビュー可能な量に制限する。例えば、1日に確認可能なプルリクエストが10件の場合は、その件数に合わせて処理を制限する。人が一定の期間の変更を説明できない場合は、ループの段階を下げる。

## 9 型ごとの規則

### 9.1 ターンベースのループ

検証の手順をスキルに書き、全ての手順を通過するまで完了を報告させない。手順のいずれかが失敗した場合は、修正して最初の手順から再試行させる。指示には、対象、症状及び完了の状態を書く。

指示の例は、[表13](#table-13)による。

<a id="table-13"></a>表13−指示の例

| 指示の良否 | 例 |
| --- | --- |
| 曖昧 | “ログインの不具合を直して” |
| 具体的 | “セッションの期限切れの後にログインが失敗するという報告がある。`src/auth/` のトークンの更新を調査し、再現するテストを書いてから直す” |

### 9.2 ゴールベースのループ

完了の条件には、[表14](#table-14)の事項を書く。

<a id="table-14"></a>表14−完了の条件に書く事項

| 事項 | 例：認証の修正 | 例：月次レポート |
| --- | --- | --- |
| 確認できる一つの終了状態 | `test/auth` の全てのテストが通る。 | 全部門の合計が会計の総額と一致する。 |
| 確認の方法 | `pnpm test test/auth` の終了コードが0である。 | `scripts/reconcile.py` が“不一致0件”と出力する。 |
| 途中で変更してはならないもの | 既存のテストのファイルを変更しない。 | 会計システムの元データを変更しない。 |
| 回数又は時間の上限 | 20ターンで停止する。 | 10ターンで停止する。 |

Claude Codeの `/goal` の判定用のモデルは、会話に表れた内容だけで判定し、コマンドを実行しない。完了の証拠となるコマンドの出力が会話に表れるように、確認の方法を条件に書く。厳密な判定が必要な場合は、Stopフック又は外側のスクリプトで検証のコマンドを実行する。

### 9.3 時間ベースのループ

実行の場所及び端末の状態への依存を確認して選ぶ。

実行の場所は、[表15](#table-15)による。

<a id="table-15"></a>表15−実行の場所

| 実行の場所 | 端末の電源 | ローカルのファイル | 用途 |
| --- | --- | --- | --- |
| セッション内（Claude Codeの `/loop`） | 必要。セッションを開いておく。 | 使用できる。 | 作業中の短い確認（例：`/loop 15m` でCIの結果を確認し、失敗の場合は修正する） |
| 端末のアプリ（Claude Codeのデスクトップアプリ、Codexのアプリ） | 必要。アプリを起動しておく。 | 使用できる。 | ローカルの環境が必要な定期作業（例：毎朝9時に手元のフォルダの請求書を集計する） |
| クラウド（Claude Codeのクラウドスケジュールタスク、GitHub Actions） | 不要 | 使用できない。毎回リポジトリを取得し直す。 | 端末に依存しない定期作業（例：毎晩、依存関係の更新を確認して提案する） |

間隔は、対象が変化する頻度に合わせる。外部の処理の完了又は返答を待機する場合は、イベントで起動する方法を優先する。

### 9.4 イベント駆動のループ

イベントごとに、一つの作業とその完了の条件とを対応させる。同じイベントが短時間に大量に届いた場合に備えて、処理する件数の上限を定める。

イベントごとの作業は、[表16](#table-16)による。

<a id="table-16"></a>表16−イベントごとの作業

| イベント | 作業 | 完了の条件 | 上限 |
| --- | --- | --- | --- |
| プルリクエストの作成 | 仕様と照合してレビューする。 | 指摘をコメントするか、指摘なしと報告する。 | 1件あたり10ターン |
| 問い合わせの到着 | 分類し、FAQから回答の下書きを作成する。 | ラベル及び出典付きの下書きがある。 | 1時間に50件 |
| 請求書のファイルの追加 | 項目を抽出して台帳へ転記する。 | 合計が請求書の金額と一致する。 | 1日に200件 |

### 9.5 期限付きの最適化のループ

評価で数値を測れる目標を、終了時刻まで改善し続ける場合は、[表17](#table-17)の仕組みを用意する。[エージェントハーネス](../../templates/agent-harness/README.md)のテンプレートは、これらをClaude Code及びCodexの両方で実装している。

<a id="table-17"></a>表17−期限付きの最適化の仕組み

| 仕組み | 内容 |
| --- | --- |
| 条件書 | 目標、評価の方法、環境、禁止事項及び最終状態の要件を、実行ごとの文書に書く（例：`CONDITIONS.md`）。 |
| 評価のCLI | 評価、記録並びに環境の反映及び復元を一つのCLIにまとめ、エージェントはCLIを通してだけ環境を操作する。 |
| 判定 | 基準を3回測定し、揺れの幅と5%とのうち大きい方を超えた改善だけを残す。改善しない変更は、成果物に加えてデータ又は設定も含めて元に戻す。 |
| 継続 | Stopフックで終了時刻までの停止を阻止し、エージェントが終了した場合は起動スクリプトが同じセッションを再開する。 |
| 通知 | 最高の結果が30分更新されない場合、又は最終段階に入った場合に、フックで状態を伝える。 |
| 最終段階 | 終了時刻の40分前から新しい改善を開始せず、最良の状態へ戻し、再起動後の状態及び評価を確認する。 |
| 強制終了 | 終了時刻を過ぎた場合は、起動スクリプトがエージェント及び評価の処理を停止する。 |

## 10 記録及び改善

### 10.1 反復ごとに記録を残す

反復ごとに、実行のID、開始及び終了の時刻、対象、結果、検証の出力、人へ引き継いだ件数及び使用したトークンの量を記録する。

反復ごとの記録の項目は、[表18](#table-18)による。

<a id="table-18"></a>表18−反復ごとの記録の項目

| 項目 | 例 |
| --- | --- |
| 実行のID | `2026-11-04-0900` |
| 対象及び結果 | バグ報告 #4217<br>`routed` |
| 検証の出力 | `labels ok, assignee ok` |
| 人へ引き継いだ件数 | 3件 |
| トークンの量 | 42 000 |

### 10.2 失敗をハーネス及びループの改善につなげる

ループが停止しなかった場合、誤った結果で停止した場合、又は同じ失敗を繰り返した場合は、記録から原因を特定し、停止条件、検証又はハーネスの構成要素のいずれかを変更する。ハーネスの構成要素の変更は、[ハーネスエンジニアリングガイドラインの9章](harness-engineering-guidelines.md#9-ハーネスの改善)による。

新しいループは、本番と同じ形の小さな対象（例：1 000ファイルのうちの3ファイル）で予行し、停止する位置及び過剰に実行する位置を確認してから広げる。

## 11 チェックリスト

- トリガー、作業の単位、状態、検証、停止条件、人の確認点及び記録を全て定め、文書に書いた。
- 完了の条件を、終了コード、数値又は件数で確認できる形にした。
- 無人で実行するループで、外側から強制する検証を使用している。
- 生成及び検証を別のコンテキストに分け、レビュアーに検査の出力を渡している。
- 回数、費用及び時間のうち少なくとも一つの上限があり、上限で停止した場合に人へ通知する。
- 進まない状態を検出して停止し、人がいつでも停止できる。
- 状態を会話の外に置き、途中で停止しても再開できる。
- 並列のエージェントが作業ディレクトリを分け、同じ対象を同時に操作しない。
- 報告の段階から開始している。
