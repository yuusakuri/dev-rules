## 1 はじめに

### 1.1 目的

本書の目的は、人が毎回指示を出さなくても、AIエージェントが作業を繰り返し、検証された結果で止まるループを、一貫した基準で設計できるようにすることである。

### 1.2 適用範囲

本書は、Claude CodeやCodexなどのAIエージェントを、どのきっかけで起動し、どの条件で作業を繰り返し、どう検証し、いつ止めるかの設計を規定する。

ループの中でエージェントに与える指示、道具、検査は、[ハーネスエンジニアリングガイドライン](harness-engineering-guidelines.md)による。

### 1.3 用語及び定義

| 用語 | 定義 |
| --- | --- |
| ループ | 停止条件を満たすまで、エージェントが計画、実行、観察、検証を繰り返す制御の単位。 |
| トリガー | ループの1回の実行を始めるきっかけ。人の指示、時刻、外部のイベントがある。 |
| 停止条件 | ループを終える条件。完了の条件と、上限や異常による打ち切りの条件からなる。 |
| 作成役 | 成果物を作るエージェント。 |
| 検証役 | 作成役とは別のコンテキストで、成果物が完了の条件を満たすかを判定するエージェントまたはプログラム。 |
| 状態 | 反復の間で引き継ぐ、計画、進捗、判断の記録。会話の外のファイルやデータベースに置く。 |

## 2. ループの構成要素

### ループを作る前に構成要素を全て決める

ループは、次の構成要素を全て決めてから動かす。決めていない構成要素があるループは、止まらない、誤った結果で止まる、同じ失敗を繰り返す。

| 構成要素 | 決める事項 | 例：毎朝のバグ報告の仕分け |
| --- | --- | --- |
| トリガー | 何が1回の実行を始めるか。 | 平日の毎朝9時。 |
| 作業の単位 | 1回の反復で扱う範囲。 | バグ報告1件。 |
| 状態 | 反復の間で何をどこへ引き継ぐか。 | 処理済みの報告のIDを `triage-state.json` に記録する。 |
| 検証 | 完了をどの証拠で、誰が判定するか。 | 全ての報告に定義済みの8種のラベルのいずれかと担当者があることを、スクリプトで確かめる。 |
| 停止条件 | 完了の条件、回数、時間、費用の上限、異常の検出。 | 未処理が0件で終わる。50件または20ドルで打ち切る。同じ報告で3回失敗したら人へ回す。 |
| 人の確認点 | どの操作の前に人が判断するか。 | 報告者への返信は、担当者が内容を確かめて送る。 |
| 記録 | 反復ごとに何を残すか。 | 実行のID、処理件数、人へ回した件数、トークンの量を `runs.jsonl` に追記する。 |

構成要素は、ループの設定とともに作業場所の文書へ書き、ループの変更と一緒に更新する。

### 1回の反復では1つの作業単位を扱う

1回の反復では、1つの機能、1つの修正、1つの項目だけを扱わせる。複数の作業を同時に進めると、コンテキストを使い切る、未完成の変更が残る、どの変更が失敗の原因かを特定できない。

Anthropicは、200件を超える機能からなるアプリケーションの開発で、1回のセッションを1つの機能に限定したことが、作業の抱え込みを防ぐ決め手になったと報告している。

### 決まった手順はスクリプトに任せる

手順が決まっていて判断を必要としない処理は、エージェントに推論させず、スクリプトで実行する。スクリプトは毎回同じ結果を返し、推論より安い。たとえば、CSVの取得と集計、リンク切れの確認、前回の結果との差分の抽出はスクリプトに任せ、差分の原因の説明だけをエージェントに任せる。

## 3. ループの型の選び方

### トリガーと停止条件で型を選ぶ

ループは、トリガーと停止条件によって次の型に分ける。最も単純な型から始め、人が作業の遅れの原因になっている箇所だけを、より自律的な型へ移す。

| 型 | トリガー | 停止条件 | 人が手放すもの | 適する作業 | 例 |
| --- | --- | --- | --- | --- | --- |
| ターンベース | 人の指示 | エージェントが完了したか、追加の情報が必要と判断する。 | 検証 | 短い作業、探索、判断を伴う作業 | 「いいねボタンを追加し、テストを通して報告する」。人が結果を見て次を指示する。 |
| ゴールベース | 人が完了の条件を与える。 | 完了の条件を満たすか、上限に達する。 | 停止の判断 | 完了を機械的に確認できる作業 | 「トップページのLighthouseの性能スコアを90以上にする。5回試して届かなければ止める」 |
| 時間ベース | 一定の間隔 | 人が取り消すか、対象の作業が終わる。 | きっかけ | 定期的な確認、外部の変化への対応 | 「5分ごとにプルリクエストを確認し、レビューの指摘と失敗したCIに対応する」「毎週月曜の8時に先週の売上を集計して共有する」 |
| イベント駆動 | 問い合わせの到着、ファイルの追加、外部のサービスからの通知などのイベント | 個々の作業は完了の条件で終わる。ループ自体は人が止めるまで続く。 | 指示 | 定型化した繰り返しの作業 | 「フィードバックのチャンネルに届いたバグ報告を毎時確認し、分類、修正案の作成、報告者への回答案の作成を行う」 |
| 期限付きの最適化 | 人が目標と終了時刻を与える。 | 終了時刻に達する。 | 改善の繰り返し | 評価で数値を測れる目標を、期限まで改善し続ける作業 | 「明朝9時まで、負荷試験のスコアを上げ続ける」 |

### ツールの機能を型に対応させる

| 型 | Claude Code | Codex | ツールの機能を使わない場合 |
| --- | --- | --- | --- |
| ターンベース | 通常の対話と、検証の手順を書いたスキル | 通常の対話と、検証の手順を書いたスキル | なし |
| ゴールベース | `/goal`、Stopフック | `/goal`、Stopフック | 外側のスクリプトが非対話モードのエージェントを繰り返し起動し、検証のコマンドの終了コードで止める。 |
| 時間ベース | セッション内の `/loop`、デスクトップアプリのスケジュールされたタスク、クラウドのスケジュールされたタスク（`/schedule`）、GitHub Actionsの `schedule` | アプリのスケジュールされたタスク、Codex GitHub Actionと `schedule` | cronなどから非対話モードのエージェントを起動する。 |
| イベント駆動 | クラウドのスケジュールされたタスクのGitHubとAPIのトリガー、Claude Code GitHub Actions、channels | イベントで起動するスケジュールされたタスク（Gmail、Slack、GitHub）、Codex GitHub Action | Webhookを受けて、非対話モードのエージェントかSDKを起動する。 |
| 期限付きの最適化 | 起動スクリプト、Stopフック、評価のCLI | 起動スクリプト、Stopフック、評価のCLI | [エージェントハーネス](../../templates/agent-harness/README.md)のテンプレートを使う。 |

ループの制御を自分のプログラムに組み込む場合は、Claude CodeはAgent SDK（Python、TypeScript）、CodexはCodex SDK（TypeScript、Python）を使う。

## 4. 検証

### 完了は機械的な証拠で判定する

完了は、エージェントの報告ではなく、コマンドの終了コード、数値、件数で判定する。完了の条件は、次のように確認できる形にして与える。

| 曖昧な依頼 | 確認できる完了の条件 | 確かめる方法 |
| --- | --- | --- |
| ログインの不具合を直す | セッションの期限切れの後にログインが失敗する事象を再現するテストを追加し、そのテストと既存のテストが全て通る。 | `pnpm test` の終了コードが0である。 |
| トップページを速くする | Lighthouseの性能スコアが、3回の計測の中央値で90以上になる。 | `lighthouse` の出力のスコアを確かめる。 |
| ロガーを新しいAPIへ移す | `files.txt` の全てのファイルを移し、古いAPIの呼び出しが0件で、テストが通る。 | `grep` の件数と、テストの終了コードを確かめる。 |
| 変更履歴を整える | 今週マージされた全てのプルリクエストに対応する項目が `CHANGELOG.md` にある。 | GitHubのプルリクエストの一覧と照合する。 |
| バグ報告を片付ける | `needs-triage` のラベルが付いたIssueが0件になる。 | `gh issue list` の件数を確かめる。 |
| 月次売上レポートを作る | 全部門の行があり、部門の合計が会計システムの月次の総額と1円単位で一致する。 | 照合のスクリプトの結果を確かめる。 |
| 顧客データを移行する | 移行元と移行先の件数が一致し、メールアドレスの重複と必須の項目の欠損が0件である。 | SQLの集計を確かめる。 |
| 競合を調査する | 指定した5社の全てに、価格、主要な機能、対象の顧客の3項目があり、全ての値に出典のURLがある。 | 空欄とURLの応答をスクリプトで確かめる。 |
| FAQを更新する | 直近30日の問い合わせの上位20件の全てに回答があり、リンク切れが0件である。 | 問い合わせの集計とFAQの見出しを照合する。 |

複数の条件がある場合は、全ての条件を満たした時だけ完了とする。

### 検証の強さを理解して選ぶ

検証の方法によって、エージェントが誤った完了を報告した時に止められるかが異なる。無人で動かすループには、外側から強制する方法を使う。

| 方法 | 判定する者 | 強制の強さ | 例 |
| --- | --- | --- | --- |
| 指示の中で自己検証を求める | 作成役自身 | 弱い。誤った完了をそのまま報告することがある。 | 「認証のテストを実行し、通るまで続ける」 |
| 検証の手順をスキルにする | 手順に従う作成役 | 弱い。手順を省くことがある。 | 画面を操作して前後を撮影し、コンソールの新しいエラーが0件であることを確かめるスキル。 |
| ツールの組み込みの判定（`/goal`） | 判定用のモデル | 中程度。判定用のモデルは会話の内容だけを読み、コマンドを実行しない。 | `/goal test/auth の全てのテストが通り、リントのエラーが0件である` |
| 別のコンテキストの検証役 | 補助エージェント | 中程度。検証役も推論で判定する。 | 差分を `SPEC.md` と照合し、未実装の要件だけを報告する補助エージェント。 |
| Stopフックで検証のコマンドを実行する | フックのスクリプト | 強い。検証が通るまで停止を阻止する。 | `pnpm tsc --noEmit` が失敗する間は、終了コード2で停止を阻止する。 |
| 外側のスクリプトやSDKで検証のコマンドを実行する | ループの外のプログラム | 強い。検証の結果で次の反復を決める。 | `files.txt` のファイルを1件ずつ `claude -p --max-turns 20` に渡し、`OK` か `FAIL` の応答で次へ進む。 |

どの方法でも、「テストは全て通った」という報告だけを信じず、実行したコマンドと出力を証拠として残させる。

### 生成と検証を分ける

作成役が自分の成果物を検証すると、誤りを見逃しやすい。検証役は作成役と別のコンテキストで動かし、既定で不合格とする。検証役には、成果物、完了の条件、検査の出力を必ず渡す。

Anthropicの例では、単独のエージェントは20分と9ドルでゲームの作成ツールを作ったが中心の機能が動かなかった。計画役、作成役、ブラウザーで操作して採点する評価役に分けた構成は、6時間と200ドルを使って動くアプリケーションを作った。

### 主観的な目標は確認できる部分だけを自動化する

読みやすさやデザインのように機械で確認できない目標は、ループで完了を判定しない。確認できる部分だけをループに任せ、残りは人か評価の基準で較正した検証役が判定する。

| 目標 | ループに任せる部分 | 人か検証役が判定する部分 |
| --- | --- | --- |
| 提案書を読みやすくする | 必須の見出しの有無、1文の長さの上限、用語の統一、リンク切れ | 論旨が顧客の課題に答えているか。 |
| 画面のデザインを整える | コントラスト比、コンソールのエラー、画面の幅ごとの表示の崩れ | 全体の印象と独自性。 |

### 揺れのある数値は複数回の計測で比べる

性能やスコアのように、同じ状態でも計測ごとに値が揺れる指標は、1回の計測で比べない。基準を複数回測って中央値と揺れの幅を求め、揺れの幅を超えた差だけを改善とみなす。

たとえば、基準の3回の計測が98、100、102なら、中央値は100、揺れの幅は4%である。変更後の103は+3%で揺れの幅に収まるため再度計測し、110は+10%のため改善として残す。

## 5. 停止条件と予算

### 全ての自律ループに上限を設ける

完了の条件だけでは、条件を満たせない場合にループが止まらない。完了の条件に加えて、次の上限のうち少なくとも1つを設ける。

| 上限 | Claude Code | Codex |
| --- | --- | --- |
| 回数 | 非対話モードの `--max-turns 20`、Agent SDKの `maxTurns`、`/goal` の条件の「20ターンで止める」 | `/goal` の条件の「20ターンで止める」 |
| 費用 | 非対話モードの `--max-budget-usd 5.00`、Agent SDKの `maxBudgetUsd` | `/goal` のトークンの予算 |
| 時間 | 起動スクリプトの終了時刻、ジョブのタイムアウトの30分 | 起動スクリプトの終了時刻、ジョブのタイムアウトの30分 |
| 期間 | セッション内の `/loop` は7日で失効する。 | スケジュールされたタスクを人が停止する。 |

上限に達して止まった場合は、達成できなかったことと現在の状態を人へ通知する。

上限の値は、小さな対象で実行した実績から決める。参考として、Anthropicの報告では、ゲームの作成ツールに6時間と200ドル、音楽の制作ツールに3時間50分と124.70ドルを要した。

### 進まない状態を検出して止める

同じ失敗を繰り返す、残る問題が変わらない、道具を使わずに応答だけを繰り返す状態は、上限を待たずに止める。たとえば、同じエラーの文面が3回続いた時や、未処理の件数が3回の反復で減らない時に止めて、人へ回す。

StopフックでClaude Codeの停止を阻止する場合は、入力の `stop_hook_active` を確認し、同じ理由で阻止を繰り返さないようにする。Claude Codeは、道具の実行を挟まずにStopフックが8回続けて停止を阻止すると、フックを無視して停止する。

### 人がいつでも止められるようにする

ループには、人が即座に止める手段を用意する。`runs/current/STOP` のような停止の印のファイル、スケジュールの取り消し、`/goal clear` のように、エージェントの判断を経ずに効く手段を使う。

### トークンの使用量を管理する

| 対策 | 内容 | 例 |
| --- | --- | --- |
| 作業に合うモデルを選ぶ | 定型の作業は小さく速いモデル、判断を伴う作業は高性能なモデルに任せる。 | 報告の分類はClaude Haiku、修正の方針の判断はClaude Opusに任せる。 |
| 実行の間隔を対象の変化に合わせる | 対象がほとんど変化しない時は、間隔を長くするか、イベントで起動する。 | 週に数件しか届かない問い合わせは、5分ごとに確認せず、受信のイベントで起動する。 |
| 何もない時はすぐ終わる | 処理する項目がない場合は、推論を始めずに終える。 | 未処理の件数をスクリプトで数え、0件ならエージェントを起動しない。 |
| 大きな実行は小さく試す | 多数のエージェントを起動する実行は、一部の対象で試してから広げる。 | 1,000ファイルの移行は、3ファイルで試して指示を直してから全件を流す。 |
| 使用量を確認する | Claude Codeの `/usage`、`/goal` の状態表示で、実行ごとの使用量を確認する。 | 週に1回、ループごとのトークンの量と処理件数を比べる。 |

## 6. 状態と再開

### 状態は会話の外に置く

計画、進捗、未完了の項目、判断の理由は、作業場所のファイル、変更の履歴、課題の管理の仕組みに置く。会話の中だけにある情報は、圧縮やセッションの切り替えで失われる。たとえば、Ralphループは、毎回同じ `PROMPT.md` を渡し、残りの項目を `fix_plan.md` で引き継ぐ。

### 反復ごとのコンテキストの扱いを決める

反復ごとに新しいコンテキストで始めるか、同じセッションを続けるかを決める。

| 方式 | 利点 | 注意点 |
| --- | --- | --- |
| 毎回新しいコンテキストで始める（例：1ファイルずつの移行、1件ずつの問い合わせの処理） | 古い情報や誤った推論を引き継がない。 | 必要な状態を全てファイルから読み直させる。 |
| 同じセッションを続ける（例：1つの不具合の調査、レビューの指摘への対応） | 直前の作業の詳細を使える。 | 長くなると圧縮で情報が失われ、品質が下がる。作業の区切りで新しいセッションへ切り替える。 |

### 状態のファイルを整理する

完了した項目、古い計画、解決済みの問題が状態のファイルに残ると、エージェントが同じ作業を繰り返す。状態のファイルは、完了した項目を移すか削除して整理する。

### 処理が止まっても再開できるようにする

ループの処理は、途中で終了しても同じ状態から再開できるようにする。起動スクリプトは、エージェントが予期せず終了した場合に、セッションIDを使って同じセッションを再開する。外部への操作は、同じ操作を2回実行しても結果が変わらないようにする。

## 7. 並列と競合

### 並列のエージェントは作業場所を分ける

複数のエージェントを並列に動かす場合は、作業場所をエージェントごとに分ける。Claude CodeとCodexは、Gitの作業ツリーで作業場所を分けられる。Anthropicの例では、バグ報告1件に対して3つの修正案を別々の作業ツリーで作り、判定役のエージェントが批判的に比べて選ぶ。

### 同じ対象を複数のループが操作しない

複数のループが同じファイルや項目を操作すると、変更が衝突する。ループは操作の前に、対象を他のループが処理中でないことを確かめ、`in-progress` のラベルのような処理中の印を残す。ループを動かす基盤に同時実行を制限する機能があれば、それを使う。

### ループが自分の出力で再び起動しないようにする

イベント駆動のループは、ループ自身の書き込みや投稿で再び起動しないようにする。起動したユーザーがボットの場合は既定で処理せず、処理するボットを明示する。

## 8. 自律の段階と人の確認点

### 報告だけの段階から始める

新しいループは、次の段階を順に進める。前の段階で、検出の精度と誤りの頻度を一定の期間計測してから、次の段階へ移る。

| 段階 | ループが行うこと | 人が行うこと | 例：バグ報告の仕分け | 次へ進む目安 |
| --- | --- | --- | --- | --- |
| 報告 | 調査し、結果を報告する。成果物は変更しない。 | 報告を読み、対応を決める。 | 分類と担当者の案を一覧にしてSlackへ投稿する。 | 2週間、人が案を直した割合が10%以下である。 |
| 提案 | 変更を作り、検証して提案する。 | 確認し、採用を判断する。 | ラベルを付け、回答の下書きを作る。 | 2週間、人が下書きを大きく直した割合が5%以下である。 |
| 無人の実行 | 変更から反映まで行う。 | 定期的に結果を確認する。 | ラベルの付与と定型の回答の送信まで行う。 | 週に1回、抜き取りで確認する。 |

無人の実行で取り消しが続く場合は、そのループを提案の段階へ戻す。目安の数値は、作業の重要度に合わせて決める。

### 人が理解できる量に出力を保つ

ループが作る変更が、人がレビューできる量を超えると、理解されないまま変更が積み上がる。ループの出力の量を、レビューできる量（例：1日に10件のプルリクエスト）に合わせて制限する。人が一定の期間の変更を説明できない場合は、ループの段階を下げる。

## 9. 型ごとの規則

### ターンベースのループ

検証の手順をスキルに書き、全ての手順を通過するまで完了を報告させない。手順のいずれかが失敗した場合は、修正して最初の手順からやり直させる。指示には、対象、症状、完了の状態を書く。

| 指示の良否 | 例 |
| --- | --- |
| 曖昧 | 「ログインの不具合を直して」 |
| 具体的 | 「セッションの期限切れの後にログインが失敗するという報告がある。`src/auth/` のトークンの更新を調べ、再現するテストを書いてから直す」 |

### ゴールベースのループ

完了の条件には、次の事項を書く。

| 事項 | 例：認証の修正 | 例：月次レポート |
| --- | --- | --- |
| 確認できる1つの終了状態 | `test/auth` の全てのテストが通る。 | 全部門の合計が会計の総額と一致する。 |
| 確認の方法 | `pnpm test test/auth` の終了コードが0である。 | `scripts/reconcile.py` が「不一致0件」と出力する。 |
| 途中で変えてはならないもの | 既存のテストのファイルを変更しない。 | 会計システムの元データを変更しない。 |
| 回数または時間の上限 | 20ターンで止める。 | 10ターンで止める。 |

Claude Codeの `/goal` の判定用のモデルは、会話に表れた内容だけで判定し、コマンドを実行しない。完了の証拠となるコマンドの出力が会話に表れるように、確認の方法を条件に書く。厳密な判定が必要な場合は、Stopフックか外側のスクリプトで検証のコマンドを実行する。

### 時間ベースのループ

実行の場所と、端末の状態への依存を確かめて選ぶ。

| 実行の場所 | 端末の電源 | ローカルのファイル | 用途 |
| --- | --- | --- | --- |
| セッション内（Claude Codeの `/loop`） | 必要。セッションを開いておく。 | 使える。 | 作業中の短い確認（例：`/loop 15m` でCIの結果を確認し、失敗なら直す） |
| 端末のアプリ（Claude Codeのデスクトップアプリ、Codexのアプリ） | 必要。アプリを起動しておく。 | 使える。 | ローカルの環境が必要な定期作業（例：毎朝9時に手元のフォルダの請求書を集計する） |
| クラウド（Claude Codeのクラウドのスケジュールされたタスク、GitHub Actions） | 不要 | 使えない。毎回作業場所を取得し直す。 | 端末に依存しない定期作業（例：毎晩、依存関係の更新を確かめて提案する） |

間隔は、対象が変化する頻度に合わせる。外部の処理の完了や返答を待つ場合は、イベントで起動する方法を優先する。

### イベント駆動のループ

イベントごとに、1つの作業と、その完了の条件を対応させる。同じイベントが短時間に大量に届いた場合に備えて、処理する件数の上限を決める。

| イベント | 作業 | 完了の条件 | 上限 |
| --- | --- | --- | --- |
| プルリクエストの作成 | 仕様と照合してレビューする。 | 指摘をコメントするか、指摘なしと報告する。 | 1件あたり10ターン |
| 問い合わせの到着 | 分類し、FAQから回答の下書きを作る。 | ラベルと、出典付きの下書きがある。 | 1時間に50件 |
| 請求書のファイルの追加 | 項目を抽出して台帳へ転記する。 | 合計が請求書の金額と一致する。 | 1日に200件 |

### 期限付きの最適化のループ

評価で数値を測れる目標を、終了時刻まで改善し続ける場合は、次の仕組みを用意する。[エージェントハーネス](../../templates/agent-harness/README.md)のテンプレートは、これらをClaude CodeとCodexの両方で実装している。

| 仕組み | 内容 |
| --- | --- |
| 条件書 | 目標、評価の方法、環境、禁止事項、最終状態の要件を、実行ごとの文書に書く（例：`CONDITIONS.md`）。 |
| 評価のCLI | 評価、記録、環境の反映と復元を1つのCLIにまとめ、エージェントはCLIを通してだけ環境を操作する。 |
| 判定 | 基準を3回測り、揺れの幅と5%の大きい方を超えた改善だけを残す。改善しない変更は、成果物に加えてデータや設定も含めて元に戻す。 |
| 継続 | Stopフックで終了時刻までの停止を阻止し、エージェントが終了した場合は起動スクリプトが同じセッションを再開する。 |
| 通知 | 最高の結果が30分更新されない時と、最終段階に入った時に、フックで状態を伝える。 |
| 最終段階 | 終了時刻の40分前から新しい改善を始めず、最良の状態へ戻し、再起動後の状態と評価を確かめる。 |
| 強制終了 | 終了時刻を過ぎたら、起動スクリプトがエージェントと評価の処理を止める。 |

## 10. 記録と改善

### 反復ごとに記録を残す

反復ごとに、実行のID、開始と終了の時刻、対象、結果、検証の出力、人へ引き継いだ件数、使用したトークンの量を記録する。

| 項目 | 例 |
| --- | --- |
| 実行のID | `2026-11-04-0900` |
| 対象と結果 | バグ報告 #4217、`routed` |
| 検証の出力 | `labels ok, assignee ok` |
| 人へ引き継いだ件数 | 3件 |
| トークンの量 | 42,000 |

### 失敗をハーネスとループの改善につなげる

ループが止まらなかった、誤った結果で止まった、同じ失敗を繰り返した場合は、記録から原因を特定し、停止条件、検証、ハーネスの構成要素のいずれかを変更する。ハーネスの構成要素の変更は、[ハーネスエンジニアリングガイドライン](harness-engineering-guidelines.md)の9章による。

新しいループは、本番と同じ形の小さな対象（例：1,000ファイルのうちの3ファイル）で予行し、止まる位置とやり過ぎる位置を確かめてから広げる。

---

## 11. チェックリスト

- トリガー、作業の単位、状態、検証、停止条件、人の確認点、記録を全て決め、文書に書いた。
- 完了の条件を、終了コード、数値、件数で確認できる形にした。
- 無人で動かすループで、外側から強制する検証を使っている。
- 生成と検証を別のコンテキストに分け、検証役に検査の出力を渡している。
- 回数、費用、時間のうち少なくとも1つの上限があり、上限で止まった時に人へ通知する。
- 進まない状態を検出して止め、人がいつでも止められる。
- 状態を会話の外に置き、途中で止まっても再開できる。
- 並列のエージェントが作業場所を分け、同じ対象を同時に操作しない。
- 報告の段階から始めている。
