# LLMアプリケーション設計ガイドライン

## 1 はじめに

### 1.1 目的

本書の目的は、LLMを組み込んだ機能、特にエージェント型の機能を、品質、応答の速さ、安全性及び費用を管理しながら設計し、運用するための判断基準を共有することである。

### 1.2 適用範囲

本書は、製品の機能としてLLMを呼び出すアプリケーションの構成、ツール、プロンプト、検索拡張生成、安全性、及び評価と監視を含む運用（LLMOps）について規定する。

開発の作業にAIエージェントを使う仕組みは、[ハーネスエンジニアリングガイドライン](harness-engineering-guidelines.md)による。画像を入力とする処理の構成は、[画像AI処理設計ガイドライン](../architecture/image-ai-pipeline-guidelines.md)による。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| LLM（large language model、大規模言語モデル） | 大量の文章を学習し、文章の生成又は分析を行うモデル。 |
| プロンプト | LLMへ渡す指示、例及び入力の全体。 |
| ツール | LLMが呼び出しを要求し、アプリケーションが実行する関数又はAPI。 |
| ワークフロー | LLMの呼出しとツールの実行を、あらかじめ決めた順序で組み合わせた処理。 |
| エージェント | LLMが自ら次の行動を選び、ツールの実行と結果の観察を繰り返して目的を達成する処理。 |
| RAG（Retrieval-Augmented Generation、検索拡張生成） | 質問に関係する資料を検索し、プロンプトに加えて生成させる方式。 |
| 埋め込み | 文章の意味を数値のベクトルで表したもの。 |
| 構造化出力 | 指定したスキーマに従う形式でLLMに出力させること。 |
| プロンプトインジェクション | 入力又は取得した資料に含まれる文章によって、LLMに意図しない動作をさせる攻撃。 |
| 評価セット | 入力と、期待する出力又は採点の基準とを組にした、品質の測定用のデータ。 |
| トレース | 一つの要求で行ったLLMの呼出し、ツールの実行及びその入出力の記録。 |
| MCP（Model Context Protocol） | AIアプリケーションと外部のツール又はデータを接続するための通信規約。 |

## 2 構成の選択

### 2.1 最も単純な構成から始める

構成は、[表2](#table-2)の上の行から順に検討し、評価セットで目標を満たす最も単純な構成を選ぶ。構成が複雑になるほど、LLMの呼出しが増え、応答の遅延、費用及び失敗の箇所が増える。

<a id="table-2"></a>表2−構成の選択

| 構成 | 適する処理 | 例 |
| --- | --- | --- |
| LLMを使わない処理 | 規則で判定できる処理、計算、形式の変換 | 入力の検証、合計の計算、日付の整形 |
| 1回のLLMの呼出し | 一つの入力から一つの出力を作る処理 | 分類、要約、情報の抽出、翻訳 |
| 検索又はツールを伴う1回の呼出し | 外部の資料又は最新のデータが必要な処理 | 社内文書に基づく回答 |
| ワークフロー | 手順が決まっている複数の段階の処理 | 抽出した結果を検証してから文書を生成する。問合せの種類で処理を振り分ける。 |
| エージェント | 必要な手順の数と順序を事前に決められない処理 | 調査、複数のシステムを横断する操作 |
| 複数のエージェント | 独立して並行に進められる大きな処理 | 多数の資料の並行調査 |

### 2.2 モデルを選ぶ

最初は最も能力の高いモデルで評価セットの目標を満たす構成を作り、その後、より小さく速いモデルで同じ評価を行う。目標を満たす中で、応答の遅延と費用が最も小さいモデルを選ぶ。処理の段階ごとに異なるモデルを使ってもよい。

モデルは、別名ではなく、版を固定した識別子で指定する。別名は、提供元の更新で指すモデルが変わり、評価していないモデルで動作する。

## 3 応答の速さ

利用者が体感する遅延を小さくするため、次による。

- 生成した文章は、逐次表示する。利用者が最初の文字を見るまでの時間が、全体の生成時間より短くなる。

- 変わらない指示、資料及びツールの定義をプロンプトの先頭に置き、プロンプトキャッシュを使う。キャッシュされた部分は、処理時間と費用が減る。

- 独立したLLMの呼出し及びツールの実行は、並列に行う。

- 出力の長さに上限を設け、必要な分だけを生成させる。

- 結果を待たなくてよい処理は、非同期のジョブにし、急がない大量の処理はバッチAPIを使う。

- 利用者の操作を待たせる処理には、タイムアウトを設け、超えた場合の代わりの応答を用意する。

## 4 エージェント型の機能

### 4.1 ツールを設計する

ツールは、次によって設計する。

- ツールの数を、目的に必要な範囲に絞る。似た機能のツールが複数あると、LLMが選択を誤る。

- 名前と説明に、何をするツールで、いつ使うかを書く。

- 入力は、スキーマで型と値の範囲を定義する。

- 出力は、LLMが次の判断に必要な情報だけを、短く返す。大量の結果は、絞込み又はページ送りで返す。

- エラーは、LLMが次に取るべき行動が分かる文で返す。

- 書込みを行うツールは、べき等にする。

複数のアプリケーションでツールを共有する場合は、MCPで提供する。

### 4.2 権限を利用者の範囲に限る

エージェントが実行するツールには、操作している利用者の権限を適用する。サービス全体の権限でツールを実行すると、利用者が本来できない操作をエージェント経由で実行できる。

### 4.3 取り消せない操作は人が承認する

メールの送信、決済、データの削除、外部への公開など、取り消せない操作又は外部へ影響する操作は、実行する内容を利用者に示し、承認を得てから実行する。

### 4.4 上限を設ける

エージェントの1回の実行には、LLMの呼出しの回数、トークン数、実行時間及び費用の上限を設ける。上限に達した場合は、そこまでの結果と停止の理由を利用者に示す。

### 4.5 実行の状態を保存する

数十秒を超えるエージェントの実行は、非同期のジョブにし、実行の状態と途中の結果を保存する。保存すれば、接続が切れても再開でき、利用者は進捗を確認できる。

### 4.6 実行の過程を示す

エージェントの実行中は、実行している段階、使ったツール及び参照した資料を利用者に示し、いつでも中止できるようにする。回答には、根拠とした資料への参照を付ける。

## 5 プロンプトと出力

### 5.1 プロンプトをコードと同じく管理する

プロンプトは、ソースコードの中に散在させず、版を付けてリポジトリで管理し、変更はレビューと評価を経て反映する。プロンプトの変更は、コードの変更と同じく、機能の振る舞いを変える。

### 5.2 構造化出力を使う

プログラムで処理する出力は、構造化出力でスキーマを指定し、受け取った後もスキーマで検証する。自由な文章から値を取り出す処理は、形式の揺れで失敗する。

### 5.3 LLMの出力を信頼できない入力として扱う

LLMの出力は、外部からの入力と同じく扱い、HTMLへの埋込みではエスケープし、データベースの問合せではパラメーターとして渡し、コマンドとして実行しない。

## 6 RAG

RAGは、次によって設計する。

- 資料は、見出し、段落など文書の構造に沿って分割する。

- 検索は、キーワードによる検索と埋め込みによる検索を組み合わせ、上位の候補を並べ替えてからプロンプトに加える。

- 検索の時点で、利用者が閲覧できる資料だけに絞り込む。生成の後に絞り込んでも、閲覧できない資料の内容が回答に混ざる。

- 検索の精度と、生成の品質とを、別々に評価する。

- 資料の更新と削除を、索引へ反映する。

## 7 安全性

### 7.1 OWASP Top 10 for LLM Applicationsに従う

LLMアプリケーションのセキュリティは、OWASP Top 10 for LLM Applicationsの各項目への対策を確認する。

### 7.2 プロンプトインジェクションを前提にする

利用者の入力、Webページ、文書、メール及びツールの結果に含まれる文章は、LLMへの指示として働く可能性がある。システムプロンプトの指示だけでは、これを防げない。外部の文章を読むエージェントには、次の三つを同時に持たせない。

- 非公開のデータへのアクセス

- 信頼できない外部の文章の読込み

- 外部への送信の手段

三つが必要な場合は、外部への送信に利用者の承認を必須にする。

### 7.3 機密情報を守る

- APIキー、パスワードなどの機密情報を、プロンプトに含めない。

- システムプロンプトの内容は、利用者に漏れることを前提に書く。

- 処理に不要な個人情報は、LLMへ送る前に除くか置き換える。

- 外部のLLMサービスのデータの保存期間、学習への利用の有無及び処理する地域を確認する。

- プロンプトと出力を記録する場合は、個人情報を含むものとして、閲覧の権限と保存期間を限る。

### 7.4 費用の悪用を防ぐ

利用者ごとに、要求の頻度とトークン数の上限を設ける。上限がなければ、一人の利用者の大量の要求で費用が急増する。

## 8 LLMOps

### 8.1 評価

評価は、次によって行う。

- 機能の成功の基準を、正答率、形式の適合率、遅延、費用など、測定できる指標と目標値で決める。

- 評価セットは、実際の利用で想定する入力の分布に、境界の事例と攻撃的な入力を加えて作る。

- 採点は、コードで判定できるものはコードで行う。コードで判定できないものは、人の採点と照合して較正したLLMによる採点を使う。

- プロンプト、モデル、ツール又は検索の設定を変更するたびに、CIで評価を実行し、基準の結果と比べる。

- LLMの出力は同じ入力でも揺れるため、評価は複数回実行して比べる。

### 8.2 版の記録

要求ごとに、モデルの識別子、プロンプトの版、生成の設定、ツールの定義の版及び検索の索引の版を記録する。記録がなければ、品質が変わった原因を特定できない。

### 8.3 トレース

LLMの呼出しとツールの実行ごとに、入力、出力、トークン数、遅延、費用及びエラーをトレースとして記録する。トレースは、OpenTelemetryの生成AIの規約に沿った属性で出力する。

### 8.4 本番での監視

本番では、次を監視する。

- 遅延、エラー率、トークン数及び費用

- 利用者の評価、再生成及び訂正の頻度

- 抽出した一部の要求に対する、人又はLLMによる品質の確認

費用又はエラー率が急増した場合は、通知する。

### 8.5 変更の展開

プロンプト及びモデルの変更は、機能フラグで一部の利用者から展開し、指標を確認してから全体へ広げる。指標が悪化した場合は、すぐに戻せるようにする。

### 8.6 モデルの提供終了に備える

提供元のモデルの提供終了の予定を確認し、終了の前に後継のモデルで評価を行ってから移行する。主要な提供元が停止した場合に備え、代わりのモデル又は提供元への切替えを用意する。

## 9 チェックリスト

- [表2](#table-2)で、評価の目標を満たす最も単純な構成を選んでいる。

- モデルを、版を固定した識別子で指定している。

- 生成した文章を逐次表示し、プロンプトキャッシュを使っている。

- ツールの数が目的に必要な範囲に絞られ、名前と説明から用途が分かる。

- ツールを、利用者の権限で実行している。

- 取り消せない操作の前に、利用者の承認を得ている。

- エージェントの実行に、回数、トークン数、時間及び費用の上限がある。

- プロンプトに版があり、リポジトリで管理されている。

- LLMの出力を、スキーマで検証し、信頼できない入力として扱っている。

- RAGの検索で、利用者が閲覧できる資料だけに絞り込んでいる。

- 非公開のデータ、信頼できない文章及び外部への送信の三つを、承認なしに同時に持たせていない。

- 評価セットがあり、変更のたびにCIで評価している。

- 要求ごとに、モデル、プロンプト及び設定の版と、トレースを記録している。

- 利用者ごとに、要求の頻度とトークン数の上限がある。
