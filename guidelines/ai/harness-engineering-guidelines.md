# ハーネスエンジニアリングガイドライン

## 1 はじめに

### 1.1 目的

この文書は、AIエージェントの作業における、自律的なタスク実行及び出力品質の安定化を目的とする。

### 1.2 適用範囲

この文書は、AIエージェントに作業を任せるための指示、ツール、検査及び実行制御について規定する。

この文書は、Claude Code、CodexなどのAIエージェントを対話又は無人で実行する場合に適用する。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| LLM（large language model、大規模言語モデル） | 大量の文章を学習し、文章の生成又は分析を行うモデル。 |
| MCP（Model Context Protocol） | AIアプリケーションと外部のツール又はデータを接続するための通信規約。 |
| コンテキスト | モデルが応答を生成する際に参照する指示、会話及びツールの出力などの情報。 |
| フック | 指定したイベントの発生時に処理を実行する仕組み。 |
| ハーネス | モデルの外側で、エージェントに与える指示、ツール、検査、記録及び実行の制御の仕組みの全体。この文書では、ツールの提供者が組み込んだ部分を除き、利用者が追加する部分を指す。 |
| リポジトリ | エージェントが読み書きするファイル及び変更履歴を管理する場所。プロジェクト指示、スキル及び設定もここに置く。 |
| 成果物 | エージェントが作成する文書、データ、プログラム、設定などの作業の結果。 |
| ガイド | エージェントが行動する前に、望ましい行動へ誘導する仕組み。プロジェクト指示、スキル、ひな形などがある。 |
| センサー | エージェントが行動した後に、成果物を検査して修正を促す仕組み。検査のスクリプト、レビューを行うエージェントなどがある。 |
| 決定論的な検査 | 形式、表記、数値、参照先の存在の確認のように、同じ入力に同じ結果を返す検査。 |
| 非決定論的な検査 | LLMによるレビュー又は評価のように、モデルの判断に基づく検査。 |
| トークン | モデルが入力及び出力を処理するために文章を区切る単位。 |
| ループ | 停止条件を満たすまで、エージェントが計画、実行、観察及び検証を繰り返す制御の単位。 |
| トリガー | ループの1回の実行を開始するきっかけ。人の指示、時刻及び外部のイベントがある。 |
| 停止条件 | ループを終了する条件。完了の条件、及び上限又は異常による打切りの条件からなる。 |
| 生成エージェント | 成果物を作成するエージェント。 |
| 評価エージェント | 生成エージェントとは別のコンテキストで、成果物が完了の条件を満たすかを評価するエージェント。 |
| 状態 | 反復の間で引き継ぐ、計画、進捗及び判断の記録。 |

## 2 指示及び検査の設計原則

### 2.1 エージェントの失敗はハーネスの不足として扱う

エージェントが誤った手順を使用する、規約に反する、確認を省くといった失敗をした場合は、その場で修正を指示するだけで終了しない。同じ失敗が再び発生しないように、指示、ツール又は検査のいずれかを変更する。

失敗が繰り返される場合は、エージェントに不足しているツール、規則、ひな形又は資料を特定し、リポジトリへ追加する。

失敗ごとのハーネスの変更は、[表2](#table-2)による。

<a id="table-2"></a>表2−失敗ごとのハーネスの変更

| 発生した失敗 | 変更 |
| --- | --- |
| pnpmのプロジェクトで `npm install` を実行した。 | プロジェクト指示に“パッケージの操作はpnpmで行う”と書く。 |
| 月次レポートの売上を税込で集計した。 | プロジェクト指示に“売上は税抜で集計する”と書き、会計システムの総額と照合する検査を加える。 |
| 画面の変更で、表示を確認せずに完了と報告した。 | 開発サーバーを起動して画面を撮影する手順をスキルにする。 |

### 2.2 守らせる規則は仕組みで強制する

実行を保証する必要がある規則は、フック及び検査で強制する。プロジェクト指示又はスキルに書いた要求だけでは、実行したことを確認できないためである。

規則の種類ごとの置き場所は、[表3](#table-3)による。

<a id="table-3"></a>表3−規則の種類ごとの置き場所

| 規則の種類 | 置き場所 |
| --- | --- |
| 判断の目安<br>手順<br>規約の意図（例：見積書は結論から書く） | プロジェクト指示<br>スキル |
| 毎回同じ処理を実行する（例：ファイルの変更後に `prettier --write` を実行する） | フック |
| 成果物が規約を満たしていることを確認する（例：`tsc --noEmit` が通るまで完了にしない） | 検査 |

指示の文面を強めても守られない規則は、フック又は検査へ移す。逆に、好みにすぎないフックは削除し、エージェントの判断に任せる。

### 2.3 ガイドとセンサーとを組み合わせる

各規則には、事前に実施方法を伝えるガイド及び事後に結果を検査するセンサーを用意する。両方を組み合わせ、作業前に手順を示すとともに、実施後の違反を検出する。

ガイド及びセンサーの例は、[表4](#table-4)による。

<a id="table-4"></a>表4−ガイド及びセンサーの例

| 規則 | ガイド | センサー |
| --- | --- | --- |
| エラーのログにリクエストIDを含める。 | プロジェクト指示にログの書き方を書く。 | エラーのログの呼出しを検査し、違反をファイル及び行で報告するスクリプト。 |
| 列を削除するデータ移行には、データの移し替えの手順を含める。 | 移行の手順をスキルにする。 | 列の削除だけを含む移行を不合格にする検査。 |
| 見積書に、前提条件、範囲、金額、有効期限の4項目を含める。 | 見積書のひな形を置く。 | 4項目の見出しの有無を確認するスクリプト。 |

### 2.4 決定論的な検査を優先する

検査は、同じ入力に同じ結果を返す決定論的な方法を優先する。結果の比較が容易であり、形式又は数値の違反を繰り返し検出することが可能になる。意味の判断を要する箇所には、その後にLLMなどによる非決定論的な検査を使用する。

例えば、提案書の必須の見出しの有無及びリンク切れは決定論的な検査で確認し、論旨が顧客の課題に答えているかは非決定論的な検査で確認する。

### 2.5 小さく開始し、失敗を確認してから追加する

最初は、プロジェクト指示及び合否を返す検査コマンドを一つ用意する。その後は、実際に発生した失敗の原因に対応する構成要素を補い、効果を検証する。

### 2.6 モデルの能力に合わせて見直す

ハーネスの構成要素は、モデルが単独ではできないことを補うために置く。新しいモデルへ切り替えた場合は、各構成要素を外した場合の結果を確認し、効果のなくなった構成要素を取り除く。

Anthropicのアプリケーション開発のハーネスでは、Claude Sonnet 4.5で必要だったコンテキストのリセットをClaude Opus 4.5で廃止し、スプリント単位の分割及び評価をClaude Opus 4.6で廃止して、計画エージェント及び最後に1回だけ実行する評価エージェントを残した。

## 3 構成要素の選び方

### 3.1 目的に合う構成要素を選ぶ

構成要素は、作業に必要な情報を必要な時点で渡す方式から選ぶ。常に読み込む情報は全ての作業の費用及び精度に影響するため、特定の作業だけで必要な情報は、その作業を開始するときに読み込む。

構成要素は、[表5](#table-5)による。

<a id="table-5"></a>表5−構成要素

| 構成要素 | 目的 | コンテキストへの影響 | Claude Code | Codex |
| --- | --- | --- | --- | --- |
| プロジェクト指示 | 全ての作業で必要な事実及び規則を伝える。 | 常に入る。 | `CLAUDE.md`。`AGENTS.md` も読み込める。 | `AGENTS.md`<br>`AGENTS.override.md` |
| 範囲を限定した指示 | 特定のディレクトリ又はファイルの種類だけに適用する規則を伝える。 | 該当する範囲で入る。 | `.claude/rules/*.md`（`paths` で対象を限定する）、サブディレクトリの `CLAUDE.md` | サブディレクトリの `AGENTS.md` |
| スキル | 手順、参照資料及び確認の方法を必要な場合に読み込む。 | 説明だけが常に入り、本体は使用する場合に入る。 | `.claude/skills/<名前>/SKILL.md` | `.agents/skills/<名前>/SKILL.md` |
| サブエージェント | 独立したコンテキストで作業させ、要約だけを受け取る。 | 主のコンテキストには結果だけが入る。 | `.claude/agents/*.md` | `.codex/agents/*.toml` |
| 外部のツール | 外部のサービス又はデータへ接続する。 | ツールの名前及び説明が入る。 | MCPサーバー | MCPサーバー |
| フック | 定めた時点で処理を必ず実行する。 | 出力を返した場合だけ入る。 | `.claude/settings.json` の `hooks` | `.codex/hooks.json` |
| 検査 | 成果物を検査し、修正を促す。 | 失敗の出力だけが入る。 | フック又は定期的な処理から実行する。 | フック又は定期的な処理から実行する。 |

実行の起動、反復及び停止の仕組みは、[9章](#9-ループの設計)による。

[表6](#table-6)のきっかけが発生した場合に、対応する構成要素を追加する。

<a id="table-6"></a>表6−構成要素を追加するきっかけ

## 4 プロジェクト指示

### 4.1 プロジェクト指示は目次として短く保つ

プロジェクト指示は、全ての作業でコンテキストを占めるため、詳細を書かず、詳細な文書への道順を示す目次とする。1ファイルあたり200行以内を目安にする。CodexはAGENTS.mdの合計が既定で32KiBを超えると、それ以降を読み込まない。

### 4.2 全ての作業で必要な事実だけを書く

プロジェクト指示には、[表7](#table-7)の事項を書く。

<a id="table-7"></a>表7−プロジェクト指示に書く事項

| 書く事項 | 例 |
| --- | --- |
| 結果の確認方法 | “1ファイルのテストは `pnpm test <ファイル>`、全体は `pnpm test` で実行する” |
| 読むと誤解する箇所 | “`legacy/` の書き方は新しいコードで真似しない”“`archive/` は使われていないように見えるが、月次の集計が参照している” |
| リポジトリから読み取れない決定 | “エラーの処理は `AppError` に統一すると決めた”“売上は税抜で集計する” |
| 2回訂正した事項 | “金額は3桁ごとにカンマで区切る” |

ファイルの一覧又は一般的な言語の規約のように、読めば分かることは書かない。書く前に、エージェントが読んで検出できるか、実際に参照するかを確認し、どちらも当てはまる場合は書かない。

一部の範囲だけに適用する規則は範囲を限定した指示へ、複数の手順からなる作業はスキルへ分ける。

### 4.3 両ツールで共有する指示はAGENTS.mdに書く

Claude Code及びCodexの両方で使用するリポジトリでは、プロジェクト指示を `AGENTS.md` に書き、`CLAUDE.md` からは `@AGENTS.md` で取り込む。同じ内容を二つのファイルに書くと、片方だけが更新されて矛盾する。

### 4.4 知識はリポジトリに置く

判断の経緯、規約、計画及び仕様は、変更履歴を管理する文書としてリポジトリに配置し、プロジェクト指示から参照する。会話だけで共有した事項又は接続していない文書ツールにある事項も、作業時に参照可能になる。

### 4.5 矛盾及び古い記述を取り除く

プロジェクト指示、範囲を限定した指示及びスキルを定期的に見直し、矛盾及び古い記述を修正する。作業の種類によって適用される指示が変化する場合も、判断の不一致を防ぐ。

## 5 スキル及びサブエージェント

### 5.1 繰り返す手順をスキルにする

複数の手順からなる作業、参照資料及びチームの基準は、スキルにする。スキルの説明には、どの作業で使用するかを具体的に書く。説明が曖昧だと、エージェントは必要なスキルを使用しないか、誤ったスキルを使用する。

スキルの説明の例は、[表8](#table-8)による。

<a id="table-8"></a>表8−スキルの説明の例

| 説明の良否 | 例 |
| --- | --- |
| 曖昧 | “レポートを助ける” |
| 具体的 | “月次売上レポートを作成又は更新する場合に使用する。部門別の集計、会計システムの総額との照合、前月比の算出の手順を含む” |

### 5.2 確認の手順をスキルにする

作業の完了前に行う確認を、手順としてスキルに書く。確認の手順には、実行するコマンド、確認する結果及び失敗した場合の対応を書き、全ての手順を通過するまで完了を報告させない。完了の報告には、実行したコマンド及び出力を証拠として含めさせる。

確認のスキルの例は、[表9](#table-9)による。

<a id="table-9"></a>表9−確認のスキルの例

| スキル | 手順 |
| --- | --- |
| `verify-frontend-change` | 開発サーバーを起動する。変更した操作を実行し、操作の前後の画面を撮影する。コンソールの新しいエラーが0件であることを確認する。Core Web Vitalsを計測する。失敗した場合は修正し、最初の手順から再試行する。 |
| `verify-log-hygiene` | エラーの処理のログにリクエストIDがあり、リクエストの本文を含まないことを確認する。違反をファイル及び行で報告し、修正する。 |
| `verify-monthly-report` | 全部門の行があることを確認する。部門の合計と会計システムの総額とが1円単位で一致することを確認する。前月比の計算を再計算して照合する。不一致の部門及び差額を報告する。 |

### 5.3 大量の読み込み及び独立した作業はサブエージェントへ渡す

多数のファイルの調査、記録の分析及び独立した部分の作業は、サブエージェントへ渡し、主のコンテキストには要約だけを戻す。

例えば、Anthropicのマーケティングのチームは、数百件の広告のCSVから成果の悪い広告を検出するサブエージェントと、文字数の制限の中で広告文の案を作成するサブエージェントとに分けている。

### 5.4 生成及び評価を別のコンテキストに分ける

エージェントは、自分が作成した成果物を甘く評価する。成果物の評価は、生成したコンテキストとは別のサブエージェントに行わせる。評価エージェントには、生成の経緯ではなく、成果物、評価の基準及び検査の出力を渡す。完了の条件を満たす証拠がある場合だけ合格と判定する。

Anthropicの例では、単独のエージェントは20分及び9ドルでゲームの作成ツールを作成したが、中心の機能が動作しなかった。計画エージェント、生成エージェント及びブラウザーで操作して採点する評価エージェントに分けた構成は、6時間及び200ドルを使用して、動作するアプリケーションを作成した。

評価エージェントが甘い判定をする場合は、評価の記録を読み、人の判断と異なる箇所を手順及び基準へ反映する。主観的な基準には、点数の内訳を付けた評価の例を与える。

評価の基準は、項目及び合格のしきい値で書き、一つでもしきい値を下回る場合は差し戻す。Anthropicは、画面のデザインの評価エージェントに[表10](#table-10)の項目を使用し、モデルが既定で苦手な上の2項目の重みを高くした。

<a id="table-10"></a>表10−デザインの評価の項目

| 項目 | 確認すること |
| --- | --- |
| デザインの質 | 全体が一貫した印象を持つまとまりになっているか。 |
| 独自性 | ひな形のままではなく、意図した選択の跡があるか。 |
| 作り込み | 文字の組み方、余白、配色及びコントラストが整っているか。 |
| 機能性 | 利用者が操作を理解し、目的を達成できるか。 |

レビューを依頼されたエージェントは、問題を必ず何か検出しようとする。依頼では対象を絞り、例えば“差分を `SPEC.md` と照合し、未実装の要件と、挙げた例外の処理の漏れだけを報告する。書き方の好みは報告しない”と指示する。

### 5.5 サブエージェントのツールを役割に合わせて選ぶ

調査又は評価を行うサブエージェントには、読み取りのツールだけを与える。書き込みが必要なサブエージェントを並列に実行する場合は、作業ディレクトリを分ける。

## 6 エージェントが使用するツール及び環境

### 6.1 エージェントが自分で結果を確認できるようにする

エージェントが成果物を確認するためのツールを用意し、プロジェクト指示又はスキルで使用方法を示す。

結果の確認に用いるツールは、[表11](#table-11)による。

<a id="table-11"></a>表11−結果の確認に用いるツール

| ツール | 例 |
| --- | --- |
| 変更した部分だけを検査するコマンド | `pnpm test src/auth/session.test.ts`、`markdownlint docs/pricing.md` |
| 成果物を実際に使用して確認する手段 | Playwrightで画面を操作して撮影する。生成したPDFを画像にして確認する。SQLで移行後の件数を集計する。 |
| 実行の記録を検索する手段 | 直近1時間のエラーのログを、リクエストIDで検索するコマンド。 |

### 6.2 環境の準備を一つのコマンドにする

ツールの導入、データの準備及び実行環境の起動は、`./init.sh` のような一つのコマンドで実行できるようにする。エージェントが準備の方法を毎回調査すると、時間を浪費し、準備の誤りが作業の誤りに見える。

### 6.3 ツールの出力をエージェントが読める形にする

ツールの出力は、必要な情報だけを短く返す。エラーの出力には、違反した規則及び修正の方法を含める。長い出力はファイルへ保存し、要約及び保存先を返す。

ツールの出力の例は、[表12](#table-12)による。

<a id="table-12"></a>表12−ツールの出力の例

| 出力の良否 | 例 |
| --- | --- |
| 修正できない | `check failed` |
| 修正できる | `reports/2026-10.md:12 営業部の合計が会計の総額と1 200円一致しない。data/ledger.csv の10月分から再集計する。` |

### 6.4 ツールの数及び重複を抑える

役割が重なるツールが多いと、エージェントは使用するツールを誤る。ツールは役割が重ならないように選び、使用しない外部のツールは接続しない。

### 6.5 広く使われていて資料のそろったツールを選ぶ

エージェントが扱うツール、形式及びライブラリは、広く使われていて、資料がそろい、挙動を説明できるものを選ぶ。

## 7 検査

### 7.1 速い検査は変更のたびに実行する

成果物の形式、表記、参照先及び数値の整合を確認する速い検査は、ファイルの変更後のフックで実行し、結果をエージェントへ返す。

成果物ごとの検査は、[表13](#table-13)による。

<a id="table-13"></a>表13−成果物ごとの検査

| 成果物 | 速い検査 | 重い検査 |
| --- | --- | --- |
| プログラム | フォーマッター<br>ESLint<br>`tsc --noEmit`<br>変更したファイルのテスト | 全てのテスト<br>ミューテーションテスト<br>依存の方向の検査 |
| 文書 | markdownlint<br>リンク切れ<br>用語の表記の検査 | 全文書の用語の統一<br>仕様との照合<br>評価エージェントのレビュー |
| データ | スキーマの検証<br>必須の項目の欠損の検査 | 移行元との件数及び合計の照合、重複の検査 |
| 集計レポート | 全部門の行の有無<br>合計の再計算 | 会計システムの総額との照合<br>前月比の異常値の確認 |

### 7.2 重い検査は区切りで実行する

成果物の全体を対象とする検査、及び時間のかかる検査は、作業の区切り又は定期的な処理で実行する。区切りの検査では、速い検査も再度実行する。

### 7.3 構成の規則を検査で強制する

成果物の構成、命名、大きさ、書式などの規則は、検査のスクリプトで確認する。検査の失敗の出力には、修正の方法を含め、エージェントが出力だけで修正できるようにする。例えば、OpenAIのチームは、層の間の依存の方向、ログの形式及びファイルの大きさをリンター及び構造のテストで検査し、エラーの文面に修正の方法を書いている。

### 7.4 劣化を継続的に検出する

使われなくなった資料、重複、古くなった記述、成果物の間の不一致及びリンク切れは、定期的に検出する。検出した項目は、範囲を絞った修正として、エージェントに定期的に修正させる。OpenAIのチームは、週の20%を使用していた金曜日の整理作業を、基準からの逸脱を検出して修正を提案する定期的なエージェントへ移した。

### 7.5 非決定論的な検査は基準で較正する

LLMによるレビュー又は評価を検査に使用する場合は、評価の基準、合格のしきい値（例：各項目を5段階で評価し、全項目が4以上で合格）及び評価の例を与える。非決定論的な検査の結果は、決定論的な検査の結果を上書きしない。

## 8 状態の引き継ぎ及び再開

### 8.1 進捗はコンテキストの外に残す

長い作業では、コンテキストの圧縮又はセッションの切り替えで、それまでの経緯が失われる。作業の計画、進捗、未完了の項目及び判断の理由は、リポジトリのファイル、変更履歴又は課題トラッカーへ残す。例えば、Ralphループは、毎回同じ `PROMPT.md` を渡し、残りの項目を `fix_plan.md` で引き継ぐ。

進捗を残すファイルは、[表14](#table-14)による。

<a id="table-14"></a>表14−進捗を残すファイル

| ファイル | 内容 |
| --- | --- |
| `SPEC.md` | 完了の定義。人とエージェントとの間で合意した要件及び例外。 |
| `progress.md` | 各セッションの終了時に追記する、実施した事項、次に実施する事項及び判断の理由。 |
| `items.json` | 項目ごとの完了の状態。 |
| `init.sh` | 環境を準備し、基本の動作を確認するスクリプト。 |

### 8.2 機械が更新する状態は構造化した形式にする

完了した項目の一覧のように、エージェントが更新する状態は、JSONなどの構造化した形式で保存し、更新してよい項目を限定する。自由な文章の形式では、エージェントが項目を書き換える、又は削除する場合がある。

Anthropicのアプリケーション開発の例では、200件を超える機能を、分類、説明、確認の手順、`passes` の4項目で一覧にし、全てを `passes: false` で開始して、エージェントには `passes` だけを更新させた。

### 8.3 セッションの開始時に状態を読み込ませる

セッションの開始時には、作業ディレクトリ、変更履歴、進捗のファイル及び未完了の項目を確認させる。フックで、セッションの開始時及び圧縮の後に、現在の状態をコンテキストへ加える。Anthropicの例では、作業ディレクトリの確認、`git log` 及び進捗のファイルの読み込み、機能の一覧からの選択、並びに `init.sh` 及び基本の動作の確認を順に行わせている。

### 8.4 1回のセッション又は反復で扱う作業を限定する

1回のセッション又は反復で扱う作業は、機能1件、問い合わせ1件、ファイル1件のように一つの項目に限定し、完了するたびに確認及び変更の記録を行わせる。複数の項目を同時に進めると、コンテキストを使用し切る、未完成の変更が残る、又はどの変更が失敗の原因かを特定できなくなる。

Anthropicは、200件を超える機能からなるアプリケーションの開発で、1回のセッションを一つの機能に限定したことが、作業の抱え込みを防ぐ要因になったと報告している。

### 8.5 反復ごとのコンテキストの扱いを定める

反復ごとに新しいコンテキストで開始するか、同じセッションを継続するかを決定する。

コンテキストの扱いの方式は、[表15](#table-15)による。

<a id="table-15"></a>表15−コンテキストの扱いの方式

| 方式 | 利点 | 注意点 |
| --- | --- | --- |
| 毎回新しいコンテキストで開始する（例：1ファイルずつの移行、1件ずつの問い合わせの処理） | 古い情報又は誤った推論を引き継がない。 | 必要な状態を全てファイルから読み直させる。 |
| 同じセッションを継続する（例：一つの不具合の調査、レビューの指摘への対応） | 直前の作業の詳細を使用できる。 | 長くなると圧縮で情報が失われ、品質が下がる。作業の区切りで新しいセッションへ切り替える。 |

### 8.6 状態のファイルを整理する

状態のファイルは、完了した項目を履歴へ移動するか削除して整理する。進行中の作業と履歴とを区別し、同じ作業の再実行を防ぐ。

### 8.7 処理が停止しても再開できるようにする

ループの処理は、途中で終了しても同じ状態から再開できるようにする。起動スクリプトは、エージェントが予期せず終了した場合に、セッションIDを使用して同じセッションを再開する。外部への操作は、同じ操作を2回実行しても結果が変化しないようにする。

## 9 ループの設計

### 9.1 ループを作成する前に構成要素を全て定める

ループの中でエージェントに与える指示、ツール及び検査は、[2章](#2-指示及び検査の設計原則)〜[7章](#7-検査)による。

ループは、[表16](#table-16)の構成要素を全て定めてから実行する。定めていない構成要素があるループは、停止しない、誤った結果で停止する、又は同じ失敗を繰り返す。

<a id="table-16"></a>表16−ループの構成要素

| 構成要素 | 定める事項 | 例：毎朝のバグ報告の仕分け |
| --- | --- | --- |
| トリガー | 何が1回の実行を開始するか。 | 平日の毎朝9時。 |
| 作業の単位 | 1回の反復で扱う範囲。 | バグ報告1件。 |
| 状態 | 反復の間で何をどこへ引き継ぐか。 | 処理済みの報告のIDを `triage-state.json` に記録する。 |
| 検証 | 完了をどの証拠で、誰が判定するか。 | 全ての報告に定義済みの8種のラベルのいずれかと担当者があることを、スクリプトで確認する。 |
| 停止条件 | 完了の条件、回数、時間及び費用の上限並びに異常の検出 | 未処理が0件で終了する。50件又は20ドルで打ち切る。同じ報告で3回失敗した場合は、人へ回す。 |
| 人の確認点 | どの操作の前に人が判断するか。 | 報告者への返信は、担当者が内容を確認して送る。 |
| 記録 | 反復ごとに何を残すか。 | 実行のID、処理件数、人へ回した件数及びトークンの量を `runs.jsonl` に追記する。 |

構成要素は、ループの設定とともにリポジトリの文書へ書き、ループの変更と同時に更新する。

### 9.2 確定した手順はスクリプトに任せる

手順が確定しており判断を必要としない処理は、エージェントに推論させず、スクリプトで実行する。スクリプトは毎回同じ結果を返し、推論より安い。例えば、CSVの取得及び集計、リンク切れの確認並びに前回の結果との差分の抽出はスクリプトに任せ、差分の原因の説明だけをエージェントに任せる。

### 9.3 トリガー及び停止条件で型を選ぶ

ループは、起動する時点及び終了を判定する方法を選んで構成する。[表17](#table-17)は、代表的な構成を比較したものである。定期実行するゴールベースのループのように、起動方式と終了方式とを組み合わせてもよい。

| ターンベース | 人の指示 | エージェントが完了したか、追加の情報が必要と判断する。 | 手順の実行及び検証 | 短い作業<br>探索<br>判断を伴う作業 | “いいねボタンを追加し、テストを通して報告する”。人が結果を見て次を指示する。 |

| 期限付きの最適化 | 人が目標及び終了時刻を与える。 | 終了時刻に達する。 | 改善案の選択及び反復 | 評価で数値を測れる目標を<br>期限まで改善し続ける作業 | “明朝9時まで、負荷試験のスコアを上げ続ける” |

## 10 ループの検証

### 10.1 完了は機械的な証拠で判定する

完了は、エージェントの報告ではなく、コマンドの終了コード、数値又は件数で判定する。完了の条件は、[表19](#table-19)のように確認できる形にして与える。

<a id="table-19"></a>表19−完了の条件の例

| 曖昧な依頼 | 確認できる完了の条件 | 確認する方法 |
| --- | --- | --- |
| ログインの不具合を修正する | セッションの期限切れの後にログインが失敗する事象を再現するテストを追加し、そのテスト及び既存のテストが全て通る。 | `pnpm test` の終了コードが0である。 |
| トップページを速くする | Lighthouseの性能スコアが、3回の計測の中央値で90以上になる。 | `lighthouse` の出力のスコアを確認する。 |
| ロガーを新しいAPIへ移す | `files.txt` の全てのファイルを移し、古いAPIの呼出しが0件で、テストが通る。 | `grep` の件数及びテストの終了コードを確認する。 |
| 変更履歴を整える | 今週マージされた全てのプルリクエストに対応する項目が `CHANGELOG.md` にある。 | GitHubのプルリクエストの一覧と照合する。 |
| バグ報告を片付ける | `needs-triage` のラベルが付いたIssueが0件になる。 | `gh issue list` の件数を確認する。 |
| 月次売上レポートを作成する | 全部門の行があり、部門の合計が会計システムの月次の総額と1円単位で一致する。 | 照合のスクリプトの結果を確認する。 |
| 顧客データを移行する | 移行元と移行先との件数が一致し、メールアドレスの重複及び必須の項目の欠損が0件である。 | SQLの集計を確認する。 |
| 競合を調査する | 指定した5社の全てに、価格、主要な機能、対象の顧客の3項目があり、全ての値に出典のURLがある。 | 空欄及びURLの応答をスクリプトで確認する。 |
| FAQを更新する | 直近30日の問い合わせの上位20件の全てに回答があり、リンク切れが0件である。 | 問い合わせの集計とFAQの見出しとを照合する。 |

複数の条件がある場合は、全ての条件を満たした場合だけ完了とする。

### 10.2 検証の強さを理解して選ぶ

検証の方法によって、エージェントが誤った完了を報告した場合に停止できるかが異なる。無人で実行するループには、外側から強制する方法を使用する。

検証の方法は、[表20](#table-20)による。

<a id="table-20"></a>表20−検証の方法

| 方法 | 判定する者 | 強制の強さ | 例 |
| --- | --- | --- | --- |
| 指示の中で自己検証を求める | 生成エージェント自身 | 弱い。誤った完了をそのまま報告することがある。 | “認証のテストを実行し、通るまで続ける” |
| 検証の手順をスキルにする | 手順に従う生成エージェント | 弱い。手順を省くことがある。 | 画面を操作して前後を撮影し、コンソールの新しいエラーが0件であることを確認するスキル。 |
| ツールの組み込みの判定（`/goal`） | 判定用のモデル | 中程度。判定用のモデルは会話の内容だけを読み、コマンドを実行しない。 | `/goal test/auth の全てのテストが通り、リントのエラーが0件である` |
| 別のコンテキストの評価エージェント | サブエージェント | 中程度。評価エージェントも推論で判定する。 | 差分を `SPEC.md` と照合し、未実装の要件だけを報告するサブエージェント。 |
| Stopフックで検証のコマンドを実行する | フックのスクリプト | 強い。検証が通るまで停止を阻止する。 | `pnpm tsc --noEmit` が失敗する間は、終了コード2で停止を阻止する。 |
| 外側のスクリプト又はSDKで検証のコマンドを実行する | ループの外のプログラム | 強い。検証の結果で次の反復を決定する。 | `files.txt` のファイルを1件ずつ `claude -p --max-turns 20` に渡す。各実行の後にスクリプトが `grep` で古いAPIの呼出しを数えてテストを実行し、エージェントの応答ではなく、その結果で次へ進む。 |

どの方法でも、“テストは全て通った”という報告だけを信じず、実行したコマンド及び出力を証拠として残させる。

### 10.3 主観的な目標は確認できる部分だけを自動化する

読みやすさ又はデザインのように機械で確認できない目標は、ループで完了を判定しない。確認できる部分だけをループに任せ、残りは、人又は評価の基準で較正した評価エージェントが判定する。

主観的な目標の分担は、[表21](#table-21)による。

<a id="table-21"></a>表21−主観的な目標の分担

| 目標 | ループに任せる部分 | 人又は評価エージェントが判定する部分 |
| --- | --- | --- |
| 提案書を読みやすくする | 必須の見出しの有無<br>1文の長さの上限<br>用語の統一<br>リンク切れ | 論旨が顧客の課題に答えているか。 |
| 画面のデザインを整える | コントラスト比<br>コンソールのエラー<br>画面の幅ごとの表示の崩れ | 全体の印象及び独自性。 |

### 10.4 揺れのある数値は複数回の計測で比較する

性能又はスコアのように、同じ状態でも計測ごとに値が揺れる指標は、1回の計測で比較しない。基準を複数回測定して中央値及び揺れの幅を求め、揺れの幅を超えた差だけを改善とみなす。

例えば、基準の3回の計測が98、100及び102の場合は、中央値は100、揺れの幅は4%である。変更後の103は+3%で揺れの幅に収まるため再度計測し、110は+10%のため改善として残す。

## 11 停止条件及び予算

### 11.1 全ての自律ループに上限を設ける

全ての自律ループに、完了の条件及び[表22](#table-22)の上限を少なくとも一つ設ける。完了の条件を満たせない場合も、反復を打ち切ることが可能になる。

<a id="table-22"></a>表22−反復の上限

| 上限 | Claude Code | Codex |
| --- | --- | --- |
| 回数 | 非対話モードの `--max-turns 20`<br>Agent SDKの `maxTurns`<br>`/goal` の条件の“20ターンで止める” | `/goal` の条件の“20ターンで止める” |
| 費用 | 非対話モードの `--max-budget-usd 5.00`、Agent SDKの `maxBudgetUsd` | `/goal` のトークンの予算 |
| 時間 | 起動スクリプトの終了時刻<br>ジョブのタイムアウトの30分 | 起動スクリプトの終了時刻<br>ジョブのタイムアウトの30分 |
| 期間 | セッション内の `/loop` は7日で失効する。 | スケジュールタスクを人が停止する。 |

上限に達して停止した場合は、達成できなかった事項及び現在の状態を人へ通知する。

上限の値は、小さな対象で実行した実績から決定する。参考として、Anthropicの報告では、ゲームの作成ツールに6時間及び200ドル、音楽の制作ツールに3時間50分及び124.70ドルを要した。

### 11.2 進まない状態を検出して停止する

同じ失敗を繰り返す状態、残る問題が変化しない状態、及びツールを使用せずに応答だけを繰り返す状態では、上限を待機せずに停止する。例えば、同じエラーの文面が3回続いた場合、又は未処理の件数が3回の反復で減らない場合に停止して、人へ回す。

StopフックでClaude Codeの停止を阻止する場合は、入力の `stop_hook_active` を確認し、同じ理由で阻止を繰り返さないようにする。Claude Codeは、ツールの実行を挟まずにStopフックが8回続けて停止を阻止すると、フックを無視して停止する。

### 11.3 人がいつでも停止できるようにする

ループには、人が即座に停止する手段を用意する。`runs/current/STOP` のような停止の印のファイル、スケジュールの取消し、`/goal clear` のように、エージェントの判断を経ずに機能する手段を使用する。

### 11.4 トークンの使用量を管理する

トークンの使用量の対策は、[表23](#table-23)による。

<a id="table-23"></a>表23−トークンの使用量の対策

| 対策 | 内容 | 例 |
| --- | --- | --- |
| 作業に合うモデルを選ぶ | 定型の作業は小さく速いモデル、判断を伴う作業は高性能なモデルに任せる。 | 報告の分類はClaude Haiku、修正の方針の判断はClaude Opusに任せる。 |
| 実行の間隔を対象の変化に合わせる | 対象がほとんど変化しない場合は、間隔を長くするか、イベントで起動する。 | 週に数件しか届かない問い合わせは、5分ごとに確認せず、受信のイベントで起動する。 |
| 処理する項目がない場合は直ちに終了する | 処理する項目がない場合は、推論を開始せずに終了する。 | 未処理の件数をスクリプトで数え、0件ならエージェントを起動しない。 |
| 大きな実行は小さく試す | 多数のエージェントを起動する実行は、一部の対象で試してから広げる。 | 1 000ファイルの移行は、3ファイルで試して指示を修正してから全件を実行する。 |
| 使用量を確認する | Claude Codeの `/usage` 及び `/goal` の状態表示で、実行ごとの使用量を確認する。 | 週に1回、ループごとのトークンの量及び処理件数を比較する。 |

## 12 並列及び競合

### 12.1 並列のエージェントは作業ディレクトリを分ける

複数のエージェントを並列に実行する場合は、作業ディレクトリをエージェントごとに分ける。Claude Code及びCodexは、Gitのworktreeで作業ディレクトリを分けられる。Anthropicの例では、バグ報告1件に対して三つの修正案を別々のworktreeで作成し、判定するエージェントが批判的に比較して選ぶ。

### 12.2 同じ対象を複数のループが操作しない

ループは操作の前に、対象を他のループが処理中でないことを確認し、`in-progress` のラベルのような処理中の印を残す。ループを実行する基盤に同時実行を制限する機能があれば、それを使用する。

### 12.3 ループが自分の出力で再び起動しないようにする

イベント駆動のループは、ループ自身の書き込み又は投稿で再び起動しないようにする。起動したユーザーがボットの場合は既定で処理せず、処理するボットを明示する。

## 13 自律の段階及び人の確認点

### 13.1 報告だけの段階から開始する

新しいループは、次の段階を順に進める。前の段階で、検出の精度及び誤りの頻度を一定の期間計測してから、次の段階へ移る。

自律の段階は、[表24](#table-24)による。

<a id="table-24"></a>表24−自律の段階

| 段階 | ループが行うこと | 人が行うこと | 例：バグ報告の仕分け | 次へ進む目安 |
| --- | --- | --- | --- | --- |
| 報告 | 調査し、結果を報告する。成果物は変更しない。 | 報告を読み、対応を決定する。 | 分類及び担当者の案を一覧にしてSlackへ投稿する。 | 2週間、人が案を修正した割合が10%以下である。 |
| 提案 | 変更を作成し、検証して提案する。 | 確認し、採用を判断する。 | ラベルを付け、回答の下書きを作成する。 | 2週間、人が下書きを大きく修正した割合が5%以下である。 |
| 無人の実行 | 変更から反映まで行う。 | 定期的に結果を確認する。 | ラベルの付与及び定型の回答の送信まで行う。 | 週に1回、抜き取りで確認する。 |

無人の実行で取り消しが続く場合は、そのループを提案の段階へ戻す。目安の数値は、作業の重要度に合わせて決定する。

### 13.2 人が理解できる量に出力を保つ

ループの出力量は、人がレビュー可能な量に制限する。例えば、1日に確認可能なプルリクエストが10件の場合は、その件数に合わせて処理を制限する。人が一定の期間の変更を説明できない場合は、ループの段階を下げる。

## 14 ループの型ごとの規則

### 14.1 ターンベースのループ

検証の手順をスキルに書き、全ての手順を通過するまで完了を報告させない。手順のいずれかが失敗した場合は、修正して最初の手順から再試行させる。指示には、対象、症状及び完了の状態を書く。

指示の例は、[表25](#table-25)による。

<a id="table-25"></a>表25−指示の例

| 指示の良否 | 例 |
| --- | --- |
| 曖昧 | “ログインの不具合を直して” |
| 具体的 | “セッションの期限切れの後にログインが失敗するという報告がある。`src/auth/` のトークンの更新を調査し、再現するテストを書いてから直す” |

### 14.2 ゴールベースのループ

完了の条件には、[表26](#table-26)の事項を書く。

<a id="table-26"></a>表26−完了の条件に書く事項

| 事項 | 例：認証の修正 | 例：月次レポート |
| --- | --- | --- |
| 確認できる一つの終了状態 | `test/auth` の全てのテストが通る。 | 全部門の合計が会計の総額と一致する。 |
| 確認の方法 | `pnpm test test/auth` の終了コードが0である。 | `scripts/reconcile.py` が“不一致0件”と出力する。 |
| 途中で変更してはならないもの | 既存のテストのファイルを変更しない。 | 会計システムの元データを変更しない。 |
| 回数又は時間の上限 | 20ターンで停止する。 | 10ターンで停止する。 |

Claude Codeの `/goal` の判定用のモデルは、会話に表れた内容だけで判定し、コマンドを実行しない。完了の証拠となるコマンドの出力が会話に表れるように、確認の方法を条件に書く。厳密な判定が必要な場合は、Stopフック又は外側のスクリプトで検証のコマンドを実行する。

### 14.3 時間ベースのループ

実行の場所及び端末の状態への依存を確認して選ぶ。

実行の場所は、[表27](#table-27)による。

<a id="table-27"></a>表27−実行の場所

| 実行の場所 | 端末の電源 | ローカルのファイル | 用途 |
| --- | --- | --- | --- |
| セッション内（Claude Codeの `/loop`） | 必要。セッションを開いておく。 | 使用できる。 | 作業中の短い確認（例：`/loop 15m` でCIの結果を確認し、失敗の場合は修正する） |
| 端末のアプリ（Claude Codeのデスクトップアプリ、Codexのアプリ） | 必要。アプリを起動しておく。 | 使用できる。 | ローカルの環境が必要な定期作業（例：毎朝9時に手元のフォルダの請求書を集計する） |
| クラウド（Claude Codeのクラウドスケジュールタスク、GitHub Actions） | 不要 | 使用できない。毎回リポジトリを取得し直す。 | 端末に依存しない定期作業（例：毎晩、依存関係の更新を確認して提案する） |

間隔は、対象が変化する頻度に合わせる。外部の処理の完了又は返答を待機する場合は、イベントで起動する方法を優先する。

### 14.4 イベント駆動のループ

イベントごとに、一つの作業とその完了の条件とを対応させる。同じイベントが短時間に大量に届いた場合に備えて、処理する件数の上限を定める。

イベントごとの作業は、[表28](#table-28)による。

<a id="table-28"></a>表28−イベントごとの作業

| イベント | 作業 | 完了の条件 | 上限 |
| --- | --- | --- | --- |
| プルリクエストの作成 | 仕様と照合してレビューする。 | 指摘をコメントするか、指摘なしと報告する。 | 1件あたり10ターン |
| 問い合わせの到着 | 分類し、FAQから回答の下書きを作成する。 | ラベル及び出典付きの下書きがある。 | 1時間に50件 |
| 請求書のファイルの追加 | 項目を抽出して台帳へ転記する。 | 合計が請求書の金額と一致する。 | 1日に200件 |

### 14.5 期限付きの最適化のループ

評価で数値を測れる目標を、終了時刻まで改善し続ける場合は、[表29](#table-29)の仕組みを用意する。[エージェントハーネス](../../templates/agent-harness/README.md)のテンプレートは、これらをClaude Code及びCodexの両方で実装している。

<a id="table-29"></a>表29−期限付きの最適化の仕組み

| 仕組み | 内容 |
| --- | --- |
| 条件書 | 目標、評価の方法、環境、禁止事項及び最終状態の要件を、実行ごとの文書に書く（例：`CONDITIONS.md`）。 |
| 評価のCLI | 評価、記録並びに環境の反映及び復元を一つのCLIにまとめ、エージェントはCLIを通してだけ環境を操作する。 |
| 判定 | 基準を3回測定し、揺れの幅と5%とのうち大きい方を超えた改善だけを残す。改善しない変更は、成果物に加えてデータ又は設定も含めて元に戻す。 |
| 継続 | Stopフックで終了時刻までの停止を阻止し、エージェントが終了した場合は起動スクリプトが同じセッションを再開する。 |
| 通知 | 最高の結果が30分更新されない場合、又は最終段階に入った場合に、フックで状態を伝える。 |
| 最終段階 | 終了時刻の40分前から新しい改善を開始せず、最良の状態へ戻し、再起動後の状態及び評価を確認する。 |
| 強制終了 | 終了時刻を過ぎた場合は、起動スクリプトがエージェント及び評価の処理を停止する。 |

## 15 ハーネス及びループの改善

### 15.1 失敗の原因に対応する構成要素を修正する

エージェントの失敗は、原因を分類し、対応する構成要素を変更する。

失敗の原因ごとの変更は、[表30](#table-30)による。

<a id="table-30"></a>表30−失敗の原因ごとの変更

| 失敗の原因 | 変更する構成要素 | 例 |
| --- | --- | --- |
| 誤ったコマンド又はツールを使用した。 | プロジェクト指示<br>ツール | テストを全件で実行し続けた → 1ファイルだけのコマンドを書く。 |
| 手順を飛ばした、順序を誤った。 | スキル | 照合の前にレポートを完了とした → 照合を手順に含める。 |
| 誤りが検出されずに残った。 | 検査 | 税込と税抜の取り違えが残った → 会計の総額との照合を加える。 |
| 必要な知識がなかった。 | リポジトリの資料<br>スキル | 会議で決めた締め日を知らなかった → 決定を文書にして参照する。 |
| 準備又は起動の方法を調査するのに時間を使用した。 | 環境の準備のコマンド | セッションごとに起動の方法を調査した → `init.sh` を用意する。 |
| 自分の成果物を誤って合格とした。 | 別のコンテキストの評価エージェント<br>検査 | 単体テストだけで機能を完了とした → 画面を操作して確認する評価エージェントを置く。 |

### 15.2 ハーネスの変更をレビューする

ハーネスのファイルは、変更履歴を残し、変更をレビューする。エージェントがハーネスを変更する場合も、人がレビューしてから取り込む。

### 15.3 ハーネスの効果を確認する

一度も失敗を検出しない検査は、品質が高いことを示すとは限らない。意図的に規則へ違反した成果物（例：合計を1円ずらしたレポート、リンクを切った文書）で、検査が失敗を検出することを確認する。

### 15.4 同じ形の作業にはテンプレートを使用する

同じ形の作業（例：業務APIのサービス、データの可視化、月次レポート）が複数ある場合は、ガイド及びセンサーをテンプレートにまとめて共有する。テンプレートから作成したリポジトリでも、テンプレートの更新を取り込む手順を定めておく。

### 15.5 反復ごとに記録を残す

反復ごとに、実行のID、開始及び終了の時刻、対象、結果、検証の出力、人へ引き継いだ件数及び使用したトークンの量を記録する。

反復ごとの記録の項目は、[表31](#table-31)による。

<a id="table-31"></a>表31−反復ごとの記録の項目

| 項目 | 例 |
| --- | --- |
| 実行のID | `2026-11-04-0900` |
| 対象及び結果 | バグ報告 #4217<br>`routed` |
| 検証の出力 | `labels ok, assignee ok` |
| 人へ引き継いだ件数 | 3件 |
| トークンの量 | 42 000 |

### 15.6 失敗をハーネス及びループの改善につなげる

ループが停止しなかった場合、誤った結果で停止した場合、又は同じ失敗を繰り返した場合は、記録から原因を特定し、停止条件、検証又はハーネスの構成要素のいずれかを変更する。ハーネスの構成要素の変更は、[15.1](#151-失敗の原因に対応する構成要素を修正する)による。

新しいループは、本番と同じ形の小さな対象（例：1 000ファイルのうちの3ファイル）で予行し、停止する位置及び過剰に実行する位置を確認してから広げる。

## 16 チェックリスト

- プロジェクト指示が目次として短く保たれ、詳細な資料及び手順への道順を示している。
- Claude Code及びCodexの両方で使用する場合に、プロジェクト指示が `AGENTS.md` の1か所にある。
- 必ず守らせる規則を、指示ではなくフック及び検査で強制している。
- 規則ごとに、事前に誘導するガイド及び事後に検出するセンサーがある。
- エージェントが自分で成果物を確認するためのツール及びその使用方法の説明がある。
- 速い検査を変更のたびに、重い検査を作業の区切りで実行している。
- 成果物の評価を、生成とは別のコンテキストで行い、評価エージェントに検査の出力を渡している。
- 進捗及び判断の理由が、コンテキストの外のファイルに残る。
- エージェントの失敗を、対応する構成要素の変更につなげている。
- トリガー、作業の単位、状態、検証、停止条件、人の確認点及び記録を全て定め、文書に書いた。
- 完了の条件を、終了コード、数値又は件数で確認できる形にした。
- 無人で実行するループで、外側から強制する検証を使用している。
- 回数、費用及び時間のうち少なくとも一つの上限があり、上限で停止した場合に人へ通知する。
- 進まない状態を検出して停止し、人がいつでも停止できる。
- 途中で停止しても再開できる。
- 並列のエージェントが作業ディレクトリを分け、同じ対象を同時に操作しない。
- 報告の段階から開始している。
