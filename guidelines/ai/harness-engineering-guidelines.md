## 1 はじめに

### 1.1 目的

本書の目的は、AIエージェントが少ない監督で正しい結果を出せるように、エージェントを取り囲む指示、道具、検査を一貫した基準で設計できるようにすることである。

### 1.2 適用範囲

本書は、Claude CodeやCodexなどのAIエージェントを使うリポジトリと実行環境に、利用者が追加する設定、文書、スクリプト、検査の設計を規定する。対話で使う場合にも、無人で動かす場合にも適用する。

本書は、コードの作成に限らず、文書の作成、調査、データの処理などの作業にも適用する。コードを前提とした検査（テスト、リンター、型検査）は、作業の成果物に合った検査（文書の構文やリンクの検査、データの検証、数値の照合）に置き換える。

エージェントをいつ起動し、どの条件で繰り返し、いつ止めるかは、[ループエンジニアリングガイドライン](loop-engineering-guidelines.md)で規定する。

### 1.3 用語及び定義

| 用語 | 定義 |
| --- | --- |
| ハーネス | モデルの外側で、エージェントに与える指示、道具、検査、記録の仕組みの全体。本書では、ツールの提供者が組み込んだ部分を除き、利用者が追加する部分を指す。 |
| ガイド | エージェントが行動する前に、望ましい行動へ誘導する仕組み。常設の指示、スキル、型定義、コード生成などがある。 |
| センサー | エージェントが行動した後に、結果を検査して修正を促す仕組み。テスト、リンター、型検査、レビューを行うエージェントなどがある。 |
| 決定的な検査 | テスト、リンター、型検査のように、同じ入力に同じ結果を返す検査。 |
| 推論による検査 | LLMによるレビューや評価のように、モデルの判断に基づく検査。 |

## 2. 基本の考え方

### エージェントの失敗はハーネスの不足として扱う

エージェントが誤ったコマンドを使う、規約に反する、検証を省くといった失敗をした場合は、その場で修正を指示するだけで終えない。同じ失敗が二度と起きないように、指示、道具、検査のいずれかを変更する。

失敗が繰り返す場合は、エージェントに不足している道具、規則、抽象化、文書を特定し、リポジトリへ追加する。

### 守らせる規則は仕組みで強制する

常設の指示やスキルは、エージェントへの要求であり、実行を保証しない。必ず守らせる規則は、フックとCIの検査で強制する。

| 規則の種類 | 置き場所 |
| --- | --- |
| 判断の目安、手順、規約の意図 | 常設の指示、スキル |
| 毎回同じ処理を実行する | フック |
| 変更が規約を満たしていることを確かめる | テスト、リンター、構造の検査、CI |

### ガイドとセンサーを組み合わせる

ガイドだけでは、規則が守られたかを確かめられない。センサーだけでは、エージェントが同じ誤りを繰り返す。規則ごとに、事前に誘導するガイドと、事後に検出するセンサーの両方を用意する。

### 決定的な検査を優先する

決定的な検査は、速く、安く、結果が揺れないため、変更のたびに実行できる。推論による検査は、意味の判断が必要な場合に限り、決定的な検査の後に補助として使う。

### 小さく始め、失敗を見てから足す

ハーネスは、最初から全ての構成要素をそろえない。エージェントが実際に失敗した箇所に対応する構成要素を追加する。

### モデルの能力に合わせて見直す

ハーネスの構成要素は、モデルが単独ではできないことを補うために置く。新しいモデルへ切り替えた時は、各構成要素を外した場合の結果を確かめ、効果のなくなった構成要素を取り除く。

## 3. 構成要素の選び方

### 目的に合う構成要素を選ぶ

構成要素は、エージェントのコンテキストへ常に入るものから、必要な時だけ入るもの、コンテキストの外で動くものまである。コンテキストに常に入るものほど、全ての作業の費用と精度に影響するため、目的に合う最も軽い構成要素を選ぶ。

| 構成要素 | 目的 | コンテキストへの影響 | Claude Code | Codex |
| --- | --- | --- | --- | --- |
| 常設の指示 | 全ての作業で必要な事実と規則を伝える。 | 常に入る。 | `CLAUDE.md`。`AGENTS.md` も読み込める。 | `AGENTS.md`、`AGENTS.override.md` |
| 範囲を限定した指示 | 特定のディレクトリやファイルの種類だけに効く規則を伝える。 | 該当する範囲で入る。 | `.claude/rules/*.md`（`paths` で対象を限定する）、サブディレクトリの `CLAUDE.md` | サブディレクトリの `AGENTS.md` |
| スキル | 手順、参照資料、検証の方法を必要な時に読み込む。 | 説明だけが常に入り、本体は使う時に入る。 | `.claude/skills/<名前>/SKILL.md` | `.agents/skills/<名前>/SKILL.md` |
| 補助エージェント | 独立したコンテキストで作業させ、要約だけを受け取る。 | 主のコンテキストには結果だけが入る。 | `.claude/agents/*.md` | `.codex/agents/*.toml` |
| 外部の道具 | 外部のサービスやデータへ接続する。 | 道具の名前と説明が入る。 | MCPサーバー | MCPサーバー |
| フック | 決まった時点で処理を必ず実行する。 | 出力を返した時だけ入る。 | `.claude/settings.json` の `hooks` | `.codex/hooks.json` |
| 検査 | 変更の結果を検査し、修正を促す。 | 失敗の出力だけが入る。 | フックとCIから実行する。 | フックとCIから実行する。 |

### 構成要素を追加するきっかけを決めておく

次のきっかけが起きた時に、対応する構成要素を追加する。

| きっかけ | 追加する構成要素 |
| --- | --- |
| 同じ規約やコマンドを2回誤った。 | 常設の指示へ追記する。 |
| 一部のディレクトリだけで必要な規則が、常設の指示を長くしている。 | 範囲を限定した指示へ移す。 |
| 同じ手順を3回以上説明した。 | スキルにする。 |
| エージェントが見えない画面やシステムから、人が情報を写している。 | 外部の道具として接続する。 |
| 調査の出力が主のコンテキストを埋めている。 | 補助エージェントへ渡す。 |
| 毎回必ず実行させたい処理がある。 | フックにする。 |
| 同じ構成を別のリポジトリでも使う。 | プラグインやテンプレートにまとめる。 |

## 4. 常設の指示

### 常設の指示は目次として短く保つ

常設の指示は、全ての作業でコンテキストを占めるため、詳細を書かず、詳細な文書への道順を示す目次とする。1ファイルあたり200行以内を目安にする。CodexはAGENTS.mdの合計が既定で32KiBを超えると、それ以降を読み込まない。

### 全ての作業で必要な事実だけを書く

常設の指示には、次の事項を書く。

- ビルド、テスト、リント、起動のコマンド。
- ディレクトリの構成と、主要な文書の場所。
- 全体に適用する規約と、禁止事項。
- 作業の完了前に行う検証。

一部の範囲だけに効く規則は範囲を限定した指示へ、複数の手順からなる作業はスキルへ分ける。

### 両ツールで共有する指示はAGENTS.mdに書く

Claude CodeとCodexの両方で使うリポジトリでは、常設の指示を `AGENTS.md` に書き、`CLAUDE.md` からは `@AGENTS.md` で取り込む。同じ内容を2つのファイルに書くと、片方だけが更新されて矛盾する。

### 知識はリポジトリに置く

エージェントは、チャット、外部の文書ツール、人の記憶にある知識を読めない。設計の判断、規約、計画、仕様は、バージョン管理された文書としてリポジトリへ置き、常設の指示から参照する。

### 矛盾と古い記述を取り除く

矛盾する指示があると、エージェントはどちらかを任意に選ぶ。常設の指示、範囲を限定した指示、スキルを定期的に見直し、矛盾と古い記述を取り除く。

## 5. スキルと補助エージェント

### 繰り返す手順をスキルにする

複数の手順からなる作業、参照資料、チームの基準はスキルにする。スキルの説明には、どの作業で使うかを具体的に書く。説明が曖昧だと、エージェントは必要なスキルを使わないか、誤ったスキルを使う。

### 検証の手順をスキルにする

作業の完了前に行う検証を、手順としてスキルに書く。検証の手順には、実行するコマンド、確認する結果、失敗した場合の対応を書き、全ての手順を通過するまで完了を報告させない。

### 大量の読み込みと独立した作業は補助エージェントへ渡す

多数のファイルの調査、ログの分析、独立した部分の作業は補助エージェントへ渡し、主のコンテキストには要約だけを戻す。

### 生成と評価を別のコンテキストに分ける

エージェントは、自分が作った成果物を甘く評価する。成果物の評価は、生成したコンテキストとは別の補助エージェントに行わせる。評価役には、生成の経緯ではなく、成果物、評価の基準、検査の出力を渡す。

評価役が甘い判定をする場合は、評価の記録を読み、人の判断と食い違った箇所を手順と基準へ反映する。主観的な基準には、点数の内訳を付けた評価の例を与える。

### 補助エージェントの道具を役割に合わせて選ぶ

調査役やレビュー役の補助エージェントには、読み取りの道具だけを与える。書き込みが必要な補助エージェントは、作業ツリーを分けて動かす。

## 6. エージェントが使う道具と環境

### エージェントが自分で動作を確かめられるようにする

エージェントが結果を確かめるための道具を用意し、常設の指示かスキルで使い方を示す。

- 対象のテストだけを実行するコマンド。
- アプリケーションを起動し、画面の取得、操作、コンソールのエラーの確認を行う手段。
- ログ、メトリクス、トレースを検索する手段。

並列に作業する場合は、作業ツリーごとにアプリケーションを起動できるようにする。

### 環境の準備を1つのコマンドにする

依存関係の導入、データの準備、アプリケーションの起動は、1つのコマンドで実行できるようにする。エージェントが準備の方法を毎回調べると、時間を浪費し、準備の誤りが作業の誤りに見える。

### 道具の出力をエージェントが読める形にする

道具の出力は、必要な情報だけを短く返す。エラーの出力には、違反した規則と、修正の方法を含める。長い出力はファイルへ保存し、要約と保存先を返す。

### 道具の数と重複を抑える

役割が重なる道具が多いと、エージェントは使う道具を誤る。道具は役割が重ならないように選び、使わない外部の道具は接続しない。

### 変更しやすい技術を選ぶ

エージェントが扱う依存関係は、安定していて文書がそろい、挙動を説明できるものを選ぶ。小さな機能のために挙動の分かりにくい依存関係を加えるより、リポジトリ内に実装する方が扱いやすい場合がある。

## 7. 検査

### 速い検査は変更のたびに実行する

フォーマッター、リンター、型検査、対象のテストは、ファイルの変更後のフックかコミット前に実行し、結果をエージェントへ返す。

### 重い検査は統合後に実行する

全体のテスト、ミューテーションテスト、アーキテクチャの検査、詳細なレビューは、CIで実行する。CIでは、速い検査も再度実行する。

### アーキテクチャの規則を検査で強制する

層の間の依存の方向、命名、ファイルの大きさ、ログの形式などの規則は、リンターや構造のテストで検査する。検査の失敗の出力には、修正の方法を含め、エージェントが出力だけで修正できるようにする。

### 劣化を継続的に検出する

使われないコード、重複、依存関係の脆弱性、文書と実装の食い違いは、定期的に検出する。検出した項目は、修正の範囲を絞った変更として、エージェントに定期的に修正させる。

### 推論による検査は基準で較正する

LLMによるレビューや評価を検査に使う場合は、評価の基準、合格の閾値、評価の例を与える。推論による検査の結果は、決定的な検査の結果を上書きしない。

## 8. 状態の引き継ぎ

### 進捗はコンテキストの外に残す

長い作業では、コンテキストの圧縮やセッションの切り替えで、それまでの経緯が失われる。作業の計画、進捗、判断の理由は、リポジトリ内のファイルとコミットの履歴へ残す。

### 機械が更新する状態は構造化した形式にする

完了した項目の一覧のように、エージェントが更新する状態は、JSONなどの構造化した形式で保存し、更新してよい項目を限定する。自由な文章の形式では、エージェントが項目を書き換えたり削除したりしやすい。

### セッションの開始時に状態を読み込ませる

セッションの開始時には、作業ディレクトリ、コミットの履歴、進捗のファイル、未完了の項目を確認させる。フックで、セッションの開始時と圧縮の後に、現在の状態をコンテキストへ加える。

### 1回のセッションで扱う作業を限定する

1回のセッションで扱う作業は1つの機能や1つの修正に限定し、終わるたびに検証とコミットを行わせる。複数の作業を同時に進めると、未完成の変更が残ったまま次のセッションへ渡る。

## 9. ハーネスの改善

### 失敗の原因に対応する構成要素を直す

エージェントの失敗は、原因を分類し、対応する構成要素を変更する。

| 失敗の原因 | 変更する構成要素 |
| --- | --- |
| 誤ったコマンドや道具を使った。 | 常設の指示、道具 |
| 手順を飛ばした、順序を誤った。 | スキル |
| 誤りが検出されずに残った。 | 検査 |
| 必要な知識がなかった。 | リポジトリ内の文書、スキル |
| 準備や起動の方法を調べるのに時間を使った。 | 環境の準備のコマンド |
| 自分の成果物を誤って合格とした。 | 別のコンテキストの評価役、検査 |

### ハーネスの変更をレビューする

ハーネスのファイルは、コードと同じくバージョン管理し、変更をレビューする。エージェントがハーネスを変更する場合も、人がレビューしてから取り込む。

### ハーネスの効果を確かめる

一度も失敗を検出しない検査は、品質が高いことを示すとは限らない。意図的に規則へ違反した変更で、検査が失敗を検出することを確かめる。

### 同じ形のリポジトリにはテンプレートを使う

同じ構成のサービスが複数ある場合は、ガイドとセンサーをテンプレートにまとめて共有する。テンプレートから作ったリポジトリでも、テンプレートの更新を取り込む手順を決めておく。

## 10. チェックリスト

- 常設の指示が目次として短く保たれ、詳細な文書と手順への道順を示している。
- Claude CodeとCodexの両方で使う場合に、常設の指示が `AGENTS.md` の1か所にある。
- 必ず守らせる規則を、指示ではなくフックとCIで強制している。
- 規則ごとに、事前に誘導するガイドと、事後に検出するセンサーがある。
- エージェントが自分で動作を確かめるための道具と、その使い方の説明がある。
- 速い検査を変更のたびに、重い検査をCIで実行している。
- 成果物の評価を、生成とは別のコンテキストで行っている。
- 進捗と判断の理由が、コンテキストの外のファイルに残る。
- エージェントの失敗を、対応する構成要素の変更につなげている。
