## 1 はじめに

### 1.1 目的

本書の目的は、AIエージェントが少ない監督で正しい成果物を出せるように、エージェントを取り囲む指示、ツール、検査を一貫した基準で設計できるようにすることである。

### 1.2 適用範囲

本書は、Claude CodeやCodexなどのAIエージェントに作業を任せる際に、リポジトリと実行環境へ利用者が追加する設定、文書、スクリプト、検査の設計を規定する。対話で使う場合にも、無人で動かす場合にも適用する。

エージェントをいつ起動し、どの条件で繰り返し、いつ止めるかは、[ループエンジニアリングガイドライン](loop-engineering-guidelines.md)で規定する。

### 1.3 用語及び定義

| 用語 | 定義 |
| --- | --- |
| ハーネス | モデルの外側で、エージェントに与える指示、ツール、検査、記録の仕組みの全体。本書では、ツールの提供者が組み込んだ部分を除き、利用者が追加する部分を指す。 |
| リポジトリ | エージェントが読み書きするファイルと変更履歴を管理する場所。プロジェクト指示、スキル、設定もここに置く。 |
| 成果物 | エージェントが作る文書、データ、プログラム、設定などの作業の結果。 |
| ガイド | エージェントが行動する前に、望ましい行動へ誘導する仕組み。プロジェクト指示、スキル、ひな形などがある。 |
| センサー | エージェントが行動した後に、成果物を検査して修正を促す仕組み。検査のスクリプト、レビューを行うエージェントなどがある。 |
| 決定論的な検査 | 形式、表記、数値、参照先の存在の確認のように、同じ入力に同じ結果を返す検査。 |
| 非決定論的な検査 | LLMによるレビューや評価のように、モデルの判断に基づく検査。 |

## 2. 基本の考え方

### エージェントの失敗はハーネスの不足として扱う

エージェントが誤った手順を使う、規約に反する、確認を省くといった失敗をした場合は、その場で修正を指示するだけで終えない。同じ失敗が二度と起きないように、指示、ツール、検査のいずれかを変更する。

失敗が繰り返す場合は、エージェントに不足しているツール、規則、ひな形、資料を特定し、リポジトリへ追加する。

| 起きた失敗 | 変更 |
| --- | --- |
| pnpmのプロジェクトで `npm install` を実行した。 | プロジェクト指示に「パッケージの操作はpnpmで行う」と書く。 |
| 月次レポートの売上を税込で集計した。 | プロジェクト指示に「売上は税抜で集計する」と書き、会計システムの総額と照合する検査を加える。 |
| 画面の変更で、表示を確かめずに完了と報告した。 | 開発サーバーを起動して画面を撮る手順をスキルにする。 |

### 守らせる規則は仕組みで強制する

プロジェクト指示やスキルは、エージェントへの要求であり、実行を保証しない。必ず守らせる規則は、フックと検査で強制する。

| 規則の種類 | 置き場所 |
| --- | --- |
| 判断の目安、手順、規約の意図（例：見積書は結論から書く） | プロジェクト指示、スキル |
| 毎回同じ処理を実行する（例：ファイルの変更後に `prettier --write` を実行する） | フック |
| 成果物が規約を満たしていることを確かめる（例：`tsc --noEmit` が通るまで完了にしない） | 検査 |

指示の文面を強めても守られない規則は、フックか検査へ移す。逆に、好みにすぎないフックは削除し、エージェントの判断に任せる。

### ガイドとセンサーを組み合わせる

ガイドだけでは、規則が守られたかを確かめられない。センサーだけでは、エージェントが同じ誤りを繰り返す。規則ごとに、事前に誘導するガイドと、事後に検出するセンサーの両方を用意する。

| 規則 | ガイド | センサー |
| --- | --- | --- |
| エラーのログにリクエストIDを含める。 | プロジェクト指示にログの書き方を書く。 | エラーのログの呼び出しを検査し、違反をファイルと行で報告するスクリプト。 |
| 列を削除するデータ移行には、データの移し替えの手順を含める。 | 移行の手順をスキルにする。 | 列の削除だけを含む移行を不合格にする検査。 |
| 見積書に、前提条件、範囲、金額、有効期限の4項目を含める。 | 見積書のひな形を置く。 | 4項目の見出しの有無を確かめるスクリプト。 |

### 決定論的な検査を優先する

決定論的な検査は、速く、安く、結果が揺れないため、変更のたびに実行できる。非決定論的な検査は、意味の判断が必要な場合に限り、決定論的な検査の後に補助として使う。

たとえば、提案書の必須の見出しの有無とリンク切れは決定論的な検査で確かめ、論旨が顧客の課題に答えているかは非決定論的な検査で確かめる。

### 小さく始め、失敗を見てから足す

ハーネスは、最初から全ての構成要素をそろえない。最初はプロジェクト指示と、合否を返す検査のコマンドを1つ用意する。その後は、エージェントが実際に失敗した箇所に対応する構成要素を追加する。

### モデルの能力に合わせて見直す

ハーネスの構成要素は、モデルが単独ではできないことを補うために置く。新しいモデルへ切り替えた時は、各構成要素を外した場合の結果を確かめ、効果のなくなった構成要素を取り除く。

Anthropicのアプリケーション開発のハーネスでは、Claude Sonnet 4.5で必要だったコンテキストのリセットをClaude Opus 4.5で廃止し、スプリント単位の分割と評価をClaude Opus 4.6で廃止して、計画エージェントと、最後に1回だけ動く評価エージェントを残した。

## 3. 構成要素の選び方

### 目的に合う構成要素を選ぶ

構成要素は、エージェントのコンテキストへ常に入るものから、必要な時だけ入るもの、コンテキストの外で動くものまである。コンテキストに常に入るものほど、全ての作業の費用と精度に影響するため、目的に合う最も軽い構成要素を選ぶ。

| 構成要素 | 目的 | コンテキストへの影響 | Claude Code | Codex |
| --- | --- | --- | --- | --- |
| プロジェクト指示 | 全ての作業で必要な事実と規則を伝える。 | 常に入る。 | `CLAUDE.md`。`AGENTS.md` も読み込める。 | `AGENTS.md`、`AGENTS.override.md` |
| 範囲を限定した指示 | 特定のディレクトリやファイルの種類だけに効く規則を伝える。 | 該当する範囲で入る。 | `.claude/rules/*.md`（`paths` で対象を限定する）、サブディレクトリの `CLAUDE.md` | サブディレクトリの `AGENTS.md` |
| スキル | 手順、参照資料、確認の方法を必要な時に読み込む。 | 説明だけが常に入り、本体は使う時に入る。 | `.claude/skills/<名前>/SKILL.md` | `.agents/skills/<名前>/SKILL.md` |
| サブエージェント | 独立したコンテキストで作業させ、要約だけを受け取る。 | 主のコンテキストには結果だけが入る。 | `.claude/agents/*.md` | `.codex/agents/*.toml` |
| 外部のツール | 外部のサービスやデータへ接続する。 | ツールの名前と説明が入る。 | MCPサーバー | MCPサーバー |
| フック | 決まった時点で処理を必ず実行する。 | 出力を返した時だけ入る。 | `.claude/settings.json` の `hooks` | `.codex/hooks.json` |
| 検査 | 成果物を検査し、修正を促す。 | 失敗の出力だけが入る。 | フックや定期的な処理から実行する。 | フックや定期的な処理から実行する。 |

### 構成要素を追加するきっかけを決めておく

次のきっかけが起きた時に、対応する構成要素を追加する。

| きっかけ | 追加する構成要素 | 例 |
| --- | --- | --- |
| 同じ規約や手順を2回誤った。 | プロジェクト指示へ追記する。 | 「テストは `pnpm test <ファイル>` で実行する」 |
| 一部のディレクトリだけで必要な規則が、プロジェクト指示を長くしている。 | 範囲を限定した指示へ移す。 | `reports/**` だけに効く集計の規則を、`paths` を付けたファイルへ移す。 |
| 同じ手順を3回以上説明した。 | スキルにする。 | 月次の締めの手順を `monthly-close` にする。 |
| エージェントが見えない画面やシステムから、人が情報を写している。 | 外部のツールとして接続する。 | チケットの内容を貼り付ける代わりに、課題管理のMCPサーバーを接続する。 |
| 調査の出力が主のコンテキストを埋めている。 | サブエージェントへ渡す。 | 仕様書100件の検索を任せ、該当箇所の要約だけを受け取る。 |
| 毎回必ず実行させたい処理がある。 | フックにする。 | ファイルの変更後にフォーマッターを実行する。 |
| 同じ構成を別のリポジトリでも使う。 | プラグインやテンプレートにまとめる。 | 2つ目のサービスへ、同じスキルとフックを配布する。 |

## 4. プロジェクト指示

### プロジェクト指示は目次として短く保つ

プロジェクト指示は、全ての作業でコンテキストを占めるため、詳細を書かず、詳細な文書への道順を示す目次とする。1ファイルあたり200行以内を目安にする。CodexはAGENTS.mdの合計が既定で32KiBを超えると、それ以降を読み込まない。

### 全ての作業で必要な事実だけを書く

プロジェクト指示には、次の事項を書く。

| 書く事項 | 例 |
| --- | --- |
| 結果の確かめ方 | 「1ファイルのテストは `pnpm test <ファイル>`、全体は `pnpm test` で実行する」 |
| 読むと誤解する箇所 | 「`legacy/` の書き方は新しいコードで真似しない」「`archive/` は使われていないように見えるが、月次の集計が参照している」 |
| リポジトリから読み取れない決定 | 「エラーの処理は `AppError` に統一すると決めた」「売上は税抜で集計する」 |
| 2回訂正した事項 | 「金額は3桁ごとにカンマで区切る」 |

ファイルの一覧や一般的な言語の規約のように、読めば分かることは書かない。書く前に、エージェントが読んで見つけられるか、実際に見に行くかを確かめ、どちらも当てはまるなら書かない。

一部の範囲だけに効く規則は範囲を限定した指示へ、複数の手順からなる作業はスキルへ分ける。

### 両ツールで共有する指示はAGENTS.mdに書く

Claude CodeとCodexの両方で使うリポジトリでは、プロジェクト指示を `AGENTS.md` に書き、`CLAUDE.md` からは `@AGENTS.md` で取り込む。同じ内容を2つのファイルに書くと、片方だけが更新されて矛盾する。

### 知識はリポジトリに置く

エージェントは、チャット、外部の文書ツール、人の記憶にある知識を読めない。判断の経緯、規約、計画、仕様は、変更履歴が残る文書としてリポジトリへ置き、プロジェクト指示から参照する。

### 矛盾と古い記述を取り除く

矛盾する指示があると、エージェントはどちらかを任意に選ぶ。プロジェクト指示、範囲を限定した指示、スキルを定期的に見直し、矛盾と古い記述を取り除く。

## 5. スキルとサブエージェント

### 繰り返す手順をスキルにする

複数の手順からなる作業、参照資料、チームの基準はスキルにする。スキルの説明には、どの作業で使うかを具体的に書く。説明が曖昧だと、エージェントは必要なスキルを使わないか、誤ったスキルを使う。

| 説明の良否 | 例 |
| --- | --- |
| 曖昧 | 「レポートを助ける」 |
| 具体的 | 「月次売上レポートを作成または更新する時に使う。部門別の集計、会計システムの総額との照合、前月比の算出の手順を含む」 |

### 確認の手順をスキルにする

作業の完了前に行う確認を、手順としてスキルに書く。確認の手順には、実行するコマンド、確かめる結果、失敗した場合の対応を書き、全ての手順を通過するまで完了を報告させない。完了の報告には、実行したコマンドと出力を証拠として含めさせる。

| スキル | 手順 |
| --- | --- |
| `verify-frontend-change` | 開発サーバーを起動する。変更した操作を実行し、操作の前後の画面を撮る。コンソールの新しいエラーが0件であることを確かめる。Core Web Vitalsを計測する。失敗したら修正し、最初の手順からやり直す。 |
| `verify-log-hygiene` | エラーの処理のログにリクエストIDがあり、リクエストの本文を含まないことを確かめる。違反をファイルと行で報告し、修正する。 |
| `verify-monthly-report` | 全部門の行があることを確かめる。部門の合計と会計システムの総額が1円単位で一致することを確かめる。前月比の計算を再計算して照合する。不一致の部門と差額を報告する。 |

### 大量の読み込みと独立した作業はサブエージェントへ渡す

多数のファイルの調査、記録の分析、独立した部分の作業はサブエージェントへ渡し、主のコンテキストには要約だけを戻す。

たとえば、Anthropicのマーケティングのチームは、数百件の広告のCSVから成果の悪い広告を見つけるサブエージェントと、文字数の制限の中で広告文の案を作るサブエージェントに分けている。

### 生成と評価を別のコンテキストに分ける

エージェントは、自分が作った成果物を甘く評価する。成果物の評価は、生成したコンテキストとは別のサブエージェントに行わせる。評価エージェントには、生成の経緯ではなく、成果物、評価の基準、検査の出力を渡す。

評価エージェントが甘い判定をする場合は、評価の記録を読み、人の判断と食い違った箇所を手順と基準へ反映する。主観的な基準には、点数の内訳を付けた評価の例を与える。

評価の基準は、項目と合格の閾値で書き、1つでも閾値を下回れば差し戻す。Anthropicは、画面のデザインの評価エージェントに次の項目を使い、モデルが既定で苦手な上の2項目の重みを高くした。

| 項目 | 確かめること |
| --- | --- |
| デザインの質 | 全体が一貫した印象を持つまとまりになっているか。 |
| 独自性 | ひな形のままではなく、意図した選択の跡があるか。 |
| 作り込み | 文字の組み方、余白、配色、コントラストが整っているか。 |
| 機能性 | 利用者が操作を理解し、目的を達成できるか。 |

レビューを頼まれたエージェントは、問題を必ず何か見つけようとする。依頼では対象を絞り、たとえば「差分を `SPEC.md` と照合し、未実装の要件と、挙げた例外の処理の漏れだけを報告する。書き方の好みは報告しない」と指示する。

### サブエージェントのツールを役割に合わせて選ぶ

調査や評価を行うサブエージェントには、読み取りのツールだけを与える。書き込みが必要なサブエージェントを並列に動かす場合は、作業ディレクトリを分ける。

## 6. エージェントが使うツールと環境

### エージェントが自分で結果を確かめられるようにする

エージェントが成果物を確かめるためのツールを用意し、プロジェクト指示かスキルで使い方を示す。

| ツール | 例 |
| --- | --- |
| 変更した部分だけを検査するコマンド | `pnpm test src/auth/session.test.ts`、`markdownlint docs/pricing.md` |
| 成果物を実際に使って確かめる手段 | Playwrightで画面を操作して撮影する。生成したPDFを画像にして確かめる。SQLで移行後の件数を集計する。 |
| 実行の記録を検索する手段 | 直近1時間のエラーのログを、リクエストIDで検索するコマンド。 |

### 環境の準備を1つのコマンドにする

ツールの導入、データの準備、実行環境の起動は、`./init.sh` のような1つのコマンドで実行できるようにする。エージェントが準備の方法を毎回調べると、時間を浪費し、準備の誤りが作業の誤りに見える。

### ツールの出力をエージェントが読める形にする

ツールの出力は、必要な情報だけを短く返す。エラーの出力には、違反した規則と、修正の方法を含める。長い出力はファイルへ保存し、要約と保存先を返す。

| 出力の良否 | 例 |
| --- | --- |
| 修正できない | `check failed` |
| 修正できる | `reports/2026-10.md:12 営業部の合計が会計の総額と1,200円一致しない。data/ledger.csv の10月分から再集計する。` |

### ツールの数と重複を抑える

役割が重なるツールが多いと、エージェントは使うツールを誤る。ツールは役割が重ならないように選び、使わない外部のツールは接続しない。

### 広く使われていて資料のそろったツールを選ぶ

エージェントが扱うツール、形式、ライブラリは、広く使われていて、資料がそろい、挙動を説明できるものを選ぶ。

## 7. 検査

### 速い検査は変更のたびに実行する

成果物の形式、表記、参照先、数値の整合を確かめる速い検査は、ファイルの変更後のフックで実行し、結果をエージェントへ返す。

| 成果物 | 速い検査 | 重い検査 |
| --- | --- | --- |
| プログラム | フォーマッター、ESLint、`tsc --noEmit`、変更したファイルのテスト | 全てのテスト、ミューテーションテスト、依存の方向の検査 |
| 文書 | markdownlint、リンク切れ、用語の表記の検査 | 全文書の用語の統一、仕様との照合、評価エージェントのレビュー |
| データ | スキーマの検証、必須の項目の欠損の検査 | 移行元との件数と合計の照合、重複の検査 |
| 集計レポート | 全部門の行の有無、合計の再計算 | 会計システムの総額との照合、前月比の異常値の確認 |

### 重い検査は区切りで実行する

成果物の全体を対象とする検査や、時間のかかる検査は、作業の区切りや定期的な処理で実行する。区切りの検査では、速い検査も再度実行する。

### 構成の規則を検査で強制する

成果物の構成、命名、大きさ、書式などの規則は、検査のスクリプトで確かめる。検査の失敗の出力には、修正の方法を含め、エージェントが出力だけで修正できるようにする。たとえば、OpenAIのチームは、層の間の依存の方向、ログの形式、ファイルの大きさをリンターと構造のテストで検査し、エラーの文面に修正の方法を書いている。

### 劣化を継続的に検出する

使われなくなった資料、重複、古くなった記述、成果物の間の食い違い、リンク切れは、定期的に検出する。検出した項目は、範囲を絞った修正として、エージェントに定期的に直させる。OpenAIのチームは、週の20%を使っていた金曜日の整理作業を、基準からの逸脱を探して修正を提案する定期的なエージェントへ移した。

### 非決定論的な検査は基準で較正する

LLMによるレビューや評価を検査に使う場合は、評価の基準、合格の閾値（例：各項目を5段階で評価し、全項目が4以上で合格）、評価の例を与える。非決定論的な検査の結果は、決定論的な検査の結果を上書きしない。

## 8. 状態の引き継ぎ

### 進捗はコンテキストの外に残す

長い作業では、コンテキストの圧縮やセッションの切り替えで、それまでの経緯が失われる。作業の計画、進捗、判断の理由は、リポジトリのファイルと変更履歴へ残す。

| ファイル | 内容 |
| --- | --- |
| `SPEC.md` | 完了の定義。人とエージェントの間で合意した要件と例外。 |
| `progress.md` | 各セッションの終わりに追記する、行ったこと、次にやること、判断の理由。 |
| `items.json` | 項目ごとの完了の状態。 |
| `init.sh` | 環境を準備し、基本の動作を確かめるスクリプト。 |

### 機械が更新する状態は構造化した形式にする

完了した項目の一覧のように、エージェントが更新する状態は、JSONなどの構造化した形式で保存し、更新してよい項目を限定する。自由な文章の形式では、エージェントが項目を書き換えたり削除したりしやすい。

Anthropicのアプリケーション開発の例では、200件を超える機能を、分類、説明、確認の手順、`passes` の4項目で一覧にし、全てを `passes: false` で始めて、エージェントには `passes` だけを更新させた。

### セッションの開始時に状態を読み込ませる

セッションの開始時には、作業ディレクトリ、変更履歴、進捗のファイル、未完了の項目を確認させる。フックで、セッションの開始時と圧縮の後に、現在の状態をコンテキストへ加える。Anthropicの例では、作業ディレクトリの確認、`git log` と進捗のファイルの読み込み、機能の一覧からの選択、`init.sh` と基本の動作の確認を順に行わせている。

### 1回のセッションで扱う作業を限定する

1回のセッションで扱う作業は、機能1件、問い合わせ1件、ファイル1件のように1つの項目に限定し、終わるたびに確認と変更の記録を行わせる。複数の項目を同時に進めると、未完成の変更が残ったまま次のセッションへ渡る。

## 9. ハーネスの改善

### 失敗の原因に対応する構成要素を直す

エージェントの失敗は、原因を分類し、対応する構成要素を変更する。

| 失敗の原因 | 変更する構成要素 | 例 |
| --- | --- | --- |
| 誤ったコマンドやツールを使った。 | プロジェクト指示、ツール | テストを全件で実行し続けた → 1ファイルだけのコマンドを書く。 |
| 手順を飛ばした、順序を誤った。 | スキル | 照合の前にレポートを完了とした → 照合を手順に含める。 |
| 誤りが検出されずに残った。 | 検査 | 税込と税抜の取り違えが残った → 会計の総額との照合を加える。 |
| 必要な知識がなかった。 | リポジトリの資料、スキル | 会議で決めた締め日を知らなかった → 決定を文書にして参照する。 |
| 準備や起動の方法を調べるのに時間を使った。 | 環境の準備のコマンド | セッションごとに起動の方法を探した → `init.sh` を用意する。 |
| 自分の成果物を誤って合格とした。 | 別のコンテキストの評価エージェント、検査 | 単体テストだけで機能を完了とした → 画面を操作して確かめる評価エージェントを置く。 |

### ハーネスの変更をレビューする

ハーネスのファイルは、変更履歴を残し、変更をレビューする。エージェントがハーネスを変更する場合も、人がレビューしてから取り込む。

### ハーネスの効果を確かめる

一度も失敗を検出しない検査は、品質が高いことを示すとは限らない。意図的に規則へ違反した成果物（例：合計を1円ずらしたレポート、リンクを切った文書）で、検査が失敗を検出することを確かめる。

### 同じ形の作業にはテンプレートを使う

同じ形の作業（例：業務APIのサービス、データの可視化、月次レポート）が複数ある場合は、ガイドとセンサーをテンプレートにまとめて共有する。テンプレートから作ったリポジトリでも、テンプレートの更新を取り込む手順を決めておく。

## 10. チェックリスト

- プロジェクト指示が目次として短く保たれ、詳細な資料と手順への道順を示している。
- Claude CodeとCodexの両方で使う場合に、プロジェクト指示が `AGENTS.md` の1か所にある。
- 必ず守らせる規則を、指示ではなくフックと検査で強制している。
- 規則ごとに、事前に誘導するガイドと、事後に検出するセンサーがある。
- エージェントが自分で成果物を確かめるためのツールと、その使い方の説明がある。
- 速い検査を変更のたびに、重い検査を作業の区切りで実行している。
- 成果物の評価を、生成とは別のコンテキストで行っている。
- 進捗と判断の理由が、コンテキストの外のファイルに残る。
- エージェントの失敗を、対応する構成要素の変更につなげている。
