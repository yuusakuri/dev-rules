# ハーネスエンジニアリングガイドライン

## 1 はじめに

### 1.1 目的

この文書の目的は、AIエージェントの利用環境を設計する人が、指示、ツール及び検査を組み合わせ、成果物の正確さを確認しながら作業を任せられるようにすることである。

### 1.2 適用範囲

この文書は、Claude Code、CodexなどのAIエージェントに作業を任せる際に、リポジトリ及び実行環境へ利用者が追加する設定、文書、スクリプト及び検査の設計を規定する。対話で使用する場合にも、無人で実行する場合にも適用する。

エージェントをいつ起動し、どの条件で繰り返し、いつ停止するかは、ループエンジニアリングガイドラインで規定する。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| LLM（large language model、大規模言語モデル） | 大量の文章を学習し、文章の生成又は分析を行うモデル。 |
| MCP（Model Context Protocol） | AIアプリケーションと外部のツール又はデータを接続するための通信規約。 |
| コンテキスト | モデルが応答を生成する際に参照する指示、会話及びツールの出力などの情報。 |
| フック | 指定したイベントの発生時に処理を実行する仕組み。 |
| ハーネス | モデルの外側で、エージェントに与える指示、ツール、検査及び記録の仕組みの全体。この文書では、ツールの提供者が組み込んだ部分を除き、利用者が追加する部分を指す。 |
| リポジトリ | エージェントが読み書きするファイル及び変更履歴を管理する場所。プロジェクト指示、スキル及び設定もここに置く。 |
| 成果物 | エージェントが作成する文書、データ、プログラム、設定などの作業の結果。 |
| ガイド | エージェントが行動する前に、望ましい行動へ誘導する仕組み。プロジェクト指示、スキル、ひな形などがある。 |
| センサー | エージェントが行動した後に、成果物を検査して修正を促す仕組み。検査のスクリプト、レビューを行うエージェントなどがある。 |
| 決定論的な検査 | 形式、表記、数値、参照先の存在の確認のように、同じ入力に同じ結果を返す検査。 |
| 非決定論的な検査 | LLMによるレビュー又は評価のように、モデルの判断に基づく検査。 |

## 2 指示及び検査の設計原則

### 2.1 エージェントの失敗はハーネスの不足として扱う

エージェントが誤った手順を使用する、規約に反する、確認を省くといった失敗をした場合は、その場で修正を指示するだけで終了しない。同じ失敗が再び発生しないように、指示、ツール又は検査のいずれかを変更する。

失敗が繰り返される場合は、エージェントに不足しているツール、規則、ひな形又は資料を特定し、リポジトリへ追加する。

失敗ごとのハーネスの変更は、[表2](#table-2)による。

<a id="table-2"></a>表2−失敗ごとのハーネスの変更

| 発生した失敗 | 変更 |
| --- | --- |
| pnpmのプロジェクトで `npm install` を実行した。 | プロジェクト指示に“パッケージの操作はpnpmで行う”と書く。 |
| 月次レポートの売上を税込で集計した。 | プロジェクト指示に“売上は税抜で集計する”と書き、会計システムの総額と照合する検査を加える。 |
| 画面の変更で、表示を確認せずに完了と報告した。 | 開発サーバーを起動して画面を撮影する手順をスキルにする。 |

### 2.2 守らせる規則は仕組みで強制する

実行を保証する必要がある規則は、フック及び検査で強制する。プロジェクト指示又はスキルに書いた要求だけでは、実行したことを確認できないためである。

規則の種類ごとの置き場所は、[表3](#table-3)による。

<a id="table-3"></a>表3−規則の種類ごとの置き場所

| 規則の種類 | 置き場所 |
| --- | --- |
| 判断の目安<br>手順<br>規約の意図（例：見積書は結論から書く） | プロジェクト指示<br>スキル |
| 毎回同じ処理を実行する（例：ファイルの変更後に `prettier --write` を実行する） | フック |
| 成果物が規約を満たしていることを確認する（例：`tsc --noEmit` が通るまで完了にしない） | 検査 |

指示の文面を強めても守られない規則は、フック又は検査へ移す。逆に、好みにすぎないフックは削除し、エージェントの判断に任せる。

### 2.3 ガイドとセンサーとを組み合わせる

各規則には、事前に実施方法を伝えるガイド及び事後に結果を検査するセンサーを用意する。両方を組み合わせ、作業前に手順を示すとともに、実施後の違反を検出する。

ガイド及びセンサーの例は、[表4](#table-4)による。

<a id="table-4"></a>表4−ガイド及びセンサーの例

| 規則 | ガイド | センサー |
| --- | --- | --- |
| エラーのログにリクエストIDを含める。 | プロジェクト指示にログの書き方を書く。 | エラーのログの呼出しを検査し、違反をファイル及び行で報告するスクリプト。 |
| 列を削除するデータ移行には、データの移し替えの手順を含める。 | 移行の手順をスキルにする。 | 列の削除だけを含む移行を不合格にする検査。 |
| 見積書に、前提条件、範囲、金額、有効期限の4項目を含める。 | 見積書のひな形を置く。 | 4項目の見出しの有無を確認するスクリプト。 |

### 2.4 決定論的な検査を優先する

検査は、同じ入力に同じ結果を返す決定論的な方法を優先する。結果の比較が容易であり、形式又は数値の違反を繰り返し検出することが可能になる。意味の判断を要する箇所には、その後にLLMなどによる非決定論的な検査を使用する。

例えば、提案書の必須の見出しの有無及びリンク切れは決定論的な検査で確認し、論旨が顧客の課題に答えているかは非決定論的な検査で確認する。

### 2.5 小さく開始し、失敗を確認してから追加する

最初は、プロジェクト指示及び合否を返す検査コマンドを一つ用意する。その後は、実際に発生した失敗の原因に対応する構成要素を補い、効果を検証する。

### 2.6 モデルの能力に合わせて見直す

ハーネスの構成要素は、モデルが単独ではできないことを補うために置く。新しいモデルへ切り替えた場合は、各構成要素を外した場合の結果を確認し、効果のなくなった構成要素を取り除く。

Anthropicのアプリケーション開発のハーネスでは、Claude Sonnet 4.5で必要だったコンテキストのリセットをClaude Opus 4.5で廃止し、スプリント単位の分割及び評価をClaude Opus 4.6で廃止して、計画エージェント及び最後に1回だけ実行する評価エージェントを残した。

## 3 構成要素の選び方

### 3.1 目的に合う構成要素を選ぶ

構成要素は、作業に必要な情報を必要な時点で渡す方式から選ぶ。常に読み込む情報は全ての作業の費用及び精度に影響するため、特定の作業だけで必要な情報は、その作業を開始するときに読み込む。

構成要素は、[表5](#table-5)による。

<a id="table-5"></a>表5−構成要素

| 構成要素 | 目的 | コンテキストへの影響 | Claude Code | Codex |
| --- | --- | --- | --- | --- |
| プロジェクト指示 | 全ての作業で必要な事実及び規則を伝える。 | 常に入る。 | `CLAUDE.md`。`AGENTS.md` も読み込める。 | `AGENTS.md`<br>`AGENTS.override.md` |
| 範囲を限定した指示 | 特定のディレクトリ又はファイルの種類だけに適用する規則を伝える。 | 該当する範囲で入る。 | `.claude/rules/*.md`（`paths` で対象を限定する）、サブディレクトリの `CLAUDE.md` | サブディレクトリの `AGENTS.md` |
| スキル | 手順、参照資料及び確認の方法を必要な場合に読み込む。 | 説明だけが常に入り、本体は使用する場合に入る。 | `.claude/skills/<名前>/SKILL.md` | `.agents/skills/<名前>/SKILL.md` |
| サブエージェント | 独立したコンテキストで作業させ、要約だけを受け取る。 | 主のコンテキストには結果だけが入る。 | `.claude/agents/*.md` | `.codex/agents/*.toml` |
| 外部のツール | 外部のサービス又はデータへ接続する。 | ツールの名前及び説明が入る。 | MCPサーバー | MCPサーバー |
| フック | 定めた時点で処理を必ず実行する。 | 出力を返した場合だけ入る。 | `.claude/settings.json` の `hooks` | `.codex/hooks.json` |
| 検査 | 成果物を検査し、修正を促す。 | 失敗の出力だけが入る。 | フック又は定期的な処理から実行する。 | フック又は定期的な処理から実行する。 |

[表6](#table-6)のきっかけが発生した場合に、対応する構成要素を追加する。

<a id="table-6"></a>表6−構成要素を追加するきっかけ

## 4 プロジェクト指示

### 4.1 プロジェクト指示は目次として短く保つ

プロジェクト指示は、全ての作業でコンテキストを占めるため、詳細を書かず、詳細な文書への道順を示す目次とする。1ファイルあたり200行以内を目安にする。CodexはAGENTS.mdの合計が既定で32KiBを超えると、それ以降を読み込まない。

### 4.2 全ての作業で必要な事実だけを書く

プロジェクト指示には、[表7](#table-7)の事項を書く。

<a id="table-7"></a>表7−プロジェクト指示に書く事項

| 書く事項 | 例 |
| --- | --- |
| 結果の確認方法 | “1ファイルのテストは `pnpm test <ファイル>`、全体は `pnpm test` で実行する” |
| 読むと誤解する箇所 | “`legacy/` の書き方は新しいコードで真似しない”“`archive/` は使われていないように見えるが、月次の集計が参照している” |
| リポジトリから読み取れない決定 | “エラーの処理は `AppError` に統一すると決めた”“売上は税抜で集計する” |
| 2回訂正した事項 | “金額は3桁ごとにカンマで区切る” |

ファイルの一覧又は一般的な言語の規約のように、読めば分かることは書かない。書く前に、エージェントが読んで検出できるか、実際に参照するかを確認し、どちらも当てはまる場合は書かない。

一部の範囲だけに適用する規則は範囲を限定した指示へ、複数の手順からなる作業はスキルへ分ける。

### 4.3 両ツールで共有する指示はAGENTS.mdに書く

Claude Code及びCodexの両方で使用するリポジトリでは、プロジェクト指示を `AGENTS.md` に書き、`CLAUDE.md` からは `@AGENTS.md` で取り込む。同じ内容を二つのファイルに書くと、片方だけが更新されて矛盾する。

### 4.4 知識はリポジトリに置く

判断の経緯、規約、計画及び仕様は、変更履歴を管理する文書としてリポジトリに配置し、プロジェクト指示から参照する。会話だけで共有した事項又は接続していない文書ツールにある事項も、作業時に参照可能になる。

### 4.5 矛盾及び古い記述を取り除く

プロジェクト指示、範囲を限定した指示及びスキルを定期的に見直し、矛盾及び古い記述を修正する。作業の種類によって適用される指示が変化する場合も、判断の不一致を防ぐ。

## 5 スキル及びサブエージェント

### 5.1 繰り返す手順をスキルにする

複数の手順からなる作業、参照資料及びチームの基準は、スキルにする。スキルの説明には、どの作業で使用するかを具体的に書く。説明が曖昧だと、エージェントは必要なスキルを使用しないか、誤ったスキルを使用する。

スキルの説明の例は、[表8](#table-8)による。

<a id="table-8"></a>表8−スキルの説明の例

| 説明の良否 | 例 |
| --- | --- |
| 曖昧 | “レポートを助ける” |
| 具体的 | “月次売上レポートを作成又は更新する場合に使用する。部門別の集計、会計システムの総額との照合、前月比の算出の手順を含む” |

### 5.2 確認の手順をスキルにする

作業の完了前に行う確認を、手順としてスキルに書く。確認の手順には、実行するコマンド、確認する結果及び失敗した場合の対応を書き、全ての手順を通過するまで完了を報告させない。完了の報告には、実行したコマンド及び出力を証拠として含めさせる。

確認のスキルの例は、[表9](#table-9)による。

<a id="table-9"></a>表9−確認のスキルの例

| スキル | 手順 |
| --- | --- |
| `verify-frontend-change` | 開発サーバーを起動する。変更した操作を実行し、操作の前後の画面を撮影する。コンソールの新しいエラーが0件であることを確認する。Core Web Vitalsを計測する。失敗した場合は修正し、最初の手順から再試行する。 |
| `verify-log-hygiene` | エラーの処理のログにリクエストIDがあり、リクエストの本文を含まないことを確認する。違反をファイル及び行で報告し、修正する。 |
| `verify-monthly-report` | 全部門の行があることを確認する。部門の合計と会計システムの総額とが1円単位で一致することを確認する。前月比の計算を再計算して照合する。不一致の部門及び差額を報告する。 |

### 5.3 大量の読み込み及び独立した作業はサブエージェントへ渡す

多数のファイルの調査、記録の分析及び独立した部分の作業は、サブエージェントへ渡し、主のコンテキストには要約だけを戻す。

例えば、Anthropicのマーケティングのチームは、数百件の広告のCSVから成果の悪い広告を検出するサブエージェントと、文字数の制限の中で広告文の案を作成するサブエージェントとに分けている。

### 5.4 生成及び評価を別のコンテキストに分ける

エージェントは、自分が作成した成果物を甘く評価する。成果物の評価は、生成したコンテキストとは別のサブエージェントに行わせる。評価エージェントには、生成の経緯ではなく、成果物、評価の基準及び検査の出力を渡す。

評価エージェントが甘い判定をする場合は、評価の記録を読み、人の判断と異なる箇所を手順及び基準へ反映する。主観的な基準には、点数の内訳を付けた評価の例を与える。

評価の基準は、項目及び合格のしきい値で書き、一つでもしきい値を下回る場合は差し戻す。Anthropicは、画面のデザインの評価エージェントに[表10](#table-10)の項目を使用し、モデルが既定で苦手な上の2項目の重みを高くした。

<a id="table-10"></a>表10−デザインの評価の項目

| 項目 | 確認すること |
| --- | --- |
| デザインの質 | 全体が一貫した印象を持つまとまりになっているか。 |
| 独自性 | ひな形のままではなく、意図した選択の跡があるか。 |
| 作り込み | 文字の組み方、余白、配色及びコントラストが整っているか。 |
| 機能性 | 利用者が操作を理解し、目的を達成できるか。 |

レビューを依頼されたエージェントは、問題を必ず何か検出しようとする。依頼では対象を絞り、例えば“差分を `SPEC.md` と照合し、未実装の要件と、挙げた例外の処理の漏れだけを報告する。書き方の好みは報告しない”と指示する。

### 5.5 サブエージェントのツールを役割に合わせて選ぶ

調査又は評価を行うサブエージェントには、読み取りのツールだけを与える。書き込みが必要なサブエージェントを並列に実行する場合は、作業ディレクトリを分ける。

## 6 エージェントが使用するツール及び環境

### 6.1 エージェントが自分で結果を確認できるようにする

エージェントが成果物を確認するためのツールを用意し、プロジェクト指示又はスキルで使用方法を示す。

結果の確認に用いるツールは、[表11](#table-11)による。

<a id="table-11"></a>表11−結果の確認に用いるツール

| ツール | 例 |
| --- | --- |
| 変更した部分だけを検査するコマンド | `pnpm test src/auth/session.test.ts`、`markdownlint docs/pricing.md` |
| 成果物を実際に使用して確認する手段 | Playwrightで画面を操作して撮影する。生成したPDFを画像にして確認する。SQLで移行後の件数を集計する。 |
| 実行の記録を検索する手段 | 直近1時間のエラーのログを、リクエストIDで検索するコマンド。 |

### 6.2 環境の準備を一つのコマンドにする

ツールの導入、データの準備及び実行環境の起動は、`./init.sh` のような一つのコマンドで実行できるようにする。エージェントが準備の方法を毎回調査すると、時間を浪費し、準備の誤りが作業の誤りに見える。

### 6.3 ツールの出力をエージェントが読める形にする

ツールの出力は、必要な情報だけを短く返す。エラーの出力には、違反した規則及び修正の方法を含める。長い出力はファイルへ保存し、要約及び保存先を返す。

ツールの出力の例は、[表12](#table-12)による。

<a id="table-12"></a>表12−ツールの出力の例

| 出力の良否 | 例 |
| --- | --- |
| 修正できない | `check failed` |
| 修正できる | `reports/2026-10.md:12 営業部の合計が会計の総額と1 200円一致しない。data/ledger.csv の10月分から再集計する。` |

### 6.4 ツールの数及び重複を抑える

役割が重なるツールが多いと、エージェントは使用するツールを誤る。ツールは役割が重ならないように選び、使用しない外部のツールは接続しない。

### 6.5 広く使われていて資料のそろったツールを選ぶ

エージェントが扱うツール、形式及びライブラリは、広く使われていて、資料がそろい、挙動を説明できるものを選ぶ。

## 7 検査

### 7.1 速い検査は変更のたびに実行する

成果物の形式、表記、参照先及び数値の整合を確認する速い検査は、ファイルの変更後のフックで実行し、結果をエージェントへ返す。

成果物ごとの検査は、[表13](#table-13)による。

<a id="table-13"></a>表13−成果物ごとの検査

| 成果物 | 速い検査 | 重い検査 |
| --- | --- | --- |
| プログラム | フォーマッター<br>ESLint<br>`tsc --noEmit`<br>変更したファイルのテスト | 全てのテスト<br>ミューテーションテスト<br>依存の方向の検査 |
| 文書 | markdownlint<br>リンク切れ<br>用語の表記の検査 | 全文書の用語の統一<br>仕様との照合<br>評価エージェントのレビュー |
| データ | スキーマの検証<br>必須の項目の欠損の検査 | 移行元との件数及び合計の照合、重複の検査 |
| 集計レポート | 全部門の行の有無<br>合計の再計算 | 会計システムの総額との照合<br>前月比の異常値の確認 |

### 7.2 重い検査は区切りで実行する

成果物の全体を対象とする検査、及び時間のかかる検査は、作業の区切り又は定期的な処理で実行する。区切りの検査では、速い検査も再度実行する。

### 7.3 構成の規則を検査で強制する

成果物の構成、命名、大きさ、書式などの規則は、検査のスクリプトで確認する。検査の失敗の出力には、修正の方法を含め、エージェントが出力だけで修正できるようにする。例えば、OpenAIのチームは、層の間の依存の方向、ログの形式及びファイルの大きさをリンター及び構造のテストで検査し、エラーの文面に修正の方法を書いている。

### 7.4 劣化を継続的に検出する

使われなくなった資料、重複、古くなった記述、成果物の間の不一致及びリンク切れは、定期的に検出する。検出した項目は、範囲を絞った修正として、エージェントに定期的に修正させる。OpenAIのチームは、週の20%を使用していた金曜日の整理作業を、基準からの逸脱を検出して修正を提案する定期的なエージェントへ移した。

### 7.5 非決定論的な検査は基準で較正する

LLMによるレビュー又は評価を検査に使用する場合は、評価の基準、合格のしきい値（例：各項目を5段階で評価し、全項目が4以上で合格）及び評価の例を与える。非決定論的な検査の結果は、決定論的な検査の結果を上書きしない。

## 8 状態の引き継ぎ

### 8.1 進捗はコンテキストの外に残す

長い作業では、コンテキストの圧縮又はセッションの切り替えで、それまでの経緯が失われる。作業の計画、進捗及び判断の理由は、リポジトリのファイル及び変更履歴へ残す。

進捗を残すファイルは、[表14](#table-14)による。

<a id="table-14"></a>表14−進捗を残すファイル

| ファイル | 内容 |
| --- | --- |
| `SPEC.md` | 完了の定義。人とエージェントとの間で合意した要件及び例外。 |
| `progress.md` | 各セッションの終了時に追記する、実施した事項、次に実施する事項及び判断の理由。 |
| `items.json` | 項目ごとの完了の状態。 |
| `init.sh` | 環境を準備し、基本の動作を確認するスクリプト。 |

### 8.2 機械が更新する状態は構造化した形式にする

完了した項目の一覧のように、エージェントが更新する状態は、JSONなどの構造化した形式で保存し、更新してよい項目を限定する。自由な文章の形式では、エージェントが項目を書き換える、又は削除する場合がある。

Anthropicのアプリケーション開発の例では、200件を超える機能を、分類、説明、確認の手順、`passes` の4項目で一覧にし、全てを `passes: false` で開始して、エージェントには `passes` だけを更新させた。

### 8.3 セッションの開始時に状態を読み込ませる

セッションの開始時には、作業ディレクトリ、変更履歴、進捗のファイル及び未完了の項目を確認させる。フックで、セッションの開始時及び圧縮の後に、現在の状態をコンテキストへ加える。Anthropicの例では、作業ディレクトリの確認、`git log` 及び進捗のファイルの読み込み、機能の一覧からの選択、並びに `init.sh` 及び基本の動作の確認を順に行わせている。

### 8.4 1回のセッションで扱う作業を限定する

1回のセッションで扱う作業は、機能1件、問い合わせ1件、ファイル1件のように一つの項目に限定し、完了するたびに確認及び変更の記録を行わせる。複数の項目を同時に進めると、未完成の変更が残ったまま次のセッションへ渡る。

## 9 ハーネスの改善

### 9.1 失敗の原因に対応する構成要素を修正する

エージェントの失敗は、原因を分類し、対応する構成要素を変更する。

失敗の原因ごとの変更は、[表15](#table-15)による。

<a id="table-15"></a>表15−失敗の原因ごとの変更

| 失敗の原因 | 変更する構成要素 | 例 |
| --- | --- | --- |
| 誤ったコマンド又はツールを使用した。 | プロジェクト指示<br>ツール | テストを全件で実行し続けた → 1ファイルだけのコマンドを書く。 |
| 手順を飛ばした、順序を誤った。 | スキル | 照合の前にレポートを完了とした → 照合を手順に含める。 |
| 誤りが検出されずに残った。 | 検査 | 税込と税抜の取り違えが残った → 会計の総額との照合を加える。 |
| 必要な知識がなかった。 | リポジトリの資料<br>スキル | 会議で決めた締め日を知らなかった → 決定を文書にして参照する。 |
| 準備又は起動の方法を調査するのに時間を使用した。 | 環境の準備のコマンド | セッションごとに起動の方法を調査した → `init.sh` を用意する。 |
| 自分の成果物を誤って合格とした。 | 別のコンテキストの評価エージェント<br>検査 | 単体テストだけで機能を完了とした → 画面を操作して確認する評価エージェントを置く。 |

### 9.2 ハーネスの変更をレビューする

ハーネスのファイルは、変更履歴を残し、変更をレビューする。エージェントがハーネスを変更する場合も、人がレビューしてから取り込む。

### 9.3 ハーネスの効果を確認する

一度も失敗を検出しない検査は、品質が高いことを示すとは限らない。意図的に規則へ違反した成果物（例：合計を1円ずらしたレポート、リンクを切った文書）で、検査が失敗を検出することを確認する。

### 9.4 同じ形の作業にはテンプレートを使用する

同じ形の作業（例：業務APIのサービス、データの可視化、月次レポート）が複数ある場合は、ガイド及びセンサーをテンプレートにまとめて共有する。テンプレートから作成したリポジトリでも、テンプレートの更新を取り込む手順を定めておく。

## 10 チェックリスト

- プロジェクト指示が目次として短く保たれ、詳細な資料及び手順への道順を示している。
- Claude Code及びCodexの両方で使用する場合に、プロジェクト指示が `AGENTS.md` の1か所にある。
- 必ず守らせる規則を、指示ではなくフック及び検査で強制している。
- 規則ごとに、事前に誘導するガイド及び事後に検出するセンサーがある。
- エージェントが自分で成果物を確認するためのツール及びその使用方法の説明がある。
- 速い検査を変更のたびに、重い検査を作業の区切りで実行している。
- 成果物の評価を、生成とは別のコンテキストで行っている。
- 進捗及び判断の理由が、コンテキストの外のファイルに残る。
- エージェントの失敗を、対応する構成要素の変更につなげている。
