# AIエージェントの認証ガイドライン

## 1 はじめに

### 1.1 目的

この文書の目的は、AIエージェントの運用者が、実行環境に応じた認証方式を選び、認証が必要な作業を継続可能にすることである。

### 1.2 適用範囲

この文書は、Claude Code、Codexなどのエージェント自身及び作業で利用するシステムの認証方式について規定する。対話で利用する環境及び無人で実行する環境に適用する。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| API（application programming interface） | プログラムから他のシステムの機能又はデータを利用するためのインターフェース。 |
| CLI（command-line interface） | コマンドを入力してプログラムを操作するインターフェース。 |
| MCP（Model Context Protocol） | AIアプリケーションと外部のツール又はデータを接続するための通信規約。 |
| OAuth | 利用者の承認に基づき、アプリケーションへアクセス権限を委任する仕組み。 |
| CDP（Chrome DevTools Protocol） | Chromium系ブラウザを外部のプログラムから操作又は調査するための通信規約。 |
| TOTP（time-based one-time password） | 共有する秘密値及び現在時刻から生成する、有効期間が短い認証コード。 |
| 認証情報 | ログインに使用するパスワード、APIキー、トークン、ワンタイムコードなどの情報。 |
| コンピュータ使用 | エージェントが画面を見て、クリック及び入力でデスクトップアプリを操作する機能。 |
| ストレージステート | ブラウザのCookie、ローカルストレージなどのログイン状態を保存したファイル。 |
| ユーザーデータディレクトリ | ブラウザのプロファイルを保存するディレクトリ。 |
| パスワードマネージャー | 認証情報を保管し、要求に応じて提供するソフトウェア。 |
| ペアリング | パスワードマネージャーの側とエージェントの側とを接続するための、最初の登録の手順。 |

## 2 方式の選び方

### 2.1 APIに近い方式から順に検討する

認証方式は、[表2](#table-2)の順に検討し、作業に必要な操作を利用可能な方式から選ぶ。MCPサーバー、CLI及びAPIは、画面の配置に依存せずに操作を実行可能なため、画面操作より先に検討する。

<a id="table-2"></a>表2−ログインの方式の検討順

| 順 | 方式 | 向く対象 | 例 |
| --- | --- | --- | --- |
| 1 | MCPサーバーのOAuth | MCPサーバーのあるサービス | `/mcp` でSentryにログインする。 |
| 2 | CLI又はAPIのトークン | CLI又はAPIのあるサービス | `gh` でプルリクエストを作成する。 |
| 3 | 保存したブラウザのログイン状態 | APIがなく、ブラウザで使用するサービス | 経費精算システムの画面を操作する。 |
| 4 | パスワードマネージャーからの入力 | ログインの状態を保てないサービス | 毎回ログインが必要な社内の管理画面を操作する。 |
| 5 | コンピュータ使用及び人のログイン | デスクトップアプリ | 会計ソフトの画面を操作する。 |

### 2.2 環境に合う方式を選ぶ

環境ごとの方式は、[表3](#table-3)による。

<a id="table-3"></a>表3−環境ごとの方式

| 環境 | 使用できる方式 | 使用できない、又は向かない方式 |
| --- | --- | --- |
| 手元のPCで対話する。 | 全ての方式。ログインの画面は、人が操作できる。 | なし |
| 手元のPCで無人で実行する。 | トークン、保存したログイン状態、パスワードマネージャーからの入力 | コンピュータ使用（Claude Codeの `-p` では使用できない。）、ログインの画面で人の操作を待機する方式 |
| クラウドのセッション又はコンテナで実行する。 | トークン、ストレージステート、手元のパスワードマネージャーとの接続 | 手元のブラウザの共有、コンピュータ使用 |
| CIで実行する。 | トークン、サービスアカウント | 人の承認を毎回必要とする方式 |

### 2.3 認証情報を会話に含めない

パスワード及びトークンの値は、プロンプト、ツールの引数、ログ及びスクリーンショットに含めない。会話に含めた値は履歴に残り、コンテキストの圧縮又は要約にも引き継がれる。エージェントには、認証済みの接続又は認証情報をコマンドへ渡す仕組みを提供する。

認証情報の渡し方は、[表4](#table-4)による。

<a id="table-4"></a>表4−認証情報の渡し方

| 悪い渡し方 | 良い渡し方 |
| --- | --- |
| プロンプトに“パスワードは xxxx”と書く。 | ログイン済みのブラウザを使用させる。 |
| ブラウザのツールの入力の引数にパスワードを渡す。 | スクリプトが環境変数から読み取ってフォームへ入力する。 |
| `cat .env` で値を読ませる。 | `op run` 又は `aac run` でコマンドの環境変数へ渡す。 |

## 3 エージェント自身のログイン

### 3.1 Claude Codeのログインを環境で選ぶ

Claude Codeのログインの方式は、[表5](#table-5)による。

<a id="table-5"></a>表5−Claude Codeのログインの方式

| 環境又は条件 | 方式 | 手順 |
| --- | --- | --- |
| 対話 | サブスクリプション | `claude` を起動してブラウザでログインする。 |
| 無人（ブラウザなし） | 長期トークン | `claude setup-token` で1年間のトークンを生成し、`CLAUDE_CODE_OAUTH_TOKEN` に設定する。 |
| 無人（API課金） | APIキー | `ANTHROPIC_API_KEY` を設定する。 |
| 短期のキー | ヘルパー | `apiKeyHelper` にキーを出力するスクリプトを設定する。 |
| 複数のアカウント | 設定の分離 | `CLAUDE_CONFIG_DIR` をアカウントごとに分ける。 |

複数の認証情報がある場合は、環境変数が `/login` より優先される。意図と異なるアカウントになる場合は、`/status` で使用中の認証情報を確認する。

クラウドのセッションは、常にサブスクリプションの認証情報を使用し、`apiKeyHelper` 及び `ANTHROPIC_API_KEY` を読み込まない。

`claude setup-token` のトークンで実行できるのは、モデルのリクエストだけである。Remote Control及びclaude.aiのコネクターには使用できない。

### 3.2 Codexのログインを環境で選ぶ

Codexのログインの方式は、[表6](#table-6)による。

<a id="table-6"></a>表6−Codexのログインの方式

| 環境 | 方式 | 手順 |
| --- | --- | --- |
| 対話 | ChatGPTのログイン | `codex login` でブラウザからログインする。 |
| ブラウザのない環境 | デバイスコード（ベータ） | ChatGPTのセキュリティ設定又はワークスペースの権限でデバイスコードのログインを有効にしてから、`codex login --device-auth` を実行する。 |
| 無人、CI | APIキー | `printenv OPENAI_API_KEY \| codex login --with-api-key` を実行する。 |
| 企業の無人の業務 | Codexのアクセストークン | ChatGPT Enterpriseの管理者からトークンの作成の権限を受けてから、`printenv CODEX_ACCESS_TOKEN \| codex login --with-access-token` を実行する。 |

Codex Cloudは、ChatGPTのログインを必要とする。

## 4 API及びMCPサーバーの認証

### 4.1 MCPサーバーはOAuthから使用する

MCPサーバーの認証の方式は、[表7](#table-7)による。

<a id="table-7"></a>表7−MCPサーバーの認証の方式

| サーバーの条件 | 方式 | 手順 |
| --- | --- | --- |
| OAuthに対応する。 | ブラウザでログインする。 | `/mcp` 又は `claude mcp login <名前>` を実行する。 |
| ブラウザのない環境で使用する。 | 認可URLの出力 | `claude mcp login <名前> --no-browser` を実行する。 |
| 動的クライアント登録に対応しない。 | 事前に登録したクライアント | `claude mcp add` に `--client-id`、`--client-secret` 及び `--callback-port` を付ける。 |
| 固定のトークンを使用する。 | 環境変数の展開 | `.mcp.json` の `headers` に `Bearer ${API_KEY}` と書く。 |
| 短期のトークン又は社内のSSOを使用する。 | 動的なヘッダー | `headersHelper` にヘッダーを出力するスクリプトを設定する。 |

`claude -p` 及びAgent SDKでは、OAuthのログインを実行できない。無人で実行する前に、対話のセッションの `/mcp` 又はシェルの `claude mcp login <名前>` でログインする。

`.mcp.json` には値を直接記載せず、環境変数で参照する。

### 4.2 トークンの権限を作業に合わせる

トークンは、担当する作業に必要な範囲で発行する。範囲が足りない場合は、MCPサーバーが403の `insufficient_scope` を返す。この場合は、`.mcp.json` の `oauth.scopes` に範囲を追加し、`/mcp` で再度ログインする。

トークンの範囲の例は、[表8](#table-8)による。

<a id="table-8"></a>表8−トークンの範囲の例

| 作業 | 発行する範囲の例 |
| --- | --- |
| Slackの通知 | `chat:write` |
| Slackの検索及び通知 | `channels:read chat:write search:read` |
| GitHubの課題の整理 | 対象のリポジトリの課題 |

## 5 コマンドへの認証情報の受け渡し

### 5.1 環境変数でコマンドに渡す

パスワードマネージャーの値は、実行するコマンドの環境変数へ渡す。エージェントはコマンドを起動するだけで、値を読み取らない。

コマンドへ認証情報を渡す手段は、[表9](#table-9)による。

<a id="table-9"></a>表9−コマンドへ認証情報を渡す手段

| 手段 | 例 | 特徴 |
| --- | --- | --- |
| 1Password CLI | `op run --env-file=.env -- ./deploy.sh` | `.env` に `op://vault/item/field` の形で参照を書く。CIではサービスアカウントで認証する。 |
| Bitwarden Agent Access | `aac run --domain example.com --env DB_USER=username --env DB_PASSWORD=password -- psql` | 要求ごとに手元で承認する。クラウドのエージェントから手元の保管庫へ接続できる。 |

環境変数の値を出力するコマンドを実行させない。確認する場合は、値ではなく文字数を出力する。

### 5.2 Agent Accessを使用する手順

Bitwarden Agent Accessは、手元のパスワードマネージャーとエージェントの環境とを、中継サーバーを経由して接続する。

Agent Accessの手順は、[表10](#table-10)による。

<a id="table-10"></a>表10−Agent Accessの手順

| 順 | 場所 | 操作 |
| --- | --- | --- |
| 1 | 手元 | `aac listen` を起動して保管庫のロックを解除し、ペアリングのトークンを表示する。 |
| 2 | エージェント | `aac connect --token <トークン> --output json` でペアリングする。 |
| 3 | エージェント | `aac run --id <項目のID> --env-all -- <コマンド>` でコマンドを実行する。 |
| 4 | 手元 | 要求を確認して承認する。 |

利用者の検証では、[表11](#table-11)の事項が報告されている。

<a id="table-11"></a>表11−Agent Accessの症状及び対処

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| 数秒で拒否される。 | 同じドメインに複数のログインがある、又は `BW_SESSION` が古い。 | 項目のIDで指定する。保管庫のロックを解除し直す。 |
| 約120秒で時間切れになる。 | 手元で承認していない。 | 承認の通知を別に用意する。 |

Agent Accessはearly previewであり、API及びプロトコルが変更されることがある。継続的な業務に組み込む場合は、版を固定する。

## 6 ブラウザのログイン

### 6.1 方式を比べて選ぶ

ブラウザのログインの方式は、[表12](#table-12)による。

<a id="table-12"></a>表12−ブラウザのログインの方式

| 方式 | 動作 | 向く場面 | 注意点 |
| --- | --- | --- | --- |
| ログイン済みのブラウザを共有する。 | 手元のChromeのログイン状態を使用する。 | 手元のPCでの対話 | 人のアカウントとして操作される。 |
| 専用のプロファイルを保つ。 | ユーザーデータディレクトリにログイン状態を保存する。 | 手元のPC又はサーバーでの無人の作業 | 一つのプロファイルを同時に使用できるのは一つのブラウザだけである。 |
| ストレージステートを読み込む。 | 保存したファイルからログイン状態を読み込む。 | クラウド、コンテナ、CI | 期限が切れた場合は、作成し直す。 |
| スクリプトで入力する。 | スクリプトが環境変数の値をフォームへ入力する。 | ログインの状態を保てないサービス | 画面の変更でスクリプトが壊れる。 |
| パスワードマネージャーが入力する。 | 人の承認の後に、パスワードマネージャーがフォームへ入力する。 | 対応するエージェント | 対応するエージェント及び環境が限られる。 |

### 6.2 Chromeを共有して、ログインの画面だけ人が操作する

Claude Codeの `--chrome` は、Chromeのログイン状態を共有し、Google Docs、Gmail、Notionなどをコネクターなしで操作できる。ログインの画面又はCAPTCHAに遭遇すると一時停止するため、人がログインしてから再開を指示する。Chrome統合は `/login` でのサインインを必要とし、APIキー又は `claude setup-token` のトークンでは使用できない。

Playwright MCPの `--extension` は、実行中のChrome又はEdgeのタブに接続して、同じようにログイン状態を使用する。

### 6.3 専用のログイン状態を保存して再利用する

ログイン状態を保存する手段は、[表13](#table-13)による。

<a id="table-13"></a>表13−ログイン状態を保存する手段

| 手段 | 設定 | 内容 |
| --- | --- | --- |
| Playwright MCPのプロファイル | `--user-data-dir=<パス>` | ブラウザのデータを保存し、次回もログインを保つ。 |
| Playwright MCPのストレージステート | `--isolated --storage-state=<パス>` | ファイルからCookie及びローカルストレージを読み込む。 |
| Playwrightのテスト | `storageState` | 初回の処理でログインしてファイルへ保存し、後の処理で読み込む。役割ごとにファイルを分ける。 |
| Browser Use | `Browser.from_system_chrome()` | Chromeのプロファイルを再利用する。 |

ログイン状態のファイルは、リポジトリに含めない。Playwrightは `playwright/.auth` に置いて `.gitignore` へ追加することを勧めている。セッションストレージにログイン状態を保存するサービスでは、セッションストレージを別に保存して復元する。セッションストレージは、`storageState` に含まれないためである。

### 6.4 フォームへの入力はスクリプトに任せる

パスワードをフォームへ入力する場合は、値を会話に渡さず、環境変数から読み込むスクリプトで入力する。Claude CodeのPlaywright MCPへ認証済みのブラウザを接続する手順の実施例を[表14](#table-14)に示す。導入前に、対象のサービスで同じ接続方法を利用可能か確認する。

<a id="table-14"></a>表14−スクリプトによるログインの手順

| 順 | 操作 |
| --- | --- |
| 1 | 使い捨てのコンテナで、Chromiumを `--remote-debugging-port=9222` 及び一時的なプロファイルで起動する。 |
| 2 | `aac run` の中でログインのスクリプトを実行する。スクリプトはCDPで接続してフォームへ入力し、送信する。 |
| 3 | スクリプトは、終了時にパスワードの欄を空にし、URLのオリジン及びパスだけを出力する。 |
| 4 | `PLAYWRIGHT_MCP_CDP_ENDPOINT=http://localhost:9222` を設定して、Playwright MCPをログイン済みのブラウザへ接続する。 |

Playwright MCPの `--secrets` は、ツールの応答に現れた値を置き換える補助の機能である。値を会話に入れない手段としては使用しない。

### 6.5 パスワードマネージャーの自動入力は対応を確認する

1Password for Agentsは、エージェントがログインの画面に到達すると、利用者の端末で承認を求め、承認の後に入力する。エージェントはパスワードを受け取らない。製品のページはClaude及びChatGPT Workを連携先に挙げているが、提供中の一覧には含まれていない。Codexの記載はない。導入の前に、使用するエージェント及び環境で動作することを確認する。

## 7 コンピュータ使用のログイン

### 7.1 先に人がログインしておく

他の方式で扱えないデスクトップアプリには、コンピュータ使用を利用する。作業の前に人がアプリへログインし、認証済みの状態でエージェントへ引き継ぐ。

コンピュータ使用の対応は、[表15](#table-15)による。

<a id="table-15"></a>表15−コンピュータ使用の対応

| 製品 | 対応 | ログインに関わる事項 |
| --- | --- | --- |
| Claude Code | CLIはmacOS、デスクトップアプリはmacOS及びWindows。Pro、Max又はUltraプランでclaude.aiの認証を使用する対話のセッションに限る。Team及びEnterpriseプランでは使用できない。 | アプリをセッションごとに承認する。ブラウザは表示だけで操作できず、Webの作業はChrome統合を使用する。 |
| Codex | ChatGPTのデスクトップアプリ。macOS及びWindows。 | アプリの使用を承認する。ブラウザでは、ログイン済みのページを操作できる。認証情報を必要とする作業は、人がその場で各段階を承認できる場合に限る。管理者の認証又はOSの許可のプロンプトは人が操作する。 |

### 7.2 コンピュータ使用の作業の手順を定める

コンピュータ使用の作業の手順は、[表16](#table-16)による。

<a id="table-16"></a>表16−コンピュータ使用の作業の手順

| 順 | 担当 | 操作 | 例 |
| --- | --- | --- | --- |
| 1 | 人 | アプリを起動してログインする。 | 会計ソフトへログインする。 |
| 2 | 人 | エージェントを起動し、対象のアプリを承認する。 | 会計ソフトだけを承認する。 |
| 3 | エージェント | 作業を進める。 | 10月の仕訳を入力する。 |
| 4 | エージェント | ログインの画面又は再認証の画面が出たら止まり、人に通知する。 | “セッションが切れた。再度ログインが必要”と通知する。 |
| 5 | 人 | ログインして、再開を指示する。 | “続けて”と返信する。 |

無人で実行するデスクトップの作業は、セッションの有効期間が長いアプリに限る。Claude Codeのコンピュータ使用は `-p` では使用できない。

## 8 二段階認証

二段階認証の種類ごとの扱いは、[表17](#table-17)による。

<a id="table-17"></a>表17−二段階認証の種類ごとの扱い

| 種類 | エージェントの扱い | 手順 |
| --- | --- | --- |
| TOTP | スクリプトで処理できる。 | パスワードマネージャーのシークレットからコードを生成して入力する。Agent Accessでは `totp` にコードではなくシークレットが入る。 |
| メールのコード | メールを読めれば処理できる。 | メールのMCPサーバーで、送信元及び時刻で絞り込み、最新の1通からコードを取得する。 |
| SMSのコード | 人が処理する。 | 人がログイン画面へコードを入力し、完了後にエージェントを再開する。 |
| パスキー | ログイン状態を再利用する。 | 人が一度ログインしてログイン状態を保存する。Agent Accessはパスキーを扱えない。 |
| 認証アプリのプッシュ通知 | 人が処理する。 | 人が端末で承認する。 |
| CAPTCHA | 人が処理する。 | エージェントを止めて、人が操作する。Chrome統合は一時停止する。 |

人の操作が頻繁に必要なサービスは、API又はサービスアカウントへの切り替えを先に検討する。

## 9 ログインの維持及び失効

### 9.1 失効を想定して停止の方法を定める

失効の検知及び対応は、[表18](#table-18)による。

<a id="table-18"></a>表18−失効の検知及び対応

| 対象 | 失効の検知 | 対応 |
| --- | --- | --- |
| Claude Code | 期限切れまで3日以内になると、起動時に警告が表示される。失効後は、`/status` に `Expired` が表示され、モデルのリクエストが `Login expired` で失敗する。 | 無人の作業の前に `/login` で更新する。 |
| Codex | ChatGPTのログインは、使用中に期限の前に自動で更新される。 | 更新できない場合は再度ログインする。 |
| MCPサーバー | `/mcp` に認証が必要と表示される。 | `/mcp` で再度ログインする。 |
| ストレージステート | ログインの画面へ転送される。 | 作業の前にログイン後のページを開いて確認する。失効している場合は、作成し直す。 |
| 長期トークン | APIが401を返す。 | 期限の前に発行し直す。`claude setup-token` のトークンの有効期間は、1年である。 |

### 9.2 作業の前にログインを確認する

無人の作業は、開始する前にログインを確認する。途中で失効すると、作業が中断する。

ログインの確認方法は、[表19](#table-19)による。

<a id="table-19"></a>表19−ログインの確認方法

| 対象 | 確認方法の例 |
| --- | --- |
| GitHub | `gh auth status` |
| Claude Code | `claude auth status`、`/status` |
| ブラウザ | ログイン後のページを開き、利用者名が表示されることを確認する。 |

### 9.3 人の操作が必要な場合に通知する

ログイン、承認又はワンタイムコードの入力で人の操作を待機する場合は、Slack又はDiscordへ通知する。通知には、対象のサービス、必要な操作及び待機している作業を記載する。

Agent Accessの承認には通知がなく、約120秒で時間切れになる。このため、通知の仕組みを別に用意する。

例 `[経費精算] ログインが必要：セッションが切れた。ログインしたら“続けて”と返信する。未処理は残り12件`

## 11 チェックリスト

- サービスごとに、MCPサーバー、CLI、API、ブラウザ、コンピュータ使用の順で方式を検討した。
- 実行する環境（手元、クラウド、CI）で使用できる方式を選んだ。
- パスワード及びトークンの値を、プロンプト、ツールの引数、ログ及びスクリーンショットに含めていない。
- Claude Code及びCodex自身のログインの方式が、無人の実行に合っている。
- `/status` で、意図したアカウント及び認証情報を使用していることを確認した。
- `.mcp.json` に値を直接記載せず、環境変数又はヘルパーで渡している。
- トークンの範囲が、担当する作業に合っている。
- ログイン状態のファイルをリポジトリに含めていない。
- コンピュータ使用の前に、人が対象のアプリへログインしている。
- 二段階認証の種類ごとに、自動で処理するか人が処理するかを決定している。
- 無人の作業の前に、ログインを確認している。
- 人の操作が必要な場合に、通知が届く。
- early previewの手段は、版を固定している。
