# AI組織構築ガイドライン

## 1 はじめに

### 1.1 目的

本書の目的は、複数のAIエージェントを運用する設計者が、成果及び費用を評価しながら、役割分担と作業の管理方法を設計可能にすることである。

### 1.2 適用範囲

本書は、複数のAIエージェントが業務を分担する構成の設計及び運用について規定する。調査、文書作成、データ分析、顧客対応及びソフトウェア開発などの業務に適用する。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| LLM（large language model、大規模言語モデル） | 大量の文章を学習し、文章の生成又は分析を行うモデル。 |
| MCP（Model Context Protocol） | AIアプリケーションと外部のツール又はデータを接続するための通信規約。 |
| AI組織 | 複数のAIエージェントに役割、指示系統、目標、予算を与えて、業務を分担させる構成。 |
| マルチエージェント | 複数のエージェントが協調して一つの目的を達成する方式。 |
| オーケストレーション | エージェントの実行の順序、作業の割り当て、結果の統合を制御すること。 |
| リーダーエージェント | 作業を分解して他のエージェントへ割り当て、結果を統合するエージェント。 |
| サブエージェント | リーダーエージェントから作業を受けて、結果を返すエージェント。 |
| チームメイト | 共有のタスクリストとメッセージで、他のエージェントと直接協調するエージェント。 |
| ハンドオフ | 作業と会話の制御を、別のエージェントへ渡すこと。 |
| タスクリスト | 作業の項目、担当、状態、依存関係を共有する一覧。 |
| 品質ゲート | タスクの完了又は工程の移行の前に、条件を満たすかを確認する仕組み。 |

## 2 導入の判断

### 2.1 一つのエージェントで足りるかを先に確認する

AI組織は、一つのエージェントの改善で足りない場合に導入する。Anthropicのデータでは、エージェントはチャットのおよそ4倍、マルチエージェントはおよそ15倍のトークンを使用する。作業の価値が費用を上回る場合に限って導入する。

処理を関数で書ける場合は、エージェントを使用せず、関数で書く。

状況ごとの構成は、[表2](#table-2)による。

<a id="table-2"></a>表2−状況ごとの構成

| 状況 | 構成 | 例 |
| --- | --- | --- |
| 手順が決まっていて、判断が要らない。 | プログラム | 売上のCSVを集計して、決まった形式の表にする。 |
| 判断は要るが、一つの流れで進む。 | 一つのエージェント | 問い合わせを読み、手順書に沿って回答の案を作る。 |
| 必要な知識が多いが、同時に使用しない。 | 一つのエージェントとスキル | 請求、契約、配送の問い合わせに、該当する手順を読み込んで答える。 |
| 互いに独立した調査又は作業を同時に進められる。 | リーダーエージェントとサブエージェント | 競合10社の価格と機能を、社ごとに並行して調査して比較表にする。 |
| 担当者どうしの議論又は反証で質が上がる。 | エージェントチーム | 解約の増加の原因について、三つの仮説を別々に検証し、互いに反証する。 |
| 継続的な業務を、役割、目標、予算で管理する。 | 階層型の組織 | 記事の企画、執筆、校閲、配信を毎週繰り返し、部門ごとの費用を管理する。 |

### 2.2 複数のエージェントが向く作業と向かない作業を見分ける

複数のエージェントが向く作業の観点は、[表3](#table-3)による。

<a id="table-3"></a>表3−複数のエージェントが向く作業の観点

| 観点 | 向く | 向かない |
| --- | --- | --- |
| 依存関係 | 互いの途中経過を待たずに進められる。 | 前の作業の結果で次の作業が変わる。 |
| 文脈 | 担当ごとに必要な情報が分かれている。 | 全員が同じ文脈と細かな判断を共有する必要がある。 |
| 成果物 | 担当ごとに独立した成果物がある。 | 一つの成果物を複数の担当が同時に書き換える。 |
| 検証 | 完了を外部の基準で確認できる。 | 完了の判断が書き手の感覚に依存する。 |

Anthropicの調査システムでは、幅広い方向を同時に調査する質問で、複数のエージェントの構成が単独のエージェントより社内の評価で90.2%高い結果を出した。一方で、Cognitionは、分担した作業が暗黙の判断の違いで噛み合わない例を示し、文脈を共有できる単一のエージェントを推奨している。作業の性質で判断し、どちらかの構成を常に正しいものとして扱わない。

### 2.3 人の組織図から始めない

組織は、部署名又は役職からではなく、成果物と、独立して進められる作業の単位から設計する。AnthropicのProject Vendでは、店舗を運営するエージェントに経営者のエージェントを加えても、同じモデルであるため同じ弱点を持ち、効果が限られた。一方で、グッズの制作を担当するエージェントは、役割が明確に分かれていたことで成果を上げた。

役割の分け方の例は、[表4](#table-4)による。

<a id="table-4"></a>表4−役割の分け方の例

| 悪い分け方 | 良い分け方 |
| --- | --- |
| CEO、部長、課長、担当者を置く。 | 企画、調査、執筆、校閲のように、成果物の異なる役割を置く。 |
| 人の部署と同じ数のエージェントを置く。 | 並行して進められる作業の数だけ、エージェントを置く。 |
| 管理の層を増やして品質を上げる。 | 明確な手順と、実際の結果による検証で品質を上げる。 |

## 3 組織の型の選び方

### 3.1 作業の流れに合う型を選ぶ

最も単純な型から始める。複数の型を組み合わせてもよい。

組織の型は、[表5](#table-5)による。

<a id="table-5"></a>表5−組織の型

| 型 | 仕組み | 向く作業 | 注意点 | 例 |
| --- | --- | --- | --- | --- |
| シーケンシャル | 決めた順序で、前の成果物を次のエージェントへ渡す。 | 工程が決まっている作業 | 前の誤りが後へ伝わる。工程の間に品質ゲートを置く。 | 調査、執筆、校閲、配信 |
| 並行 | 同じ入力又は分割した入力を、複数のエージェントが同時に処理する。 | 独立した調査、複数の観点のレビュー | 結果の統合の方法を先に決める。 | 契約書を、法務、財務、事業の観点で同時に確認する。 |
| リーダーとサブエージェント | リーダーエージェントが作業を割り当て、結果を受け取って統合する。 | 最終の成果物を一つにまとめる作業 | リーダーエージェントの文脈と判断に依存する。 | 市場調査の報告書を、分野別の調査から作る。 |
| ハンドオフ | 受付のエージェントが、専門のエージェントへ会話の制御を渡す。 | 専門の担当が直接応答する窓口 | 引き継ぐ情報を決める。振り分けの誤りを評価する。 | 問い合わせを、請求、技術、解約の担当へ振り分ける。 |
| グループチャット | 共有の会話で、複数のエージェントが順に発言する。 | 議論、提案とレビューの往復 | 長い往復になりやすい。発言の順序と終了の条件を決める。 | 提案書の案を、作成者と顧客役とレビュアーで磨く。 |
| エージェントチーム | タスクリストを共有し、チームメイトが直接やり取りする。 | 互いの結果を検証する調査、担当の分かれた開発 | 調整の負荷とトークンが増える。 | 障害の原因を、複数の仮説に分けて互いに反証する。 |
| 階層型の組織 | 目標、指示系統、予算、承認を持つ組織として、継続的に運用する。 | 長く続く複数の業務 | 管理の層が増えるほど、費用と情報の損失が増える。 | 複数の製品のマーケティングを、製品ごとのチームで運用する。 |

### 3.2 流れの制御はコードかLLMかを工程ごとに決める

流れの制御の方式は、[表6](#table-6)による。

<a id="table-6"></a>表6−流れの制御の方式

| 制御 | 使用する場面 | 利点 | 例 |
| --- | --- | --- | --- |
| コード | 順序と条件が決まっている工程 | 速度、費用、結果を予測しやすい。 | 校閲に不合格なら執筆へ戻す。 |
| LLM | 入力によって進め方が変わる工程 | 想定していない質問に対応できる。 | 質問の内容から、調査の分割の方法を決める。 |

順序を守らせる必要がある工程は、LLMの判断に任せず、コードで制御する。

### 3.3 階層を増やさない

階層は、まず2段（リーダーとその下の担当）で構成する。Claude Codeのエージェントチームでは、チームメイトは自分のチームメイトを生成できず、リーダーは一つのセッションに固定される。3段以上にするのは、チームごとに目標と予算を分けて管理する必要がある場合に限る。

## 4 役割の設計

### 4.1 役割を成果物と責任で定義する

役割は、肩書ではなく、責任、成果物、完了の条件で定義する。“優秀なマーケティング部長として振る舞う”のような肩書だけの指示では、何を作れば完了かが決まらない。

役割の定義の項目は、[表7](#table-7)による。

<a id="table-7"></a>表7−役割の定義の項目

| 項目 | 内容 | 例（週次の売上レポートの分析担当） |
| --- | --- | --- |
| 名前 | 呼び分けに使用する短い名前 | `sales-analyst` |
| 責任 | この役割だけが負う仕事 | 売上データを分析し、前週との差の原因を特定する。 |
| 入力 | 受け取る情報 | `data/sales.csv`、前週のレポート |
| 成果物 | 作るものと形式 | `analysis.md`（差の上位3件、原因、根拠の数値） |
| 完了の条件 | 確認できる条件 | 全部門の合計が会計の総額と一致する。 |
| ツール | 役割に必要なものだけ | データベースの読み取り、Python |
| 報告先 | 結果を返す相手 | `report-lead` |
| モデル | 役割の難しさに合うもの | 中位のモデル |
| 予算 | 1回の上限 | 2ドル |

### 4.2 役割の重なりと空白をなくす

全ての成果物に、責任を持つ役割を一つだけ割り当てる。[表8](#table-8)のように、成果物と役割の対応を一覧にして確認する。

<a id="table-8"></a>表8−成果物及び役割の対応の例

| 成果物 | 作る | 確認する | 承認する |
| --- | --- | --- | --- |
| 調査メモ | `researcher` | `report-lead` | なし |
| レポートの原稿 | `writer` | `reviewer` | なし |
| 配信 | `report-lead` | `reviewer` | 人 |

### 4.3 作る役割と確認する役割を分ける

エージェントは自分の成果物を甘く評価するため、作る役割と確認する役割を分ける。確認する役割には、作成の経緯を渡さず、成果物と完了の条件を渡す。

### 4.4 監督の役割を結果で確認する

監督するエージェントの判断は、売上、誤りの件数又は差し戻しの件数などの実績と比較して評価する。同じモデルには共通の弱点があるため、異なるモデル又は同じ入力に同じ結果を返す検査を併用する。Project Vendでは、経営者のエージェントが値引きなどの要求を承認した回数は、却下した回数のおよそ8倍だった。

### 4.5 モデルを役割で使い分ける

役割ごとのモデルの選び方は、[表9](#table-9)による。

<a id="table-9"></a>表9−役割ごとのモデルの選び方

| 役割 | モデルの選び方 | 例 |
| --- | --- | --- |
| リーダー | 分解と統合の判断に強いモデル | 市場調査の計画と報告書の統合 |
| 調査、抽出、整形 | 小さく速いモデル | 各社のWebページから価格を抜き出す。 |
| レビュー | 判断に強いモデル。作成者と異なるモデルも検討する。 | 報告書の結論と根拠を照合する。 |

Anthropicの調査システムでは、リーダーにClaude Opus 4、サブエージェントにClaude Sonnet 4を使用した。

## 5 委任と情報共有

### 5.1 委任には四つの項目を書く

委任では、目的、成果物の形式、使用するツールと情報源、作業の境界を書く。指示が曖昧だと、作業の重複又は漏れが起きる。Anthropicの例では、半導体不足の調査で、担当の範囲を決めなかったために、複数のサブエージェントが同じ内容を調査した。

委任に書く項目は、[表10](#table-10)による。

<a id="table-10"></a>表10−委任に書く項目

| 項目 | 曖昧な例 | 具体的な例 |
| --- | --- | --- |
| 目的 | 半導体不足を調査して。 | 2021年の車載半導体の不足が、日本の自動車メーカーの生産台数に与えた影響を明らかにする。 |
| 成果物の形式 | まとめて。 | メーカーごとの減産台数の表と、3行の要約を `auto-2021.md` に書く。 |
| ツールと情報源 | 調査して。 | 各社のIR資料と業界団体の統計を使用する。個人のブログは使用しない。 |
| 境界 | なし | 2021年の車載向けに限る。2025年の供給網は別の担当が調査する。 |

### 5.2 作業の量に応じて人数を変える

作業の難しさごとの人数の目安は、[表11](#table-11)による。

<a id="table-11"></a>表11−作業の難しさごとの人数の目安

| 作業の難しさ | 人数の目安 | 例 |
| --- | --- | --- |
| 単純な事実の確認 | 一つのエージェント（ツールの呼び出しは3〜10回） | 特定の製品の発売日を調査する。 |
| 直接の比較 | 2〜4のサブエージェント（それぞれ10〜15回） | 三つのプランの料金と機能を比べる。 |
| 複雑な調査 | 10を超えるサブエージェント | 業界全体の主要企業の役員を調査する。 |

数値は、Anthropicの調査システムの目安である。人数の規則がないと、単純な質問に50のサブエージェントを生成するような誤りが起きる。

### 5.3 共通の前提を文書で共有する

作業を分割する前に、全員が従う判断を文書で共有する。各エージェントが異なる前提で作業すると、個別の成果物を統合できなくなる。Cognitionは、ゲームの背景と鳥を別々の担当が作成し、見た目が一致しなかった例を報告している。

共有する前提の例は、[表12](#table-12)による。

<a id="table-12"></a>表12−共有する前提の例

| 共有する前提 | 例（新製品の発表資料） |
| --- | --- |
| 対象の読者 | 中堅企業の情報システム部門の責任者 |
| 用語と表記 | 製品名は“Acme Sync”、機能の名称は料金表の表記に合わせる。 |
| 形式 | 16:9のスライド、1枚に一つの主張 |
| 共通の数値 | 2026年度の目標の売上は3億円。 |
| 決定済みの事項 | 価格は発表しない。 |

### 5.4 成果物はファイルに置き、参照を渡す

サブエージェントは、成果物をファイル又は外部のシステムに保存し、保存先及び短い要約を返す。長い本文を会話で繰り返し受け渡す場合に比べ、要約による情報の欠落及びトークンの消費を抑制することが可能になる。

成果物の渡し方は、[表13](#table-13)による。

<a id="table-13"></a>表13−成果物の渡し方

| 渡し方 | 例 | 判断 |
| --- | --- | --- |
| 本文の全体を返す。 | 調査の全文をチャットの結果として返す。 | 短い結果に限る。 |
| 参照と要約を返す。 | `research/acme.md` に保存した。結論は“価格は競合より10%高い”。 | 標準とする。 |

### 5.5 新しいエージェントに必要な情報を渡す

新しく起動するエージェントは、呼び出し元の会話を知らない。Claude Codeのチームメイトは、プロジェクト指示、MCPサーバー、スキルを読み込むが、リーダーの会話履歴は引き継がない。作業に固有の情報は、起動時の指示に含める。

### 5.6 連絡は必要な場合に限る

連絡は、完了、確認の依頼、前提の変更及び作業の停止に限定し、必要な相手を指定する。全員への連絡を繰り返すと、各担当の作業が中断し、トークンの消費も増える。

## 6 タスクの管理

### 6.1 タスクを共有の一覧で管理する

全ての作業をタスクリストで管理し、会話の中だけで依頼しない。

タスクの項目は、[表14](#table-14)による。

<a id="table-14"></a>表14−タスクの項目

| 項目 | 内容 | 例 |
| --- | --- | --- |
| タイトル | 作業の内容 | A社の価格を調査する。 |
| 目標 | 紐付く上位の目標 | 第4四半期の競合の比較表を作る。 |
| 担当 | 一つの役割 | `researcher-a` |
| 状態 | 保留中、進行中、完了 | 進行中 |
| 依存関係 | 先に終わるべきタスク | 調査の対象の一覧の確定 |
| 成果物 | 保存先 | `research/a.md` |
| 完了の条件 | 確認できる条件 | 価格に出典のURLがある。 |

タスクを上位の目標に紐付けると、エージェントが作業の理由を判断に使用できる。

### 6.2 タスクの担当を一つに限る

同じタスクを複数のエージェントが同時に進めないように、取得の仕組みを設ける。

タスクの取得の方式は、[表15](#table-15)による。

<a id="table-15"></a>表15−タスクの取得の方式

| 方式 | 動作 | 例 |
| --- | --- | --- |
| リーダーの割り当て | リーダーエージェントが担当を決める。 | リーダーが、各社の調査を担当へ割り当てる。 |
| 自己取得 | 担当が未割り当てのタスクを取得する。ロックで競合を防ぐ。 | Claude Codeのエージェントチームは、ファイルロックで同時の取得を防ぐ。 |
| ロックのファイル | 取得の場合にファイルを作り、共有する。 | AnthropicのCコンパイラの例では、`current_tasks/` にファイルを置いてタスクを取得した。 |
| チェックアウト | タスク管理のツールがタスクの実行を一つに限る。 | Paperclipのチェックアウトのロック。 |

### 6.3 人数とタスクの大きさを小さく始める

Claude Codeのエージェントチームの資料は、[表16](#table-16)の目安を示している。

<a id="table-16"></a>表16−人数及びタスクの大きさの目安

| 項目 | 目安 | 理由 |
| --- | --- | --- |
| チームの人数 | 3〜5人 | 人数に比例してトークンが増え、調整の負荷も増える。 |
| 1人あたりのタスク | 5〜6個 | 担当が止まっても、他の担当へ割り当て直せる。 |
| タスクの大きさ | 明確な成果物が一つできる大きさ | 小さすぎると調整の負荷が上回り、大きすぎると無駄な作業が増える。 |

### 6.4 同じ成果物を同時に変更しない

複数のエージェントが同じファイル又は同じ文書を変更すると、上書きが起きる。担当ごとに変更するファイルを分けるか、worktree又はブランチで作業ディレクトリを分けて、統合の担当を決める。

### 6.5 全員が同じ所で止まる場合は分割し直す

全員が同じ問題で停止する場合は、独立して進められる単位へ作業を再分割する。AnthropicのCコンパイラの例では、16のエージェントがLinuxカーネルのコンパイルで同じ不具合に当たった。GCCで大半のファイルをコンパイルし、一部だけを自作のコンパイラでコンパイルする構成にして、担当ごとに別の不具合を直せるようにした。

## 7 検証と人の関与

### 7.1 完了を品質ゲートで確認する

工程の移行とタスクの完了の前に、品質ゲートを置く。Claude Codeでは、`TaskCreated`、`TaskCompleted`、`TeammateIdle` のフックで、タスクの作成又は完了を止め、チームメイトへ指摘を返せる。

工程の境界ごとの品質ゲートは、[表17](#table-17)による。

<a id="table-17"></a>表17−工程の境界ごとの品質ゲート

| 工程の境界 | 確認する条件 | 例 |
| --- | --- | --- |
| 調査から執筆 | 全ての主張に出典がある。 | 出典のURLのない行が0件である。 |
| 執筆から校閲 | 必須の見出しがあり、文字数が範囲内である。 | 検査のスクリプトが合格する。 |
| 校閲から配信 | レビュアーが基準を満たすと判定した。 | 全項目が5段階で4以上である。 |
| 開発からリリース | テストが通る。 | CIが合格する。 |

エージェントの自律性が高いほど、検証の精度が結果を左右する。Cコンパイラの例では、ほぼ完全な検証がなければ、エージェントは誤った問題を解くと報告している。

### 7.2 成果物及び検査結果で完了を確認する

完了は、成果物及び検査結果で確認する。リーダーエージェントが全てのタスクの終了前に完了と判断する場合、又はチームメイトが状態の記録を忘れる場合があるため、タスクリストの表示だけで判断しない。

### 7.3 人が判断する点を決める

判断ごとの人の関与は、[表18](#table-18)による。

<a id="table-18"></a>表18−判断ごとの人の関与

| 判断 | 人の関与 | 例 |
| --- | --- | --- |
| 目標と予算の決定 | 人が決める。 | 第4四半期の目標と部門の予算を決める。 |
| エージェントの追加と削除 | 人が承認する。 | 新しい担当の追加の提案を承認する。 |
| 社外への送信、公開、支払い | 人が承認する。 | 顧客へのメール、記事の公開、広告費の支出を承認する。 |
| 取り消せない変更 | 人が承認する。 | 本番のデータの更新を承認する。 |
| 社内の下書き、調査、分析 | 事後に確認する。 | 週次レポートの下書きをサンプルで確認する。 |
| 検査で判定できる定型の作業 | 例外だけを確認する。 | データの整形で、検査に失敗した分だけを確認する。 |

### 7.4 長時間の放置を避ける

人の確認なしに長く実行するほど、無駄な作業が増える。導入の初期は短い間隔で進捗を確認し、問題の出ない工程から確認の間隔を広げる。止めやすく、担当を入れ替えやすい構成にする。

## 8 予算と起動

### 8.1 予算を組織、役割、作業ごとに設ける

予算の単位ごとの上限は、[表19](#table-19)による。

<a id="table-19"></a>表19−予算の単位ごとの上限

| 単位 | 上限の例 | 超えた場合の動作 |
| --- | --- | --- |
| 組織 | 月に500ドル | 80%で通知し、100%で全ての作業を止める。 |
| チーム又はプロジェクト | 週次レポートに月100ドル | チームの作業を止めて、人へ確認する。 |
| 役割 | 調査の担当に月50ドル | その担当を止める。 |
| 1回の実行 | 1回に2ドル | その実行を止めて、途中の結果を残す。 |

数値は決め方の例である。実際の費用の記録に合わせて見直す。

費用の規模の例として、AnthropicのCコンパイラの例では、16のエージェントがおよそ2週間で2 000回近いセッションを実行し、20 000ドル弱を使用した。

### 8.2 起動の条件を役割ごとに決める

AI組織の担当は、常に実行せず、必要な場合に起動する。

起動の条件は、[表20](#table-20)による。

<a id="table-20"></a>表20−起動の条件

| 起動の条件 | 使用する場面 | 例 |
| --- | --- | --- |
| タスクの割り当て | 通常の作業 | 校閲のタスクが割り当てられたら起動する。 |
| メッセージ | 確認と差し戻し | レビュアーの差し戻しで、執筆の担当が起動する。 |
| スケジュール | 定期的な業務と巡回 | 毎週月曜の9時に、売上レポートの担当が起動する。 |
| 外部のイベント | 外部の変化への対応 | 問い合わせの受信で、受付の担当が起動する。 |

起動のたびに、タスクリストと状態のファイルから現在の状況を読み込ませる。

### 8.3 途中から再開できるようにする

計画、タスクの状態及び成果物をファイル又はデータベースに保存し、停止した位置から再開する。完了済みの作業を繰り返さずに済み、再実行に伴う費用を抑制することが可能になる。Anthropicの調査システムでは、リーダーエージェントが計画をメモリへ保存し、コンテキストが圧縮されても計画を失わないようにしている。

## 9 評価と改善

### 9.1 単一のエージェントと比べる

AI組織の評価では、同じ作業を一つのエージェントでも実行し、質、時間、費用を比べる。効果が費用に見合わない場合は、役割を減らすか、一つのエージェントへ戻す。

単一のエージェントとの比較の例は、[表21](#table-21)による。

<a id="table-21"></a>表21−単一のエージェントとの比較の例

| 構成 | 正解率 | 平均の時間 | 1件の費用 | 判断 |
| --- | --- | --- | --- | --- |
| 一つのエージェント | 62% | 12分 | 0.8ドル | 基準 |
| リーダーと調査の担当三つ | 85% | 4分 | 3.0ドル | 採用する。 |
| さらに監督の担当を追加 | 85% | 6分 | 4.5ドル | 効果がないため採用しない。 |

表は記録の形を示す例であり、数値は説明のための仮の値である。

### 9.2 少数の実際の作業から評価を始める

評価は、実際の作業を20件程度集めて始める。導入の初期は変更の効果が大きいため、少ない件数でも差が分かる。LLMによる採点と、人による確認を併用する。Anthropicは、人の確認で、権威のある情報源より検索上位の質の低いサイトを選ぶ傾向を発見した。

評価の対象及び指標は、[表22](#table-22)による。

<a id="table-22"></a>表22−評価の対象及び指標

| 評価の対象 | 指標 | 例 |
| --- | --- | --- |
| 成果 | 正解率、基準を満たす割合、人の修正量 | レポートの数値の正解率 |
| 効率 | 時間、トークン、費用 | 1件あたりの費用 |
| 協調 | 重複した作業、差し戻しの回数、待ち時間 | 同じ情報源を複数の担当が調査した回数 |
| 役割 | 役割ごとの費用、成果への寄与 | 監督の担当が防いだ誤りの件数 |

### 9.3 全ての実行の記録を残す

エージェントごとの入力、ツールの呼び出し、出力、費用、タスクの状態の変化を、一つの作業の単位でたどれるようにする。AI組織の失敗は、どのエージェントの判断が原因かを記録なしでは特定できない。

### 9.4 失敗を原因ごとに分類して直す

複数のエージェントの失敗を分析した研究（MAST）は、モデルの限界だけでなく、システムの設計とエージェント間の連携が主な原因になると示している。失敗は[表23](#table-23)のように分類し、モデルの変更より先に設計を直す。

<a id="table-23"></a>表23−失敗の分類

| 分類 | 失敗の例 | 直す場所 |
| --- | --- | --- |
| システムの設計 | 指示に従わない。同じ手順を繰り返す。終了の条件を認識しない。 | 役割の定義、委任の項目、停止の条件 |
| エージェント間の連携 | 確認せずに想定で進む。本来の目標から逸れる。必要な情報を伝えない。 | 共通の前提の文書、連絡の規則、タスクの目標 |
| タスクの検証 | 早く終わる。検証を省く。誤った検証をする。 | 品質ゲート、レビュアーの基準、完了の条件 |

### 9.5 役割を減らすことも改善として扱う

モデルの更新で不要になった役割がないかを定期的に確認する。役割を一つ外して評価し、結果が変わらなければ外す。

## 11 チェックリスト

- 一つのエージェントの場合と、質、時間、費用を比べて導入を判断した。
- 作業の依存関係と文脈の共有の必要性から、複数のエージェントが向くことを確認した。
- 部署又は肩書ではなく、成果物と独立した作業の単位で組織を設計した。
- 最も単純な型から始め、順序を守らせる工程をコードで制御している。
- 階層を、目標と予算を分ける必要がある場合に限って増やしている。
- 全ての役割に、責任、入力、成果物、完了の条件、ツール、報告先、モデル、予算がある。
- 全ての成果物に、責任を持つ役割が一つだけある。
- 作る役割と確認する役割を分け、監督の判断を実際の結果で確認している。
- 委任に、目的、成果物の形式、ツールと情報源、作業の境界がある。
- 作業の量に応じた人数の規則がある。
- 全員に共通する前提を文書にしてから、作業を分割している。
- 成果物をファイル又は外部のシステムに置き、参照と要約を返している。
- 全ての作業がタスクリストにあり、担当が一つに限られ、上位の目標に紐付いている。
- 同じ成果物を複数のエージェントが同時に変更しない。
- 工程の間に品質ゲートがあり、完了を成果物と検査の結果で確認している。
- 人が判断する点を決めている。
- 組織、役割、作業ごとの予算と、超えた場合の動作を決めている。
- 役割ごとの起動の条件があり、途中から再開できる。
- 実際の作業の評価セットがあり、役割ごとの費用と寄与を測っている。
- 全ての実行の記録をたどれ、失敗を原因ごとに分類している。
- 不要な役割を外せるか定期的に確認している。
