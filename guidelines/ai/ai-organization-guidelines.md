## 1 はじめに

### 1.1 目的

本書の目的は、複数のAIエージェントを人の組織のように役割分担させて運用する仕組みを、成果、費用、管理のしやすさを一貫した基準で設計できるようにすることである。

### 1.2 適用範囲

本書は、調査、資料の作成、データの分析、顧客対応、ソフトウェアの開発などの業務を複数のAIエージェントで進める構成の、導入の判断、組織の型、役割、委任、タスク、検証、予算、評価を規定する。

### 1.3 用語及び定義

| 用語 | 定義 |
| --- | --- |
| AI組織 | 複数のAIエージェントに役割、指示系統、目標、予算を与えて、業務を分担させる構成。 |
| マルチエージェント | 複数のエージェントが協調して1つの目的を達成する方式。 |
| オーケストレーション | エージェントの実行の順序、作業の割り当て、結果の統合を制御すること。 |
| リーダーエージェント | 作業を分解して他のエージェントへ割り当て、結果を統合するエージェント。 |
| サブエージェント | リーダーエージェントから作業を受けて、結果を返すエージェント。 |
| チームメイト | 共有のタスクリストとメッセージで、他のエージェントと直接協調するエージェント。 |
| ハンドオフ | 作業と会話の制御を、別のエージェントへ渡すこと。 |
| タスクリスト | 作業の項目、担当、状態、依存関係を共有する一覧。 |
| 品質ゲート | タスクの完了や工程の移行の前に、条件を満たすかを確かめる関門。 |

## 2. 導入の判断

### 1つのエージェントで足りるかを先に確かめる

AI組織は、1つのエージェントの改善で足りない場合に導入する。Anthropicのデータでは、エージェントはチャットのおよそ4倍、マルチエージェントはおよそ15倍のトークンを使う。作業の価値が費用を上回る場合に限って導入する。

処理を関数で書ける場合は、エージェントを使わず、関数で書く。

| 状況 | 構成 | 例 |
| --- | --- | --- |
| 手順が決まっていて、判断が要らない。 | プログラム | 売上のCSVを集計して、決まった形式の表にする。 |
| 判断は要るが、1つの流れで進む。 | 1つのエージェント | 問い合わせを読み、手順書に沿って回答の案を作る。 |
| 必要な知識が多いが、同時に使わない。 | 1つのエージェントとスキル | 請求、契約、配送の問い合わせに、該当する手順を読み込んで答える。 |
| 互いに独立した調査や作業を同時に進められる。 | リーダーエージェントとサブエージェント | 競合10社の価格と機能を、社ごとに並行して調べて比較表にする。 |
| 担当者どうしの議論や反証で質が上がる。 | エージェントチーム | 解約の増加の原因について、3つの仮説を別々に検証し、互いに反証する。 |
| 継続的な業務を、役割、目標、予算で管理する。 | 階層型の組織 | 記事の企画、執筆、校閲、配信を毎週繰り返し、部門ごとの費用を管理する。 |

### 複数のエージェントが向く作業と向かない作業を見分ける

| 観点 | 向く | 向かない |
| --- | --- | --- |
| 依存関係 | 互いの途中経過を待たずに進められる。 | 前の作業の結果で次の作業が変わる。 |
| 文脈 | 担当ごとに必要な情報が分かれている。 | 全員が同じ文脈と細かな判断を共有する必要がある。 |
| 成果物 | 担当ごとに独立した成果物がある。 | 1つの成果物を複数の担当が同時に書き換える。 |
| 検証 | 完了を外部の基準で確かめられる。 | 完了の判断が書き手の感覚に依存する。 |

Anthropicの調査システムでは、幅広い方向を同時に調べる質問で、複数のエージェントの構成が単独のエージェントより社内の評価で90.2%高い結果を出した。一方で、Cognitionは、分担した作業が暗黙の判断の違いで噛み合わない例を示し、文脈を共有できる単一のエージェントを推奨している。作業の性質で判断し、どちらかの構成を常に正しいものとして扱わない。

### 人の組織図から始めない

組織は、部署名や役職からではなく、成果物と、独立して進められる作業の単位から設計する。AnthropicのProject Vendでは、店舗を運営するエージェントに経営者のエージェントを加えても、同じモデルであるため同じ弱点を持ち、効果が限られた。一方で、グッズの制作を担当するエージェントは、役割が明確に分かれていたことで成果を上げた。

| 悪い分け方 | 良い分け方 |
| --- | --- |
| CEO、部長、課長、担当者を置く。 | 企画、調査、執筆、校閲のように、成果物の異なる役割を置く。 |
| 人の部署と同じ数のエージェントを置く。 | 並行して進められる作業の数だけ、エージェントを置く。 |
| 管理の層を増やして品質を上げる。 | 明確な手順と、実際の結果による検証で品質を上げる。 |

## 3. 組織の型の選び方

### 作業の流れに合う型を選ぶ

最も単純な型から始める。複数の型を組み合わせてもよい。

| 型 | 仕組み | 向く作業 | 注意点 | 例 |
| --- | --- | --- | --- | --- |
| シーケンシャル | 決めた順序で、前の成果物を次のエージェントへ渡す。 | 工程が決まっている作業 | 前の誤りが後へ伝わる。工程の間に品質ゲートを置く。 | 調査、執筆、校閲、配信 |
| 並行 | 同じ入力または分割した入力を、複数のエージェントが同時に処理する。 | 独立した調査、複数の観点のレビュー | 結果の統合の方法を先に決める。 | 契約書を、法務、財務、事業の観点で同時に確認する。 |
| リーダーとサブエージェント | リーダーエージェントが作業を割り当て、結果を受け取って統合する。 | 最終の成果物を1つにまとめる作業 | リーダーエージェントの文脈と判断に依存する。 | 市場調査の報告書を、分野別の調査から作る。 |
| ハンドオフ | 受付のエージェントが、専門のエージェントへ会話の制御を渡す。 | 専門の担当が直接応答する窓口 | 引き継ぐ情報を決める。振り分けの誤りを評価する。 | 問い合わせを、請求、技術、解約の担当へ振り分ける。 |
| グループチャット | 共有の会話で、複数のエージェントが順に発言する。 | 議論、提案とレビューの往復 | 長い往復になりやすい。発言の順序と終了の条件を決める。 | 提案書の案を、作成者と顧客役とレビュアーで磨く。 |
| エージェントチーム | タスクリストを共有し、チームメイトが直接やり取りする。 | 互いの結果を検証する調査、担当の分かれた開発 | 調整の負荷とトークンが増える。 | 障害の原因を、複数の仮説に分けて互いに反証する。 |
| 階層型の組織 | 目標、指示系統、予算、承認を持つ組織として、継続的に運用する。 | 長く続く複数の業務 | 管理の層が増えるほど、費用と情報の損失が増える。 | 複数の製品のマーケティングを、製品ごとのチームで運用する。 |

### 流れの制御はコードかLLMかを工程ごとに決める

| 制御 | 使う場面 | 利点 | 例 |
| --- | --- | --- | --- |
| コード | 順序と条件が決まっている工程 | 速度、費用、結果を予測しやすい。 | 校閲に不合格なら執筆へ戻す。 |
| LLM | 入力によって進め方が変わる工程 | 想定していない質問に対応できる。 | 質問の内容から、調査の分割の方法を決める。 |

順序を守らせる必要がある工程は、LLMの判断に任せず、コードで制御する。

### 階層を増やさない

階層は、まず2段（リーダーとその下の担当）で構成する。Claude Codeのエージェントチームでは、チームメイトは自分のチームメイトを生成できず、リーダーは1つのセッションに固定される。3段以上にするのは、チームごとに目標と予算を分けて管理する必要がある場合に限る。

## 4. 役割の設計

### 役割を成果物と責任で定義する

役割は、肩書ではなく、責任、成果物、完了の条件で定義する。「優秀なマーケティング部長として振る舞う」のような肩書だけの指示では、何を作れば完了かが決まらない。

| 項目 | 内容 | 例（週次の売上レポートの分析担当） |
| --- | --- | --- |
| 名前 | 呼び分けに使う短い名前 | `sales-analyst` |
| 責任 | この役割だけが負う仕事 | 売上データを分析し、前週との差の原因を特定する。 |
| 入力 | 受け取る情報 | `data/sales.csv`、前週のレポート |
| 成果物 | 作るものと形式 | `analysis.md`（差の上位3件、原因、根拠の数値） |
| 完了の条件 | 確かめられる条件 | 全部門の合計が会計の総額と一致する。 |
| ツール | 役割に必要なものだけ | データベースの読み取り、Python |
| 報告先 | 結果を返す相手 | `report-lead` |
| モデル | 役割の難しさに合うもの | 中位のモデル |
| 予算 | 1回の上限 | 2ドル |

### 役割の重なりと空白をなくす

全ての成果物に、責任を持つ役割を1つだけ割り当てる。次の表のように、成果物と役割の対応を一覧にして確かめる。

| 成果物 | 作る | 確かめる | 承認する |
| --- | --- | --- | --- |
| 調査メモ | `researcher` | `report-lead` | なし |
| レポートの原稿 | `writer` | `reviewer` | なし |
| 配信 | `report-lead` | `reviewer` | 人 |

### 作る役割と確かめる役割を分ける

エージェントは自分の成果物を甘く評価するため、作る役割と確かめる役割を分ける。確かめる役割には、作成の経緯を渡さず、成果物と完了の条件を渡す。

### 監督の役割を結果で確かめる

監督のエージェントは、監督される側と同じ弱点を持つことがある。Project Vendでは、経営者のエージェントは、顧客への値引きなどの甘い要求を、却下のおよそ8倍承認した。監督の役割の判断は、売上、誤りの件数、差し戻しの件数のような実際の結果と比べて確かめる。可能な場合は、異なるモデルや、決定論的な検査を併用する。

### モデルを役割で使い分ける

| 役割 | モデルの選び方 | 例 |
| --- | --- | --- |
| リーダー | 分解と統合の判断に強いモデル | 市場調査の計画と報告書の統合 |
| 調査、抽出、整形 | 小さく速いモデル | 各社のWebページから価格を抜き出す。 |
| レビュー | 判断に強いモデル。作成者と異なるモデルも検討する。 | 報告書の結論と根拠を照合する。 |

Anthropicの調査システムでは、リーダーにClaude Opus 4、サブエージェントにClaude Sonnet 4を使った。

## 5. 委任と情報共有

### 委任には4つの項目を書く

委任では、目的、成果物の形式、使うツールと情報源、作業の境界を書く。指示が曖昧だと、作業の重複や漏れが起きる。Anthropicの例では、半導体不足の調査で、担当の範囲を決めなかったために、複数のサブエージェントが同じ内容を調べた。

| 項目 | 曖昧な例 | 具体的な例 |
| --- | --- | --- |
| 目的 | 半導体不足を調べて。 | 2021年の車載半導体の不足が、日本の自動車メーカーの生産台数に与えた影響を明らかにする。 |
| 成果物の形式 | まとめて。 | メーカーごとの減産台数の表と、3行の要約を `auto-2021.md` に書く。 |
| ツールと情報源 | 調べて。 | 各社のIR資料と業界団体の統計を使う。個人のブログは使わない。 |
| 境界 | なし | 2021年の車載向けに限る。2025年の供給網は別の担当が調べる。 |

### 作業の量に応じて人数を変える

| 作業の難しさ | 人数の目安 | 例 |
| --- | --- | --- |
| 単純な事実の確認 | 1つのエージェント（ツールの呼び出しは3〜10回） | 特定の製品の発売日を調べる。 |
| 直接の比較 | 2〜4つのサブエージェント（それぞれ10〜15回） | 3つのプランの料金と機能を比べる。 |
| 複雑な調査 | 10を超えるサブエージェント | 業界全体の主要企業の役員を調べる。 |

数値は、Anthropicの調査システムの目安である。人数の規則がないと、単純な質問に50のサブエージェントを生成するような誤りが起きる。

### 共通の前提を文書で共有する

エージェントの行動には、暗黙の判断が含まれる。前提を共有しないと、Cognitionの例のように、背景の担当と鳥の担当が別々の見た目のゲームを作り、統合できなくなる。作業を分割する前に、全員に共通する判断を文書にする。

| 共有する前提 | 例（新製品の発表資料） |
| --- | --- |
| 対象の読者 | 中堅企業の情報システム部門の責任者 |
| 用語と表記 | 製品名は「Acme Sync」、機能の名称は料金表の表記に合わせる。 |
| 形式 | 16:9のスライド、1枚に1つの主張 |
| 共通の数値 | 2026年度の目標の売上は3億円。 |
| 決定済みの事項 | 価格は発表しない。 |

### 成果物はファイルに置き、参照を渡す

リーダーエージェントを介して長い本文を受け渡すと、要約のたびに情報が失われ、トークンも増える。サブエージェントは、成果物をファイルや外部のシステムに保存し、保存先と短い要約を返す。

| 渡し方 | 例 | 判断 |
| --- | --- | --- |
| 本文の全体を返す。 | 調査の全文をチャットの結果として返す。 | 短い結果に限る。 |
| 参照と要約を返す。 | `research/acme.md` に保存した。結論は「価格は競合より10%高い」。 | 標準とする。 |

### 新しいエージェントに必要な情報を渡す

新しく起動するエージェントは、呼び出し元の会話を知らない。Claude Codeのチームメイトは、プロジェクト指示、MCPサーバー、スキルを読み込むが、リーダーの会話履歴は引き継がない。作業に固有の情報は、起動時の指示に含める。

### 連絡は必要な時に限る

エージェントどうしの連絡が多いと、互いの作業を妨げ、トークンを消費する。全員への連絡は避け、相手を指定する。連絡の内容は、完了、確認の依頼、前提の変更、作業の停止に限る。

## 6. タスクの管理

### タスクを共有の一覧で管理する

全ての作業をタスクリストで管理し、会話の中だけで依頼しない。

| 項目 | 内容 | 例 |
| --- | --- | --- |
| タイトル | 作業の内容 | A社の価格を調べる。 |
| 目標 | 紐付く上位の目標 | 第4四半期の競合の比較表を作る。 |
| 担当 | 1つの役割 | `researcher-a` |
| 状態 | 保留中、進行中、完了 | 進行中 |
| 依存関係 | 先に終わるべきタスク | 調査の対象の一覧の確定 |
| 成果物 | 保存先 | `research/a.md` |
| 完了の条件 | 確かめられる条件 | 価格に出典のURLがある。 |

タスクを上位の目標に紐付けると、エージェントが作業の理由を判断に使える。

### タスクの担当を1つに限る

同じタスクを複数のエージェントが同時に進めないように、取得の仕組みを設ける。

| 方式 | 動作 | 例 |
| --- | --- | --- |
| リーダーの割り当て | リーダーエージェントが担当を決める。 | リーダーが、各社の調査を担当へ割り当てる。 |
| 自己取得 | 担当が未割り当てのタスクを取得する。ロックで競合を防ぐ。 | Claude Codeのエージェントチームは、ファイルロックで同時の取得を防ぐ。 |
| ロックのファイル | 取得の時にファイルを作り、共有する。 | AnthropicのCコンパイラの例では、`current_tasks/` にファイルを置いてタスクを取得した。 |
| チェックアウト | タスク管理のツールがタスクの実行を1つに限る。 | Paperclipのチェックアウトのロック。 |

### 人数とタスクの大きさを小さく始める

Claude Codeのエージェントチームの資料は、次の目安を示している。

| 項目 | 目安 | 理由 |
| --- | --- | --- |
| チームの人数 | 3〜5人 | 人数に比例してトークンが増え、調整の負荷も増える。 |
| 1人あたりのタスク | 5〜6個 | 担当が止まっても、他の担当へ割り当て直せる。 |
| タスクの大きさ | 明確な成果物が1つできる大きさ | 小さすぎると調整の負荷が上回り、大きすぎると無駄な作業が増える。 |

### 同じ成果物を同時に変更しない

複数のエージェントが同じファイルや同じ文書を変更すると、上書きが起きる。担当ごとに変更するファイルを分けるか、worktreeやブランチで作業ディレクトリを分けて、統合の担当を決める。

### 全員が同じ所で止まる場合は分割し直す

大きな1つの作業では、全員が同じ問題に当たり、並行の効果が消える。AnthropicのCコンパイラの例では、16のエージェントがLinuxカーネルのコンパイルで同じ不具合に当たった。GCCで大半のファイルをコンパイルし、一部だけを自作のコンパイラでコンパイルする構成にして、担当ごとに別の不具合を直せるようにした。

## 7. 検証と人の関与

### 完了を品質ゲートで確かめる

工程の移行とタスクの完了の前に、品質ゲートを置く。Claude Codeでは、`TaskCreated`、`TaskCompleted`、`TeammateIdle` のフックで、タスクの作成や完了を止め、チームメイトへ指摘を返せる。

| 工程の境界 | 確かめる条件 | 例 |
| --- | --- | --- |
| 調査から執筆 | 全ての主張に出典がある。 | 出典のURLのない行が0件である。 |
| 執筆から校閲 | 必須の見出しがあり、文字数が範囲内である。 | 検査のスクリプトが合格する。 |
| 校閲から配信 | レビュアーが基準を満たすと判定した。 | 全項目が5段階で4以上である。 |
| 開発からリリース | テストが通る。 | CIが合格する。 |

エージェントの自律性が高いほど、検証の精度が結果を左右する。Cコンパイラの例では、ほぼ完全な検証がなければ、エージェントは誤った問題を解くと報告している。

### リーダーの完了の判断を鵜呑みにしない

リーダーエージェントは、全てのタスクが終わる前に完了と判断することがある。チームメイトも、完了の記録を忘れて依存するタスクを止めることがある。タスクリストの状態ではなく、成果物と検査の結果で完了を確かめる。

### 人が判断する点を決める

| 判断 | 人の関与 | 例 |
| --- | --- | --- |
| 目標と予算の決定 | 人が決める。 | 第4四半期の目標と部門の予算を決める。 |
| エージェントの追加と削除 | 人が承認する。 | 新しい担当の追加の提案を承認する。 |
| 社外への送信、公開、支払い | 人が承認する。 | 顧客へのメール、記事の公開、広告費の支出を承認する。 |
| 取り消せない変更 | 人が承認する。 | 本番のデータの更新を承認する。 |
| 社内の下書き、調査、分析 | 事後に確かめる。 | 週次レポートの下書きをサンプルで確かめる。 |
| 検査で判定できる定型の作業 | 例外だけを確かめる。 | データの整形で、検査に失敗した分だけを確かめる。 |

### 長時間の放置を避ける

人の確認なしに長く動かすほど、無駄な作業が増える。導入の初期は短い間隔で進捗を確かめ、問題の出ない工程から確認の間隔を広げる。止めやすく、担当を入れ替えやすい構成にする。

## 8. 予算と起動

### 予算を組織、役割、作業ごとに設ける

| 単位 | 上限の例 | 超えた時の動作 |
| --- | --- | --- |
| 組織 | 月に500ドル | 80%で通知し、100%で全ての作業を止める。 |
| チームまたはプロジェクト | 週次レポートに月100ドル | チームの作業を止めて、人へ確認する。 |
| 役割 | 調査の担当に月50ドル | その担当を止める。 |
| 1回の実行 | 1回に2ドル | その実行を止めて、途中の結果を残す。 |

数値は決め方の例である。実際の費用の記録に合わせて見直す。

費用の規模の例として、AnthropicのCコンパイラの例では、16のエージェントがおよそ2週間で2,000回近いセッションを実行し、20,000ドル弱を使った。

### 起動の条件を役割ごとに決める

AI組織の担当は、常に動かさず、必要な時に起動する。

| 起動の条件 | 使う場面 | 例 |
| --- | --- | --- |
| タスクの割り当て | 通常の作業 | 校閲のタスクが割り当てられたら起動する。 |
| メッセージ | 確認と差し戻し | レビュアーの差し戻しで、執筆の担当が起動する。 |
| スケジュール | 定期的な業務と巡回 | 毎週月曜の9時に、売上レポートの担当が起動する。 |
| 外部のイベント | 外部の変化への対応 | 問い合わせの受信で、受付の担当が起動する。 |

起動のたびに、タスクリストと状態のファイルから現在の状況を読み込ませる。

### 途中から再開できるようにする

エラーのたびに最初からやり直すと、費用が増える。計画、タスクの状態、成果物をファイルやデータベースに保存し、途中から再開する。Anthropicの調査システムでは、リーダーエージェントが計画をメモリへ保存し、コンテキストが圧縮されても計画を失わないようにしている。

## 9. 評価と改善

### 単一のエージェントと比べる

AI組織の評価では、同じ作業を1つのエージェントでも実行し、質、時間、費用を比べる。効果が費用に見合わない場合は、役割を減らすか、1つのエージェントへ戻す。

| 構成 | 正解率 | 平均の時間 | 1件の費用 | 判断 |
| --- | --- | --- | --- | --- |
| 1つのエージェント | 62% | 12分 | 0.8ドル | 基準 |
| リーダーと調査の担当3つ | 85% | 4分 | 3.0ドル | 採用する。 |
| さらに監督の担当を追加 | 85% | 6分 | 4.5ドル | 効果がないため採用しない。 |

表は記録の形を示す例であり、数値は説明のための仮の値である。

### 少数の実際の作業から評価を始める

評価は、実際の作業を20件程度集めて始める。導入の初期は変更の効果が大きいため、少ない件数でも差が分かる。LLMによる採点と、人による確認を併用する。Anthropicは、人の確認で、権威のある情報源より検索上位の質の低いサイトを選ぶ傾向を発見した。

| 評価の対象 | 指標 | 例 |
| --- | --- | --- |
| 成果 | 正解率、基準を満たす割合、人の修正量 | レポートの数値の正解率 |
| 効率 | 時間、トークン、費用 | 1件あたりの費用 |
| 協調 | 重複した作業、差し戻しの回数、待ち時間 | 同じ情報源を複数の担当が調べた回数 |
| 役割 | 役割ごとの費用、成果への寄与 | 監督の担当が防いだ誤りの件数 |

### 全ての実行の記録を残す

エージェントごとの入力、ツールの呼び出し、出力、費用、タスクの状態の変化を、1つの作業の単位でたどれるようにする。AI組織の失敗は、どのエージェントの判断が原因かを記録なしでは特定できない。

### 失敗を原因ごとに分類して直す

複数のエージェントの失敗を分析した研究（MAST）は、モデルの限界だけでなく、システムの設計とエージェント間の連携が主な原因になると示している。失敗は次のように分類し、モデルの変更より先に設計を直す。

| 分類 | 失敗の例 | 直す場所 |
| --- | --- | --- |
| システムの設計 | 指示に従わない。同じ手順を繰り返す。終了の条件を認識しない。 | 役割の定義、委任の項目、停止の条件 |
| エージェント間の連携 | 確認せずに想定で進む。本来の目標から逸れる。必要な情報を伝えない。 | 共通の前提の文書、連絡の規則、タスクの目標 |
| タスクの検証 | 早く終わる。検証を省く。誤った検証をする。 | 品質ゲート、レビュアーの基準、完了の条件 |

### 役割を減らすことも改善として扱う

モデルの更新で不要になった役割がないかを定期的に確かめる。役割を1つ外して評価し、結果が変わらなければ外す。

## 11. チェックリスト

- 1つのエージェントの場合と、質、時間、費用を比べて導入を判断した。
- 作業の依存関係と文脈の共有の必要性から、複数のエージェントが向くことを確かめた。
- 部署や肩書ではなく、成果物と独立した作業の単位で組織を設計した。
- 最も単純な型から始め、順序を守らせる工程をコードで制御している。
- 階層を、目標と予算を分ける必要がある場合に限って増やしている。
- 全ての役割に、責任、入力、成果物、完了の条件、ツール、報告先、モデル、予算がある。
- 全ての成果物に、責任を持つ役割が1つだけある。
- 作る役割と確かめる役割を分け、監督の判断を実際の結果で確かめている。
- 委任に、目的、成果物の形式、ツールと情報源、作業の境界がある。
- 作業の量に応じた人数の規則がある。
- 全員に共通する前提を文書にしてから、作業を分割している。
- 成果物をファイルや外部のシステムに置き、参照と要約を返している。
- 全ての作業がタスクリストにあり、担当が1つに限られ、上位の目標に紐付いている。
- 同じ成果物を複数のエージェントが同時に変更しない。
- 工程の間に品質ゲートがあり、完了を成果物と検査の結果で確かめている。
- 人が判断する点を決めている。
- 組織、役割、作業ごとの予算と、超えた時の動作を決めている。
- 役割ごとの起動の条件があり、途中から再開できる。
- 実際の作業の評価セットがあり、役割ごとの費用と寄与を測っている。
- 全ての実行の記録をたどれ、失敗を原因ごとに分類している。
- 不要な役割を外せるか定期的に確かめている。
