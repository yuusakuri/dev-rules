# AI機能設計ガイドライン

## 1 はじめに

### 1.1 目的

本書の目的は、AIを使う機能を、扱うデータの種類によらず、品質、応答の速さ及び費用を管理しながら設計し、運用するための判断基準を共有することである。

### 1.2 適用範囲

本書は、テキスト、画像、動画、音声、文書、表形式のデータなどを入力又は出力とし、LLM、マルチモーダルモデル、音声認識、音声合成、画像及び動画の生成、埋め込み、機械学習の予測などのモデルを使う機能について規定する。

本書は、構成の選択、入力データの受付、非同期の処理、エージェント型の機能、プロンプトと出力、検索拡張生成、セキュリティ、及び評価と監視を含む運用（LLMOps）を扱う。

本書は、[アーキテクチャ設計ガイドライン](../architecture/architecture-guidelines.md)及び[通信方式ガイドライン](../architecture/communication-protocol-guidelines.md)を前提とする。開発の作業にAIエージェントを使う仕組みは、[ハーネスエンジニアリングガイドライン](harness-engineering-guidelines.md)による。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| LLM（large language model、大規模言語モデル） | 大量の文章を学習し、文章の生成又は分析を行うモデル。 |
| マルチモーダルモデル | テキストに加えて、画像、音声、動画などを入力又は出力として扱うモデル。 |
| 専用モデル | 分類、物体検出、文字認識、音声認識など、特定の処理だけを行うモデル。 |
| プロンプト | モデルへ渡す指示、例及び入力の全体。 |
| ツール | LLMが呼び出しを要求し、アプリケーションが実行する関数又はAPI。 |
| ワークフロー | モデルの呼出しとツールの実行を、あらかじめ決めた順序で組み合わせた処理。 |
| エージェント | LLMが自ら次の行動を選び、ツールの実行と結果の観察を繰り返して目的を達成する処理。 |
| RAG（Retrieval-Augmented Generation、検索拡張生成） | 入力に関係する資料を検索し、プロンプトに加えて生成させる方式。 |
| 埋め込み | テキスト、画像などの意味を数値のベクトルで表したもの。 |
| 構造化出力 | 指定したスキーマに従う形式でモデルに出力させること。 |
| プロンプトインジェクション | 入力又は取得した資料に含まれる文章によって、LLMに意図しない動作をさせる攻撃。 |
| 評価セット | 入力と、期待する出力又は採点の基準とを組にした、品質の測定用のデータ。 |
| トレース | 一つの要求で行ったモデルの呼出し、ツールの実行及びその入出力の記録。 |
| ジョブ | 一つの入力に対する一連の非同期の処理の単位。状態をもつ。 |
| ワーカー | キューからジョブを受け取って処理する実行単位。 |
| 署名付きURL | 期限と操作を限定して、認証なしでオブジェクトストレージへの読み書きを許可するURL。 |
| 信頼度 | モデルが出力した結果について、モデルが示す確からしさの値。 |
| MCP（Model Context Protocol） | AIアプリケーションと外部のツール又はデータを接続するための通信規約。 |

## 2 構成の選択

### 2.1 最も単純な構成から始める

構成は、[表2](#table-2)の上の行から順に検討し、評価セットで目標を満たす最も単純な構成を選ぶ。構成が複雑になるほど、モデルの呼出しが増え、応答の遅延、費用及び失敗の箇所が増える。

<a id="table-2"></a>表2−構成の選択

| 構成 | 適する処理 | 例 |
| --- | --- | --- |
| AIを使わない処理 | 規則で判定できる処理、計算、形式の変換 | 入力の検証、合計の計算、日付の整形 |
| 専用モデル | 出力の種類が決まっていて、大量又は低遅延で処理する必要がある処理 | 画像の分類、文字認識、音声の文字起こし |
| 1回のモデルの呼出し | 一つの入力から一つの出力を作る処理 | 要約、情報の抽出、画像の説明、翻訳 |
| 検索又はツールを伴う1回の呼出し | 外部の資料又は最新のデータが必要な処理 | 社内文書に基づく回答 |
| ワークフロー | 手順が決まっている複数の段階の処理 | 音声を文字起こししてから要約する。抽出した結果を検証してから文書を生成する。 |
| エージェント | 必要な手順の数と順序を事前に決められない処理 | 調査、複数のシステムを横断する操作 |
| 複数のエージェント | 独立して並行に進められる大きな処理 | 多数の資料の並行調査 |

### 2.2 データの種類ごとの処理方式

データの種類ごとの処理方式は、[表3](#table-3)による。

<a id="table-3"></a>表3−データの種類ごとの処理方式

| 処理 | 方式 | 性能上の要点 |
| --- | --- | --- |
| テキストの生成、抽出、分類 | LLM。分類のように出力が決まった処理は、小さなモデル又は専用モデルを使う。 | 生成した文章を逐次表示する。共通の先頭部分にプロンプトキャッシュを使う。 |
| 画像の理解（分類、文字認識、物体検出、説明） | 定型で大量の処理は専用モデル。非定型の処理はマルチモーダルモデル。 | モデルが処理する解像度まで、送る前に縮小する。 |
| 画像の生成及び編集 | 画像生成モデル | 非同期のジョブにする。生成した画像はオブジェクトストレージに保存し、CDNから配信する。 |
| 音声の文字起こし | 音声認識モデル。会話中の文字起こしはストリーミングの音声認識、録音したファイルは非同期のジョブ。 | モデルが推奨するサンプリングレートとチャンネル数に、送る前に変換する。 |
| 音声による対話 | 音声を直接入出力するリアルタイムのモデル、又は音声認識、LLM及び音声合成の各段階をストリーミングでつないだ処理 | 音声はWebRTC又はWebSocketで送る。発話の終わりを検出してすぐに応答を始め、利用者の割込みで再生を止める。 |
| 音声合成 | 音声合成モデル | ストリーミングで合成し、全体の合成を待たずに再生を始める。定型の文は合成結果をキャッシュする。 |
| 動画の理解 | 一定の間隔又は場面の変化でフレームを抽出し、音声の文字起こしと合わせてマルチモーダルモデルへ渡す。 | 非同期のジョブにし、区間ごとに並列に処理する。 |
| 動画の生成 | 動画生成モデル | 非同期のジョブにし、進捗を通知する。 |
| 文書（PDF、Office文書） | 文字の層がある部分は文字を抽出し、画像だけのページは文字認識又はマルチモーダルモデルで処理する。 | ページ単位で並列に処理する。 |
| 表形式のデータ、時系列のデータ（需要の予測、異常の検知） | 機械学習の予測モデル又は統計的な手法。LLMは集計の結果の説明にだけ使う。 | 数値の計算をLLMに行わせない。 |
| 検索、推薦 | 埋め込みとベクトル索引。キーワードによる検索と組み合わせる。 | 埋め込みは保存時に計算し、検索時に再計算しない。 |

### 2.3 モデルを選ぶ

最初は最も能力の高いモデルで評価セットの目標を満たす構成を作り、その後、より小さく速いモデル及び専用モデルで同じ評価を行う。目標を満たす中で、応答の遅延と費用が最も小さいモデルを選ぶ。処理の段階ごとに異なるモデルを使ってもよい。

モデルは、別名ではなく、版を固定した識別子で指定する。別名は、提供元の更新で指すモデルが変わり、評価していないモデルで動作する。

### 2.4 同期処理と非同期処理の選択

利用者との対話で使うテキストの生成、音声の対話など、利用者が結果を待つ処理は、同期処理にしてストリーミングで返す。画像、動画、長い音声及び大きな文書の処理は、非同期のジョブを既定とする。処理時間は入力とモデルの混雑によって変わり、外部のAIサービスは速度制限と一時的な障害を伴う。同期処理にすると、遅い要求がサーバーの接続を占有し、他の利用者の応答も遅くなる。

非同期のジョブを同期処理にするのは、次の全てを満たす場合に限る。

- 処理時間の99パーセンタイルが、利用者が待てる時間に収まる。

- 要求の量が、AIサービスの速度制限より十分に小さい。

- 失敗した場合に、利用者がその場でやり直せばよい。

## 3 応答の速さ

利用者が体感する遅延を小さくするため、次による。

- 生成したテキスト及び音声は、逐次返す。利用者が最初の結果を受け取るまでの時間が、全体の生成時間より短くなる。

- 変わらない指示、資料及びツールの定義をプロンプトの先頭に置き、プロンプトキャッシュを使う。キャッシュされた部分は、処理時間と費用が減る。

- 画像の縮小、音声の変換など、モデルに渡す前の加工は、可能な限りクライアントで行い、送るデータを減らす。

- 独立したモデルの呼出し、ツールの実行及び区間ごとの処理は、並列に行う。

- 出力の長さに上限を設け、必要な分だけを生成させる。

- 急がない大量の処理は、提供元のバッチAPIを使う。

- 利用者の操作を待たせる処理には、タイムアウトを設け、超えた場合の代わりの応答を用意する。

## 4 入力データの受付

### 4.1 オブジェクトストレージへ直接送る

画像、音声、動画及び文書のファイルは、署名付きURLを使い、クライアントからオブジェクトストレージへ直接送る。アプリケーションのサーバーを経由すると、ファイルの大きさの分だけ帯域、メモリ及び処理時間を消費し、他の要求の遅延が増える。

署名付きURLは、次によって限定する。

- 期限を数分にする。

- 書き込める保存先のキーを、サーバーが生成した一つのキーに限る。

- Content-Typeと大きさの上限を、署名の条件に含める。

会話中の音声及び映像のように、連続して流れるデータは、ファイルとして送らず、[通信方式ガイドライン](../architecture/communication-protocol-guidelines.md)によってWebRTC又はWebSocketで送る。

### 4.2 クライアントで縮小及び変換する

クライアントでは、モデルの処理に必要な品質まで、ファイルを縮小又は変換してから送る。携帯電話で撮影した画像は数MBあり、多くのモデルは、入力をそれより小さな解像度に縮小して処理する。縮小すれば、アップロードの時間、保存の費用及びモデルの処理の費用が減る。

モデルの処理に必要な解像度、サンプリングレートなどは、使うモデルの資料で確認する。原本を保存する必要がある場合は、縮小したファイルと原本を分けて送り、モデルの処理は縮小したファイルで先に始める。

### 4.3 不安定な回線に備える

モバイルアプリケーションからのアップロードは、通信が途切れても途中から再開できる方式（分割アップロード、tusなど）を使う。

### 4.4 保存先を分ける

オブジェクトストレージは、利用者からの読み取りを禁止し、検証前のファイルと検証済みのファイルとで保存先を分ける。保存先のキーは、サーバーが生成したランダムな値とし、利用者が指定したファイル名を使わない。ファイルを利用者に表示する場合は、検証済みのファイルを、期限付きの署名付きURL又は認証付きのCDNから配信する。

### 4.5 検証と正規化

ファイルは、ワーカーで次によって検証し、正規化する。クライアントでの検証は利用者への案内のためであり、改ざんできるため、サーバーでの検証を省く根拠にしない。

- ファイルの先頭のバイト列で実際の形式を判定し、許可した形式だけを受け付ける。拡張子とContent-Typeは信用しない。

- 展開又は復号する前に、画像の画素数、音声と動画の長さ、文書のページ数を読み、上限を超えるファイルを拒否する。展開すると膨大な大きさになるファイルは、展開の時点でメモリを使い果たす。

- ファイルを再エンコードし、目的の形式以外のデータを除く。

- 画像のEXIFの向きの情報に従って画素を回転させた後、メタデータを除く。

- 画像、音声及び動画を処理するライブラリは、最新の版に保ち、権限を限定した環境で実行する。

## 5 非同期の処理

### 5.1 キューには参照だけを載せる

キューには、ファイルの本体ではなく、保存先のキーとジョブのIDだけを載せる。大きなデータをキューに載せると、キューの上限と転送の時間に処理が制約される。

### 5.2 ジョブを状態で管理する

ジョブは、`pending`、`uploaded`、`processing`、`succeeded`、`failed`のような状態をもち、許可した遷移だけを行う（[ソフトウェア設計ガイドライン](../software/software-design-guidelines.md)の6.3参照）。

### 5.3 処理をべき等にする

キューは、同じメッセージを複数回配信することがある。ワーカーは、ジョブのIDとモデルの版をべき等キーにし、既に結果があるジョブを再び処理しない。

### 5.4 失敗の種類ごとに扱いを変える

失敗は、次によって扱う。

- 速度制限、タイムアウト、サーバーの一時的な障害は、間隔を指数関数的に延ばして再試行する。

- 形式の誤り、内容の拒否など、再試行しても成功しない失敗は、再試行せずに`failed`にし、理由を記録する。

- 再試行の上限に達したメッセージは、デッドレターキューへ移し、監視の対象にする。

- キューのメッセージを他のワーカーに見えなくする時間は、処理時間の上限より長くする。短いと、処理中のジョブを別のワーカーが重ねて処理する。

### 5.5 流量を制御する

外部のAIサービスを呼ぶワーカーの同時実行数は、サービスの速度制限から決め、超えないようにする。キューの長さに応じて、ワーカーの数を自動で増減する。

## 6 エージェント型の機能

### 6.1 ツールを設計する

ツールは、次によって設計する。

- ツールの数を、目的に必要な範囲に絞る。似た機能のツールが複数あると、LLMが選択を誤る。

- 名前と説明に、何をするツールで、いつ使うかを書く。

- 入力は、スキーマで型と値の範囲を定義する。

- 出力は、LLMが次の判断に必要な情報だけを、短く返す。大量の結果は、絞込み又はページ送りで返す。

- エラーは、LLMが次に取るべき行動が分かる文で返す。

- 書込みを行うツールは、べき等にする。

複数のアプリケーションでツールを共有する場合は、MCPで提供する。

### 6.2 権限を利用者の範囲に限る

エージェントが実行するツールには、操作している利用者の権限を適用する。サービス全体の権限でツールを実行すると、利用者が本来できない操作をエージェント経由で実行できる。

### 6.3 取り消せない操作は人が承認する

メールの送信、決済、データの削除、外部への公開など、取り消せない操作又は外部へ影響する操作は、実行する内容を利用者に示し、承認を得てから実行する。

### 6.4 上限を設ける

エージェントの1回の実行には、モデルの呼出しの回数、トークン数、実行時間及び費用の上限を設ける。上限に達した場合は、そこまでの結果と停止の理由を利用者に示す。

### 6.5 実行の状態を保存する

数十秒を超えるエージェントの実行は、非同期のジョブにし、実行の状態と途中の結果を保存する。保存すれば、接続が切れても再開でき、利用者は進捗を確認できる。

## 7 プロンプトと出力

### 7.1 プロンプトをコードと同じく管理する

プロンプトは、ソースコードの中に散在させず、版を付けてリポジトリで管理し、変更はレビューと評価を経て反映する。プロンプトの変更は、コードの変更と同じく、機能の振る舞いを変える。

### 7.2 出力を検証する

プログラムで処理する出力は、構造化出力でスキーマを指定し、受け取った後もスキーマで検証する。値の範囲と業務上の制約も確認してから保存する。検証に失敗した出力は、再試行するか、人の確認に回す。

### 7.3 出力を信頼できない入力として扱う

モデルの出力は、外部からの入力と同じく扱い、HTMLへの埋込みではエスケープし、データベースの問合せではパラメーターとして渡し、コマンドとして実行しない。

### 7.4 人の確認を組み込む

信頼度が閾値を下回る結果は、人が確認してから確定する。利用者が訂正した結果は保存し、評価用のデータとして使う。

## 8 RAG

RAGは、次によって設計する。

- 資料は、見出し、段落など文書の構造に沿って分割する。画像、音声及び動画は、説明文又は文字起こしを索引に加える。

- 検索は、キーワードによる検索と埋め込みによる検索を組み合わせ、上位の候補を並べ替えてからプロンプトに加える。

- 検索の時点で、利用者が閲覧できる資料だけに絞り込む。生成の後に絞り込んでも、閲覧できない資料の内容が回答に混ざる。

- 検索の精度と、生成の品質とを、別々に評価する。

- 資料の更新と削除を、索引へ反映する。

## 9 セキュリティ

### 9.1 OWASP Top 10 for LLM Applicationsに従う

LLMを使う機能のセキュリティは、OWASP Top 10 for LLM Applicationsの各項目への対策を確認する。

### 9.2 プロンプトインジェクションを前提にする

利用者の入力、Webページ、文書、画像の中の文字、音声及びツールの結果に含まれる文章は、LLMへの指示として働く可能性がある。システムプロンプトの指示だけでは、これを防げない。外部のデータを読むエージェントには、次の三つを同時に持たせない。

- 非公開のデータへのアクセス

- 信頼できない外部のデータの読込み

- 外部への送信の手段

三つが必要な場合は、外部への送信に利用者の承認を必須にする。

### 9.3 機密情報をプロンプトに含めない

APIキー、パスワードなどの機密情報を、プロンプトに含めない。システムプロンプトの内容は、利用者に漏れることを前提に書く。

### 9.4 利用量に上限を設ける

利用者ごとに、要求の頻度、トークン数、ファイルの大きさ及び処理時間の上限を設ける。上限がなければ、一人の利用者の大量の要求で費用が急増する。

## 10 結果の通知と表示

- ファイルのアップロードの直後に、クライアントのファイルからプレビューを表示し、処理の状態を示す。

- 非同期のジョブの状態の変化は、SSE又はWebSocketで通知する。これらを使えない場合は、間隔を延ばしながら問い合わせる。

- 利用者が画面を離れても処理を続け、完了をプッシュ通知又は一覧の表示で知らせる。

- エージェントの実行中は、実行している段階、使ったツール及び参照した資料を示し、いつでも中止できるようにする。

- 回答には、根拠とした資料への参照を付ける。

- 結果には、信頼度の低い箇所が分かる表示と、訂正の操作を設ける。

- 失敗した場合は、理由と、利用者が取れる操作（撮り直し、再試行など）を示す。

## 11 運用（LLMOps）

### 11.1 評価

評価は、次によって行う。

- 機能の成功の基準を、正答率、形式の適合率、遅延、費用など、測定できる指標と目標値で決める。

- 評価セットは、実際の利用で想定する入力の分布に、境界の事例と攻撃的な入力を加えて作る。画像、音声及び動画では、画質、雑音、話者などの条件の違いを含める。

- 採点は、コードで判定できるものはコードで行う。コードで判定できないものは、人の採点と照合して較正したLLMによる採点を使う。

- プロンプト、モデル、ツール、前処理又は検索の設定を変更するたびに、CIで評価を実行し、基準の結果と比べる。

- モデルの出力は同じ入力でも揺れるため、評価は複数回実行して比べる。

### 11.2 版の記録

結果ごとに、モデルの識別子、プロンプトの版、生成の設定、前処理の設定、ツールの定義の版及び検索の索引の版を記録する。記録がなければ、結果が変わった原因を特定できない。

### 11.3 トレース

モデルの呼出しとツールの実行ごとに、入力、出力、トークン数、遅延、費用及びエラーをトレースとして記録する。トレースは、OpenTelemetryの生成AIの規約に沿った属性で出力する。

### 11.4 本番での監視

本番では、次を監視する。

- 遅延、エラー率、トークン数及び費用

- 入力一つあたりの処理の費用

- キューの長さ、最も古いメッセージの経過時間、受付から完了までの時間の95パーセンタイル

- 失敗の理由ごとの件数

- 利用者の評価、再生成及び訂正の頻度

- 抽出した一部の要求に対する、人又はLLMによる品質の確認

費用又はエラー率が急増した場合は、通知する。検証前のファイルと、保存期間を過ぎたファイルは、オブジェクトストレージのライフサイクルの規則で自動で削除する。

### 11.5 変更の展開

プロンプト及びモデルの変更は、機能フラグで一部の利用者から展開し、指標を確認してから全体へ広げる。指標が悪化した場合は、すぐに戻せるようにする。

### 11.6 モデルの提供終了に備える

提供元のモデルの提供終了の予定を確認し、終了の前に後継のモデルで評価を行ってから移行する。主要な提供元が停止した場合に備え、代わりのモデル又は提供元への切替えを用意する。

## 12 チェックリスト

- [表2](#table-2)で、評価の目標を満たす最も単純な構成を選んでいる。

- データの種類ごとに、[表3](#table-3)の方式を選んでいる。

- モデルを、版を固定した識別子で指定している。

- 利用者が結果を待つ処理を逐次返し、重い処理を非同期のジョブにしている。

- ファイルが、アプリケーションのサーバーを経由していない。

- クライアントで、モデルの処理に必要な品質まで縮小又は変換している。

- ワーカーで、実際の形式と大きさを検証し、不要なメタデータを除いている。

- キューに、ファイルの本体ではなく保存先のキーを載せている。

- ワーカーの処理がべき等で、再試行する失敗と再試行しない失敗を区別している。

- ツールを利用者の権限で実行し、取り消せない操作の前に利用者の承認を得ている。

- エージェントの実行に、回数、トークン数、時間及び費用の上限がある。

- プロンプトに版があり、リポジトリで管理されている。

- モデルの出力を、スキーマで検証し、信頼できない入力として扱っている。

- RAGの検索で、利用者が閲覧できる資料だけに絞り込んでいる。

- 非公開のデータ、信頼できないデータ及び外部への送信の三つを、承認なしに同時に持たせていない。

- 評価セットがあり、変更のたびにCIで評価している。

- 結果ごとに版とトレースを記録している。

- 利用者ごとに、要求の頻度、トークン数及びファイルの大きさの上限がある。
