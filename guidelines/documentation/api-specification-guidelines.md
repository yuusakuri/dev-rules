# API仕様書作成ガイドライン

## 1 はじめに

### 1.1 目的

本書の目的は、APIの設計者、実装者及びテスト担当者が、同じ契約に基づいて開発できるようにすることである。

### 1.2 適用範囲

本書は、APIの契約ファイル及びその補足文書の作成方法について規定する。HTTP APIの設計規則は、HTTPを使用するAPIに適用する。

### 1.3 用語及び定義

この文書で用いる主な用語及び定義は、[表1](#table-1)による。

<a id="table-1"></a>表1−用語及び定義

| 用語 | 定義 |
| --- | --- |
| API（application programming interface） | プログラム間で機能又はデータを利用するためのインターフェース。 |
| 契約ファイル | リクエスト、レスポンス及び型を、機械で処理可能な形式で定義するファイル。 |
| 冪等性 | 同じ要求を繰り返した場合に、サーバー上で意図される効果が一度の要求と同じになる性質。 |
| カーソル | 一覧の続きを取得する位置をサーバーが示す値。 |

## 2 契約の記述

APIの契約は、実装より先に確定する。実装、テスト、クライアントコードの生成及び文書の生成では、同じ契約ファイルを使用する。これによって、利用者に示す仕様と実装との不一致を防ぐ。

REST APIの契約は、OpenAPI 3.x以降で記述する。gRPCではProtocol Buffers、GraphQLではSchema Definition Languageのように、採用するプロトコルに専用の定義形式がある場合は、その形式で記述する。

Markdownの補足文書には、契約ファイルだけでは表現しにくい業務上の制約、設計判断の根拠及び移行手順を記載する。契約ファイルにある項目は、その定義を参照する。

## 3 ファイル構成

API名でディレクトリを分け、対象のAPIをパスから識別可能にする。公開用、管理用及び内部用のAPIに同名のリソースがあっても、定義を区別することが可能になる。

HTTP APIのファイル構成は、[表2](#table-2)による。

<a id="table-2"></a>表2−HTTP APIのファイル構成

| パス | 記載内容 |
| --- | --- |
| `docs/specifications/api/<api-name>/openapi.yaml` | エンドポイント、スキーマ及び認証方式を定義する。 |
| `docs/specifications/api/<api-name>/<resource>.md` | リソース単位の業務上の制約及び設計判断の根拠を記載する。 |
| `docs/specifications/api/<api-name>/errors.md` | API全体のエラー種別を定義する。 |

`<api-name>`には、`public`、`admin`又は`internal`のようにAPIを識別する名称を使用する。APIが一つの場合もこの階層を設け、APIが増えた場合にも同じ配置を維持する。

## 4 リソース及びHTTPメソッド

### 4.1 リソース名

リソース名は、`/users`、`/orders`のように複数形の名詞とする。個別のリソースは、`/users/{userId}`のように識別子で指定する。

リソースの入れ子は1階層までとする。それを超える場合は、対象を独立したコレクションとして表す構成を検討する。

単純な作成、取得、更新及び削除で表せない操作は、リソースの配下に操作用のパスを設ける。例えば、有効化は`/users/{userId}/activate`で表し、動詞をクエリパラメーターへ含めない。

### 4.2 HTTPメソッドの意味

HTTPメソッドは、[表3](#table-3)の用途で使用する。冪等なメソッドでは、同じ要求を再送しても、意図される効果が一度の要求と同じになるようにする。

<a id="table-3"></a>表3−HTTPメソッドの用途及び冪等性

| メソッド | 用途 | 冪等性 |
| --- | --- | --- |
| `GET` | リソースを取得する。 | あり |
| `POST` | リソースを作成するか、他のメソッドで表せない処理を実行する。 | 保証されない |
| `PUT` | リソース全体を置換する。 | あり |
| `PATCH` | リソースを部分的に更新する。 | 更新内容に依存する |
| `DELETE` | リソースを削除する。 | あり |

`PATCH`は、同じ差分を再適用したときの効果によって冪等性が異なる。再送を許す場合は、更新形式及び競合の検出方法を契約に記載する。

## 5 一覧のページ分割

一覧の取得には、サーバーが次の取得位置を指定するカーソル方式を使用する。件数で位置を指定するオフセット方式では、取得中にデータが増減すると、同じ項目の重複又は項目の欠落が起きる。

レスポンスには、次のページを取得するためのカーソルを含める。クライアントはカーソルの内部構造を解釈せず、返された値を次の要求へ渡す。

## 6 エラー

### 6.1 エラーの形式

HTTP APIのエラーレスポンスは、RFC 9457のProblem Details形式とする。API全体で同じ形式を使用し、クライアントがエラーを一貫して処理可能にする。

標準のメンバーは、[表4](#table-4)による。必須とするメンバー及び省略時の扱いは、APIの契約に記載する。

<a id="table-4"></a>表4−Problem Detailsのメンバー

| メンバー | 意味 |
| --- | --- |
| `type` | エラー種別を識別するURI参照。省略時は`about:blank`。 |
| `title` | エラー種別を人が理解するための短い説明。 |
| `status` | このエラーに対してサーバーが返すHTTPステータスコード。 |
| `detail` | 今回発生したエラーの具体的な説明。 |
| `instance` | 今回のエラーの発生を識別するURI参照。 |

エラー種別は、`type`ごとに`errors.md`で管理する。入力項目ごとのエラー情報が必要な場合は、拡張メンバーとして定義する。

### 6.2 HTTPステータスコード

HTTPステータスコードの選択は、[表5](#table-5)による。成功時のレスポンス本文の有無も、契約に記載する。

<a id="table-5"></a>表5−HTTPステータスコードの選択

| コード | 使用する場面 |
| --- | --- |
| `200` | 取得又は更新が成功し、本文を返す場合。 |
| `201` | リソースの作成が成功した場合。 |
| `204` | 処理が成功し、本文を返さない場合。 |
| `400` | リクエストの形式が不正な場合。 |
| `401` | 認証情報がないか、無効な場合。 |
| `403` | 要求を実行する権限がない場合。 |
| `404` | 対象のリソースが存在しない場合。 |
| `409` | リソースの現在の状態と要求が競合する場合。 |
| `422` | 形式は解釈可能であるが、内容が業務上の制約を満たさない場合。 |
| `429` | 要求の頻度制限を超えた場合。 |
| `500` | サーバー内部で予期しないエラーが発生した場合。 |

## 7 バージョン及び提供終了の通知

APIのバージョンは、`/v1/users`のようにURLパスの先頭に置く。既存の利用方法との互換性を失う場合に、バージョンを上げる。

フィールドの追加又は任意パラメーターの追加は、既存のクライアントが同じ契約で動作することを確認した上で、同じバージョンに含める。既存フィールドの意味の変更、削除又は必須化は、互換性を失う変更として扱う。

利用を非推奨とするエンドポイントには、RFC 9745の`Deprecation`ヘッダーを付け、その時点を通知する。応答を終了する日時が決まっている場合は、RFC 8594の`Sunset`ヘッダーで通知する。移行先及び移行方法は、レスポンスの`Link`ヘッダーから参照可能にする。
