# Test Case Specification

> 実行前に定義するテストケース仕様の汎用テンプレート。実行結果や進捗集計はテストログ／テスト管理ツールで管理する。

## 2. 記載ガイド

テストケースは、テスト実行前に「何を、どの条件で、どの手順により確認し、何をもって合格とするか」を明確にするための仕様である。実行者が変わっても同じ解釈で実施できることを目標とする。

### 2.1 テスト対象

ソフトウェアのどの部分を確認するかを記載する。機能、画面、API、入力項目などが複雑な場合は、大項目・中項目・小項目へ分解する。

記載例:

| 大項目 | 中項目 | 小項目 |
| --- | --- | --- |
| アカウント管理 | ログイン | パスワード入力 |

### 2.2 テスト観点

そのケースで「何を確認するのか」を端的に記載する。単なる操作名ではなく、ケースを作成した意図が分かる表現にする。

悪い例: `入力チェック`

良い例: `パスワード未入力時に認証を開始できないこと`

### 2.3 実行条件

実行前に成立している必要がある前提条件を記載する。テストデータ、アカウント、権限、デバイス、環境設定、入力値などを含める。実行途中で初めて前提不足に気付くことがないよう、手順とは分離する。

記載例:

- 有効な一般ユーザーが登録済みである。
- 対象ユーザーはログアウト状態である。
- 入力値: ユーザー名=`test-user`、パスワード=空文字。

### 2.4 実行手順

具体的な操作を順序どおりに記載する。画面名、ボタン名、API、URL、コマンドなど、実行者が探さなくて済む情報を必要に応じて含める。

記載例:

1. ログイン画面を開く。
2. ユーザー名に `test-user` を入力する。
3. パスワードは入力しない。
4. ログインを実行する。

### 2.5 期待結果

どの挙動、値、表示であれば合格と判定できるかを具体的に記載する。「正しいこと」「問題ないこと」のように実行者の判断へ委ねる表現は避ける。

記載例:

- 認証要求が送信されない。
- パスワード入力欄の近傍に必須入力を示すエラーが表示される。
- ログイン後画面へ遷移しない。

独立した期待結果が複数ある場合は、可能な限りケースまたは行を分ける。これにより、一部だけ成功・失敗した場合でも判定単位を曖昧にしない。

### 2.6 参照とトレーサビリティ

テストケースから根拠となる要求、仕様、設計へ追跡できるよう、識別子またはリポジトリ内パスを記載する。外部Webページへの案内ではなく、プロジェクト内で永続的に参照できる情報を優先する。

例:

`REQ-AUTH-003`, `docs/authentication.md#password-required`

## 3. 作成規則

1. 具体的に書く。実行者によって判断が変わる表現を避ける。
2. 作成意図をテスト観点から読み取れるようにする。
3. 前提条件、操作、期待結果の役割を混同しない。
4. 要求・仕様・設計とのトレーサビリティを確保する。
5. 1ケースで確認する責務を必要以上に広げない。独立して判定したい期待結果は分割する。
6. テストケースの内容に影響しない範囲で、共通の前提条件やテストデータは再利用してよい。ただし、依存するケースがある場合は依存関係を明記する。

## 4. テストログとの分離

この文書はテストケース仕様を扱う。以下は実行結果であり、テストログ側で管理する。

- 結果判定
- 実行日時
- 実行者
- 実行環境・対象バージョン
- 不具合ID
- 証跡
- 実行時の備考

OK件数、NG件数、進捗率などの集計値もテストケース仕様には保持しない。必要な場合は、テストログまたはテスト管理ツールから算出する。
