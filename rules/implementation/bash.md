# Bash固有の追加規則

> 適用対象: Bash 3.2以上を対象とするシェルスクリプト、または`source`して利用する関数ライブラリのソースコード、テスト、プロジェクト構成を変更する場合。

## 1. 適用範囲

本書は、Bash 3.2以上でmacOSとLinuxの両方から共通利用するコードに適用する言語固有の追加規則を定義する。シェルスクリプトと、`source`して利用する関数ライブラリの双方を対象とする。

個別プロジェクト固有の公開関数一覧、名前付き引数の表記、AWSなど特定サービス向けの処理は本書に含めない。それらは利用側プロジェクトのドキュメントで管理する。

---

## 2. Bashバージョン互換性

- Bash 4以降で追加された連想配列などを使用しない。
- Bash 3.2で解釈できない構文を使用しない。
- OS名やCPUアーキテクチャを必要以上に固定せず、実際に依存する機能を基準に条件分岐する。

---

## 3. シェルオプション

ライブラリは、呼び出し元シェル全体の状態を勝手に変更しない。

`set -e`、`set -u`、`set -o pipefail`をライブラリ読み込み時に有効化しない。これらを必要とする実行スクリプトは、そのスクリプト自身の責任で設定する。

---

## 4. 関数設計

公開関数は名前空間を付ける。

形式は次のように統一する。

```text
<domain>::<action>
```

例:

```text
string::upper
path::normalize
net::dns::use-systemd-resolved
```

2階層で意味が十分な場合は2階層とし、必要な場合だけ3階層以上にする。

`feature::command-name`のように抽象度が揃わない説明は使用しない。名前空間は機能領域、末尾は処理を表す動詞または動詞句として扱う。

---

## 5. 引数設計

Bashの実装規則では、特定プロジェクト固有の引数表記を標準化しない。CLIや関数が採用する公開インターフェースに合わせて解析方法を選ぶ。

短いPOSIX形式のオプションを扱う場合は、Bash組み込みの`getopts`を利用してよい。

```text
-n VALUE
-f
```

GNU形式や複数文字の名前付き引数を扱う場合は、外部`getopt`の移植性差分へ依存せず、Bashの`while`と`case`で解析する。

```text
--name VALUE
--force
```

PowerShellに近い`-Name VALUE`形式はBash一般の規則には含めず、その形式を採用するプロジェクト側の仕様として定義する。

---

## 6. 名前付き引数パーサー

関数ライブラリでは、各関数が同じ`while / case`を重複実装しないようにする。

ただし、Bash 3.2では連想配列を利用できないため、解析結果をグローバルな疑似辞書へ蓄積する設計は避ける。

推奨する構成は、引数仕様の検査を共通関数へ寄せ、値の代入自体は呼び出し先関数のローカル変数へ明示的に行う方式とする。

例:

```bash
user::create() {
    local name=''
    local shell='/bin/bash'
    local force='false'

    while [ "$#" -gt 0 ]; do
        case "$1" in
            --name)
                arg::require-next "$#" "$1" || return 1
                name=$2
                shift 2
                ;;
            --shell)
                arg::require-next "$#" "$1" || return 1
                shell=$2
                shift 2
                ;;
            --force)
                force='true'
                shift
                ;;
            *)
                arg::unknown "$1" || return 1
                ;;
        esac
    done

    arg::require --name "$name" || return 1

    # 本処理
}
```

共通化するのは、値の存在確認、必須値の確認、型や形式の検査、不明な引数のエラー生成などとする。

値を取る引数では、次の位置引数が存在することを残り引数数から検査する。`arg::require-next`は残り引数数と現在のオプション名を受け取り、末尾に値なしで指定された場合を確実にエラーにする。空文字を値として許可するかどうかは、この存在確認とは分離して各引数の入力検査で決める。

```bash
arg::require-next() {
    local argc=$1
    local option=$2

    if [ "$argc" -lt 2 ]; then
        printf 'Error: Option %s requires a value.\n' "$option" >&2
        return 1
    fi
}
```

この補助関数は定型検査を短くするためのものであり、引数解析そのものを隠蔽しない。各公開関数では`case`を読めば、引数からローカル変数への対応が分かる状態を維持する。

関数ローカル変数への動的代入を目的に`eval`を使う設計は採用しない。これは安全性の宣伝文句ではなく、実装規則としてのみ記載する。

---

## 7. Tab補完

名前付き引数を公開する関数は、その関数と同じ名前空間に補完定義用の内部関数を1つ持つ。

公開関数が`user::create`の場合は`user::_create-args`とし、`service::restart`の場合は`service::_restart-args`とする。内部関数名から公開関数との対応を機械的に判断できるため、中央の補完dispatcherへ関数ごとの分岐を追加しない。

```bash
user::_create-args() {
    printf '%s\n' '-Name' '-Shell' '-Force'
}
```

値の候補が必要な場合も、対象関数の内部補助関数へ記述する。

```bash
service::_restart-args() {
    case "${1-}" in
        -Name)
            printf '%s\n' nginx sshd
            ;;
        '')
            printf '%s\n' -Name -Wait
            ;;
    esac
}
```

ライブラリ全体では補完dispatcherを1つだけ定義する。この関数は`COMP_WORDS[0]`から対象となる`::<処理>`を`::_<処理>-args`へ変換し、その内部補助関数を自動的に呼び出す。

補完の登録も中央の関数一覧へ手動追記しない。ライブラリの読み込み時に`::_*-args`の内部関数を検出し、対応する公開関数へ`complete -F`で補完dispatcherを登録する。

これにより、公開関数を追加する際は、その関数と対応する`::_<処理>-args`だけを同じ機能ファイルへ追加すればよい。

補完実装はBash 3.2で利用できる機能だけを使用する。

---

## 8. 引数解析と補完の整合性

Bash 3.2では、引数名、型、必須性、補完候補を汎用データ構造へ集約すると、独自DSLや区切り文字ベースの疑似構造体が必要になり、引数解析自体より複雑になりやすい。そのため、引数解析そのものを補完定義から自動生成しない。

引数解析は各公開関数の`while / case`に明示し、補完候補は対応する`::_<処理>-args`に記載する。中央のdispatcherには個別関数の知識を持たせない。

名前付き引数を公開するプロジェクトでは、公開引数一覧をドキュメントに記載し、テストで次を確認する。

- `::_<処理>-args`が返す引数を対応する公開関数が受理すること
- 公開すると定めた名前付き引数が補完候補に含まれること
- 値補完が対象引数の直後だけで動作すること
- 補完定義を持つ公開関数へ補完dispatcherが登録されること

Bash 4以降の連想配列やコード生成を前提にできる別プロジェクトでは、より強い一元管理を採用してよい。

---

## 9. 入力検査

公開関数は、処理開始前に必要な入力を検査する。

検査対象には、必須値、整数、パス、列挙値、コマンドの存在などを含める。

入力検査関数は`validate::`または対象領域に応じた明確な名前空間へまとめる。

---

## 10. エラー処理

ライブラリ関数は、回復不能なエラーでも呼び出し元シェルを`exit`させず、原則として非0のステータスを`return`する。

対話型シェルから利用される関数であるため、ライブラリ内部からシェル全体を終了させない。

エラー文は標準エラー出力へ出す。

---

## 11. OS差分

macOSとLinuxでコマンドやオプションに差がある場合は、その差分を呼び出し側へ露出させず、ユーティリティ関数内で吸収する。

GNU版とBSD版で挙動が異なる外部コマンドへ依存する前に、Bashだけで実現できないか検討する。

外部コマンドが必要な場合は、その機能を実際に使用するときに存在を確認する。

---

## 12. 外部依存

標準的なBash機能だけで十分に実装できる処理に、引数解析ライブラリなどの外部依存を追加しない。

外部依存を採用する場合は、Bash 3.2だけでは合理的に実装できない機能であり、保守性または利用者体験が明確に改善する場合に限定する。

shFlagsは採用しない。

---

## 13. source時の副作用

ライブラリを`source`しただけで、次のような呼び出し元環境の設定を書き換えない。

- `set -e`
- `set -u`
- `set -o pipefail`
- `IFS`
- カレントディレクトリ
- 利用者の既存エイリアス
- ライブラリと無関係な環境変数

公開関数と補完の登録など、ライブラリ利用に必要な定義は読み込み時に行ってよい。

---

## 14. 検証

利用者向け機能と開発環境の説明は分ける。プロジェクトの`README.md`の「特徴」へ検証ツールの説明を混ぜず、`CONTRIBUTING.md`または開発章に記載する。

| 目的 | 検証対象 | ツール |
|---|---|---|
| Bash 3.2で解釈できることを確認する。 | 構文エラー。 | `bash -n` |
| 静的な不具合と移植性の問題を検出する。 | シェルスクリプト全体。 | ShellCheck |
| 関数単位の振る舞いを検証する。 | 正常系と異常系。 | Bats-core |
| 対応環境での実行を確認する。 | macOSとLinuxそれぞれの実行結果。 | 対応するOSでのCI実行 |
