# 通信プロトコル実装規約

## 1. 概要

本書は、ネットワーク通信、シリアル通信（UART、USBなど）、独自の通信プロトコルまたはバイナリ形式の実装に関する規則を定義する。HTTP、gRPCなど、確立されたプロトコルをライブラリ経由で扱うだけの場合は対象外とする。本書は、[共通設計原則](../core/architecture.md)を前提とする。

---

## 2. プロトコル設計の基本

### ヘッダ形式

固定長のヘッダをペイロードの前に置き、少なくとも次を含める。

| 項目 | 用途 |
| ---- | ---- |
| 同期バイト | 受信データの先頭でFrameの開始位置を検出する。 |
| バージョン | プロトコルの互換性を判定する。 |
| 種別 | ペイロードの解釈方法を決定する。 |
| 長さ | ペイロードの境界を示す。 |
| チェックサム | 伝送誤りを検出する。 |

可変長ペイロードは長さフィールドで境界を明示し、区切り文字に依存しない。区切り文字方式は、区切り文字がペイロード内に出現する場合のエスケープ処理が実装と検証の負担になる。

### バージョニング

プロトコルバージョンをヘッダに含め、受信側は未対応バージョンを明示的に拒否する。フィールドの追加はバージョンを上げるか、TLV（Type-Length-Value）のような後方互換性のある拡張領域で行い、既存フィールドの意味やサイズを変更しない。

### チェックサム

CRCなどの検査値をFrameへ含め、伝送誤りを検出する。検査対象の範囲（ヘッダを含むかなど）を仕様として明記し、送受信の実装を一致させる。

## 3. バイナリパース戦略

ストリームや分割された入力からバイナリデータを解析する場合は、Deterministic Finite Automaton（決定性有限オートマトン）として解析状態と遷移条件を明示し、1回の呼び出しで1バイトだけを受け取って状態を進める関数をループから呼び出す構造を積極的に採用する。解析途中の状態を保持し、Frameが完成した時点で結果を返すことで、入力の分割位置に依存せず、固定長バッファとストリームを同じ解析器で扱える。

状態は列挙型で表現し、各状態の遷移条件と次状態を明示する。不正なバイト列を受け取った状態はエラー状態へ遷移し、上位へ終了エラーとして通知する。

これにより、状態ごとの単体テスト、異常入力からの復帰、メモリ使用量の制御が容易になる。Frame長が事前に確定しており、全データが常に一括で入手できる場合など、全データを一括処理する方が明らかに単純なときは無理に適用しない。

---

## 4. エンディアン（バイトオーダー）の扱いと型変換

プロトコル仕様が指定するバイトオーダー（Big Endian / Little Endian）を、実行環境のネイティブエンディアンに関わらず明示的に変換する。整数型を直接メモリへキャストせず、`to_be_bytes` / `from_be_bytes`のような、使用する言語が提供するバイトオーダー変換APIを使用する。

複数バイトにまたがるフィールドは、フィールドごとにエンディアンを明記する。1つのFrame内で異なるエンディアンが混在する仕様も存在するため、フィールド単位で仕様を確認する。

---

## 5. ストリーム、バッファ管理とゼロコピー

固定長の受信バッファを再利用し、Frameごとに新しいバッファを都度確保しない。受信データ量が仕様上の上限を超える場合は、上限を超えた時点でエラーとして扱い、無制限にバッファを拡張しない。

パースしたペイロードを別のバッファへコピーせずに参照できる場合は、スライスや参照を返し、不要なコピーを避ける（ゼロコピー）。参照は元のバッファの生存期間に依存するため、参照が元のバッファより長く生存する構造にしない。

---

## 6. 通信エラー、タイムアウト、切断からの復帰

すべての受信待機、送信、応答待ちにタイムアウトを設定する。詳細は共通設計原則の並行処理の規則に従う。

再送が必要な操作は冪等性を考慮し、同じ要求が重複して届いても安全に処理できる設計にする。接続が切断された場合は、保持していた解析途中の状態を破棄し、再接続後は初期状態から解析を再開する。

再接続は指数バックオフとジッターを用いて再試行間隔を広げ、接続先への再試行の集中を避ける。
