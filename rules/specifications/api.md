# API仕様書作成ルール

> 適用対象: API仕様書を新規作成または変更する場合。

> **目的：** どのプロジェクト・チーム規模・技術スタックでも通用する、読む人全員が同じ理解に到達できる仕様書を作るためのルール集。

---

## 1. ファイル構成ルール

### 1-1. ファイル分割の単位

**ルール：** 1エンドポイントグループ（リソース）= 1ファイル

```
docs/api/
├── _rules/          # このルールファイル群
├── _template/       # テンプレート群（別ファイル参照）
├── auth.md          # 認証・認可
├── users.md         # /users 系エンドポイント
├── orders.md        # /orders 系エンドポイント
└── errors.md        # エラーコード一覧（共通）
```

**理由：** リソース単位で担当者が分かれる大規模開発において、コンフリクトを最小化し、レビュー範囲を明確にするため。

### 1-2. ファイル命名規則

**ルール：** URLリソース名をそのままケバブケースで使う（例：`user-profiles.md`）

**理由：** URLと仕様書のファイル名が1対1で対応することで、「どのファイルを見ればいいか」を考えずに済むため。

---

## 2. ドキュメントメタデータルール

### 2-1. 必須ヘッダー項目

**ルール：** すべての仕様書ファイルは以下のメタデータブロックから始める。

```yaml
---
title: ユーザー管理 API
version: 1.2.0
status: stable          # draft | review | stable | deprecated
last_updated: 2025-01-15
owner: @username        # 仕様の責任者（GitHubユーザー名等）
reviewers:
  - @username-a
  - @username-b
base_url: /api/v1/users
---
```

**理由：** 「誰が最終決定権を持つか」「今どの段階か」が不明だと、古い仕様を参照し続けることになるため。

### 2-2. バージョン管理ルール

**ルール：** セマンティックバージョニング（`MAJOR.MINOR.PATCH`）を使う。

- `PATCH`：誤字・説明の補足
- `MINOR`：フィールド追加・任意パラメータ追加（後方互換）
- `MAJOR`：破壊的変更（レスポンス構造変更・フィールド削除・URL変更）

**理由：** バージョン番号から変更の影響範囲をひと目で判断できるため。

---

## 3. エンドポイント記述ルール

### 3-1. 記述順序

**ルール：** すべてのエンドポイントを以下の順序で記述する（省略不可）。

1. **概要**（1〜2文）
2. **HTTPメソッド + URL**
3. **認証要件**
4. **リクエスト**（パスパラメータ → クエリパラメータ → ヘッダー → ボディ）
5. **レスポンス**（成功 → エラー）
6. **サンプル**（リクエスト + レスポンスをセットで）
7. **備考・制約**

**理由：** 読む人が「次に何が来るか」を予測できる構造にすることで、読解速度を上げるため。

### 3-2. HTTPメソッドの使い分け

**ルール：**

| 操作 | メソッド | 条件 |
|------|----------|------|
| 取得 | GET | 副作用なし |
| 新規作成 | POST | 冪等でない |
| 完全更新 | PUT | 冪等・全フィールド必須 |
| 部分更新 | PATCH | 冪等・変更フィールドのみ |
| 削除 | DELETE | 冪等 |

**理由：** メソッドの意味論を統一することで、クライアント実装者が「このAPIはキャッシュ可能か」「再送してよいか」を仕様書外の知識で判断できるため。

### 3-3. URLパス命名規則

**ルール：**

- リソース名は **複数形の名詞**（`/users`、`/orders`）
- リソースID は `/{resource}/{id}` 形式（`/users/{userId}`）
- ネストは **2階層まで**（`/users/{userId}/orders`）
- アクションが必要な場合は動詞サフィックス（`/users/{userId}/activate`）

**理由：** 3階層以上のネストはURLが複雑になり、設計上の責務分離ができていないサインであるため。

## 4. パラメータ記述ルール

### 4-1. パラメータ定義テーブルの必須列

**ルール：** パラメータは必ず以下6列のテーブルで記述する。

| 列 | 内容 |
|----|------|
| `name` | パラメータ名（キャメルケース） |
| `type` | 型（string / integer / boolean / array / object） |
| `required` | ✅ 必須 / ⬜ 任意 |
| `default` | デフォルト値（任意パラメータのみ。なければ `-`） |
| `constraints` | バリデーション条件（`1-100`、`ISO 8601`、`max: 255文字` 等） |
| `description` | 説明（何のための値か、ビジネス的な意味を含める） |

**理由：** 「型はわかるが範囲がわからない」「必須かどうか不明」という実装ミスの原因を仕様書側で潰すため。

### 4-2. 型の表記ルール

**ルール：** 型はJSON Schemaの型名に統一し、フォーマットを明記する。

```
string (email)
string (ISO 8601 datetime)
string (UUID v4)
integer (int32)
number (float)
array<string>
array<object: OrderItem>
```

**理由：** 「文字列」だけでは実装者ごとに解釈が異なり、バリデーション漏れが発生するため。

---

## 5. レスポンス記述ルール

### 5-1. レスポンス構造の統一

**ルール：** 全エンドポイントのレスポンスを以下のエンベロープ構造に統一する。

```json
// 成功（単一リソース）
{
  "data": { ... },
  "meta": { "requestId": "uuid" }
}

// 成功（リスト）
{
  "data": [ ... ],
  "meta": {
    "requestId": "uuid",
    "total": 100,
    "page": 1,
    "perPage": 20
  }
}

// エラー
{
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "指定されたユーザーが見つかりません",
    "details": [ ... ]   // バリデーションエラー等の詳細（任意）
  },
  "meta": { "requestId": "uuid" }
}
```

**理由：** レスポンス構造が統一されていないと、クライアント側で「成功かどうかをどこで判断するか」が実装者ごとに異なり、バグの温床になるため。

### 5-2. HTTPステータスコードの使い方

**ルール：** 以下の対応表を厳守する。

| コード | 使用場面 |
|--------|----------|
| 200 | GET成功、PUT/PATCH成功 |
| 201 | POST成功（リソース作成） |
| 204 | DELETE成功（ボディなし） |
| 400 | リクエスト形式不正・バリデーションエラー |
| 401 | 認証なし・トークン無効 |
| 403 | 認証済みだが権限なし |
| 404 | リソースが存在しない |
| 409 | 競合（すでに存在する、状態が前提条件を満たさない） |
| 422 | 形式は正しいがビジネスロジックエラー |
| 429 | レートリミット超過 |
| 500 | サーバー内部エラー |

**理由：** ステータスコードの使い方がバラバラだと、クライアントが「リトライすべきか」「ユーザーに見せるべきか」を判断できないため。

### 5-3. エラーコードの命名規則

**ルール：** エラーコードは `リソース名_動詞_状態` の形式でスネークアッパーケース。

```
USER_NOT_FOUND
ORDER_ALREADY_CANCELLED
EMAIL_ALREADY_EXISTS
PAYMENT_INSUFFICIENT_BALANCE
```

**理由：** エラーコードがユニークかつ意味が読み取れる形式であれば、クライアント側で個別ハンドリングしやすく、ログ検索も効率的になるため。

## 6. サンプルコード記述ルール

### 6-1. サンプルの必須要件

**ルール：** すべてのエンドポイントに以下を記載する。

- **正常系サンプル**：最も典型的なユースケース（必須）
- **エラー系サンプル**：最も発生頻度の高いエラー最低1件（必須）
- **curl形式**：コピペして即実行できる完全なコマンド（必須）

```bash
# リクエスト例（実行可能な完全形式）
curl -X GET "https://api.example.com/api/v1/users/123" \
  -H "Authorization: Bearer {ACCESS_TOKEN}" \
  -H "Content-Type: application/json"
```

**理由：** サンプルがあることで実装者の「試しながら理解する」コストが激減し、仕様の誤読を早期に発見できるため。

### 6-2. サンプル値のルール

**ルール：**

- IDは `123`、`456` のような自明な仮値ではなく、実際の形式を反映した値を使う（UUID なら `a1b2c3d4-e5f6-7890-abcd-ef1234567890`）
- メールは `user@example.com`（RFC 5321で予約されたドメイン）
- 日付は常に `2025-01-15T09:00:00Z`（過去の具体的な日付）
- 金額は実際にありうる値（`1000`、`29800`）

**理由：** 「xxx」「dummy」等のプレースホルダーは、実装者が「自分で決めていいのか」「形式は何か」を混乱させるため。

## 7. 変更管理ルール

### 7-1. 変更履歴の記録

**ルール：** ファイル末尾に変更履歴セクションを設け、以下の形式で追記する。

```markdown
## 変更履歴

| バージョン | 日付 | 変更者 | 変更内容 |
|-----------|------|--------|---------|
| 1.2.0 | 2025-01-15 | @username | `profileImageUrl` フィールドを追加 |
| 1.1.0 | 2025-01-10 | @username | `GET /users` にソートパラメータを追加 |
| 1.0.0 | 2025-01-01 | @username | 初版リリース |
```

**理由：** git blameやPRで変更理由まで追跡するコストは高い。仕様書内に変更履歴があることで「なぜこうなったか」を即座に把握できるため。

### 7-2. 非推奨（Deprecated）の扱い

**ルール：**

1. `status: deprecated` に変更
2. 廃止予定日を明記
3. 代替エンドポイントへのリンクを追加
4. エンドポイントの冒頭に警告ブロックを追加

```markdown
> ⚠️ **Deprecated:** このエンドポイントは `2025-06-30` に廃止予定です。<br>
> 代替: [`GET /api/v2/users`](../v2/users.md)
```

**理由：** 廃止日と移行先を明示しないと、クライアントチームが移行計画を立てられないため。

## 8. レビュールール

### 8-1. マージ前チェックリスト

**ルール：** 仕様書のPRには以下を確認してからApproveする。

- [ ] メタデータヘッダーが揃っている
- [ ] 全パラメータに6列の定義テーブルがある
- [ ] 成功系・エラー系サンプルが両方ある
- [ ] エラーコードが `errors.md` の一覧に追記されている
- [ ] 破壊的変更の場合、MAJORバージョンが上がっている
- [ ] 変更履歴が追記されている

**理由：** レビュアーが何を見るべきかを明示することで、レビューの品質と速度を一定に保つため。

---

## 付録：用語統一ルール

**ルール：** プロジェクト内で以下の表記を統一する（開始時にチームで合意し追記する）。

| 概念 | 統一表記 | 禁止表記例 |
|------|----------|-----------|
| 一意識別子 | `id` | `ID`, `Id`, `identifier` |
| 作成日時 | `createdAt` | `created_at`, `createDate` |
| 更新日時 | `updatedAt` | `updated_at`, `modifiedAt` |
| 削除フラグ | `isDeleted` | `deleted`, `del_flg` |
| ページ番号 | `page` | `pageNo`, `pageNum` |
| 件数 | `perPage` | `limit`, `pageSize` |

**理由：** フィールド名の表記ゆれはクライアント実装者を最も消耗させるバグ原因の一つであるため。
