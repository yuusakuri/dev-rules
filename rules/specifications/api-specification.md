# API仕様書作成規約

## 1. 概要

本書は、API仕様書を新規作成または変更する場合に適用する。本書は、[仕様書共通規則](specification-writing.md)を前提とする。

API First原則に基づき、実装より先にAPIの契約を確定させる。REST APIでは、契約をOpenAPI（3.x以降）で記述し、実装、テスト、クライアントコード生成、ドキュメント生成の単一の情報源とする。gRPCのProtocol Buffers、GraphQLのSchema Definition Languageのように、採用するプロトコルが専用のインターフェース定義言語を持つ場合はそれを契約とし、OpenAPIを無理に適用しない。

Markdownによる補足文書は、契約ファイルだけでは表現しにくい業務ルール、判断の根拠、移行手順を記載する場所であり、契約ファイルの内容を重複して書き写す場所ではない。

---

## 2. 構成

1つのリポジトリが複数のAPI（公開API、管理API、内部API、パートナーAPIなど）を持つ場合、同じ名前のリソースが別々のAPIに存在しうる。API名で階層を分け、どのAPIの仕様かをパスから判断できるようにする。

| パス | 内容 |
| ---- | ---- |
| `docs/specifications/api/<api-name>/openapi.yaml` | そのAPIの契約。エンドポイント、スキーマ、認証方式を記述する。 |
| `docs/specifications/api/<api-name>/<resource>.md` | 契約ファイルだけでは表現しにくい、リソース単位の業務ルールと根拠を記載する。 |
| `docs/specifications/api/<api-name>/errors.md` | そのAPI全体で共通のエラーコード一覧。 |

`<api-name>`には、`public`、`admin`、`internal`のように、そのAPIを識別する名称を使う。リポジトリが持つAPIが1つの場合も`<api-name>`は省略しない。後から2つ目のAPIが追加された時にパス構成を変更せずに済む。

## 3. リソース設計

### 命名

リソース名は複数形の名詞にする（`/users`、`/orders`）。個別リソースは`/{resource}/{id}`で指定する（`/users/{userId}`）。ネストは1階層までとし、それ以上ネストが必要な場合は、対象リソースを独立したコレクションとして公開できないか見直す。

単純なCRUDで表現できない操作は、コレクションの下にサブリソースとして表現する（`/users/{userId}/activate`）。動詞をクエリパラメータへ含めない。

### HTTPメソッド

| メソッド | 用途 | 冪等性 |
| ---- | ---- | ---- |
| `GET` | 取得。副作用を持たない。 | 冪等 |
| `POST` | 新規作成、またはコレクションに属さない操作の実行。 | 冪等でない |
| `PUT` | リソース全体の置き換え。 | 冪等 |
| `PATCH` | リソースの部分更新。 | 冪等 |
| `DELETE` | 削除。 | 冪等 |

冪等なメソッドは、同じリクエストを再送しても結果が変わらないように実装する。クライアントはネットワーク断からの再送を前提にできる。

## 4. ページネーション

一覧取得はサーバー駆動のカーソルベースページングを基本とする。クライアントが指定するオフセットで位置を数えるページングは、取得中に元データが増減すると重複や欠落が発生するため使用しない。

レスポンスには、次ページを取得するための不透明なカーソルを含める。カーソルの内部構造はクライアントへ公開しない。

## 5. エラー

エラーレスポンスは[RFC 9457（Problem Details for HTTP APIs）](https://www.rfc-editor.org/rfc/rfc9457.html)の形式に統一する。

| フィールド | 内容 |
| ---- | ---- |
| `type` | エラー種別を識別するURI。 |
| `title` | エラー種別の人間可読な要約。 |
| `status` | HTTPステータスコード。 |
| `detail` | 発生した個別のエラーの説明。 |
| `instance` | エラーが発生した具体的なリクエストを識別するURI。 |

`type`ごとに一意なエラー種別を、そのAPIの`errors.md`で一覧管理する。バリデーションエラーのようにフィールド単位の詳細が必要な場合は、拡張メンバーとして追加する。

HTTPステータスコードは、次の対応を基本とする。

| コード | 使用場面 |
| ---- | ---- |
| `200` | `GET`成功、`PUT`/`PATCH`成功。 |
| `201` | `POST`成功（リソース作成）。 |
| `204` | `DELETE`成功（ボディなし）。 |
| `400` | リクエスト形式が不正。 |
| `401` | 認証情報がない、または無効。 |
| `403` | 認証済みだが権限がない。 |
| `404` | リソースが存在しない。 |
| `409` | 現在の状態と競合する。 |
| `422` | 形式は正しいが業務ルールに違反する。 |
| `429` | レート制限を超過。 |
| `500` | サーバー内部エラー。 |

## 6. バージョニングと廃止

後方互換性を保てる変更（フィールド追加、任意パラメータ追加）はバージョンを上げずに行う。既存フィールドの意味変更、削除、必須化のように後方互換性を壊す変更だけをバージョンアップの対象とする。

バージョンはURLパスの先頭に置く（`/v1/users`）。マイナー、パッチ相当の変更は追加的な変更として同じバージョン内で扱い、番号を分割しない。

エンドポイントを廃止する場合は、[RFC 9745（The Deprecation HTTP Header Field）](https://www.rfc-editor.org/rfc/rfc9745.html)と[RFC 8594（The Sunset HTTP Header Field）](https://www.rfc-editor.org/rfc/rfc8594.html)のヘッダーで、廃止済みであることと廃止予定日をクライアントへ通知する。代替エンドポイントをレスポンスヘッダーのリンクで示す。
