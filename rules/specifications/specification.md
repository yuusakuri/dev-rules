# 仕様書共通規則

## 1. 概要

本書は、ソフトウェアに関する仕様書全般に共通する規則を定義する。

開発工程ごとに作成される文書は、対応するISO/IEC/IEEE規格を参考にできる。規格への準拠を必須とはしない。

| 工程 | 文書の例 | 対応するISO/IEC/IEEE規格 |
| --- | --- | --- |
| 要件定義 | 要求仕様書（要求、機能要件、非機能要件） | ISO/IEC/IEEE 29148（StRS、SyRS、SRS） |
| 基本設計（外部設計） | システム構成、画面、UI、データベース基本設計 | ISO/IEC/IEEE 42010の一部 |
| 詳細設計（内部設計） | API仕様書、詳細処理設計 | ISO/IEC/IEEE 1016 |
| テスト | テスト計画書、テスト仕様書 | ISO/IEC/IEEE 29119 |
| 移行、運用 | 移行計画書、運用、操作マニュアル | ISO/IEC 26514 |

仕様書は、実装が従うべき正式な契約である。実装を仕様書へ合わせ、実装を起点に仕様書を書き換えない。

---

## 2. 記述

### 曖昧な表現を避ける

「適宜」「必要に応じて」「基本的に」のような、読み手の解釈に依存する表現を使わない。判定条件、数値、具体的な挙動として記述する。

NG: 一定時間応答がなければ警告する OK: 5秒以内に応答がない場合、警告灯を点灯する

### 観測可能な挙動を記述し、実現手段を記述しない

外部から観測できる挙動（入力に対する出力、状態遷移、タイミング、許容誤差）を記述し、実現手段（使用するアルゴリズム、部品、内部設計）は記述しない。実現手段を仕様書へ書くと、実装の変更のたびに仕様書の更新が必要になり、乖離しやすくなる。

### 一つの記述には一つの意味だけを持たせる

1つの条項が複数の解釈を許すと、実装者ごとに異なる実装になる。

### 正常系だけでなく境界と例外を記述する

正常系に加え、上限、下限、タイムアウト、異常入力、通信断、権限がない場合など、境界と異常系を記述する。省略は実装漏れとテスト漏れに直結する。

## 3. 識別子

仕様書が扱う対象（画面、部品、メッセージ、状態、信号、コマンド、要求など）には一意な識別子を付け、実装、テスト、障害報告から仕様書の該当箇所を追跡できるようにする。

識別子は `<PREFIX>-<DOMAIN>-<NNN>` の形式にする。PREFIXで対象の種別、DOMAINで機能領域を表す。対象が特定の親（画面など）に属し、親の中での連番を表す場合は `<PREFIX>-<PARENT-DOMAIN>-<PARENT-NNN>-<NNN>` のように親の識別子をそのまま連結してよい。

| 対象 | 識別子例 |
| --- | --- |
| 画面 | `SCR-USER-001` |
| APIレート制限ポリシー | `RL-BILLING-002` |
| ネットワークルーティングルール | `RT-EDGE-012` |
| ストレージレプリケーションポリシー | `RPL-OBJECT-004` |
| アクセス制御ポリシー | `ACL-STORAGE-005` |

---

## 4. ファイル構成

1つの対象領域（リソース、画面、インターフェース、サブシステムなど）につき1ファイルとする。担当領域が分かれる大規模開発では、コンフリクトとレビュー範囲を最小化するため。

ファイル名は、対象を指す既存の識別子や名称をそのまま使う。仕様書の外からでも、どのファイルを見ればよいかが一意に判断できるようにする。

---

## 5. メタデータ

すべての仕様書ファイルは、少なくとも次のメタデータを持つ。

| 項目 | 内容 |
| --- | --- |
| バージョン | セマンティックバージョニング（`MAJOR.MINOR.PATCH`）。 |
| ステータス | `draft` / `review` / `stable` / `deprecated` のいずれか。 |
| 最終更新日 | ISO 8601形式（`YYYY-MM-DD`）。 |
| 責任者 | 仕様の最終決定権を持つ人物。 |
