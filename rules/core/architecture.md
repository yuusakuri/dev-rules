## 1. 責務の分離

### 中核ロジックを外部技術から独立させる

業務ロジックをデータベース、通信方式、画面、フレームワークなどの外部技術から独立させ、業務上の制約を一貫して適用するために採用する。
これにより、外部技術を変更しても業務ロジックへの影響を抑えられ、テストも容易になる。

### 外部データの型と内部で使う型を分離する

DBや外部APIなどの外部データの型と、業務ロジックで使う型を分離し、境界で相互変換する。外部仕様の変更が業務ロジックへ影響することを防ぎ、内部モデルの一貫性と保守性を高められる。

### Single Responsibility（単一責務の原則）

1つのモジュール、クラスが変化する理由は1つだけにする。変化する理由が1つに絞られていると、ある機能を変更したときに無関係なコードへ影響が波及しない。「このクラスが変化する原因は何か」を自問し、複数の答えが出る場合は責務を分割する。

### Interface Segregation（インターフェース分離の原則）

呼び出し元が使わないメソッドをインターフェースに含めない。巨大なインターフェースを1つ持つと、実装クラスは不要なメソッドの実装を強制され、呼び出し元は自分に無関係な変更の影響を受ける。目的ごとに小さなインターフェースに分割することで、変更の影響範囲を必要な範囲に限定できる。

### 読み取りと書き込みを分離する

読み取りと書き込みで必要な処理、状態、依存関係、性能要件が異なる場合は、それぞれを別の型に分離する。利用側には必要な操作だけを公開し、読み取りと書き込みを独立して実装、所有、テストできる構造にする。これにより、責務が明確になり、不要な依存を防ぎ、並行処理や実装の差し替えが容易になる。

## 2. 依存関係の管理

### Dependency Inversion（依存性逆転の原則）

上位モジュールは下位モジュールの具体的な実装に依存せず、どちらも抽象（インターフェース）に依存する。具体的な実装への直接依存をなくすことで、実装を差し替えてもコードを変更する必要がなくなり、テスト時にモックへ置き換えることもできる。

### Liskov Substitution（リスコフの置換原則）

あるインターフェースの実装を別の実装に差し替えたとき、呼び出し元の動作が壊れてはならない。「差し替えが安全に行える」という保証があって初めて Dependency Inversion が実際に機能する。実装クラスがインターフェースの定義した事前条件、事後条件、不変条件を破ると、呼び出し元が暗黙的に特定の実装に依存することになる。

### Open/Closed（開放閉鎖の原則）

モジュールは新しい振る舞いの追加に対して開いており、既存コードの変更に対して閉じているべき。機能追加のたびに既存コードを修正すると変更が波及して想定外の影響が出る。インターフェースと Dependency Inversion を組み合わせることで、既存コードを変更せず新しい実装を追加するだけで機能を拡張できる。

### 実行環境に依存する処理を差し替え可能にする

外部 I/O、永続化、時刻、ID 生成、乱数など、実行環境によって結果が変わるものは、呼び出し元から差し替えられる形で抽象化する。こうすることで、業務ロジックを外部サービスや DB に接続せずにテストでき、時刻や ID 生成をテスト用の固定値に差し替えることができる。

### 依存関係を明示的に渡す

依存する機能やオブジェクトは、関数の引数または型のフィールドとして外部から明示的に渡す依存性の注入を採用する。グローバル状態やサービスロケータのように依存関係を隠す仕組みは、処理の理解とテストを難しくするため避ける。これにより、変更すべき部分を特定しやすくなり、テスト用の実装へ差し替えやすくなる。

依存関係の構築は、基本的に手動DI（Composition Rootでの直接的な生成と受け渡し）で行う。依存グラフが大きくなり、手動での構築コード自体が保守対象として複雑化する場合は、DIフレームワークの採用を検討する。フレームワークを採用する場合も、依存関係を隠すグローバルな解決の仕組みとしてではなく、Composition Rootでの構築を機械化する手段として使う。

### Composition Rootに依存関係の生成と接続を集約する

依存関係の生成と接続は、Composition Rootとして各アプリケーションの起動処理に集約する。業務処理から依存関係の組み立てを分離することを目的とし、アプリケーション全体の構成と実装の選択を一か所で確認できる。これにより、実装の差し替えや設定変更が容易になり、業務処理を依存関係の生成方法から独立させられる。

### 循環依存

A → B → A のような循環依存はモジュール間の境界が崩壊している状態を示す。一方を変更するともう一方も変更が必要になり、単独でのビルドやテストもできなくなる。lint で検出し、依存方向を見直す。共通部分は両者から依存される下位モジュールとして切り出す。

### 初期化、終了の順序

初期化処理は依存される側から依存する側の順に行い、終了処理はその逆順で行う。順序を誤ると、未初期化のモジュールへのアクセスや解放済みリソースへのアクセスが発生する。

### 設定値をロジックに直接埋め込まない

タイムアウト値、リトライ回数、アドレスなどをコードに直接書くと、値を変えるためにコードの変更とビルドが必要になる。設定ファイル、環境変数、設定オブジェクト経由で取得する。

## 3. 複雑性の制御

### YAGNI（You Aren't Gonna Need It）

必要になるまで作らない。将来使うかもしれない機能、抽象化、汎用化は今作らない。不要な実装はコードの複雑さを増し、実際の要件が来たときに設計が合わないことも多い。

### KISS（Keep It Simple）

複数の実装方法があれば最も単純なものを選ぶ。

### DRY（Don't Repeat Yourself）

同じ概念や業務知識が複数箇所に重複すると、変更時にすべての箇所を修正する必要が生じ、修正漏れがバグになる。重複を関数化、共通化することで変更箇所を1か所に集約する。

共通化するかどうかは、出現回数ではなく重複しているコードが同じ概念、同じ業務知識を表しているかで判断する。コードの形がたまたま似ているだけで、変更される理由や意味が異なる場合は共通化しない。意味の異なるコードを1つの実装へ統合すると、片方の都合による変更がもう片方に波及する不要な結合が生まれる。早すぎる共通化は YAGNI にも反する。

### 同じ情報を複数の状態として保持しない

他の状態から計算できる値は、原則として独立した状態として保存せず、必要な時点で導出する。情報源を一つにすることで、更新漏れによる不整合を防げる。

### Law of Demeter（最小知識の原則）

モジュールは直接依存する相手とだけ通信する。`a.getB().getC().doSomething()` のような連鎖は A が B と C の内部構造を知りすぎており、B や C の変更が A に波及する。

### 副作用は境界に閉じ込める

ファイル書き込み、ネットワーク送受信、グローバル状態の変更といった副作用を、ロジックを担う関数の中に混在させない。ロジック層の関数は同じ入力に対して常に同じ結果を返す純粋な処理だけを行い、副作用を持つ処理は Infrastructure 層、ハンドラー、エントリポイントなど明確に定められた境界にのみ記述する。これにより、ロジック層はテスト時に実際の I/O を必要とせず、副作用の発生箇所が明確になる。

## 4. モジュール、クラス設計

### 内部構造を外部へ公開しない

利用側が子要素の配置や内部状態を直接操作しなければならない設計を避ける。コンポーネント自身が内部構造を管理することで、内部変更が利用側へ波及することを防げる。

### 型で制約と状態を表現する

入力値の制約や取り得る状態を型で表現し、無効な値や不正な状態遷移をコンパイル時または生成時に防ぐ。

### 継承と委譲

継承より委譲を優先する。継承はインターフェースの実装（振る舞いの契約）の目的でのみ使用し、実装の再利用を目的とした継承は行わない。

実装継承では、子クラスが親クラスの内部実装に直接依存するため、親クラスの内部を変更すると子クラスに影響が及ぶ。委譲では、依存するのは相手の公開インターフェースだけであり、相手の内部実装が変わっても呼び出し元は影響を受けない。また委譲では依存する相手をインターフェース経由で差し替えられるため、テストが容易になる。

### 集合データ型の扱い

#### 業務上の制約がある集合

要素の追加、削除、並び順、重複、件数などに業務上の制約があり、集合全体として整合性を保つ必要がある場合、集合は生のコレクション型のまま持たせず、専用の型にカプセル化する。この型は、生のコレクション操作を隠し、許可された操作と検証を一か所にまとめる。
これにより、不正な状態を作りにくくなり、集合に関する業務ロジックの重複や実装漏れを防げる。

### ネストの深さ

ネストが3段階以上になる場合は、早期 return または関数抽出でネストを解消する。

## 5. 設計パターン

### オブジェクト生成

生成に必要な引数が多い場合や、任意項目を組み合わせて複雑なオブジェクトを段階的に構築する場合に、Builderパターンを採用する。
生成手順を専用のBuilderに分離することで、コンストラクタの引数過多や生成処理の重複を防げる。

条件によって異なる実装を返す場合や、外部リソースを参照して生成する場合は、専用の生成関数またはFactoryパターンで生成の詳細を隠蔽する。

### アルゴリズムや処理の切り替えを可能にする

同じ処理の「やり方」を差し替えたい場合、if / switch の分岐が増え続ける。Strategy パターンで各アルゴリズムをインターフェースとして定義し、呼び出し元を変更せずに実装を差し替えられるようにする。

### 状態遷移を安全に管理する

モジュールが複数の状態を持ち、状態ごとに振る舞いが異なる場合、条件分岐が複雑になる。State パターンで各状態を独立した単位として表現し、遷移ロジックを集約する。

### Fluent API

関連する設定や操作を連続して記述した方が分かりやすい場合は、Fluent APIによるメソッドチェーンを使用する。各メソッドは自身または次の操作段階を表す型を返し、利用側が一連の処理を順番に記述できるようにする。

### 操作を値として表現する

操作を遅延実行、キューイング、再試行、記録、取り消しする必要がある場合は、Commandパターンを使用する。操作の種類と入力をCommandとして表現し、操作を要求する側と実行する側を分離する。これにより、操作の実行順序や実行方法を、操作を要求するコードから独立して変更できる。

### 外部モジュールや非互換インターフェースへの依存を隠蔽する

外部ライブラリやモジュールの API をそのまま内部コードに露出させると、差し替えるときに影響範囲が広がる。Adapter パターンでラッパーを挟み、内部コードが外部の具体的な API に依存しない構造にする。

### 既存モジュールに手を加えずに機能を追加する

既存の実装を変更せずに横断的な処理（ロギング、計測、リトライ）を追加したい場合、Decorator パターンでラッパーを被せて機能を差し込む。元のインターフェースを保ったまま振る舞いを拡張できる。

### モジュールへのアクセスを制御する

遅延初期化、権限チェック、アクセス回数制限など、対象モジュールへのアクセスを制御する必要がある場合、Proxy パターンを使う。呼び出し元からは本物と同じインターフェースで扱えるまま、アクセス制御のロジックを Proxy が引き受ける。

### 複雑なサブシステムをシンプルな窓口で隠す

複数のコンポーネントを個別に呼び出すと呼び出し元が複雑になる場合、Facade パターンで統一した窓口を1つ提供し、内部の複雑さを隠蔽する。

## 6. 命名

### 規則

| ルール | 内容 |
|---|---|
| 名前の具体性 | 名前だけで役割、対象、処理内容が推測できるようにする。接続先、扱うデータ、責務を含め、`Abstract`、`Base`、`Common`、`Shared`、`Manager`、`Helper`、`Process`、`Util`、`Object`、`Raw` のような汎用名は使わない。責務を表す具体的な名前を使う。 |
| 省略、略語 | 独自略語は禁止する。業界標準の略語は使用してよい。NG: `tbl`、OK: `table` `uuid` |
| 短く命名する | 文脈上明らかな語は省く。意味を損なわない範囲で簡潔にする |
| 抽象と具体、インターフェース | 抽象側（インターフェース）には汎用的、概念的な名前を付ける。`I` プレフィックスと `Impl` サフィックスは禁止。具体側（実装）には詳細、技術的な名前を付ける。インターフェースは能力、役割を表す名詞または形容詞にする。NG: `IOrderRepository` / `OrderRepositoryImpl`、OK: `OrderRepository` / `PostgresOrderRepository` |
| データ構造 | 内部の処理状態を名前に含めない。データ構造としてふさわしいドメイン名を付ける。NG: `ParsedMessage`、`RawFrame`、OK: `Message`、`Frame` |
| 真偽値 | `is` / `has` / `can` / `should` プレフィックス |
| 関数名 | 動詞で始める |
| 要求と完了イベントの型名 | 処理の実行を求める型名は`Request`で終える。完了した出来事を表すイベントの型名には過去形を使用する。例：`InitRequest`、`Initialized` |
| イベント待受属性名 | 要求またはイベントの発生を待ち受ける属性名は`on_`で始め、その後に対応する型名をsnake_caseで続ける。例：`on_init_request`、`on_initialized` |
| イベント処理関数名 | 要求またはイベントを受け取って処理する関数名は`handle_`で始め、その後に対応する型名をsnake_caseで続ける。例：`handle_init_request`、`handle_initialized` |
| 定数、マジックナンバー | マジックナンバーを避け、意味を持つ名前付き定数にする。 |

## 7. エラーハンドリング

- エラー型はモジュール、レイヤーごとに定義し、上位へ変換して伝播させる
- 強制的なエラー無視は禁止。呼び出し元が戻り値、エラーコードを必ず確認できる設計にする
- エラーはログの記録に必要な文脈が揃う境界まで伝播させる。ログの記録方法は9章に従う

---

## 8. 並行処理

### メインスレッドを長時間占有しない

メインスレッドでは、完了時間を予測できない同期処理や、長時間または連続的にスレッドを占有する処理を行わない。I/O、重い計算、ロック待ち、同期IPCなどは別スレッドで実行し、メインスレッドでの処理実行は必要最低限にする。

- イベントやコールバックを待つ目的でポーリングループを使わない。割り込み、シグナル、チャネル、セマフォなどのプラットフォーム機構を使う
- スレッド、タスク間でのメモリ共有は可能な限り避け、メッセージパッシングを優先する
- 共有リソースへのアクセスはミューテックス、セマフォ等で保護し、デッドロックが発生しない順序でロックを取得する
- タイムアウトをすべての外部 I/O、ブロッキング操作に設定する

---

## 9. ログ

- ログは簡潔に、必要最小限にする
- デバッグ目的の一時ログをリリースコードに残さない
- ログは、誰の、どのリクエストによる処理かという文脈を把握できる境界（ハンドラー、エントリーポイントなど最外郭の処理）で1回だけ出力する。エラーの発生源では文脈が欠けるため出力せず、上位へ伝播させる（伝播のたびに出力しない）
- 機密情報（鍵、パスワード、個人情報）をログに出力しない
- ログレベルを適切に使い分ける（DEBUG / INFO / WARN / ERROR）

---

## 10. パフォーマンス

- 計測してから最適化する。推測での最適化は禁止
- キャッシュは TTL、最大件数、無効化戦略をセットで設計する

---

## 11. ドキュメント規則

### コードコメント

- WHY を書く（WHAT はコードを見れば分かる）
- コメントアウトされたコードは残さない。バージョン管理の履歴に任せる
- 暫定的な固定値には `TODO:` を付け、値の意味と変更が必要な理由を明記する

### 公開 API、モジュール

モジュールが利用側へ公開する関数とモジュールにはドキュメントコメントを書く。内部実装を分割するために export している要素は対象に含めない。エラーケースと戻り値の意味を必ず記載する。

### ADR（Architecture Decision Records）

重要な設計決定は `docs/adr/` に記録する。例外を認める場合も ADR として記録し、理由と結果を残す。

---

## 12. 開発フロー

PR マージ前にフォーマットチェック、静的解析 / lint、全テスト実行、依存関係の脆弱性スキャンをすべて通過することを必須とする。lint の警告はエラー扱いにする。

### ブランチ戦略：GitHub Flow

`main` は常にデプロイ可能な状態を保つ。直接プッシュは禁止。PR は最低1名のレビュー承認が必須。Squash merge で履歴を線形に保つ。

```
main
  └── feature/order-placement
  └── fix/order-validation-bug
  └── refactor/use-case-extraction
```

### コミットメッセージ：Conventional Commits

```
feat(order): add place order use case
fix(auth): correct token expiration check
refactor(order): extract validated value types
test(order): add repository integration tests
docs(readme): update setup instructions
chore(deps): upgrade dependency version
```
